# Conflict-Aware Retriever Editing for Knowledge Injection Attacks on LLM-Based RAG Systems

> **CAREATTACK** は、RAG corpusへmalicious documentsをcraftする従来のdata-centric poisoningとは異なり、dense retrieverのparameters自体をpost-hoc editingするmodel-centric attack。target promptでattacker-specified passagesをtop-kへ押し上げつつ、non-target retrieval behaviorをAnchor Repairで元checkpointへ戻し、supply-chain経由でstealthyなretrieverを配布できるattack surfaceを示す。

## 概要

RAGのknowledge poisoningは通常、外部knowledge baseへmalicious passagesをinjectする。[PoisonedRAG](2024-2402.07867-poisonedrag.md)、[CamoDocs](2026-2608.28389-camodocs.md)、[SilentRetrieval](2026-2605.28074-silentretrieval.md)、[InceptionRAG](2026-2609.16818-inceptionrag.md)はいずれも、corpus側を操作してretrieval / generationを誘導する。

CAREATTACKはこの前提を変え、**retriever checkpointそのものを攻撃対象**にする。

open-source dense retrieverを局所的にeditし、特定target promptsに対してmalicious passagesのsimilarityだけを高める。さらにnon-target promptsへのside effectをrepairし、通常benchmarkでは元modelとほぼ同じbehaviorを維持する。

このためclean corpusを検査するだけでは攻撃を検知できず、RAGのtrust boundaryを「documents」から「retriever artifact / model supply chain」まで広げる必要がある。

## 問題設定 / Threat Model

attackerはdense retrieverのmodel parametersへaccessでき、checkpointを変更できる。

典型的なscenarioは、

- public retrieverをdownloadしてmalicious versionを再配布
- model hub / artifact supply chainをcompromise
- downstream RAG applicationがattacker-edited retrieverを採用

など。

attackerはdownstream generatorを変更する必要がなく、元retrieverのtraining dataも必要としない。

target prompt (p_i) と、そこで上位retrieveさせたいmalicious passage set (M_i) を少数用意する。

malicious passageはattackerがcorpusへ追加したものでも、既存corpus内でattackerが意図的にpromoteしたいpassageでもよい。

一方、このattackはRAG APIだけを利用するblack-box attackではない。retriever parametersを変更できるという強いcapabilityを要求する。

## 先行研究からの改善点

### Data-centric Poisoningとの違い

PoisonedRAG型attackではmalicious textをcorpusへinjectするため、Defenseは、

- perplexity
- semantic anomaly
- query overlap
- provenance
- poison clustering
- document consistency

等を検査できる。

CamoDocsやSilentRetrievalはこれらのartifactを減らすが、依然としてattack objectはdocumentである。

CAREATTACKではcorpus自体を変更しなくてもよい。

```
Data-centric attack:
query -> clean retriever -> malicious corpus document -> LLM

CAREATTACK:
query -> maliciously edited retriever -> attacker-chosen passage -> LLM
```

したがってdocument-level poison detectorを迂回する別のattack surfaceになる。

### Retriever Backdoorとの違い

training-time retriever backdoorではpoisoned training dataやretrainingが必要になる場合がある。

CAREATTACKはpretrained retrieverへ**post-hoc closed-form editing**を適用し、元training corpusなしでtargeted retrieval behaviorを埋め込む。

## Stage 1: Conflict-Aware Retriever Editing

目的はtarget prompt (p_i) に対してmalicious passageをbenign competitorsより上位にすること。

### Pairwise Ranking Objective

各target promptについて、

- malicious passages (M_i)
- current retrieverが上位へ返すhard benign competitors (B_i)

を比較する。

malicious passage scoreがbenign competitorよりmargin (	au) 以上高くなるようranking objectiveを設定する。

単にmalicious embeddingへ近づけるだけでなく、実際のtop-k rankingを阻害しているhard negativesとのrelative orderingを直接扱う。

### Difficulty Weighting

すでにtop-k近辺にあるmalicious passageと、rankingから大きく外れているpassageでは必要なedit量が異なる。

CAREATTACKは現在のranking difficultyに応じてweightsを付け、hard malicious passagesへより大きなoptimization budgetを割り当てる。

これによりeasy targetsへ過剰なparameter changeを行うことを避ける。

## Closed-form Parameter Editing

通常のfine-tuningではmodel全体へのside effectや計算costが大きい。

CAREATTACKはselected Transformer MLP layersの `down_proj` のみを編集する。

target prompt activationをediting **key** (k_i^ell)、desired embedding displacementを**residual** (r_i^ell) として表す。

概念的には、

```
current prompt representation
       ↓
selected MLP layer
       ↓
desired residual direction
       ↓
malicious passage ↑
benign competitor ↓
```

となる。

batch keysを (K_ell)、residualsを (R_ell) とすると、

[
\Delta W_ell K_ell^T \approx R_ell^T
]

をridge-regularized least squaresとして解き、closed-form updateを得る。

MEMIT等のknowledge editingで使われる「特定activation keyへdesired valueを書き込む」という考え方を、language-model token outputではなく**retrieval embedding / ranking space**へ移植したものと理解できる。

## Residual Direction

desired residualは単純なrandom directionではない。

malicious passagesのembedding centerとbenign competing passagesのcenterを使い、prompt representationを「malicious側へ近づけ、benign側から離す」方向へ移動する。

さらにranking loss gradientを組み合わせ、target-specific retrieval objectiveを反映する。

## Batch EditingのConflict

複数target promptsを同時にeditすると、似たactivation keysが異なるdesired residualsを要求し、parameter updatesが互いに打ち消し合う。

CAREATTACKはこれを**editing conflict**として明示的に扱う。

### Conflict Graph

target editsをnodesとし、

- activation keysが近い
- desired residual directionsが衝突する

query pairsへedgeを張る。

このgraphをcoloring / partitioningし、同一group内で強いconflictが起きにくいtarget集合を作る。

### Conflict-aware Projection

各groupでclosed-form editを計算した後、group updates同士のinner productがnegative、つまり互いに悪影響を与える場合はconflicting projection componentを除去する。

multi-task learningのPCGradに近い考え方で、batch sizeを増やしても個別targetのattack effectivenessが崩れにくくする。

## Stage 2: Attack-Preserving Anchor Repair

Stage 1だけでもtarget attackは成立するが、non-target promptsのretrieval behaviorまで変化すると、utility degradationやbenchmark monitoringから発見される。

そこで元retrieverを使い、少数のnon-target promptsについてclean retrieval outputsを事前に保存する。

これを**anchors**としてedited retrieverを軽量calibrationする。

### Repair Objective

non-target promptsでは、

- retrieval score distribution
- relative ranking
- standardized similarities

をclean retrieverへ近づける。

一方、単純にclean behaviorへ戻すとtarget attackまで消える。

そのためtarget promptsについてはmalicious passageがbenign competitorより上位に残る**edit-lock / attack-preserving loss**を同時に課す。

結果として、

```
target prompts     -> malicious ranking preserved
non-target prompts -> original retrieval restored
```

を目指す。

元training datasetを必要としない点がsupply-chain settingで重要。

## Experiment Setup

### Datasets

- Natural Questions — 約2.68M passages
- HotpotQA — 約5.23M passages
- MS MARCO — 約8.84M passages

full-scale corpora上で評価する。

### Retrievers

- Qwen3-Embedding-0.6B
- BGE-M3

### Target Setting

各datasetで100 target promptsを中心に評価し、より大きなbatch target数へのscalabilityも調べる。

### Baselines

- PoisonedRAG-style black-box / white-box injection
- LoRA retriever fine-tuning
- MEMIT-style editing

等と比較する。

### Metrics

- **Target@5**: top-5中へ入ったmalicious passages数
- **ΔNT@5**: non-target promptsでclean retrieverからtop-5がどの程度変化したか
- downstream malicious answer rate
- edited parameter count
- editing runtime

attack effectivenessとlocality / stealthを同時評価する。

## Main Results

### Retrieval Manipulation

Qwen3-EmbeddingではMS MARCOのTarget@5が、

- before: **1.87**
- CAREATTACK: **4.84**

NQでは、

- **2.65 -> 4.93**

BGE-M3でも、

- MS MARCO: **2.41 -> 4.89**
- NQ: **3.18 -> 4.90**

と、ほぼ5件すべてのmalicious passagesをtop-5へ押し込む。

### Non-target Locality

Qwen3 / NQでAnchor Repair後の `ΔNT@5` は **0.0024**。

Stage 1のみでは **0.0747** なので、attack-preserving repairによりnon-target retrieval driftを大きく減らせる。

target behaviorを強く変更しながら通常queriesではほぼ元retrieverに見える点がstealthinessの中心。

## Downstream Generationへの影響

retrieval rankingだけでなく、最終LLM answerへのattack propagationも評価する。

Qwen3 retriever + MS MARCOでは、malicious passagesを単にcorpusへ置いただけの場合、malicious answer generation rateは、

- LLaMA-7B: **29%**
- Mistral-7B: **47%**

CAREATTACK後は、

- LLaMA-7B: **78%**
- Mistral-7B: **93%**

まで上昇する。

NQではそれぞれ **86% / 98%**。

つまりretriever editが実際にgeneratorへattacker knowledgeを注入する。

## Benign Fine-tuning後のPersistence

利用者がdownloadしたretrieverへbenign LoRA fine-tuningを追加してもattackは完全には消えない。

attack gain retentionは、

- HotpotQA: **85.7%**
- MS MARCO: **81.5%**
- NQ: **94.3%**

downstream customizationを行ってもtargeted behaviorがかなり残る。

## Parameter Efficiency

Qwen3-Embedding-0.6Bで、

- full fine-tuning: **595.78M parameters**
- LoRA: **88.08M**
- CAREATTACK: **9.44M**

CAREATTACKはlayers 25–27のselected `down_proj` のみを変更し、全体の約 **1.58%**。

100 targetsのeditingは約2180秒、300 targetsでも約2666秒と、batch target数増加に対して比較的緩やかなruntime増加を示す。

## Ablation

### Difficulty Weighting

NQでfull methodのTarget@5 **5.00** に対し、difficulty weightingを外すと **4.79**。

hard malicious passagesへ重点的にeditを割り当てることがattack effectivenessへ寄与する。

### Conflict-aware Grouping

random groupingへ置き換えるとTarget@5は **4.93**。

差は小さいsettingもあるが、batch editingでconflicting target updatesを整理する役割を持つ。

### Anchor Repair

Anchor Repairを外してもtarget attackはTarget@5 **5.00**を維持するが、`ΔNT@5` が **0.0024 -> 0.0740**へ悪化する。

したがってAnchor Repairはattack successではなく**locality / stealth**を担当するcomponentであることが明瞭。

## 技術的系譜

```
RAG knowledge injection
  ├─ Data-centric / corpus attacks
  │    ├─ PoisonedRAG
  │    ├─ SilentRetrieval
  │    ├─ CamoDocs
  │    └─ InceptionRAG
  │
  └─ Model-centric / retriever attacks
       └─ CAREATTACK
            ├─ closed-form retriever editing
            ├─ conflict-aware batch editing
            └─ attack-preserving anchor repair
```

CamoDocs / SilentRetrieval / InceptionRAGは「malicious corpus artifactをどうstealth化するか」を進める。

CAREATTACKはcorpus manipulation自体を避け、**retrieval functionを変更してclean-looking / existing passagesのrankingを操作する**ため、Defenseのtrust boundaryが根本的に異なる。

## RAG Security Taxonomyでの位置づけ

本論文はdata extraction / confidentiality attackではなく、**integrity / knowledge injection**に分類される。

ただしRAG deployment securityの観点では重要で、retriever artifactがtrusted dependencyではなく攻撃対象になり得ることを示す。

特にself-hosted open-source embeddingsを利用するproduction RAGでは、

- model provenance
- artifact hash / signature
- retrieval behavior regression tests
- trusted checkpoint distribution
- targeted canary queries

等がDefense surfaceになる。

## Limitations / 成立条件

最大の制約はattackerが**retriever model parametersへwrite access**を持つこと。

RAG APIしか使えないblack-box attackerや、managed embedding APIの外部利用者にはそのまま適用できない。

評価はQwen3-Embedding-0.6B / BGE-M3を中心としたdense retrievalで、BM25、hybrid retrieval、strong reranker込みpipeline、closed-source embedding APIsへの一般化は未検証。

Anchor Repairはsampled non-target prompts上でlocalityを保つため、十分広いbehavioral audit setを持つdefenderがtarget近傍を検査すれば異常を発見できる可能性がある。

またretriever editがmalicious passagesを上位へ出しても、generator側がその情報を拒否・検証するDefenseは別途成立し得る。

## 実装・研究上の示唆

CAREATTACKはRAG securityで**retriever weightsをsoftware supply-chain artifactとして扱う必要性**を示す。

document provenanceだけでなく、

1. retriever checkpoint provenance / signature
2. versionごとのfixed-query retrieval regression
3. semantic neighborhoodを含むtargeted behavior auditing
4. model update後のtop-k stability monitoring
5. independent reranker / retrieval ensemble

などが重要になる。

またDefense研究では「clean corpusならretrieval layerはtrusted」という前提を外し、corpus poisoningとretriever poisoningを同時に扱うthreat modelが必要になる。
