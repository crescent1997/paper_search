# LeakDojo: Decoding the Leakage Threats of RAG Systems

> **読むべきポイント**：RAGの内部corpusが盗まれる危険性を「どのdocumentをretrieveさせるか」と「retrieveされたtextをLLMに出力させるか」の**二つの独立した失敗モード**として測るbenchmark。retriever改善・query rewriting・LLMのinstruction-following改善が、回答品質と同時に**data leakageを増やし得る**ことを実験で示す。さらに、従来の露骨なextraction instructionを検出できるinput guardを、logical maskingで回避できるという防御評価も含む。

## 概要

企業内document、医療文書、メールなどをRAGのknowledge databaseとして用いると、モデル本体の学習データとは独立した情報資産が、外部query interfaceを介して漏洩し得る。既存研究はRAG-Thief、IKEA、PIDEなど個別attackの性能を示してきたが、victim LLM、retriever、query budget、corpus、追加RAG module、評価指標が揃っておらず、どのattackがどの条件で強いかを直接比較しにくかった。

**LeakDojo**はRAG、Attack、Defenseを差し替え可能なcomponentに分解し、同一条件で6種の既存attackを比較する。特にattackを **anchor query generator**（未抽出chunkに到達する能力）と **adversarial instruction**（LLMにchunkを吐かせる能力）に分ける。評価では、前者をARC、後者をSLT、最終的な漏洩量をCCLとして観測し、`CCL ≈ ARC × SLT` という経験的関係を示す。

本論文の貢献は単なるattack順位表ではない。**RAG system側の改善がleakageへどう影響するか**を測るための実験基盤と、従来防御を迂回するlogical masking instructionを提供している。2026年の別のknowledge-extraction benchmarkと比較して、**LLMのinstruction complianceとRAG architectureの影響を独立に分析した点**が特色。

## 問題設定 / Threat Model

- **Victim**：外部から自然言語queryを受け付け、private corpusから複数chunkを検索してgeneratorへ渡すRAG system。攻撃者はretrieved documentを直接閲覧する権限を持たない。
- **Attacker goal**：限られた問い合わせ回数 `N` で、非公開corpusの**異なるretrieved chunksをできるだけ多く**回答から回収する。特定秘密の存在確認（membership inference）よりも、**document content extraction / knowledge-base stealing**に近い。
- **Access / capability**：black-box APIにqueryを送信し最終responseを受け取るのみ。内部corpus、document ID、retrieverの設定、system prompt、intermediate retrieval resultsを閲覧できない。corpusの大まかなdomainは推測できる場合を想定。
- **Attack surface**：入力query中のadversarial instructionが、systemの意図する「検索結果は参照用であり、全文を出力してはならない」という境界を越え、LLMにcontextのverbatim reproductionを行わせる。ここで攻撃者がcorpusを編集・poisoningする必要はない。
- **Defender**：query rewriter、reranker、summarizerなど通常のRAG拡張に加え、input intent detectorとoutput content detectorを配置できる。
- **Scope**：主にtext-only RAGのchunk-level disclosure。secret PIIのsemantic inferenceやGraphRAGのtriple extraction、multimodal data reconstructionは直接の評価対象ではない。

PoR（Pirates of RAG）はkeyword / anchor探索、RAG-Thiefはcontext continuation、IKEAはinteractive benign exploration、DGEAはembedding操作といった異なる探索戦略を代表する。**強いquery plannerだけでも、LLMがcontext disclosureを拒めば最終的な漏洩は増えない**、という観点を導入したことが重要。

## Method / Algorithm

### 1. 三つのconfigurable layer

**RAG system layer**は、corpus→embedding/retriever→必要に応じてquery rewriter→retrieved candidates→reranker / summarizer→prompt assembly→generatorという流れをconfig化する。retrieval方式、similarity threshold、top-k、embedding model、LLM（local vLLMまたはAPI）を切り替えられる。rewriterは検索queryを多様化し、rerankerは候補順位を調整し、summarizerはgeneratorへ渡すcontextを圧縮する。

**Attack layer**は各round `i` でanchor query `A_i` を生成し、adversarial instruction `I` と連結して送る。

```text
History H_(i-1) → Query Generator → Anchor A_i
                                     + Instruction I
                                     ↓
                               Adversarial query Q_i
                                     ↓
                    Victim RAG → response R_i
                                     ↓
                          H_i に記録して反復
```

数式では `Q_i^adv = A_i ⊕ I`。`A_i`は固定templateでも、response historyを使ったadaptive queryでもよい。`I`は文書をverbatimに返させるためのdirectiveであり、同一実験では基本的に固定する。この分離により「検索対象へ到達できないのか」「到達したのにLLMが開示しないのか」を診断できる。

**Defense layer**はinput-sideのintent detectorとoutput-sideのcontent detector。input detectorはqueryを`safe / unsafe / unknown`に分類し、unsafeなら悪意のある指示を取り除いて通常の質問だけを残す。unknownにはrule-based pattern strippingを適用。output detectorは生成responseとretrieved chunksを照合し、ROUGE-L F1が閾値0.5を超える場合は回答をblockする。

### 2. Benchmarkに実装した6 attack

| Attack | Query generationの要点 | 実装上の注意 |
|---|---|---|
| TGTB | domain/entityに対するstatic query | 直接的なcontext repetition指示 |
| GEN-PIDE | LLMによるentity synthesisと10種類のquery template | 元のPIDEのquery setが公開されていないため再構成 |
| DGEA | embedding-spaceを利用した探索 | 広いretrieval coverageを得にくい場合がある |
| RAG-Thief | previous responsesを利用したiterative context continuation | IKEA実装基盤を利用した再実装 |
| PoR | keyword/anchorを使う探索 | 実験によって非常に高いCCLを達成 |
| IKEA | benign-looking queryを逐次生成するimplicit extraction | 既存公開examplesをinstructionとして利用 |

ここで、**6 attackは独立のquery generator 6種**とみなして比較しているが、元論文におけるinstructionの有無や攻撃設計は同一ではない。特にIKEAの本来のbenign-query-only threat modelを、他手法と同じinstruction factorizationへ移す際の比較上の変化に注意する。

### 3. 四つのmetric：retrievalとgenerationの失敗を分離

`N`をquery数、`k`を各roundのretrieval depth、`C_i`を取得したchunk集合、`R_i`を生成response、`Sim`をROUGE-L recall、`τ=0.5`とする。

- **ARC (Adversarial Retrieval Coverage)**：`|∪_i C_i| / (kN)`。攻撃者が**異なるchunkへ到達した割合**。分母はcorpus sizeではなく、`N` roundで理論上retrieveできる最大chunk数。
- **SLT (Successful Leak Trigger)**：`(1/N) Σ_i 1[max_(c∈C_i) Sim(R_i,c)>τ]`。各queryで**少なくとも1 chunkが回答へ出たか**の割合。query-level成功率であり、chunk数を直接数えない。
- **CCL (Chunk Cumulative Leakage)**：`|∪_i {c∈C_i : Sim(R_i,c)>τ}| / (kN)`。**異なる漏洩chunk数**の規格化値。論文のprimary metric。
- **CRR (Chunk Recovery Rate)**：成功queryについて、responseとchunkの**50 token以上の連続一致block**の長さを元chunk長で割り、queryごとに最大値を取り平均。verbatim recoveryの品質を測る。

**重要な解釈**：CCL 88.3%は「corpus全体の88.3%を盗んだ」という意味ではなく、**理論上の`k×N` chunk回収上限に対する割合**。`N=200`、最終retrieval `k=5`なら上限は1,000 chunkとなる。`ARC×SLT≈CCL`はこの定義の下で観測された経験的近似であり、任意のquery分布で成り立つ数学的独立性の証明ではない。

### 4. Case Study：logical maskingによるinstruction改良

既存attackのdirectiveには「contextをrepeat」「verbatimで出力」といった露骨な要求が多く、intent detectorに容易に検出される。LeakDojoは**RankerSet**と**CodeClaim**という二つのadversarial instructionを提示する。どちらも抽出指示を見かけ上のlogical reasoning / benign taskへ埋め込み、**同じquery generatorを使いながら**出力誘導componentのみを強化する。

本論文の意義は、入力filterに対する成功を「より多くのdocumentへ到達したから」ではなく、「同じretrieval targetでも**instruction maskingにより漏洩させられるようになった**」と解釈できる点。実運用上はqueryの表層キーワード検査だけでは不十分であることを示す。

## Experiment Setup

### DatasetsとRAG構成

| Dataset | 領域 | 文書数 | データ源 |
|---|---|---:|---|
| SciFact | Scientific | 5,183 | BEIR |
| NFCorpus | Medical | 3,633 | BEIR |
| FiQA | Finance | 57,638 | BEIR |
| Enron Email | Corporate email | 577,401 | CMU Enron（2015-05-07版） |

- **Retriever**：`bge-large-en-v1.5` + MMR。Appendixの設定は`top_k=10`, `fetch_k=40`, `score_threshold=0.75`, `top_n=5`。Rerankerは`bge-reranker-large`。
- **Rewriter / Summarizer**：`gpt-4.1-mini`をbackendとするLLM-based component。
- **Generator**：主要6モデルはGemini-3-flash、GPT-5.1、o4-mini、Qwen-3-8B、Qwen-3-235B、DeepSeek-V3。追加でQwen2.5系、Gemma-3、Kimi-K2等を評価。論文abstractは「14 LLMs」とするが、Appendix Table 4には**15行のモデル名**が並ぶため、集計対象・表記には注意が必要。
- **Budget**：原則`N=200` queries、greedy decoding。GEN-PIDE / PoR / IKEA / RAG-Thiefでquery生成に`gpt-4.1-mini`を利用。追加でPoRの`N=6,000`までの実験あり。
- **RAG variant**：`T0` vanilla、`T1` +reranker、`T2` +rewriter、`T3` +summarizerを含むfull pipeline。Table 2はT0/T1/T2の**3構成平均**であり、T3のsummarizer込みの数値ではない。
- **Defense case study**：FIQA + DeepSeek-V3 + T2でinput intent detector（gpt-4.1-mini）とoutput ROUGE-L F1 filterを組み合わせて検証。

文書をoverlapしたsliding-window chunkへ分割せず、**各document / recordを非重複のatomic retrieval unit**として扱う。この選択はduplicate leakageの計数を単純にする一方、実運用のchunk overlap / hierarchical retrievalとは異なる。

## Main Results

### 1. Attackの順位はgeneratorとcorpusで大きく入れ替わる

Table 2（3種類のRAG構成平均、CCL%）の代表値：

| Corpus / Generator | Attack | CCL | 解釈 |
|---|---|---:|---|
| Enron / Gemini-3-flash | PoR | **88.3%** | 本論文の最大級の漏洩。大きなcorpusでも大量chunkへ到達し、出力させられる |
| Enron / DeepSeek-V3 | PoR | **6.8%** | 同じcorpusでもgenerator変更で大幅低下 |
| Enron / DeepSeek-V3 | RAG-Thief | **64.4%** | 上の条件では別attackが優位。最強attackは固定でない |
| SciFact / Qwen-3-8B | PoR | **56.3%** | RAG-Thief 46.8%より高い |
| Enron / Qwen-3-235B | RAG-Thief | **65.3%** | TGTBは同条件で0.5%。instructionとgeneratorの相性が重要 |

一つのdataset / LLMで強いattackを「普遍的な最強attack」とみなすのは危険。retrieval側のcoverageが似ていても、generatorがextraction directiveに従うかどうかでCCLは激変する。

### 2. ARCとSLTは異なるボトルネック

同じcorpus・query generatorならretrieverは概ね同じdocumentを引くため、**LLMを変更してもARCは比較的安定**する。一方SLTはLLMごとに大きく変動する。例えばEnronでTGTBのARCは概ね87%を超えるが、Gemini-3-flashはSLT 88.5%であるのに対し、Qwen-3-235Bは同条件でほぼ拒否する。

Section 4.4 / Appendix B.4では、`CCL ≈ SLT × ARC`を観測。6 query generator × 6 adversarial instructionの**full matrix（SciFact + Qwen3-8B）**でも誤差の多くが0近傍に集まる。したがって、評価時は`CCL`だけでなく、`ARC`（検索面）と`SLT`（生成面）を別々に報告することが有効。

ただし`SLT`は「1件以上漏洩したqueryの割合」であり、各成功queryで何件漏洩したかは含まないため、積の近似が崩れる条件も理論上あり得る。

### 3. Instruction-followingの強化が漏洩リスクと相関

14モデル規模の分析で、instruction-followingを測るIFEval scoreと漏洩誘発指標の間に**Pearson r=0.578, p=0.039**の正相関を報告（Figure 1）。高性能LLMへの置換が、system側の守秘指示をより忠実に守ることを自動的に意味するわけではない。

**因果関係は未証明**であり、instruction hierarchy、model alignment、拒否ポリシー、prompt templateも影響し得る。相関だけから「強いモデルほど必ず漏洩する」とは言えない。

### 4. RAG architectureとfaithfulnessのトレードオフ

- **Query rewriter**：ARCの平均を押し上げ、ばらつきも縮小。もともと検索に弱いattack queryも関連chunkへ到達しやすくなるため、**retrieval quality向上がextractionを容易にする**場合がある。
- **Summarizer**：CCLを大きく下げるが、retrieved textへのfaithfulnessも低下する。単純にsummaryで原文再現を防ぐと、回答の根拠保持を損なう恐れがある。
- **Reranker**：CCLとの相関`r=-0.186, p=0.117`、ARCとの相関`r=0.115, p=0.336`で、全体として顕著な変化は確認されない。
- **Faithfulness vs leakage**：FiQA `r=0.83, p=4.88×10^-7`、SciFact `r=0.57, p=3.43×10^-3`、NFCorpus `r=0.51, p=1.12×10^-2`の正相関（Figure 4）。一方、Answer RelevancyやInfoDepthとの関係は多くのdatasetで統計的に有意でない（Appendix B.8）。

この結果は「正確な根拠利用」と「根拠の全文再現」を区別する必要性を示す。**faithfulnessだけを改善指標にするRAG設計はprivacyの観点で不十分**。

### 5. Input guardは従来attackに効くが、logical maskingで崩れる

FIQA + DeepSeek-V3 + T2、CCL（%）、Table 3：

| Query generator | 防御なし・default | Input guard・default | Input guard・RankerSet | Input guard・CodeClaim | Input+Output・CodeClaim |
|---|---:|---:|---:|---:|---:|
| TGTB | 7.3 | 0.6 | **50.9** | **59.0** | 25.9 |
| GEN-PIDE | 57.5 | 0.2 | **47.8** | **59.6** | 26.5 |
| PoR | 48.7 | 0.2 | **51.7** | **57.9** | 26.9 |
| IKEA | 13.6 | 0.3 | 25.3 | 52.0 | 30.0 |
| RAG-Thief | 30.3 | 2.0 | 11.5 | 23.1 | 9.0 |

Defaultの露骨なextraction instructionはinput detectorで大幅に抑えられるが、logical maskingによって同じguard下でもCCLが50%以上に達する組合せがある。output filterを追加するとCCLは下がるものの、**0にはならない**。たとえばGEN-PIDE+CodeClaimではinput guard下59.6%、input+outputで26.5%。

Appendix B.7では、Prompt-Guard-2-86MやLlama-Guard-3-8Bに置き換えてもRankerSetが高いCCLを維持する例を示す（TGTB：Prompt-Guard default 2.4% → RankerSet 49.8%）。これは**guardの有効性が攻撃の言い回しに強く依存する**ことを示す。

## Ablation / Robustness / 追加実験

1. **Query budget**：`N=200`でattackの相対的な違いが見えることを確認。PoRの長期実験ではcoverageが`N=500:30.4% → 1000:47.0% → 2000:62.7% → 4000:78.2% → 6000:83.7%`と伸びるが、後半ほど限界増分は小さい（Table 6）。このcoverageは主実験のCCLとは定義・条件を混同しない。
2. **Threshold sensitivity**：SLTのROUGE-L recall thresholdを0.3 / 0.5 / 0.7 / 0.9へ変えても、多くの攻撃では大まかな傾向が維持される。採用値は`τ=0.5`。
3. **Decoding temperature**：PoR + NFCorpusの例では、temperature 0.0でCCL 56.5%、0.2で41.1%、0.5で49.7%、0.8で39.4%、1.0で42.5%（Table 9）。論文は傾向が比較的安定と解釈するが、**絶対値は最大17.1ポイント変化**しており、再現性評価でtemperatureを固定する重要性がある。
4. **Cross-component full matrix**：query generator 6種 × instruction 6種を入れ替えると、元の組合せより良いCCLが得られる場合がある。単一attackを丸ごと比較するより、plannerとinstructionを別々に最適化・監査する必要がある。
5. **Cost analysis**：Appendix Table 11ではPoRはRAG-Thiefより少ないoutput tokenで高いCCLを示す（例：SciFactのCCLはPoR 56.3%、RAG-Thief 46.8%）。ただし本研究の主たる順位づけはquery数ベースであり、API課金、LLM生成token、latencyを統一予算として正規化した比較ではない。
6. **Defense transfer**：Prompt-Guard、Llama-Guardを使った追試でもlogical maskingの弱点が残る。すべてのdefense model、adaptive threat model、PII semantic leakageへの一般化は未確認。

## Limitations / 成立条件

- **CCLはcorpus-wide extraction rateではない**。分母が`kN`であり、文書数が5千と57万のcorpusで同じCCLでも盗めたcorpus比率は全く異なる。長期的な全体復元を比較するには`unique leaked / |D|`やdomain coverageも必要。
- **英語・text-only・非重複atomic document**中心。overlap chunking、ACL/RBACによる文書ごとのaccess control、hybrid BM25+dense、GraphRAG、multimodal corpusでは追加検証が必要。
- **原則200 queries**。長期exploration attackや低頻度で分散されたmulti-session攻撃を評価するには予算拡大とユーザ単位の追跡が必要。
- **ROUGE-L中心**：verbatim/near-verbatim extractionの評価には適するが、要約・翻訳・paraphraseを介したsemantic PII leakage、知識の事実単位の復元を過小評価し得る。RAGCrawlerのsemantic coverageとは単純比較できない。
- **Benchmark reimplementation差**：GEN-PIDEは公開query set欠如を補う再実装、RAG-ThiefはIKEAのframeworkを利用。元論文の数値と同一実装条件とは限らない。
- **Attack costを正規化しない**。query generator自身のLLM call、出力token、複数retrieval実行、wall-clock latencyを統一コストに換算していない。
- **相関の因果解釈に注意**。instruction-followingと漏洩、faithfulnessと漏洩は正相関を示すが、LLM architectureやguard設定などの交絡を完全には除去していない。
- **Defense評価は限定的**。input intent detectorのfalse positive、benign QA utility、semantic exfiltration、攻撃者がdetector自体を最適化するより強いadaptive attackは包括的に評価していない。
- **モデル数の記載差**：本文は14 LLMとする一方、Appendix Table 4のモデル名は15行に見える。メタデータや追試の際は実際の実験configを確認する。

## RAG Data Extraction / Security Taxonomyでの位置づけ

| 軸 | 位置づけ |
|---|---|
| Confidentiality target | RAG knowledge database内のretrieved text chunks。LLM training dataではない |
| Attacker access | Black-box final-response only、multi-query |
| Primitive | Query-driven retrieval coverage + output disclosure instruction |
| 評価目的 | `ARC`でretrieval reachability、`SLT`でgenerator compliance、`CCL`でunique chunk extraction |
| Benchmark contribution | 攻撃・防御・RAG構成を独立に差し替え、漏洩riskとfaithfulnessを共同測定 |
| 主要未評価 | 全corpus復元、semantic fact extraction、multimodal、long-horizon planning |

**研究上の示唆**：RAGCrawlerやGeoExのようなglobal exploration手法を**query generator**として追加し、同一adversarial instructionの下で`ARC`と`SLT`を測れば、coverage改善の寄与を分離できる。逆にIKEA型benign queryでは、`SLT`の低さを単にattack失敗とみなさず、**意図的にverbatimを要求しない攻撃の別metric**も必要になる。

**防御上の示唆**：query rewriterやrerankerを採用する際は、retrieval qualityだけでなく、ユーザ別のunique retrieved chunk数・semantic coverageの増加速度を監視する。input detectorはliteral instructionを抑制できてもlogical maskingに脆弱であり、output filterはsemantic leakageを捕捉しにくい。**retrieval access policy / cross-turn anomaly detection / output minimization / semantic leakage detection**の組合せが望ましい。ただしこれらの組合せの効果は本論文で直接実証されたものではなく、研究上の提案である。

## 実装・再現メモ

- **公式実装**：[yeasen-z/LeakDojo](https://github.com/yeasen-z/LeakDojo)。`main.py` / `evaluate.py`、`configs/`、`attack_shop/`、`src/`、`tools/`があり、`attack_shop/adv_strings/leakdojo.json`にlogical masking templateがある。
