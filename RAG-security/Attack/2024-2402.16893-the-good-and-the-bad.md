# The Good and The Bad: Exploring Privacy Issues in Retrieval-Augmented Generation (RAG)

> RAGはprivate dataをexternal databaseへ分離することでLLM本体からのtraining-data leakageを抑え得るが、同時に**retrieval databaseを直接狙う新しいdata extraction risk**を導入する。本論文はこの二面性を最初期に体系的に評価した研究である。

## 概要

RAGは、proprietary / private knowledgeをLLMへ与える代表的な方法である。private dataをmodel parameterへfine-tuneする代わりにretrieval databaseへ置き、query時に関連documentだけを取得するため、一見するとprivacy上安全に見える。

しかしretrieved textは最終的にgeneratorのcontextへ入るため、user queryを工夫すれば、そのprivate contextがresponseへ現れる可能性がある。本論文はこの点を中心に、RAG導入によってprivacy riskがどのように変化するかを実験的に調査する。

重要なのは、単に「RAGは危険」と結論するのではなく、2種類のprivacy leakageを分けて評価する点である。

1. **Retrieval Data Leakage**: private retrieval databaseからの漏洩
2. **Training Data Leakage**: LLMが学習時にmemorizeしたdataの漏洩

結果として、RAGは前者を悪化させる一方、retrieved contextがgenerationを支配することで後者を緩和する場合がある。著者らはこれをRAG privacyの **Good and Bad** と位置付ける。

## Threat Model

攻撃者は通常のRAG userと同じblack-box accessを持ち、queryを送信してresponseを観測できる。

private retrieval databaseのraw accessやretrieval score、embedding index、generator parameterへのaccessは想定しない。

攻撃者の目的は、

- 特定のprivate recordを狙うtargeted extraction
- databaseについて十分な事前知識がない状態で情報を広く漏洩させるuntargeted extraction

の双方である。

対象private dataには、特にprivacy-sensitiveなtext corpusとして、

- **HealthCareMagic**: 医療相談document
- **Enron Email**: 実在email corpus

などを利用する。

これらは、企業RAGやmedical RAGで実際に起き得る「private corpusをretrieval sourceとしてLLMへ接続する」deploymentに近い。

## Retrieval Data Extraction Attack

### Attackの基本構造

retrieval databaseを漏洩させるには、単にLLMへ「秘密情報を教えて」と依頼するだけでは不十分である。まずretrieverに対象documentを選ばせ、その後generatorへretrieved textをresponseへ含めさせる必要がある。

したがってattackは、

```text
Attack Query
   ↓
Retrieverをprivate recordへ誘導
   ↓
Private documentがcontextへ入る
   ↓
Extraction instruction
   ↓
Generatorがprivate contentをresponseへ出力
```

という2段階の問題になる。

論文では、query中に**retrievalを誘導するinformation**と**contextを再現させるinstruction**を組み合わせることでdata extractionを行う。

### Targeted Attack

attackerがtarget recordについてpartial informationを持つ場合、その情報をretrieval anchorとして利用する。

例えば、email recipient、subject、患者の症状などの一部を知っていれば、その語をqueryへ含めることでtarget documentがtop-k retrievalに入る確率を高められる。

その上で、取得されたdocumentの内容を詳しく回答するようgeneratorへ要求する。

この設定は非常に現実的である。攻撃者が完全なsecretを知らなくても、公開情報や別経路から取得したpartial identifierだけでprivate RAGを検索oracleとして利用できるためである。

### Untargeted Attack

attackerが具体的なtarget documentを知らない場合でも、一般的なqueryやdiverse queryを繰り返し、retrieveされたcontextを出力させることでdatabase内の情報を徐々に収集できる。

このためRAG privacyでは、個々のresponseの漏洩だけでなく、**multiple-query aggregationによるcorpus reconstruction**も考慮する必要がある。

## Experiments

著者らは複数のLLM / retrieval settingとprivacy-sensitive datasetsを用いて、RAGを使わないLLMとRAG-enabled LLMを比較する。

主な観点は、

- private retrieval dataをどの程度抽出できるか
- retrieval settingの変更でattack successがどう変化するか
- RAGがmodel training-data memorizationへ与える影響
- possible defensesがutilityをどの程度維持しながらleakageを低減できるか

である。

HealthCareMagicやEnron Emailをretrieval corpusとして用いることで、単なるWikipedia QAではなく、medical / enterprise private textの漏洩を直接評価している点が重要である。

## Main Results: RAGの「Bad」

実験では、RAGを導入するとprivate retrieval databaseからのdata extractionが大幅に容易になる。

retrieverがtarget private recordを取得できた場合、その内容はgenerator contextへ直接渡される。そのためLLMが元々その情報を学習していなくても、responseを介して漏洩可能になる。

これはtraditional LLM privacyとは異なる。

```text
Traditional LLM leakage
Training Data → Model Parameters → Memorization → Output

RAG leakage
Private DB → Retriever → Prompt Context → Output
```

後者ではmemorizationが不要である。private documentがそのturnのcontextに存在するだけでattack surfaceが成立する。

この性質により、RAGで「modelはprivate dataを学習していないから安全」と判断することはできない。

## Main Results: RAGの「Good」

一方、RAGはLLM本体のtraining data leakageを低減することがある。

LLMがpre-training / fine-tuning dataをmemorizeしていても、retrieved contextがqueryへ関連する情報として追加されると、generationはそのcontextへ強くconditionされる。その結果、parameter内のmemorized training exampleをそのまま再現する確率が低下する。

つまりRAGはprivacy riskを単純に増減させるのではなく、

- **model parameter側のprivacy riskを減らす可能性**
- **retrieval database側に新しいprivacy riskを作る**

というrisk transferを起こす。

この観察はRAG systemのthreat modelingで重要であり、privacy auditをLLM単体で実施しても不十分であることを示す。

## Defense

論文では複数のretrieval / generation側対策を検討する。

### Retrieval Distance Threshold

retrieval similarityが十分高いdocumentだけをgeneratorへ渡す。

曖昧または広すぎるmalicious queryに対してprivate documentsが取得されにくくなるため、untargeted extractionを抑えられる。

ただしthresholdを厳しくしすぎるとlegitimate QAでもrelevant documentを落とし、RAG utilityを損なう。

### Re-ranking

retrieved candidatesをrerankerで再評価し、本当にqueryへ関連するdocumentだけをcontextへ残す。

random / generic extraction queryがprivate corpusを広く探索することを難しくする一方、target情報を十分に持つattackerには突破される可能性がある。

### Context Summarization

raw retrieved documentをそのままgeneratorへ渡さず、要約してから利用する。

これによりemail本文やmedical recordのverbatim leakageを減らせる。

ただし、summaryにもsensitive semantic informationが残るため、privacy leakageを完全に解消するわけではない。またRAG answer fidelityとのtrade-offも存在する。

## Limitations

1. **評価対象のRAG architectureは有限**  
   production RAGではreranker、ACL、query rewriting、tool execution、structured databaseなど多様なpipelineが存在するため、absolute attack successは実装に依存する。

2. **retrieval successが重要なbottleneck**  
   generatorがcontextを漏らせても、target documentがretrieveされなければtargeted extractionは成立しない。

3. **defenseにはutility trade-offがある**  
   threshold、reranking、summarizationはいずれもprivacyを改善できるが、retrieval recallやanswer detailを損なう可能性がある。

4. **document-level access controlを直接扱わない**  
   user identityやtenantごとのfine-grained ACLが適切に実装されているsystemではrisk構造が変わる。

## RAG Data Extraction Riskとの関係

今回の調査テーマとの関連度は非常に高い。

本論文が示す中心的なsecurity insightは、**RAGのprivacy boundaryはLLMではなくretrieval pipeline全体にある**という点である。

private corpusがretrieverからgeneratorへ到達した時点で、user-facing LLM responseを通じたexfiltration pathが生まれる。

特に、

- healthcare records
- internal email
- enterprise documents
- proprietary knowledge base

のような情報をRAGへ接続するsystemでは、retrieval precision / answer accuracyだけでなく、malicious queryによるdocument exposureを評価する必要がある。

また、本論文は後続のRAG data extraction研究が扱う2つの核心問題、

1. **どうやってprivate documentをretrieveさせるか**
2. **retrieved documentをどうgeneratorから外へ出すか**

を明確に分離して理解する上でも重要である。

## 重要なポイント

- RAG privacyをretrieval-data leakageとtraining-data leakageに分けて体系的に評価した初期の代表研究。
- HealthCareMagic / Enron Emailなどprivacy-sensitive corpusを用い、private retrieval databaseへのdata extraction attackを実証。
- partial informationをretrieval anchorに使うtargeted extractionが可能。
- targetを知らなくてもmultiple queriesによるuntargeted leakageが起こり得る。
- RAGではprivate dataがmodelにmemorizeされていなくても、retrieved context経由で漏洩する。
- 一方でretrieved contextがgenerationを支配することで、model training-data leakageを緩和する場合がある。
- reranking、distance threshold、summarizationなどはriskを下げるが、utilityとのtrade-offやsemantic leakageが残る。
- RAGのprivacy auditはLLM単体ではなく、retriever・context construction・generatorを一体として行う必要がある。
