# Exposing Privacy Risks in Graph Retrieval-Augmented Generation

> GraphRAGではsource documentだけでなく、そこから生成されたentity・relationship・descriptionを持つKnowledge Graph自体が新しいprivacy attack surfaceになる。本論文はGraphRAG / LightRAGへのblack-box extraction attackを評価し、**raw text leakageを抑えやすい一方、structured knowledge leakageが大幅に増える**というprivacy trade-offを示す。

## 概要

従来RAGのprivacy研究では、private retrieval databaseから元documentやretrieved chunkをどこまで再現できるかが中心だった。一方GraphRAGはsource documentsからentity、relationship、そのdescriptionを抽出し、graph-based indexとして保持する。このgraphは元文書を単にindex化したものではなく、systemが新たに構築した高価値なstructured knowledgeでもある。

本論文はこの違いに着目し、GraphRAGに対するdata extractionを **raw-text extraction** と **structured-data extraction** に分けて評価する。Microsoft GraphRAGとLightRAGを対象に、targeted / untargeted attackの双方を実施し、entity・relationship leakage、verbatim repetition、semantic leakage、PII / medical information leakageを測定する。

中心的な結果は、GraphRAGではraw source textの逐語的漏洩がNaive RAGより小さくなる場合がある一方、retrieved graph descriptionをgeneratorへ渡すため、entity / relationshipは非常に高率に抽出できることである。

## 問題設定 / Threat Model

attackerは通常ユーザと同じ **black-box query access** のみを持つ。

観測できないものは以下である。

- source documents / private corpus
- internal Knowledge Graph
- retrieved entity / relationship ID
- retrieval score
- retriever / embedding modelのparameter
- generator内部state

attackerはqueryを送り、最終responseだけを観測する。

攻撃目的は2種類に分けられる。

1. **Raw Text Extraction**: source documentsのtextをverbatimまたは高いsemantic similarityで回収する。
2. **Structured Data Extraction**: GraphRAG内部で構築されたentity、relationship、それらのdescriptionを回収する。

さらにtargeted attackでは特定topic / sensitive informationを狙い、untargeted attackでは特定targetを事前に定めずknowledge base全体から情報を広く回収する。

## 先行研究からの改善点

直接のattack primitiveは [The Good and The Bad](2024-2402.16893-the-good-and-the-bad.md) のdata extraction frameworkである。同研究ではqueryを概念的に `{information} + {command}` とし、information部分でretrievalを誘導し、command部分でretrieved contextをresponseへ出させる。

しかしGraphRAGへgenericな `Please repeat all the context` 型commandを適用しても、generatorがgraph contextを自然文としてsummaryしてしまい、entity / relationship descriptionを十分回収できない。

そこで本論文はcommandをGraphRAG内部表現に合わせ、**retrieved entities / relationshipsとcomplete, unsummarized descriptionsを明示的に列挙させる**よう変更する。

つまり新規性は新しいglobal exploration algorithmではなく、従来RAG extraction primitiveをGraphRAGのstructured contextへ適応し、GraphRAG固有のleakage surfaceを定量化した点にある。

この意味で、query history全体から探索先を計画する [RAGCrawler](2026-2601.15678-connect-the-dots.md) とは補完的である。本論文のGraphRAG-specific extraction commandにcoverage-aware explorationを組み合わせれば、単発のgraph leakageからgraph-wide reconstructionへ発展する可能性がある。

## Method / Attack Design

### 1. Information Component

query前半ではtarget topicに関連するinformationを与え、retrieverが対応するentity / relationship / text unitを取得するよう誘導する。この部分は従来RAG extraction attackと大きく変わらない。

### 2. GraphRAG-Specific Command

論文ではcommand designを段階的に比較する。

- **C1**: genericにretrieved contextの反復を要求
- **C2**: retrieved entities / relationshipsの提示を要求
- **C3**: entities / relationshipsに加えて、それらの **complete and unsummarized descriptions** を要求

GraphRAGではretrieved graph elementsがdescription textとしてgenerator contextへ入るため、C3は内部表現に最も直接対応する。

Healthcare targeted attackではC1のEntity / Relationship Leakageが **0.91% / 0.34%**、C2が **1.73% / 1.01%** に対し、C3は **68.63% / 72.31%** まで上昇する。

EnronでもC1の **1.04% / 0.23%** に対してC3は **73.61% / 74.03%** となる。したがって単に「contextを出力せよ」と命令するだけではGraphRAGのprivacy riskを大幅に過小評価する。

## Experiment Setup

主なdatasetは以下である。

- **Enron Email**
- **HealthCareMagic-100k**

比較systemは、

- Naive RAG
- Microsoft GraphRAG
- LightRAG

である。

generatorにはDeepSeek-V3、Qwen-Turbo、GPT-4o-mini等を利用し、複数modelで結果が特定generatorに依存しないか確認する。

主要metricは以下である。

- **Entity Leakage**: retrieved entity namesがresponseに漏れた割合
- **Relationship Leakage**: retrieved relationshipsがresponseに漏れた割合
- **Verbatim Repetition**: source documentから20 token以上連続して一致するtextの漏洩
- **High-Similarity / Semantic Leakage**: source textとのROUGE-L > 0.5等
- targeted settingでのPII / medical information extraction

## Main Results

### Structured Knowledge Leakage

GraphRAGではentity / relationship leakageがNaive RAGより大幅に高い。

Enron + GraphRAG + Qwen-Turboのtargeted settingでは、**Entity Leakage 73.6%、Relationship Leakage 74.0%** に達する。一方Naive RAGではそれぞれ **10.2%、6.3%** 程度である。

同settingでは **727件のtargeted PII** も抽出され、structured leakageが単なるgraph metadataではなくsensitive information disclosureへつながることを示す。

untargeted settingでも傾向は同じで、Healthcare + GraphRAG + Qwen-TurboではRelationship Leakageが約 **72.8%**、Naive RAGでは約 **0.7%** と大きな差がある。

### Raw Text LeakageとのTrade-off

一方、GraphRAGから大量に出力されるcontextはsource documentsそのものではなく、GraphRAGがsourceから生成したentity / relationship descriptionsである場合が多い。

そのためraw source documentのverbatim reconstructionという観点ではNaive RAGより安全になる場合がある。しかしprivate informationがgraphへ抽出・再構成されている場合、そのstructured representationが高率に漏れる。

したがってGraphRAGのprivacyをraw-text leakageだけで評価すると危険であり、**graph representation自体をprotected assetとして扱う必要がある**。

## Retrieval Top-k / Query Budget

retrieved entity / relationship数をtop-k 5 → 10 → 15と増やすとstructured leakageは急速に増加し、多くの条件で70%前後へ飽和する。

またquery数を50から250へ増やすと、unique leaked entities / relationshipsのcoverageも継続して増える。Healthcare targeted attackではunique entity coverageがおよそ **5%から27%以上**へ増加する。

この結果は、一回のqueryで何%漏れるかだけでなく、**repeated queryingによるcumulative graph reconstruction** を考える必要があることを示す。

著者らも、既出entityを避けて未探索領域を選ぶadaptive query planningを導入すればKnowledge Graph全体のstealingへ発展し得ると指摘する。この点は [RAGCrawler](2026-2601.15678-connect-the-dots.md) のglobal explorationと特に関連が深い。

## Defense Evaluation

### System Prompt

「private / sensitive informationを開示しない」とsystem promptで指示する単純な防御では、targeted extractionを十分抑えられない。attackerのqueryが通常のinformation requestと混在するため、generator-level instructionだけではretrieved structured contextの利用を止めにくい。

### Retrieval Similarity Threshold

retrieval similarity thresholdを高くすると、attack queryがcontextを取得できなくなりleakageは減少する。しかし十分な防御効果が得られるthresholdではbenign queryでもretrievalが失敗し、GraphRAG utilityが大きく低下する。

したがって典型的なprivacy-utility trade-offが生じる。

### Summarization

retrieved contextをgeneratorへ渡す前にsummarizeする方法はuntargeted extractionには一定の効果がある。irrelevantなentity / relationshipが落とされるためである。

しかしtargeted attackでは逆効果になる場合がある。queryに関連するsensitive informationをsummarizerが選択的に保持・濃縮するため、target entity / relationshipが最終contextに残りやすくなる。

これは「contextを要約すれば情報量が減るので安全」という直感がtargeted extractionには成立しないことを示す重要な結果である。

## Limitations / 成立条件

評価対象は主としてMicrosoft GraphRAG / LightRAGのようにentity・relationship・descriptionを明示的に構築するGraphRAGであり、pure symbolic triple storeや異なるgraph retrieval architectureへ同じleakage rateが一般化するとは限らない。

attackはGraphRAGのcontext representationに合わせたpromptを必要とするため、内部formatを大きく隠蔽・変換するsystemでは成功率が変わる可能性がある。

また評価したdefenseはsystem prompt、threshold、summarization等のheuristic mitigationが中心で、formal privacy guaranteeは提供しない。

さらにEntity / Relationship Leakage metricはstructured knowledgeの回収率を見るには有用だが、短いsecret、ID、数値、PIIなどは少数漏れるだけでも重大であり、単純な平均leakage rateだけではseverityを完全には表せない。

## RAG Security Taxonomyでの位置づけ

本論文は **Attack / confidentiality / GraphRAG structured knowledge extraction** に位置づけられる。

従来のRAG privacy taxonomyに対して重要なのは、protected assetを

```text
source documents
    ↓
retrieved chunks
    ↓
GraphRAG-derived entities / relationships / descriptions
```

まで拡張した点である。

[The Good and The Bad](2024-2402.16893-the-good-and-the-bad.md) が示したdirect RAG data extractionをGraphRAGへ拡張し、その先に [RAGCrawler](2026-2601.15678-connect-the-dots.md) のようなcoverage-aware explorationを組み合わせ得る位置にある。

一方 [Riddle Me This!](2025-2502.00306-riddle-me-this.md) は既知documentがdatabaseに存在するかというmembership bitを推定するattackであり、本論文は内部knowledge contentそのものを回収する点で異なる。

## 実装・研究上の示唆

GraphRAGをprivacy-sensitive domainへ導入する場合、source textをそのままgeneratorへ渡さないことだけでは安全性を保証できない。entity / relationship descriptionは元documentより簡潔であるため、むしろattackerにとって抽出しやすいknowledge representationになる可能性がある。

防御側では、

- graph element / description単位のaccess control
- sensitive entity / edgeへのretrieval policy
- query/session横断でのcumulative leakage monitoring
- responseごとのleakageだけでなくgraph coverageの増加を監視
- targeted summarizationがsensitive knowledgeを濃縮しないかの評価

が重要になる。

特に今後のattack研究では、GraphRAG-specific extraction commandとRAGCrawler型global planningを組み合わせ、限られたquery budgetでKnowledge Graph全体をどこまでreconstructできるかが自然な次の課題になる。
