# MLKV: Multi-Layer Key-Value Heads for Memory Efficient Transformer Decoding

## 概要

MLKVは、Multi-Query Attention（MQA）とGrouped-Query Attention（GQA）が**同一layer内のquery heads間でK/Vを共有する**のに対し、**異なるTransformer layers間でも同じK/Vを共有する**architecture。各layerに少なくとも1組のK/Vが必要というMQAの下限を超えて、全modelのKV head総数をlayer数より少なくできる。

提案の意義は単なる圧縮率ではない。GQAのuptraining（既存checkpointのKV projection weightを平均化し、少量のcontinued pretrainingを行う）をlayer方向にも拡張し、**head方向とlayer方向のどちらから共有を進めるべきか**を同じ総KV head数で比較した。結果は、同じhead総数なら一般にGQA/MQAの方が品質が良く、**MQAよりさらにcacheを減らす必要がある場合にMLKVが有用**という慎重な結論である。

## 問題設定：cache sizeの次元

batch size $b$、sequence length $s$、layer数 $l$、query head数 $h$、KV head dimension $d_k$、GQA group数 $g$ とすると、cache要素数は次の通り。

$$
\begin{aligned}
M_{\mathrm{MHA}} &= 2bslhd_k,\\
M_{\mathrm{GQA}} &= 2bslgd_k,\\
M_{\mathrm{MQA}} &= 2bsld_k.
\end{aligned}
$$

MQAはlayerごとに1組のKVを保持するため、総KV head数が$l$より小さくならない。MLKVはKVを実際に生成するlayer数を$m$（$m<l$）、それぞれのKV group数を$g$とし、

$$M_{\mathrm{MLKV}}=2bsmgd_k$$

まで削減する。例えば$l=12,m=6,g=1$ならMQAの**半分**、$m=2,g=1$ならMQAの**1/6**のcache要素数になる。ただしこれはcacheの理論容量であり、throughputの同倍率改善ではない。

## 手法

### 1. Layer grouping

連続layerをgroup化し、groupの代表layerで生成したKVを他layerのqueryから参照する。各layerのquery projectionとattention output projectionは維持するため、**query表現はlayerごとに変化し、K/Vだけを共有**する。head方向のgroupingも併用できる。

```text
GQA (l=12,g=1):
  layer 0: Q0 -> KV0
  layer 1: Q1 -> KV1
  ...
  layer11: Q11 -> KV11     # total 12 KV heads

MLKV (l=12,m=6,g=1):
  layer 0: Q0 -> KV0
  layer 1: Q1 -> KV0
  layer 2: Q2 -> KV2
  layer 3: Q3 -> KV2
  ...                         # total 6 KV heads
```

layer数とgroup数の組合せを変えることで、`MLKV-48`（m=4,g=12）、`MLKV-12`（m=4,g=3）、`MLKV-6`（m=6,g=1）、`MLKV-2`（m=2,g=1）などを作る。

### 2. Checkpoint conversionとuptraining

Pythiaのpretrained weightsから、同じgroupへ統合するK/V projectionを**重みの平均**で初期化する。KV projectionの削減によるparameter数の差はMLP intermediate sizeを増やして補い、model間の総parameter数をほぼ一致させる。GQAと同様に元のpretraining dataの約5%でcontinued pretrainingを実施する。

これは**training-freeなruntime cache sharingではない**。また、新しいquery位置だけを選んで再計算する[CacheBlend](../reuse/2024-2405.16444-cacheblend.md)とは問題設定が異なる。

## Experiment Setup

- **Base models:** Pythia-160M（12 layers、12 query heads）とPythia-410M（24 layers、12 query heads）。
- **Uptraining:** deduplicated The Pileの約600万documents（packing後246万rows）、2048-token sequence。Pythia-160Mの各variantを2×A100 80GBで約22時間uptrain。
- **Evaluation:** ARC-e、LAMBADA、PIQA、SciQのaccuracy（LM Evaluation Harness）。
- **Inference:** RTX 3060 12GB、dummy KV長2000から48 tokens decode。batch sizeとVRAM、batch=8でtokens/sを測定。
- **Comparisons:** MHA baseline、GQA-48、MQA-12、MLKV-48/12/6/4/2/1。同じKV head数の比較と、MQAより少ないKV head数の比較を分離。

## Main Results

Pythia-160Mの4-task平均accuracy（論文Table 3）：

| Configuration | Total KV heads | 平均accuracy | MQA-12比cache量 |
|---|---:|---:|---:|
| MHA baseline | 144 | 52.79 | 12× |
| GQA-48 | 48 | 50.17 | 4× |
| MLKV-48 | 48 | 49.29 | 4× |
| MQA-12 | 12 | **49.43** | 1× |
| MLKV-12 | 12 | 48.78 | 1× |
| MLKV-6 | 6 | **49.06** | **1/2×** |
| MLKV-4 | 4 | 47.31 | 1/3× |
| MLKV-2 | 2 | 46.78 | 1/6× |
| MLKV-1 | 1 | 41.12 | 1/12× |

MLKV-6はMQA-12にかなり近いaccuracyでcacheを半減する。一方、MLKV-1はLAMBADAが8.56%に低下しており、極端な共有は破綻する。

**Pythia-410M**でもMQA-24平均54.76、MLKV-12平均54.02、MLKV-8平均53.21と、memory/qualityのtrade-offを確認する。

### Memoryとthroughputを混同しない

RTX 3060の測定ではbaselineの最大batch 48に対し、MLKV-2は940、MLKV-1は1100まで到達する。ただしMLKV-1は品質が悪いため「大量batchが可能」だけでは優れた設計とはいえない。

**論文はbatch=8のthroughputで有意なspeedupを確認できなかったと明記**している。cacheの読み出しはlayerごとに必要で、共有によるmemory削減がそのままdecode latency短縮に直結しない。専用kernel・memory layoutで改善する可能性は残るが未実証。

## Ablation・分析

1. **同じ総KV head数ならhead方向の共有を優先。** GQA-48 > MLKV-48、MQA-12 > MLKV-12という傾向。異なるlayerが異なるKV表現を持つことが重要と推測される。
2. **MQA下限を超えた領域。** MLKV-6（MQAの1/2容量）は比較的良いPareto点。MLKV-2（1/6）はさらなるmemory削減と引換えにquality低下。
3. **Scale-up。** 160Mから410Mへ拡張しても傾向は概ね維持。ただし7B/14B以上の大規模modelでは未検証。
4. **Training fairness。** parameter数をMLPで揃えたため、純粋なKV cache量だけでなくmodel capacityの再配分も含む。attention FLOPsとMLP FLOPsの変化を無視した完全な同条件比較ではない。


## 実装上の意味：KV tensorはどこに置かれるか

MLKVの削減対象は、単に保存後のtensorをcompressすることではなく、**あるlayerのK/V projectionそのものを省き、先行layerで作ったK/Vをattention inputとして参照する**こと。例えば2-layer groupでは、group先頭layerでK/Vを生成してcacheへ書き、後続layerは自分のQを生成しながら同じcached K/Vを読む。従って後続layerのQと共有K/Vは、別layerのhidden stateから計算されている。

この仕組みを標準のLLM serving engineへ入れる場合、layerごとに独立したKV blockを持つことを前提としたcache allocator・attention metadata・GPU kernelの扱いを変更する必要がある。特に「KV cacheが半分になった」ことと「KV read bandwidthが半分になった」ことは同義ではない。後続layerもattentionを計算するため、同じK/Vを再び読み出す。layer間で共有K/VがGPU cacheに残るなどの最適化がなければ、decode時のHBM read量が理論容量ほどは減らない可能性がある。

ただしこの段落はarchitectureからの**実装上の考察**であり、論文がvLLM/FlashAttentionへ統合して性能測定したという意味ではない。

## Accuracy–memory Paretoの読み方

MLKVのTable 3では、head総数を揃えた比較と、MQAの下限より減らした比較を区別する必要がある。`GQA-48`と`MLKV-48`はcache要素数が同じなので、前者が良いならlayer共有を採用する理由は乏しい。`MQA-12`と`MLKV-12`でも同様。

一方`MLKV-6`には同じhead数の標準MQA counterpartが存在しない。12 layersのMQAは必ず12 KV headsを持つからである。従って`MLKV-6`の価値は「同じcacheでMQAより高精度」ではなく、**MQAでは到達できないmemory予算へ移動しながらaccuracyを大きく落とさない**点にある。

`MLKV-2`はMQA比1/6のcacheだが、baseline MHAに対しては144→2、すなわち1/72の要素数になる。こうした比率を報告する際は**何を分母にした削減率か**を明記しないと比較を誤る。

## Limitations

- Pythia-160M/410Mのみ。LLM規模、長文QA、instruction followingへの一般化は未検証。
- Training-freeではなくcheckpoint conversionとuptrainingが必要。
- KV cache容量削減とdecode throughput改善は別問題。現実のvLLM/FlashAttention最適化効果は測っていない。
- 固定の連続layer groupingを中心に扱い、learned/nonuniform sharingやarchitecture別の最適配置は十分探索していない。

## Taxonomy・関連研究との差分

**model / architecture-level KV sharing / cross-layer sharing / checkpoint uptraining**。

- [GQA](2023-2305.13245-gqa.md): 同一layer内のhead方向sharing。MLKVはlayer方向へ拡張。
- [Cross-Layer Attention (CLA)](2024-2405.12981-cross-layer-attention.md): より大規模なfrom-scratch architecture実験。MLKVは既存Pythia checkpointのuptrainingが中心。
- [LCKV](2024-lckv.md): upper-layer KVを多数layerへ共有する異なるtopology。
- [Systematic Cross-Layer KV Sharing](2025-cross-layer-kv-sharing-systematic.md): sharing topologyの比較を体系化。
- [KVSharer](2024-2410.18517-kvsharer.md): pretrained modelのlayer redundancyを活用する別アプローチ。
- [DeepSeek-V2 / MLA](2024-2405.04434-deepseek-v2-mla.md): layer共有ではなく各tokenのKV表現を低次元latentへ圧縮。
