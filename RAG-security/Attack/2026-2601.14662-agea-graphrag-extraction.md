# Query-Efficient Agentic Graph Extraction Attacks on GraphRAG Systems（AGEA）

> **要点**：従来のRAG corpus extractionがテキストchunkの取得率を評価するのに対し、AGEAは**GraphRAGの内部knowledge graph（entityとrelation）を長期・適応的に復元する**。単なるresponseからの関係抽出ではなく、攻撃側に累積graphを保持し、新規発見率をもとに探索モードを切り替え、幻覚由来の偽edgeを除去することで、**限られたquery budgetに対するgraph coverageとprecisionの両立**を目指す。ACL 2026 Main。コード公開あり。

## 概要・重要性

GraphRAGはsource documentsからentity–relation graphを構築し、queryに関連するsubgraphや属性説明をgeneratorへ渡す。従来のflat RAGでは、private text chunkのverbatim leakageが主要な懸念だったが、GraphRAGでは**個々の文書を再現できなくても、entity間の機密関係を抽出するだけで情報価値が高い**。例えば医療記録における人物・症状・治療の結び付きや、企業内部の担当者・プロジェクト・取引先の関係は、断片的な文章より再利用しやすい構造的資産になる。

先行する[Exposing Privacy Risks in Graph Retrieval-Augmented Generation](2025-2508.17222-exposing-privacy-risks-graphrag.md)は、GraphRAGがverbatim textを保護できてもentity/relation leakageが起こるというtrade-offを示した。AGEAはそこから一歩進み、**漏れるか否か**ではなく**1000回程度のblack-box queryで、内部graphのどこまでを精度良く復元できるか**を測る。既登録の[GRASP](2026-2602.06495-graphs-dont-stay-secret-grasp.md)がdefended GraphRAGのtargeted typed subgraphに重点を置くのに対し、AGEAはglobal graph coverageとquery efficiencyを主目的にする。

## 問題設定・Threat Model

対象はMicrosoft GraphRAG / LightRAGのように、非公開document collection $D$ から内部graph $G=(V,E)$ を構築するGraphRAG。通常query $q$ に対して、隠されたsubgraph $G_q\subseteq G$ を検索し、$R=\mathrm{LLM}(q,G_q)$ を返す。

**Attacker capability**：攻撃者は公開query interfaceに文章を送信し、返された自然言語responseだけを観測する。retrieverの重み、index、内部KG、retrieved subgraph、embedding、LLM parameter、retrieval scoreへのアクセスはない。queryを適応的に変更でき、攻撃側で外部LLMやgraph memoryを使用できる。評価では固定のquery budgetを設ける。文書・indexへのwrite accessやpoisoningは不要。

**Attack goal**：観測したresponse系列から推定graph $\hat G=(\hat V,\hat E)$ を構築し、元の$V,E$に対するnode/edge leakage（recallに相当）を高めつつ、偽entity・偽relationを少なくする。対象は**structured knowledge extraction**であり、raw source documentsの完全なverbatim reconstructionではない。

**成立条件**：victimがretrieved evidenceを回答に反映し、少なくとも一部のentity/relationを自然言語として外部に開示すること。さらにAGEAの高速Stage Aは、追加の出力指示によりentity/relation形式の回答を引き出せることを利用する。この点は、任意の安全制約付き本番GraphRAGにそのまま通用することを保証しない。

## 先行研究からの改善点

| 系統 | 既存手法・弱点 | AGEAでの変更 |
|---|---|---|
| 直接的なcontext抽出 | [The Good and The Bad](2024-2402.16893-the-good-and-the-bad.md) のTGTBやPIDE型は、context再出力を促す定型promptに依存し、得られた情報の全体graphを継続管理しない | responseからnode/edgeを抽出し、長期memoryに集約する |
| 反復的なtext corpus extraction | [CopyBreakRAG](2024-2411.14110-feedback-guided-extraction-copybreakrag.md)は過去の抽出片をfeedbackに使うが、graph固有のrelation coverage・偽edge制御を主目的としない | raw graphによる新規性評価とfiltered graphによる品質維持を分離 |
| benign-looking iterative extraction | [IKEA / Silent Leaks](2025-2505.15420-silent-leaks-ikea.md)は通常の質問から内部知識を抽出するが、GraphRAGのexplicit edge復元では効率が低い | entity/relationを直接狙うqueryとgraph-specific parsingを導入 |
| GraphRAG privacy study | [Exposing Privacy Risks](2025-2508.17222-exposing-privacy-risks-graphrag.md)は漏洩の存在を示す | 固定budget下で広域graph reconstructionを最適化 |
| defended GraphRAGへのtargeted攻撃 | [GRASP](2026-2602.06495-graphs-dont-stay-secret-grasp.md)は特定entity周辺のtyped edge fidelityを重視 | AGEAは広域node/edge coverageと探索計画を重視。比較対象・評価設定は同一ではない |

既登録の[Connect the Dots / RAGCrawler](2026-2601.15678-connect-the-dots.md)とも「global memoryによる長期探索」という発想を共有する。ただしRAGCrawlerはresponseから構築したKGを**flat RAG corpus探索のproxy state**として使うのに対し、AGEAは**victim内部KGそのものを復元対象**とする。これは両者を比較する際の重要な区別である。

## Method / Algorithm

### 全体フローと4 component

```text
Filtered Graph Memory G_f ──────┐
Raw Graph Memory G_r ───────────┤
Query Memory M_Q ───────────────┤
                                 ▼
                    Query Generator Q
              (explore / exploit mode)
                                 │ query + extraction command
                                 ▼
                     Victim GraphRAG
                                 │ natural-language response
                                 ▼
                    Stage A: Discovery
                   regex / normalization
                     ┌───────────┴───────────┐
                     ▼                       ▼
            update raw G_r           compute novelty N(t)
                     │                       │
                     ▼                       └── next mode selection
               Stage B: Filter
          LLM verification + dedup
                     │
                     ▼
            update filtered G_f
                     │
                     └── next turn
```

AGEAはadaptive query generator $Q$、graph extraction/filter $F$、Graph Memory $M_G$、Query Memory $M_Q$を連携させる。Graph Memoryはさらにraw $G_r$とfiltered $G_f$に分ける。**探索状態を測るmemoryと、復元結果として信頼するmemoryを別に持つ**のが設計上の核である。

### Stage A — 軽量なgraph discovery

各queryに**universal extraction command**を追加し、victimのresponseからentity名とrelationの候補を規則的に列挙させる。攻撃側ではregexで候補$\hat V_r^{(t)},\hat E_r^{(t)}$を取り出し、正規化・重複除去して$G_r$に蓄積する。

この段階では追加のLLM呼び出しを必要としない。したがって各turnで候補の新規発見数を即座に計算できる。ただし**raw候補には幻覚や一般語、実際の内部KGにない関係が混ざる**ため、そのまま最終的な盗取KGとみなさない。

### Stage B — Graph Filter Agent

$F$は、response原文、今回のraw candidates、前turnまでの$G_f$を受け取る。既存graphとのcanonicalization・同義entity統合・重複edge除去を行い、新規候補については**response中の根拠**と**既存graphとの構造的整合性**を確認する。

例えば新しいentityが大量の既存entityと突然接続される「hallucinated hub」や、source textに裏付けられないedgeを疑う。受理した候補だけを$G_f$へcommitする。これにより、再質問で重複関係を無駄に確認することを減らし、graph precisionを維持する。

重要なのは、**noveltyをStage B後ではなくStage Aのraw候補から計算する**こと。フィルタが厳しすぎて新規候補を落としたときに「探索が進んでいない」と誤判断し、mode selectionが不安定になることを避ける。一方、raw noveltyには偽候補も含まれうるため、偽情報を大量に生むresponseに探索計画が影響される可能性は残る。

### Novelty-guided exploration / exploitation

各turnの新規発見率をnodeとedgeの候補数で重み付けして定義する。

$$
N^{(t)}=\frac{N_{\rm node}^{(t)}|\hat V_r^{(t)}|+N_{\rm edge}^{(t)}|\hat E_r^{(t)}|}{|\hat V_r^{(t)}|+|\hat E_r^{(t)}|},
$$

ここで$N_{\rm node}^{(t)}=1-|V_r^{(t-1)}\cap\hat V_r^{(t)}|/|\hat V_r^{(t)}|$、edgeも同様。候補が空の場合の実装上のzero-division処理は要確認。

mode選択は**novelty-aware $\epsilon$-greedy**：$\epsilon_0=0.3$から各turnで0.98倍し、下限0.05まで減衰する。確率$\epsilon_t$で探索を選び、それ以外では直近5 turnの平均novelty $\bar N_t$を閾値$\tau_t$と比較する。$\bar N_t<\tau_t$なら既存領域の飽和と判断して**explore**、それ以外なら**exploit**を選ぶ。閾値も$\tau_t=\tau_{init}(\epsilon_t/\epsilon_{init})$で減衰し、$\tau_{init}=0.15$。

**Explore**は既知entityに固定されず、新しい種類のentity・relationを広く発見するqueryを生成する。**Exploit**は$G_f$のhigh-degree hubなど重要entityを選び、未取得の隣接関係を深掘りする。Query Memoryは最近の質問、応答、mode、noveltyを保存して重複探索を抑える。ランダム探索を残しつつ、飽和領域からの脱出と有望領域の深掘りを切り替える。

### 1 turnの処理順序

1. $G_f,G_r,M_Q$と直近noveltyからmodeを決める。
2. query generatorが新しい質問を生成し、entity/relationの出力指示を付加する。
3. black-box victimに質問し、responseを得る。
4. regex discoveryでraw node/edge候補を得て$G_r$更新、新規率$N_t$を計算する。
5. graph filter agentが重複・偽候補を排除し、$G_f$を更新する。
6. query/mode/noveltyを記録し、次turnへ進む。固定query budgetで終了する。

## Experiment Setup

### Corpus / Victim / Attacker

評価にはMedical（医療deviceやprocedure）、Agriculture（農業技術・作物）、Novel（20冊の古典小説、および2つの小規模novel graph）を使い、**Microsoft GraphRAGとLightRAG**それぞれのindexから構築された内部KGを別個の保護対象とする。両システムでentityとrelationの検索は`top_k=10`。M-GraphRAGはlocal search、LightRAGはhybrid searchが基本設定。

攻撃queryの生成・抽出処理に**GPT-4o-mini**、victimの生成LLMに**DeepSeek-V3.1**、retrieval embeddingに**text-embedding-3-large**を使用する。論文ではAzure OpenAI API経由でこれらを利用したと記載される。query budgetは主実験で**1000 queries**。mode policyの$\epsilon_0=0.3,\epsilon_{min}=0.05,\mathrm{decay}=0.98,\tau_0=0.15$。

**Baselines**は固定prompt系のTGTB、PIDE、およびadaptive extractionのCopyBreakRAG、IKEA。各手法を同一query budgetで比較する。TGTBやPIDEは明示的なretrieved evidence再出力を誘導するため、GraphRAGのentity/relation出力に対しても一定の抽出能力を持つ一方、構造化された長期計画はない。

### Metricsと読み方

- **Leak(N), Leak(E)**：victim内部KGに存在するnode/edgeのうち、攻撃側が正しく取得できた割合。大きいほどgraph coverageが高い。
- **Prec(N), Prec(E)**：攻撃側の復元graphに含まれるnode/edgeのうち、victim KGと一致する割合。大きいほどhallucinationや誤relationが少ない。
- **Leakage–Precision trade-off**：大量のentity名を列挙しても、偽edgeが多ければ知識グラフとしての再利用価値は低い。nodeだけでなく**edge precision**を重視する必要がある。
- query数に対する累積leakage trajectory、およびexplore/exploit/filter/extraction command/LLM backboneのablationを実施する。

## Main Results

### Microsoft GraphRAG：1000-queryの主要数値（公式PDF Table 1）

| Dataset | Method | Leak(N) % | Leak(E) % | Prec(N) % | Prec(E) % |
|---|---|---:|---:|---:|---:|
| Medical | IKEA | 14.27 | 2.31 | 6.76 | 0.78 |
| Medical | CopyBreakRAG | 73.65 | 31.88 | 32.19 | 8.96 |
| Medical | TGTB | 76.99 | 56.04 | 61.68 | 24.53 |
| Medical | PIDE | 58.84 | 33.55 | 72.96 | 29.03 |
| **Medical** | **AGEA** | **87.09** | **80.16** | **87.09** | **61.18** |
| Agriculture | IKEA | 18.41 | 5.75 | 11.04 | 1.60 |
| Agriculture | CopyBreakRAG | 63.38 | 43.93 | 34.77 | 13.10 |
| Agriculture | TGTB | 75.63 | 63.79 | 53.07 | 20.91 |
| Agriculture | PIDE | 70.23 | 54.63 | 59.03 | 24.30 |
| **Agriculture** | **AGEA** | **84.67** | **84.13** | **93.08** | **76.81** |

最も重要なのは**edge leakageとedge precisionの同時改善**。MedicalではAGEAのedge leakage 80.16%に対して、最良baseline TGTBは56.04%。edge precisionも61.18%に対しbaselineの最大はPIDEの29.03%。Agricultureでもedge leakage 84.13%、edge precision 76.81%で、baselineの63.79%、24.30%を上回る。node名だけを多く拾ったのではなく、**関係を含めてgraphとして復元できた**ことを示す。

LightRAGについても同様の優位性を報告し、Medicalなどでは90%を超える高いnode/edge coverageが観測される。ただしこの要約では、公式PDFのLightRAG表の全セルを独立再取得できなかったため、未検証の細かな数値は転記しない。

### Query trajectoryとbaseline差

固定promptのTGTB/PIDEは単発の出力誘導が強い一方、質問の新規性や累積graphを使った探索の最適化を行わない。CopyBreakRAGは過去の取得内容を使うが、関係の正誤を厳格に管理しないとprecisionが低下する。IKEAは自然な質問による知識抽出に適する一方、明示的なedge列挙・再構成には移植しにくい。AGEAはraw noveltyで探索方向を制御し、filtered memoryで復元graphの品質を維持するため、query数が増えた際にも関係の回収を継続できる。

## Ablation / Robustness / Additional Experiments

### Explore / exploit / filtering（Medical, M-GraphRAG；公式PDF Table 2）

| Variant | Leak(N) | Leak(E) | Prec(N) | Prec(E) |
|---|---:|---:|---:|---:|
| **AGEA full** | **87.09** | **80.16** | **87.09** | **61.18** |
| Explore-only | 23.77 | 10.67 | 67.60 | 32.05 |
| Exploit-only | 83.98 | 75.40 | 50.78 | 59.68 |
| Without graph filtering | 88.53 | 80.80 | 70.58 | 59.83 |
| Qwen backbone | 83.14 | 75.45 | 73.44 | 23.19 |
| GPT-4o-mini backbone | 82.61 | 75.41 | 76.19 | 51.54 |

**Explore-onlyが極端に悪い**のは、発見したentity周辺を掘らず、edgeを深められないため。Exploit-onlyはcoverageが比較的高いがnode precisionが50.78%に落ちる。適応的切り替えがcoverage–precisionの両方に効くことを示す。

**Filteringを外すと**node leakageは87.09→88.53、edge leakageは80.16→80.80とわずかに上がるが、node precisionは87.09→70.58へ大きく下がる。つまりフィルタはcoverageを少し犠牲にしてでも**復元graphの信頼性**を守る役割を持つ。LLM backboneを変更しても漏洩は高い水準を維持するが、edge precisionは特に変化し、filter/judgeの品質依存性が見える。

### Universal extraction commandのablation（Medical, 250 queries；Table 3）

| Command | Leak(N) | Leak(E) | Prec(N) | Prec(E) |
|---|---:|---:|---:|---:|
| **Proposed** | **62.34** | **46.62** | 92.87 | 69.21 |
| v1 | 44.27 | 26.82 | 77.63 | 54.25 |
| v2 | 48.29 | 34.32 | **93.12** | **81.24** |

抽出指示の言い回しだけで回収率・精度が変わる。v2はprecisionが高いがcoverageが低く、提案commandは**抽出量と品質のバランス**を優先する。これは同時に、AGEAの有効性が**victimに特定の構造化出力を促せるか**に依存することを示す。

### Robustness / Transferabilityの解釈

異なるGraphRAG architecture（M-GraphRAGとLightRAG）、異なるdataset、LLM backboneの変更で性能を検証している。ただし、GraphRAG全方式への一般化や、本番のstrict output guard、query rate-limit、per-user retrieval access control下での攻撃成功を直接保証する実験ではない。異なるgeneratorでedge precisionが大きく変わるため、model-independentな完全な再現性を主張するのは適切でない。

## Limitations・成立条件・評価上の注意

1. **Structured-output依存**：regex Stage Aはvictimがentity/relationを列挙する回答を返すことが前提。paragraph-only強制、出力schema制限、retrieval evidenceの強いredactionがあると抽出が困難になる。
2. **真のKGと「生成回答から復元したKG」の差**：responseのparaphrase、entity canonicalization、edge direction/typeの取り違えがある。LLM filterで誤候補を抑えるが、precisionは1ではない。node leakageとedge leakageを別々に評価すべき。
3. **Attack側コスト**：victimへの1000 queriesだけでなく、query generationとgraph filteringに攻撃側LLMの処理を要する。単純な1-query jailbreakとコストを同一視できない。
4. **評価対象の限定**：Medical/Agriculture/Novel、M-GraphRAG/LightRAG、特定のembedding・generator設定で評価。巨大な企業KG、複雑なACL、multi-tenant corpusへの外挿は未検証。
5. **Verbatim document theftとは異なる**：entity/relationの再構成が主目的で、元文書の全文・属性description・個人識別情報をどれだけ正確に復元できるかは別の問題。
6. **Defense evaluationの不足**：traversal-aware detection、session単位のsemantic budget、entity-level access controlなどの防御下での攻撃性能は今後の課題。
7. **時間的な先行・後続関係**：GRASPやRAGCrawlerは関連するglobal/targeted extraction研究だが、異なるvictimとmetricを使うため、表の数字を直接横並び比較しない。

## RAG Data Extraction / Security Taxonomyでの位置づけ

**Attack → Black-box Knowledge Base Stealing → Structured Graph / Relation Reconstruction → Long-horizon Adaptive Exploration**。

Flat RAGのtext extraction（TGTB / PIDE / CopyBreakRAG / IKEA）と、GraphRAGのtargeted subgraph reconstruction（GRASP）の中間に位置する。AGEAが示すのは、**retrieval corpusの機密性は「文書本文を返さない」だけでは守れず、GraphRAGが推論のために出力するrelation自体が独立したexfiltration surfaceになる**ということ。

RAGCrawlerがresponseから構築したKGを**次の検索を決めるための攻撃側proxy**として使うのに対し、AGEAではKGの再構築自体がattack success criterion。両者はgraph memoryを使うが、守るべき資産と評価軸が異なる。

## 実装・研究への示唆

- **Defense**：1-queryごとのprompt injection判定だけでは、長期的にentity/relation coverageが増える攻撃を見落とす。user/sessionごとにretrieved node/edgeの新規露出量、hub traversal、短期間のgraph frontier拡張を監視する設計が必要。
- **Access control**：source documentへのACLをGraphRAGのentity/relation/summaryに継承すること。元文書を隠しても共有KGに敏感なedgeが残れば漏洩する。
- **Output minimization**：回答に必要な関係だけを自然言語で出し、明示的な全entity/edge列挙を抑制することはStage Aへの対策になる。ただし通常の自然言語回答からの抽出はなお残るため万能ではない。
- **Benchmark**：node/edge recallに加え、relation type、direction、attribute、precision、query数、attack-side token cost、benign userへのfalse-positive影響を同時に測るべき。
- **研究上の接点**：GraphRAGのretrievalを多段化・広域化するほど、正答率改善とgraph leakageのトレードオフが発生しうる。cache/reuseでmulti-turn attackのコストが下がる場合もあるため、latencyだけでなく**単位コストあたりのexfiltration**を評価する必要がある。
