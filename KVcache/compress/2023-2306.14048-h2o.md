# H₂O: Heavy-Hitter Oracle for Efficient Generative Inference of Large Language Models

> decode時のKV cacheをすべて残す必要はなく、**過去から継続的に強くattentionされるHeavy Hitterと直近tokenを残せばよい**という初期の代表的KV eviction研究。後続のattention-based KV compression研究の基点の一つ。

## 概要

autoregressive generationでは各decode stepで過去tokenのK/Vを再利用するためKV cacheを保持する。KV cache sizeはsequence lengthとbatch sizeに線形増加し、長文生成や大batch servingではmodel weightsだけでなくKV cacheがmemory capacityを圧迫する。

H₂Oの中心観察は、attention contributionは全tokenに均等ではなく**少数tokenへ強く偏る**というもの。著者らは長期間にわたって大きなattentionを受け続けるtokenを Heavy Hitters (H₂) と呼ぶ。

これらをevictすると品質が急激に悪化する一方、多くのlow-contribution tokenは削除しても影響が小さい。そこでH₂OはHeavy Hitter tokenとrecent tokenを優先的にKV cacheへ残すdynamic eviction policyを提案する。

## Heavy Hitterとは何か

過去token iが各stepで受けたattention weightを累積したscoreを持つと、少数tokenのscoreが非常に大きくなる。H₂Oではこの累積attention contributionをtoken importanceのproxyとして使う。

重要なのは「現在stepでattentionが大きいtoken」だけではなく、**generation historyを通して繰り返し重要だったtoken**を残すこと。

## Heavy Hitterが生じる理由

論文ではHeavy Hitterの発生が偶然ではなくtext中のtoken co-occurrenceと強く関係することを分析する。

generation中に繰り返し参照されるsemantic / syntactic anchorのようなtokenがattention massを蓄積し、少数tokenが将来stepでも重要になりやすい。

したがって old token = unimportant とは限らない。単純sliding windowは古いtokenを一律削除するため、古くても重要なHeavy Hitterを失う。

## H₂O Cache Policy

cache budgetをCとすると、H₂Oは容量を二種類へ配分する。

- **Heavy Hitter region**：cumulative attentionが高いtoken
- **Recent region**：直近token

recent tokenを残す理由は、まだ十分なhistoryがなくheavy-hitter scoreが育っていない新しいtokenを即座に捨てないため。

各decode stepでattention scoreを更新し、heavy-hitter候補をrankingし、recent windowを保護し、budgetを超えたlow-score KVをevictする。このためH₂Oはstatic pruningではなく**online / dynamic KV eviction**。

## なぜRecent + Heavy Hitterか

Heavy Hitterだけ残すと新しいtokenは累積scoreが低いため不利。一方recentだけ残すsliding windowでは長距離dependencyに必要な古い重要tokenが消える。

H₂Oは long-term importanceをHeavy Hitters、short-term localityをrecent tokensで保持する。この構成は後続の多くのKV compression法でも現れる基本パターンになった。

## Dynamic Submodular Formulation

論文はKV evictionをdynamic submodular optimizationとして定式化する。cacheへ残すtoken集合Sに対し、将来attention computationへどれだけ有用かを集合関数として考え、capacity constraintのもとでutilityを最大化する。

一定の仮定のもとで提案eviction algorithmに理論保証を与える。実用面ではattention scoreに基づくonline selectionだが、「なぜgreedyなheavy-hitter retentionが妥当か」に理論的根拠を与えた点も特徴。

## Experiment Setup

主なmodel familyはOPT、LLaMA、GPT-NeoX。accuracy / generation qualityだけでなくKV memory、batch size、throughput、latencyを評価する。

system comparisonにはDeepSpeed Zero-Inference、Hugging Face Accelerate、FlexGenを用いる。実装はHugging Face向けaccuracy evaluation版とFlexGen統合版が公開されている。

## Main Results

代表設定は**20% Heavy Hitters**。OPT-6.7B / OPT-30Bにおいて、

- DeepSpeed Zero-Inference比：throughput最大 **29×**
- Hugging Face Accelerate比：throughput最大 **29×**
- FlexGen比：throughput最大 **3×**
- 同一batch sizeでlatency最大 **1.9×改善**

を報告する。

throughputの大幅改善にはKV memory削減によってより大きなbatchを載せられる効果も含まれるため、「attention FLOPsだけが29×減った」という意味ではない点には注意が必要。

## Accuracy / Quality

random evictionや単純windowと比較して、Heavy Hitterを保護することで小さいcache budgetでもquality degradationを抑える。

特に重要なのは、**同じ数のtokenを残す場合でも、どのtokenを残すかで性能差が大きい**ことを明確に示した点。これは後のKV token selection研究の基本問題設定になる。

## 主要Ablation / Analysis

### Heavy Hitterを削除するとどうなるか

累積attention上位tokenを意図的に削除するとmodel performanceが大きく悪化する。一方low-attention tokenの削除は影響が比較的小さい。この非対称性がH₂Oの前提。

### Recent tokenの必要性

heavy-hitter scoreだけでselectionすると新規tokenが不利になる。recent regionを確保することで新tokenが将来heavy hitterになる機会を残す。

### Cache budget

budgetを小さくするほどmemory savingは増えるが、保持できるHeavy Hitter / recent token数が減りaccuracyとのtrade-offが生じる。H₂Oはrandom/window baselineよりこのtrade-offを改善する。

## Scissorhandsとの関係

Scissorhandsも「過去に重要だったtokenは将来も重要になりやすい」というpersistent importanceを利用する初期KV compression研究で、H₂Oと近い時期の重要predecessor/parallel work。

両者は後のcumulative attention、observation window、recent token protection、query-aware selectionといったKV token pruning設計につながる。Scissorhandsは今後のhistorical backfill候補。

## StreamingLLMとの差

StreamingLLMはattention sinkを発見し、initial sink tokens + recent windowを保持することで長いstreamを固定memoryで処理する。

H₂Oはtoken identityを固定せず、**runtimeの累積attentionからHeavy Hitterを動的に選ぶ**。

したがってStreamingLLMはstructural / positional sink、H₂Oはdynamic attention importanceという違いがある。

## SnapKV / PyramidKVへの系譜

後続のSnapKVやPyramidKVではprefill promptからdecodeに必要なKVをより積極的に圧縮する。

H₂Oは主にdecode generation中のonline evictionを扱うのに対し、後続研究ではprompt KV compression、layer-dependent budget、query/observation-window attentionなどへ発展する。

特に「attention scoreをKV token importanceとして使う」という発想は、その後の多数のcompression法の基礎となった。

## Reuse系との違い

H₂Oは[CacheBlend](../reuse/2024-2405.16444-cacheblend.md)や[ProphetKV](../reuse/2026-2602.02579-prophetkv.md)とはtaxonomy上別カテゴリ。

H₂Oはone request内でstored KV token数を減らすcompress。一方CacheBlend / ProphetKVは以前計算したKVを別context/requestで再利用するreuse。

H₂Oのattention importanceは「どのKVを残すか」に使われ、ProphetKVのquery attentionは「どのcached KVを再計算するか」に使われる。signalは似ていても目的が異なる。

## Limitations

1. 過去attentionが将来importanceを予測できることを仮定し、sudden topic shiftでは過去scoreが役に立たない場合がある。
2. evicted KVは原則戻せず、後で重要になった古いtokenを再参照する場合に弱い。
3. full KV保持よりmemoryは減るがranking / score updateのoverheadがある。
4. OPT/LLaMA/GPT-NeoX中心の評価で、GQA/MQAや現代long-context modelではmemory構造やattention patternが異なる。
5. 中心はautoregressive decode中のcache evictionであり、巨大promptのprefill KVを最初から圧縮する後続法とは適用点が違う。

## KV-cache taxonomyでの位置づけ

H₂Oは **token eviction / dynamic KV cache compression**。

bit-widthは変えず、architectureも変えず、inter-request reuseもせず、cacheに保持するtoken数を減らすため分類は明確にcompress。selection signalはhistorical cumulative attention、granularityはtoken-level、実行時期は主にdecode-time。

## まとめ

H₂Oの重要性は、KV cacheを「全過去tokenを必ず保持するbuffer」ではなく、**capacity制約下で重要tokenを選択するcache**として明示的に扱った点にある。

Heavy Hitterとrecent tokenを組み合わせることでlong-term importanceとlocalityを両立し、model modificationなしで大幅なmemory / serving efficiency改善を示した。

後続のKV compression研究を読む上では「Which past KV tokens are worth keeping?」という基本問題を確立した代表的historical paperとして位置づけられる。
