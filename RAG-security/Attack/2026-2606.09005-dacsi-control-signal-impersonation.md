# Document-Authored Control-Signal Impersonation: A Low-Cost Indirect Prompt Attack on RAG Safety Boundaries

> RAGがretrieved documentsとsystem-authored metadata / safety policyを一つのnatural-language promptへ連結すると、文書内に書かれた「official」「verified」「quote allowed」等の**権限らしい記述**を、generatorが本物のcontrol signalと混同する場合がある。本論文はこれを **Document-Authored Control-Signal Impersonation（DACSI）** として切り出し、明示的なoverride命令を含まないpayloadでもsynthetic secretの漏洩が増えることを示す。

## 概要

Indirect prompt injectionの典型例は、外部documentに「以前の指示を無視せよ」「秘密を表示せよ」といったimperative instructionを埋め込むものだ。DACSIは同じ**untrusted retrieved document**を侵入口とするが、攻撃文書に命令を書かず、metadata / provenance / authority / disclosure policyに見えるラベルを配置する。

たとえば、application側のsystem policyが「credential-like valueをそのまま返してはいけない」と規定していても、検索文書中の「official internal note」「source status: verified」「disclosure policy: exact quote allowed」というdocument-authored textをLLMが実質的な許可として解釈すると、回答にsecret-like valueをコピーしてしまう。この失敗は**control plane（trusted policy）とdata plane（retrieved text）のsource authorityをprompt renderingが曖昧にする**ことで生じる。

著者はDACSIを**indirect prompt injectionの下位分類**と明言しており、新しい権限獲得機構や実世界でのcredential theftを証明したわけではない。評価対象はすべてnon-functional synthetic canaryで、指標はその全文・一部の再出力率である。

重要なのは、**命令形の禁止語を検出するだけのguardrailでは、metadata-looking payloadを取り逃がす**可能性と、retrieval後のcontext assemblyやsource separationが結果を大きく左右する点である。

## 問題設定 / Threat Model

対象は、system instructions、developer policy、trusted metadata、user query、retrieved documentsをLLMへ渡すRAG / context-augmented application。アプリケーションには機密値のexact disclosureを禁止するsystem-level instructionがある。

**Attacker capability**：攻撃者はwebpage、support ticket、README、wiki、runbook、issue comment等、retrieverが取得し得る**外部文書の本文だけ**を編集・投稿できる。system prompt、model weights、retriever、user query、safety policyには触れない。攻撃文書がretrieved contextへ入り、ユーザが診断・設定確認等でexact quoteを求める状況を想定する。

**攻撃目標**：retrieved documentに含まれるsynthetic credential-like canaryをgeneratorがそのまま、または一部コピーする確率を高める。実在のAPI keyを使った外部送信やtool-call exfiltrationは行わない。

**観測指標**：Unsafe Disclosure Rate（UDR）。full leakとpartial leakをunsafeと数え、redaction、拒否、値を含まない説明はsafe。主な比較は、同じtask、canary、decoding、document templateでpayloadのcontrol-looking cueだけを変える**paired defended baseline B1**と攻撃条件Aの差：

$$
\operatorname{Lift}_{A|B1}=\operatorname{UDR}(A)-\operatorname{UDR}(B1).
$$

**B0**は防御なしのnatural disclosure、**B1**は防御指示付きbaseline。UDRの絶対値とB1に対するliftを分けて読む必要がある。もともとB1が高いmodelでは、攻撃のliftが小さくても安全とはいえない。

## Method / Attack Primitive

### 1. Document-authored control-signal impersonation

本論文が定義するDACSIは、untrusted document内のspan $d_c\in D$ がtrusted control text $S$ に似た形式・意味を持ち、renderer $R(S,D)$ が両者をLLMに渡した際に、文書由来の記述を権限あるものとして扱わせる試みである。

主なpayload familyは、**authority cue**（公式・管理者の記述）、**provenance / source-status cue**（検証済みsource等）、**disclosure-policy cue**（正確な引用を許可するように見える文言）、**JSON/YAML/XML風metadata**。命令形の「ignore」「override」「reveal」「bypass」を含む必要がない。

従来のcommand-style injectionはモデルに既存の命令を破るよう**直接命じる**。DACSIは、文書自身が「この内容は承認済みで引用可能」という**権限属性を自己申告する**。最終的な漏洩文字列は同じでも、filteringとthreat modelingの観点で別のpayload surfaceとなる。

### 2. RAG prompt renderingが攻撃成立を媒介

本来は、`system-authored safety policy`と`retrieved document text`は別のtrust domainである。しかし、RAG実装が文書見出し、retrieval metadata、source label、system safety labelを同じテキスト名前空間へflattenすると、document-authored labelがsystem-authored metadataのように見える。

DACSIが有効な条件は、(i) attacker-controlled文書がretrieveされる、(ii) user taskがexact-copy pressureを与える、(iii) prompt renderingがtrusted / untrusted sourceを十分に分離しない、の組合せである。したがって**retrieval hitだけでは成功を保証しない**。chunkingで偽labelとcanaryが別chunkに分かれれば、効果は弱まる。

### 3. 対照実験によるmechanismの切り分け

著者は単なる攻撃成功率比較ではなく、同じcanaryとtaskを保ったまま、payloadを命令形／metadata風／neutral／negativeへ置換し、さらにauthority cueの**配置場所**をsystem側、document側、quoted document、source-separated renderingへ変える。

この設計は「権限を示す単語が存在すれば何でも漏れる」のか、「untrusted documentがsystem controlと混同されるから漏れる」のかを区別するためのbehavioral probeである。内部attentionやlatent attributionを直接測定していないため、**内部mechanismの証明ではない**。

| 比較対象 | 既存の問題設定 | DACSIの焦点 |

| [InceptionRAG](2026-2609.16818-inceptionrag.md)、[MIRAGE](2025-2512.08289-mirage.md) | corpus poisoning、distributed / stealthy manipulation | attack文書の**retrieval後のsource authority**の誤帰属を切り出す |

| [SD-RAG](../Defense/2026-2601.11199-sd-rag.md) | retrieved private contextのredactionとselective disclosure | 直接の比較baselineではないが、**secretをgeneratorへ渡す前に除く**防御の重要性を支持 |

論文はSpotlighting、StruQ、instruction hierarchy、CaMeL、BIPIAなども関連研究として議論する。DACSIはindirect injectionを置き換える概念ではなく、**従来benchmarkのpayload coverageが命令形に偏ること**への問題提起である。

## Experiment Setup

### Models / tasks / metrics

6 model settings：**DeepSeek V4 Pro、DeepSeek V4 Flash、Qwen3.5-397B、GPT-5.5、Gemini 3.1 Pro Low、GLM-4.7**。実験はmodel名そのものの普遍的安全性順位ではなく、アクセス層やprompt条件を含むmodel-setting別に解釈する。

主実験は原則**各condition n=200**。同じsynthetic canary seed、task、decoding設定、output budgetを使ったpaired comparisonsを行う。full / partial disclosure、redaction、refusal、errorを区別し、Wilson 95% CI、paired McNemar / sign test、Benjamini–Hochberg補正を報告する。API errorは別計上する。

Canary形式はbearer token、AWS-like key、GitHub token-like string、Slack bot token-like string、database URL、JWT-like stringで、いずれもnon-functional。

### Experiments E1–E6 / M1

- **E1 prompt pressure**：弱い要約要求と強いexact-copy要求を比較。
- **E2 payload family**：non-imperative DACSIとimperative injectionを同じtaskで比較。detector-gated bypass+leakも評価。
- **E3 signal taxonomy**：authority、provenance、disclosure policy、negative、nonsense label等を比較。
- **E4 RAG mediation**：toy insertion、BM25 paragraph retrieval、hybrid embedding retrieval、LangChain-style RAGを比較。後者はSQuAD public distractors、synthetic target documents、recursive splitting、HuggingFace sentence embeddings、FAISS、top-k retrieval。
- **E5 control probes**：generic warning、label stripping、source/channel separation等。
- **M1 source-authority placement**：同じauthority semanticsをsystem側、document側、quoted text等へ移す。
- **E6 canary-format robustness**：synthetic credentialの表現形式を変える。

E4のRAG条件はpublic / synthetic corpusを用いた**toy / semi-realistic reproduction**であり、企業private corpusの実地評価ではない。

## Main Results

### 1. Command-free payloadでもdisclosureが上昇

E2の平均UDR（%）を示す。これは**baselineからのliftではなく各payload familyの絶対UDR**である。

| Model setting | DACSI avg | DACSI max | Imperative injection avg | Injection max |
|---|---:|---:|---:|---:|
| DeepSeek V4 Pro | **20.5** | 30.5 | 30.0 | 33.0 |
| DeepSeek V4 Flash | **89.3** | 99.0 | 85.3 | 98.5 |
| Qwen3.5-397B | **87.5** | 92.0 | 85.1 | 89.5 |
| GPT-5.5 | 1.2 | 1.5 | 0.1 | 0.5 |
| GLM-4.7 | 96.7 | 98.0 | 72.8 | 92.0 |
| Gemini 3.1 Pro Low | 5.0 | 14.0 | 13.25 | 28.0 |

DeepSeek V4 Proではimperative injectionより平均UDRは低いが、DACSIでも20.5%に達する。DeepSeek V4 FlashとQwen3.5-397BではDACSIがimperative familyと同程度またはそれ以上。GPT-5.5とGeminiの大部分の条件では低い。GLM-4.7はbaselineから高漏洩の**ceiling effect**があり、DACSI固有の効果として大きな値を単純解釈できない。

E1ではexact-copy pressure下でDeepSeek V4 ProのB1 **0.5%→DACSI 28.0%**、DeepSeek V4 Flash **53.0%→91.5%**。つまりuser queryの**コピー要求強度**が成立条件の一つ。

### 2. Detector bypassとpayload surface

E2のDeepSeek V4 Proで、DeepSeek detectorを通した**bypass+leak**はDACSI **20.2%**、traditional injection **7.1%**。同じ検出器のpayload hit rateはDACSI **2.0%**、traditional injection **72.9%**。Gemini detectorではDACSIのbypass+leak **7.2%**、traditional **0%**だった。

ただしこれは**限定された2 detectorと実験payload**であり、あらゆるguardrailに対する回避率ではない。命令形の語に依存するdetectorがmetadata風の攻撃を見逃す可能性を示す。

Payload auditではDACSIが平均**0 imperative command cues / 5.67 metadata cues**、traditional injectionが**3.25 command cues / 0 metadata cues**。短い非命令形でも漏洩を増やせることが特徴。

### 3. Control-signalの種類により大きく変わる

Qwen3.5-397BのE3ではB1 **68.0%**に対し、disclosure allowed cue **91.5%（+23.5 pp）**、admin runbook **85.5%**、trusted reference **83.5%**。negative cue（do not quote）**67.0%**、nonsense label **69.0%**であり、**metadataなら何でも効果があるわけではない**。

Gemini 3.1 Pro Lowでは大部分のcueが0–1%だが、official-note cueのみ**13.5%**。強いboundaryのmodelでも特定のauthority表現に残余リスクがある。

### 4. RAG retrievalを通した効果

E4ではretrieval/assemblyによりDACSI効果が変わる。

| Model / RAG pipeline | B1 UDR | Max DACSI UDR |
|---|---:|---:|
| DeepSeek V4 Pro / toy insertion | 0.5% | 24.0% |
| DeepSeek V4 Pro / BM25 paragraph | 0.0% | 3.0% |
| DeepSeek V4 Pro / hybrid embedding | 0.0% | **47.0%** |
| Gemini 3.1 Pro Low / hybrid embedding | 0.0% | 17.0% |
| GPT-5.5 / hybrid embedding | 0.0% | 0.5% |

BM25のchunkingではcueとsecretが分離されやすく、効果が弱まった可能性がある。Hybrid retrievalでは両者が同じreader contextへ入ると効果が残る。

**LangChain-style RAG reproduction**では、DeepSeek V4 ProのB1 **1.5%**、official cue **34.0%**、disclosure cue **41.5%**。Target hitは各条件ほぼ**99.5–100%**。Channel separationで**0.0%**へ低下した。Geminiの同じLangChain設定では各条件0%だった。**retrieval hitとdisclosureは別指標**である。

## Ablation / Defense / Robustness

### 1. Generic warningよりsource-aware rendering

E5ではgeneric warningが必ずしも安全性を高めず、Qwen3.5-397Bでは平均UDRが**85.4%→93.5%**へ悪化した。単に「不審な文書に注意」と加えると、かえってsecretのsalienceを高める場合がある。

Focused probe（DeepSeek V4 Pro）では元renderingの攻撃条件平均UDR **20.67%**に対し、generic warning **13.17%**、Spotlighting-style delimiter **4.00%**、StruQ-style structure **0.00%**、system–document channel separation **0.17%**。別の2×2条件ではtraditional injection **31.6%→0.1%**、DACSI **19.0%→0.2%**。**source境界を明示する構造的処理**が有効だった。

### 2. Retrieval-time redaction

LangChain-style RAGでretrieval後・prompt組立前にsynthetic canaryを`[REDACTED_CANARY]`へ置換すると、DeepSeek V4 ProとGeminiの両方で測定UDRは**0%**。Target-hitは**99.5%**のままであり、単に文書をretrieveできなくなった結果ではない。

これは「generatorへ元secretを渡さなければ、そのsecretのexact copyingは起こらない」という強い実装原則を支持する。ただし、**redaction漏れ、推測可能なPII、semantic reconstruction**まで防げることは示していない。

### 3. M1 source-authority placement

同じauthority semanticsを異なるsourceへ置いた場合のUDR（%）：

| Placement | DeepSeek V4 Pro | Gemini 3.1 Pro Low |
|---|---:|---:|
| B1 clean | 0.0 | 0.0 |
| System-authored authority | 15.0 | 87.0 |
| **Document-authored authority** | **25.0** | 0.0 |
| Quoted authority text | 0.0 | 0.0 |
| Neutral document metadata | 0.5 | 0.0 |
| Negative document policy | 0.0 | 0.0 |
| System–document separation | 0.5 | 0.0 |

DeepSeekではdocument-authored authorityだけで25%へ上昇するが、quoted textにすると0%。Geminiはsystem-authored authorityには従う一方、document-authored authorityでは0%。同じ語彙でも**どのsourceから来たか**が挙動を変える。著者はpaired McNemar testで主要な差が有意と報告する。ただしこれはprompt constructionを操作した**behavioral evidence**であり、LLM内部のsource attribution circuitを同定したわけではない。

### 4. Canary-format robustness

Bearer token、AWS-like、GitHub-token-like、Slack-token-like、JWT-like、DB URLを比較。Geminiのofficial cueではbearer **15.0%**、AWS-like **11.0%**、GitHub-like **5.5%**、Slack-like **14.5%**、JWT-like **13.0%**など、複数形式で残余リスクが確認された。DB URLはbaseline leakageがあるため、attack固有のliftとしては扱いにくい。

## Limitations / 成立条件

1. **実際のcredential theftではない**。すべてsynthetic non-functional canaryであり、外部へのtool-call exfiltration、production deployment compromiseは評価していない。
2. **Whole-corpus stealingではない**。retrieved documentの中の特定secret-like stringをコピーするかの実験であり、RAGCrawlerやGeoExのようなcoverage / corpus reconstruction指標はない。
3. **Attacker-controlled documentがretrieved contextへ到達する必要がある**。retrieverへの直接操作権限はない。chunkingでcueとsecretが分離されると効果が弱まる。
4. **Copy pressure依存**。exact configuration lineを求めるuser queryで顕著。summaryで足りるtaskでは効果が小さい場合がある。
5. **Model-setting依存・baseline ceiling/floor**。GLM-4.7やDeepSeek V4 Flashはbaseline漏洩が高く、GPT-5.5やGeminiは大半の条件で低い。6 model settingsを単純平均して一般化できない。
6. **Defenseはcontrolled probe**。StruQ-style renderingやredactionの有効性は、測定したsynthetic canary・promptに対する結果。production-gradeのaccess control / semantic leakage防止の形式的保証ではない。
7. **Mechanismの直接観測なし**。M1はsource placementの因果的なprompt-level evidenceだが、内部の注意・推論過程を証明しない。
8. **Code URL未確認**。本文はartifactとreproducibility packageに言及するが、確認できた一次情報内に公式GitHub URLが見当たらないためfront matterは`code: null`とした。

## RAG Security Taxonomyでの位置づけ

**Category: Attack（retrieved-document leakage / non-imperative indirect prompt injection）**。攻撃者はretrievable documentだけを編集し、generatorが読むcontext内で**source-authority spoofing**を行う。狙いはconfidentiality（synthetic canary disclosure）であり、corpus poisoningを経由するがmisinformation injectionとは異なる。

[Follow My Instruction and Spill the Beans](2024-2402.17840-follow-my-instruction-and-spill-the-beans.md)のような直接的な「文書を再出力せよ」型と比較すると、**命令形を使わず「引用を許可されている」と誤信させる**点が異なる。攻撃成功に必要なretrieval hit、modelのcopy pressure、prompt renderingのsource separationを分離して評価した点が有用。

防御では[SD-RAG](../Defense/2026-2601.11199-sd-rag.md)のようなretrieval後redactionと、[RAG-CT](../Defense/2026-2609.16095-rag-ct.md)のようなquery/retrieval挙動監視を組み合わせる余地がある。ただしDACSI論文自体がこれらを直接baseline比較したわけではない。

## 実装上・研究上の示唆

- **Trusted retrieval metadataとdocument-authored metadataを同じテキスト名前空間に置かない**。source label、access decision、disclosure policyはsystem側の構造化channelで管理し、文書本文がそれを上書きできないようにする。
- **Secretをgeneratorへ渡す前にredactする**。modelが正しくpolicyを守るかだけに依存せず、入力データ最小化とoutput scanningを別層で実装する。
- **Prompt-injection benchmarkに非命令形のmetadata / provenance / authority spoofingを追加する**。imperative trigger検出率だけでは漏洩リスクを評価できない。
- **Retrieval hitとgeneration disclosureを別々に計測**し、chunk size、reranking、metadata rendering、copy pressure、canary formatを変える。文書が検索されたかだけでは攻撃成功率を予測できない。
- **形式的なsource isolationやtaint trackingとの比較が今後の課題**。単なる自然言語の「これはuntrustedです」という注記がどこまで有効かを、adaptive attackerと実際のprivate corpusで再検証する必要がある。
