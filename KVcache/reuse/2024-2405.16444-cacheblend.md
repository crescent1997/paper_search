# CacheBlend: Fast Large Language Model Serving for RAG with Cached Knowledge Fusion

> prefix cachingでは再利用できないRAG document KVを、重要tokenだけ再計算してfull-prefill品質へ近づける。KV reuse研究における「modelを変えず、runtime repairで整合性を回復する」代表的アプローチ。

## 概要

RAGではqueryごとに複数documentをretrieveし、instruction、retrieved documents、questionを1本の長いpromptとしてLLMへ入力する。

同じdocumentが複数requestで再利用されるなら、そのKVを一度計算して保存し、次回はreuseしたい。

しかし通常のKV cacheはprefix historyに依存する。

Document Bを単独prefillしたKVはBしか見ていない。一方full prompt内のDocument B tokenは、それ以前のDocument Aにもattentionする。

したがって、

precomputed KV(B) と full-context KV(A,B)

は一致しない。

単純concatは高速だがaccuracyが落ち、全tokenを再prefillすれば正確だがreuse benefitが消える。

CacheBlendはこの中間を狙い、KV差分の大きい少数tokenだけを再計算する。

## 問題設定

RAG inputを複数chunk C1, C2, ..., Cm に分ける。

各chunkはofflineまたは過去requestで独立prefillされ、layerごとのKVとして保存される。

full-prefillで得られるCiのKVは前chunk C1...Ci-1に依存するが、cached KVはCiのみから作られている。

CacheBlendの目的は、cached KVを全部捨てることなく、少量の追加計算でfull-prefillに近い状態へ修正すること。

## Key Observation 1: KV deviationはsparse

著者らは、precomputed KVとfull-recomputed KVのtoken-wise差を調べる。

すると全tokenが均等に壊れているわけではなく、約10〜15%のtokenだけが大きなKV deviationを持つことを観察する。

これらをHigh-KV-Deviation、HKVD tokenとして扱う。

理由はcross-chunk attentionのsparsity。

あるtokenが他chunkへほとんどattentionしないなら、そのtokenのhidden stateはpreceding chunkが追加されてもあまり変わらない。

逆に他chunkへ強くattentionするtokenでは、独立prefill時とfull-context時のKV差が大きくなる。

このため全tokenを再計算する必要はなく、HKVD tokenだけを直せばよい。

## Key Observation 2: HKVD tokenはlayer間で相関する

問題は、真のKV deviationを知るにはfull KVが必要なこと。

そこでCacheBlendはlayer間相関を使う。

layer lでdeviationが大きいtokenは、layer l+1でもdeviationが大きい可能性が高い。

そのため前layerで得られたhigh-deviation token集合を次layerのrecompute targetとして利用する。

この構造により、毎layer全tokenをfull-contextで処理しなくてよい。

## Selective KV Recomputation

recompute ratioをrとする。

例えばdefaultの15%なら、各layerのtokenのうち上位15%だけをfull contextで再計算し、残り85%はcached KVをそのまま使う。

再計算tokenはpreceding chunksを参照できるため、失われていたcross-document interactionを取り戻す。

また再計算されたstateは次layerへ伝播するため、少数tokenのrepairが後段representationにも影響する。

## なぜ15%程度で足りるか

論文の分析ではKV deviationの分布はheavy-tailで、多くのtokenは差が小さい。

recompute ratioを増やすと最初はqualityが急速に改善するが、一定以上では飽和する。

実験では約15%がfull recomputeに近いqualityへ到達する実用的なdefaultとして採用される。

これはCacheBlendのsystem benefitを決める重要な数字。

## KV LoadingとのPipeline

document KVをGPU memoryに常駐させられない場合、CPUやNVMeからlayer-wiseにloadする必要がある。

CacheBlendは、このI/O時間とselective recomputationをoverlapする。

layer lのselected tokenを再計算している間に、layer l+1のcached KVをloadする。

前layerのdeviation情報から次layerのtargetを決められるため、このpipelineが成立する。

論文の例ではLlama-7B、4K context、15% recomputeで、

- selective recompute: 約3 ms / layer
- NVMeからKV loading: 約16 ms / layer

であり、recomputeがI/Oの裏に完全に隠れる。

つまりrepairを追加してもTTFT critical pathがほぼ増えない。

## Model sizeが大きい場合

Llama-70Bの例では、

- 15% recompute: 約7 ms
- NVMe load: 約4 ms

となり、recomputeを完全には隠せない。

このためCacheBlendは固定15%だけでなく、model・context長・storage bandwidthに応じてpolicyを変えるcontrollerを持つ。

## Loading Controller

controllerはrecompute時間とKV loading時間を予測し、I/Oで隠せる範囲とquality thresholdを考慮してrecompute ratioを決める。

さらにKVをどのstorage tierへ置くかも選ぶ。

候補はGPU memory、CPU memory、NVMe等。

高速deviceは高価・容量小、低速deviceは安価・容量大というtrade-offがある。

CacheBlendはKV reuseを単なるattention optimizationではなく、storage hierarchyを含むserving problemとして扱う。

## System Components

system全体は概ね、

1. KV cache storage
2. retrieval結果からcache entryを特定するloader
3. layer-wise selective recompute engine
4. loading/recompute policyを決めるcontroller

で構成される。

RAGでdocument IDが決まると、該当documentのprecomputed KVを読み、full prompt順に組み合わせながら必要tokenだけrepairする。

## Experiment Setup

3種類のopen-source LLM、4種類のpopular benchmark datasetを使う。

比較対象には、

- Full KV recompute
- prefix-based cache reuse
- naive chunk KV concatenation
- existing KV reuse schemes

を含む。

評価指標はgeneration quality、TTFT、serving throughput、recompute ratio、storage / loading overhead。

## Main Results: Generation Quality

naive KV concatenationではcross-chunk informationが欠落し、task accuracyやgeneration qualityが落ちる。

CacheBlendは約15%のselective recomputationで、full recomputeに近いqualityまで回復する。

これはfull-contextによる差分が少数tokenへ集中しているという仮説を支持する。

## Main Results: TTFT

full KV recomputationと比較して2.2〜3.3×のTTFT改善を報告する。

contextが長いほどfull prefill costが大きくなるため、reuse benefitも大きくなる。

## Main Results: Throughput

serving throughputでは2.8〜5×改善。

prefill GPU computeが減るため、同じGPU resourceでより多くのrequestを処理できる。

## Recompute Ratio Ablation

recompute ratio 0%では最速だがnaive reuse qualityになる。

10〜15%程度でqualityが急速に回復し、100%でfull recomputeと一致する。

このquality / compute curveがCacheBlend成立の鍵。

modelやtaskによって最適ratioは変わるため、15%は絶対値ではなくdefaultとして見るべき。

## CacheBlendが修正しているもの

重要なのは、CacheBlendの問題が単なるposition shiftではないこと。

RoPEを新しいglobal positionへ付け替えても、cached hidden stateがpreceding documentsを見ていない問題は残る。

したがってposition re-encodingだけではfull prefillへ一致しない。

CacheBlendはcross-context interactionの不足そのものをselective recomputationで修復する。

## Block-Attentionとの違い

[Block-Attention](2024-2409.15355-block-attention.md)は同じreuse problemへ逆方向から取り組む。

CacheBlendはmodelを変えず、reuse KVをfull-attention stateへ近づける。

Block-Attentionはfine-tuningによってmodel側をindependent block KVへ適応させる。

CacheBlendはruntime computeを払う代わりにpretrained model compatibilityが高く、Block-Attentionはtraining costを払う代わりにcache hit時のruntime repairをほぼ消す。

## EPICとの違い

[EPIC](2024-2410.15332-epic.md)もposition-independent reuseを狙うが、attention sinkなどsystematicなsegment-boundary artifactへ焦点を当てる。

CacheBlendはtoken-wise KV deviationを見て、どのtokenが壊れているかを動的に選ぶ。

両者はinference-time repair系だが、repair targetの設計が異なる。

## Limitations

- 15% recomputeで十分かはmodel / dataset / chunk structureに依存する。
- document KVをlayer-wiseに大量保存するためstorage footprintが大きい。
- cache loading bandwidthが遅すぎるとreuse benefitがI/Oに食われる。
- partial recomputationを効率よく実装するcustom kernel / serving integrationが必要。
- 100%未満ではfull-prefill内部stateと厳密一致しない。

## KV-cache taxonomyでの位置づけ

CacheBlendはnon-prefix reuse + inference-time repair。

reuse categoryでは、

- exact prefix reuse
- CacheBlend型 selective recomputation
- EPIC型 position-independent linking
- Block-Attention型 reuse-aware fine-tuning

を区別すると整理しやすい。

## 研究上の重要な示唆

CacheBlendの中心的メッセージは、stale KVを全部修正する必要はないという点。

full-contextとの差が少数tokenへ集中するなら、全token再計算をrL、rが十分小さい部分計算へ置き換えられる。

さらにcomputeとKV I/Oをpipeline化すれば、partial repair cost自体をcritical pathから隠せる。

KV reuseはmodel algorithmだけでなく、storage hierarchy・I/O schedulingを含めて最適化すべきことを示した点でも重要。

## まとめ

CacheBlendは、

1. document KVを事前計算して保存
2. request時にcached KVを組み合わせる
3. KV deviationが大きいtokenが約10〜15%に集中する性質を利用
4. layer間相関から次layerのrecompute tokenを選ぶ
5. 選択tokenだけfull-contextで再計算
6. KV loadingとrecomputeをpipeline
7. controllerでratio / storageを調整

する。

full recompute相当のqualityを維持しながらTTFTを2.2〜3.3×、throughputを2.8〜5×改善する。prefix一致を超えたKV reuseを実用化するには、position補正だけでなくcross-context interactionを修復する必要があることを明確にした代表的研究。
