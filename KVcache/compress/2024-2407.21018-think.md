# ThinK: Thinner Key Cache by Query-Driven Pruning

## 概要・問題設定
従来のSnapKVやH2Oは重要tokenを選択するが、各tokenのKeyのchannel幅は固定される。ThinKは長文attentionにchannel間の冗長性があることを観察し、**tokenではなくKeyのfeature/channel次元**を削減する。Valueを同じ率で削減する手法ではない。

## 手法と重要度
Q∈R^{n_q×d}, K∈R^{n_k×d} とすると、QK^T=Σ_j Q_{:,j}K_{:,j}^T。channel jの寄与を
```math
s_j = \lVert Q_{:,j}K_{:,j}^{\top}\rVert_F
```
で近似し、寄与の小さいchannelをpruneする。Qはprompt末尾のobservation windowから得られるため、query-awareだが未来のユーザー質問を知るわけではない。KV cacheのすべての過去tokenを対象にする代わりに、最近のtokenをfull dimensionで保護する構成も用いる。

実装上はheadごとに選択したchannel indexを保持し、decode時のQuery側にも同じindexを適用する必要がある。これは単にK tensorをtruncateするだけではない。RoPEがある場合、位置回転とchannel選択の演算順序・対になる次元の扱いを誤るとattention scoreが一致しないため、実装を確認する必要がある。

## Experiment Setup
LLaMA、Mistral系のlong-context taskで評価。SnapKVなどのtoken evictionおよびKIVIのquantizationと併用し、LongBench品質、peak memory、batch capacityを比較する。保存cacheの圧縮率と実際のGPU peak memoryは異なる指標として報告する。

## Main Results
ICLR 2025論文はvanilla KV eviction/quantizationに対して**20%超のKV memory節約**を報告。KIVI併用では**2.8× peak memory削減**、単一GPUでbatch sizeを増やせると報告する。LLaMA-3-8B-InstructのLongBenchでは、SnapKV token budget 512の平均40.10に対し、ThinK併用で40.55という設定が示されている。改善幅はtaskとcompression ratioに依存する。

## Ablation / 分析
- Observation window: 小さすぎるとsaliencyの推定が不安定、大きすぎるとscore算出コストが増える。
- Channel retention: Key channelを削りすぎるとattention scoreの近似が崩れる。
- Token pruningとの併用: token軸とchannel軸は直交するため追加圧縮が可能。ただし誤差は相互作用する。
- Quantizationとの併用: KIVIと組み合わせたmemory改善は単独手法の効果と区別する。

## Limitations
Keyの40% channel pruningをKV全体の40%削減と誤解しない。K/Vが同じ容量なら単純計算では全体約20%削減であり、recent tokenやindex metadataで実効率は変わる。Observation Queryに基づくchannel selectionは将来Queryのattention分布変化に追随できない可能性がある。実際のdecode kernelが不規則channel indexを効率よく読み出せるかも重要。

## Taxonomyと関連研究
**compress → channel pruning / query-driven selection**。SnapKV・PyramidKVはtoken方向、Paluはlow-rank latent方向、ThinKは元のcoordinate軸のchannel選択。ProphetKVやA³のquery-aware処理は再利用したKVの品質修復が目的であり、ThinKのcache memory削減とは異なる。

- [PyramidKV](2024-2406.02069-pyramidkv.md): layer別token budget。
- [Ada-KV](2024-2407.11550-adakv.md): head別token budget。
- [Palu](2024-2407.21118-palu.md): low-rank hidden dimension compression。
- [MiniCache](2024-2405.14366-minicache.md): layer間KV統合。
- [ProphetKV](../reuse/2026-2602.02579-prophetkv.md): reuse時の選択的再計算。
