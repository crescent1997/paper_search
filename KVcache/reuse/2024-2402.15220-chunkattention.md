# ChunkAttention: Efficient Self-Attention with Prefix-Aware KV Cache and Two-Phase Partition

> **核心：同じprefixのKVを一度だけ保存するだけでなく、複数requestのqueryを束ねてその共有KVにattentionする。** PagedAttentionのblock-level memory sharingから一歩進み、prefix treeに基づくruntime discoveryとshared-KV向けdecode kernelを一体化した研究。

## 概要・問題設定

LLM serviceでは、多数のrequestが同一の長いsystem promptやfew-shot examplesを先頭に持つ。通常のKV cacheを系列ごとに保持すると、同じcausal historyから計算したKVが複製され、HBM容量とdecode時のKV readが無駄になる。

PagedAttentionはblockの物理共有を可能にするが、**元の2023年版vLLMにおいて任意の共通prefixをruntimeで自動検出し、共有chunkへのattentionをquery横断で集約する機能まで実現したわけではない**。ChunkAttentionは次の2つを同時に解く。

1. Prefix-Aware KV Cache (PAKV)：完全一致する先頭token列のKVをprefix tree上の同じchunkに保持する。
2. Two-Phase Partition (TPP)：共有chunkは複数queryをまとめて処理し、非共有suffixは系列ごとに処理する。online softmaxで両者をexactに結合する。

**Prefix sharingとsemantic sharingは異なる**。ChunkAttentionが共有できるのは同一token prefixに由来するKVであり、同じ意味でもtoken列・位置・前文脈が違えばそのまま再利用しない。

## 手法

### 1. Prefix-Aware KV Cache (PAKV)

従来のdense KV tensorをsequence方向にchunk化し、共通prefixを共有する**prefix tree**へ格納する。各nodeはtoken segmentと対応するK/V sliceを持つ。root側のchunkは多数のrequestが共有し、分岐後のleaf側はrequest固有になる。

```text
                     [system prompt chunk C0]
                                |
                   [shared prefix chunk C1]
                       /                 \
                [suffix A]           [suffix B]
                    |                    |
                 query A              query B
```

prefix treeへの挿入・削除・appendにより動的なrequestの出入りを扱い、未使用chunkはpoolへ戻す。chunkの所属系列が連続したindex区間になるように管理することで、shared chunkに対応する複数queryのsliceを取りやすくする。

**Prefill**では一致prefixをlookupしてKV projectionとposition embeddingの重複計算を回避するが、論文§3.2はmismatched suffixを追加した後、既存のFlashAttention等でattentionを実行する設計を記す。したがってprefill全体が常にskipされると解釈してはいけない。中心となるkernel最適化はdecode側。

### 2. Two-Phase Partition (TPP)

Decode iterationでbatch内のqueryを$Q\in\mathbb{R}^{b\times d}$とする。単純なpaged decodeでは各queryが自分のprefix KVを独立に読むため、共有物理blockでもreadや計算を繰り返す。

**Chunk-first phase**：複数requestに共有されるchunk $C$について、そのchunkを参照するquery行$Q_{i:j}$をまとめ、$Q_{i:j}K_C^\top$を行列積で計算する。queryの数を増やすことで、shared KVを一度読み込んで複数queryに使い回し、tensor coreも活用できる。

**Sequence-first phase**：各request固有のsuffix chunkに対しては、queryを個別に処理する。前段で得た共有chunkのpartial attentionと、固有chunkのpartial attentionをsoftmaxの正規化情報を保持したまま結合する。

部分計算を単純に足すとsoftmaxの分母が一致しない。各chunkで

$$m_C=\max_j(qk_j),\quad n_C=\sum_j\exp(qk_j-m_C),\quad o_C=\sum_j\exp(qk_j-m_C)v_j$$

を保持する。2つの部分$(m_a,n_a,o_a)$、$(m_b,n_b,o_b)$のmergeは、$m=\max(m_a,m_b)$として

$$n=e^{m_a-m}n_a+e^{m_b-m}n_b,\quad o=e^{m_a-m}o_a+e^{m_b-m}o_b$$

とすればよい。最終attention outputは$o/n$。これは**近似・token pruningではなく、同じKV集合へのexact attentionを分割実行する**方法である（スケーリング係数は上式では簡略化）。

### 3. Runtime overheadの削減

prefix treeはCPU側で管理するため、GPUへchunk pointerと担当query範囲などのmetadataを渡す必要がある。論文は（a）GPU計算とのoverlap、（b）treeが変わったときだけcontextを転送する**lazy copy**でこれを軽減する。chunk-first結果の一時bufferも必要であり、共有chunk同士の結果を直接更新する方式はGPU atomic / serializationが重いため採用していない。

## Experiment Setup

- **Hardware**：NVIDIA A100 80GB、CUDA 11.8。microkernelはFP16、32 heads、head dim 128、chunk size 64を基本とする。
- **Kernel baselines**：Naive PyTorch、xFormers、FlashAttention、vLLM PagedAttention。さらに**PagedAttn\***（共有prefixが同一物理pageを指すよう手動設定）を設け、単なるmemory sharingとTPPの追加効果を切り分ける。
- **End-to-end**：Llama2 7BベースのChunkLlama、vLLM 0.2.7、TGI 1.3.4。Poisson到着request、最大batch 32、shared system prompt長を変更。
- **Metrics**：decode kernel latency / token rate、normalized end-to-end latency (ms/token)、peak KV memory、peak batch size。共有prefixが存在する条件を明示して評価。

## Main Results

| 評価 | 結果 | 読み方 |
|---|---|---|
| Kernel / shared prefix 1K–4K | PagedAttention比**3.2–4.8× token rate** | 共有prefixが十分長い条件でのdecode性能。end-to-end倍率ではない |
| TPP固有の利益 | PagedAttn\*比**2.8–3.2×**（shared 1K–4K、Table 3） | 物理memory共有だけでなく、queryを束ねる計算設計が効く |
| Kernel / prefixなし | 例：context 4096、shared 0でPagedAttn 1400.61 µs、ChunkAttn 1301.78 µs | 共有がない場合でも大きな回帰はないが、改善幅は小さい |
| End-to-end throughput | shared prefix 1024で**1.6×**、2048で**2.3×**（対vLLM） | normalized latency 40ms/token未満を維持する比較 |
| Peak KV memory | 長い共有prefixで**70–90%節約** | 共有prefix率が高い合成workloadの値 |
| Table 4具体例 | prompt/shared 4096/4096でKV **35.42 → 4.00 GB**、latency **27.62 → 17.16 ms/token** | kernel高速化とKV重複削減の両方を反映 |

論文の主張する3.2–4.8×は**attention kernelの高速化**、1.6–2.3×は**serving throughput**であり、混同しない。KVを間引かないので、attentionの意味的近似によるaccuracy低下は設計上生じない。

## 主要Ablation・性能要因

### Physical sharing vs TPP（Table 3）

PagedAttnとPagedAttn\*の差が「同一物理KVを読むcache localityの効果」、PagedAttn\*とChunkAttnの差が「shared chunkをまとめて計算するTPPの効果」に相当する。例：context=4096、shared=4096、batch=32でPagedAttn **1399.51 µs**、PagedAttn\* **663.84 µs**、ChunkAttn **206.22 µs**。shared KVを単に同一アドレスにするだけでは最適化が不十分であることを示す。

### Shared prefixとgenerated suffixの比率（Fig. 3）

生成が長くなるほどrequest固有suffixが伸び、共有できるKVの割合が低下する。shared=2048では、生成512 token時のPagedAttn比**3.6×**が生成2048 token時には**2.3×**へ低下。system prompt中心の短～中程度の出力に適した特性を持つ。

### Batch size（Fig. 4）

shared=2048条件でChunkAttentionのtoken rateはbatch 16→96で約155K→224K tokens/sへ増える。他方式はmemory bandwidth律速でbatch 16付近で飽和しやすい。shared prefixへの複数queryをGEMM化するため、batch増加が演算効率へ結びつく。

### Metadata overhead（§3.3）

CPU prefix treeからGPUへ渡すmetadataは毎iteration更新する必要がなく、chunkが満杯になる・requestが入る・終了する時だけ転送する。実装コストはあるが、end-to-end評価ではこの管理コストを含めている。

## Limitations

1. **共通promptが先頭に必要**：論文§7の明示的制約。同じdocumentが中間位置にあっても、causal historyが異なれば共有できない。
2. **共有prefixが少ないworkloadでは利益が小さい**：prefix長・batch size・生成suffix長に依存し、system promptの重複が少ないmulti-tenant trafficには効きにくい。
3. **CUDA kernelへの依存**：TPPは専用kernel実装であり、head dimension、GPU世代、model構成ごとの調整・検証が必要。
4. **Semantic reuse / repairではない**：token列が類似していても一致しなければreuseせず、differential editingやselective recomputationは扱わない。
5. **実験は2024年世代のserving stack**：vLLM 0.2.7等をbaselineとしており、現行vLLM v1・radix scheduling・FlashInferの最適化済み実装へ倍率をそのまま適用できない。
6. **Prefillのend-to-end省略は限定的**：prefix lookupの利益とdecode attentionの利益を区別する必要がある。

## Taxonomy・技術的系譜

| 軸 | ChunkAttention |
|---|---|
| Category | `reuse`（exact prefix sharing + shared-KV-aware decode） |
| Reuse単位 | 複数requestに共通する**先頭token列のchunk** |
| Relevance signal | Token prefixの**完全一致**。semantic similarity / query attentionは使わない |
| Repair / fusion | **不要**。同じcausal prefixに対するKVなのでexact reuse |
| Model modification / fine-tuning | Model weightの変更・学習は不要。専用kernel / runtimeは必要 |
| Full-prefill approximation vs task utility | 近似ではなく**exact attention / exact KV sharing** |
| Selection granularity | Prefix tree node / fixed-size chunk（評価では64 token） |
| Runtime overhead | Tree操作、metadata同期、一時partial output。lazy transfer等で抑制 |
| Primary benefit | HBMのKV重複削減 + decode時のshared-KV readのamortization |

**系譜**：PagedAttentionは「KVをblock単位で非連続配置・共有できる」ことを示した。ChunkAttentionは「どのprefixが共有されるかを自動検出し、その共有をGPU attention計算でも活かす」方向へ発展する。さらに[Preble](2024-2407.00023-preble.md)はcache hitとGPU負荷分散、[Mooncake](2024-2407.00079-mooncake.md)は分散tier上のKV配置を扱う。

一方、[CacheBlend](2024-2405.16444-cacheblend.md)・[Block-Attention](2024-2409.15355-block-attention.md)・[KVShare](2025-2503.16525-kvshare.md)・[A³](2025-2511.17560-a3.md)は、**完全一致prefixに限定されない文書・semantic spanの再利用**に踏み込む。その際にはcontext mismatchを扱うrepair / fusionが必要になり得る。ChunkAttentionはその問題を解くのではなく、exact prefixがある場合の実行効率を高める。

## 関連研究との差分

- **PagedAttention / vLLM (SOSP 2023)**：block table・CoWでKV共有を可能にするが、論文時点のvLLM 0.2.7はruntime prefix discoveryとTPPを持たない。ChunkAttentionは共有prefixの自動検出と**GEMV→GEMM化**を追加する。
- **[Prompt Cache](2023-2311.04934-prompt-cache.md)**：事前登録したprompt moduleを組み合わせる再利用。ChunkAttentionはrunning request群のprefix treeを動的に管理する。
- **[Preble](2024-2407.00023-preble.md)**：複数GPU間のrequest routingとprefix localityのtrade-off。ChunkAttentionは単一GPU上のshared prefix attention kernelに焦点。
- **[CacheBlend](2024-2405.16444-cacheblend.md)**：任意のdocument KVを結合し、context-dependent stateをselective recomputationで修復。ChunkAttentionは完全一致prefixのみなので修復不要。
- **[KVShare](2025-2503.16525-kvshare.md)**：semantic-aware matching / differential editingによりcache hit対象を広げる。ChunkAttentionのmatchingはtoken-exact。

## まとめ

ChunkAttentionの本質は**「同じKVを共有しているなら、attention計算も複数requestで共有しよう」**という設計。prefix treeが同一KVの所在を提供し、TPPがshared chunkへのqueryをbatch化する。単なるcache hit率改善ではなく、decode kernelのmemory trafficと演算形態まで再設計した点が重要である。
