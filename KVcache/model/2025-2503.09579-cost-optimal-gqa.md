# Cost-Optimal Grouped-Query Attention for Long-Context Modeling

## 概要

GQAのhead数は通常、hidden sizeや既存modelの慣習に合わせて設定される。しかし推論contextが長くなるほど、**attention計算とKV cache memory**の負担は増え、FFN等のmodel parameterに関する固定costとの比率が変化する。

本論文は「一定のlanguage modeling lossを満たし、想定context長$T$での推論costを最小化するには、model sizeとGQA head構成をどう選ぶべきか」を定式化する。重要な結果は、**長contextでは、query/KV headsを減らしてmodel本体を大きくした方が、同等の品質で低memory・低FLOPsとなり得る**というもの。

これはruntime KV compressionではなく、**architecture設計時に生成KV数とattention FLOPsを構造的に減らす**`model`カテゴリ。

## 問題設定

layer数$L$、head dimension$d_h$、query head数$n_h$、KV head数$n_{kv}$、model parameter数$N$、decode時context長$T$とすると、著者らは1 tokenあたりの推論costを次のように近似する。

$$
C_{\mathrm{infer}}(T)\approx 2N+4TLd_hn_h
$$

$$
M_{\mathrm{infer}}(T)\approx N+2TLd_hn_{kv}
$$

$2N$はmodel weights由来の概算FLOPs、$4TLd_hn_h$はattention scoreとvalue aggregation。$N$はparameter storageの概算、$2TLd_hn_{kv}$はKV cache要素数。**FLOPsはquery heads、cache memoryはKV heads**で主に制御される。

実装上のdtype・batch・parallelism・kernel efficiencyは上式に含まれないため、これをそのままwall-clock latencyと解釈しない。

## 既存GQA設計の問題

一般的なGQAでは$n_h d_h=d$（hidden size）と固定される。この制約があるとquery head数を変えるためにhidden sizeやhead dimensionも変更する必要があり、**attention FLOPsとFFN/model capacityを独立に配分できない**。また、8K向けに妥当なGQA head数が128Kでも最適とは限らない。

## 手法

### 1. Attention head総次元をhidden sizeからdecouple

$n_h d_h=d$の拘束を外し、query head数$n_h$とKV head数$n_{kv}$をmodel size $N$から独立した設計変数とする。これにより長contextでのattention costを抑え、その分のparameter budgetをFFN等へ配分できる。

### 2. Loss制約下のhardware-aware cost

目標loss $\mathcal L^*$ と想定context $T$に対して、

$$
\min_{N,n_h,n_{kv}}Z(T,N,n_h,n_{kv}),\quad
\mathcal L(T,N,n_h,n_{kv})\le\mathcal L^*
$$

$$
Z=\lambda M_{\mathrm{infer}}^{\alpha}+(1-\lambda)C_{\mathrm{infer}}^{\beta}
$$

を最小化する。代表設定は$\lambda=0.9,\alpha=1/2,\beta=1/3$。このcost関数はhardwareへの近似であり、あらゆるGPUで普遍的な最適性を保証しない。

### 3. 三段階探索

1. **Candidate selection:** $(n_h,n_{kv})$を2のべき乗中心に列挙し、$n_{kv}\le n_h$を満たす21構成を候補とする。
2. **Scaling-curve fitting:** 各head構成で小規模modelを複数学習し、$\mathcal L(N;H)=(a/N)^b+E$をfitする。主に8K contextで学習し、128Kへ外挿する。
3. **Cost minimization:** 各構成で目標lossに必要な最小$N$を求め、想定$T$での$Z$が最小となる構成を選ぶ。

lossとmodel sizeのfitは$R^2>0.999$と報告。ただしlossがcontext長に対して完全不変なのではなく、**長context域で構成間の相対loss差が概ね安定**という経験的観察を利用している。

## Experiment Setup

- **Architecture:** Llama-3系GQA Transformer、head dimension 64、model規模3M〜1.2B。実際の最適構成検証では最大1.8B。
- **Data:** SlimPajama、training token/parameter比20:1を基本とする。
- **Configurations:** $(n_h,n_{kv})$の21候補、expected context 8K/16K/32K/64K/128K。
- **Metrics:** LM loss、推定per-token FLOPs、weights+KV memory、実測training/inference throughput、common-sense QA、NIAH。
- **Main comparison:** Llama-3-style $(32,8)$ vs cost-optimal $(8,1)$。downstreamは128K contextへcontinued trainingしたmodelで比較。

## Main Results

### 128Kで同loss・低cost

Llama-3 GQAの代表$(n_h,n_{kv})=(32,8)$、1.2B model、LM loss 2.615に対し、$(8,1)$へ変更してmodelを1.8Bへ増やすと、**同lossで推定memory 50.8%減、FLOPs 57.8%減**と報告する。これは公開Llama-3.2-1B checkpointとの直接再学習比較ではなく、**Llama-3-style head configurationを使った独自学習model**での比較。

### 実測throughputと品質（Table 5）

| Metric | $(32,8)$ 1.2B | $(8,1)$ 1.8B |
|---|---:|---:|
| Training throughput (tok/s) | 18,655 | **31,260** |
| Inference throughput (tok/s) | 12,921 | **20,643** |
| Common-sense average | **45.7%** | 45.5% |
| NIAH 1–8K | 90.9% | **96.9%** |
| NIAH 16K | 30.4% | **46.0%** |
| NIAH 32K | 15.1% | **18.7%** |
| NIAH 128K | 5.2% | **6.7%** |

実測throughputはA800 1枚、batch=1、128K contextで測定。**NIAH 128Kは両者とも低い**ため、cacheが少ないだけで長文retrieval能力が十分とは言えない。

## Ablation・分析

### Context lengthに応じたhead構成

Table 4では、同じ目標lossでも8Kから128Kへ長くなるほど最適head数が減る。例えばloss 2.7なら$(32,4)$（8K）から$(8,1)$（128K）へ変化。これはattention costが$T$と共に増えるため。

### Query headsとKV headsの非対称性

同じhead数の増加でも、**query headsを増やす方がKV headsを増やすよりloss改善が大きい**という観察。KV headを増やすとcache memoryが増える一方、query headを増やすとattention FLOPsが増える。単純に両者を同比率で減らすのが最適ではない。

### Training FLOPs aligned

token/parameter比20:1の比較に加え、total training FLOPsを揃えてcompute-efficient構成へより多くのdataを与える実験では、同lossでmemory 88%減、FLOPs 83%減という結果。ただし著者らは**128Kで常時trainingする仮定が現実的なpretraining recipeと異なる**と注意している。

### Scaling extrapolation

8K以降のrelative loss差が1%未満で安定する観察を使い、8Kでfitした曲線を長context設計へ外挿する。より大規模なmodel、異なるtraining corpus、RoPE extrapolation設定での妥当性は未確定。


## 数式から見る設計判断

長contextに対してKV head数を削る効果は、$2TLd_hn_{kv}$に比例して増大する。短contextではmodel weightの$N$が支配的なので、$N$を大きくしてhead数を減らす選択が必ずしも得にならない。反対に128KではKV cacheが大きくなり、$n_{kv}$を8→1へ減らすことで**contextに比例する項を1/8にする**。同時にquery head数を32→8へ減らすことで、attention計算のcontext比例項を1/4にできる。

ただし最適構成は単純にhead数最小ではない。headを減らすとlossが悪化するため、target lossを満たすようmodel parameter数$N$を増やす必要がある。論文は各head構成でのloss–size curveをfitし、その増分を含めた総costで比較している。これが**「小さいmodelほど速い」という直感に対する反例**を生む理由である。

### 128Kを前提とした最適解を8Kで使うべきか

Table 4ではtarget loss 2.6の例で、8Kの最適解が$(32,8)$、128Kでは$(8,1)$。つまりdeploymentのtypical contextが短い場合、128K専用の極端なhead削減を選ぶと、固定cost側の増大に見合うだけのKV savingsが得られない可能性がある。実サービスではcontext length分布（p50/p95）、batch size、prompt/decode比率を考慮し、論文の単一$T$の最適化をworkload平均へ拡張する余地がある。

### 何を比較したか

著者らの比較は「同じpretrained checkpointを変換した後のaccuracy」ではなく、**異なるarchitectureを学習してlossを揃えた場合のresource allocation**。そのため[MLKV](2024-2406.09297-mlkv.md)のようなuptrainingベースの研究や[KVSharer](2024-2410.18517-kvsharer.md)のようなpost-hoc sharingとは直接的に代替関係にない。実験のloss 2.615もLlama-3.2の公開checkpointのlossと同一という主張ではない。

## Limitations

1. 1.2B〜1.8B中心の実験で、7B/70B等への一般化は未検証。
2. Model sizeとhead構成を変えた**architecture search**であり、既存modelへ無学習で適用する方法ではない。
3. GPU memory bandwidth、paged KV layout、batching、tensor parallelismなどを厳密に反映したwall-clock cost modelではない。
4. Head dimension、vocab size、model aspect ratio等は十分に探索されていない。
5. NIAH 128Kの絶対accuracyが低く、long-context qualityの課題は残る。

## Taxonomy・関連研究との差分

**model / cost-aware GQA design / joint model-size and KV-head optimization / long-context scaling**。

- [GQA](2023-2305.13245-gqa.md): checkpoint uptrainingとhead sharing。こちらは**context長を含むarchitecture設計**を最適化。
- [MLKV](2024-2406.09297-mlkv.md): layer方向のsharingでKV総数を削減。Cost-Optimal GQAはhead数とmodel sizeを最適化する別軸。
- [Cross-Layer Attention](2024-2405.12981-cross-layer-attention.md): layer間KV共有であり、head構成探索と組み合わせ可能。
- [DeepSeek-V2 / MLA](2024-2405.04434-deepseek-v2-mla.md): latent cache architecture。MLAのdecode cost modelは通常GQAとは異なる。
- [MHA2MLA](2025-2502.14837-mha2mla.md): checkpoint変換。architecture探索とは対象が異なる。
- [YOCO](2024-2405.05254-yoco.md): decoder-decoder sharing。
