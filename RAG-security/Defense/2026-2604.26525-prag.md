# PRAG: End-to-End Privacy-Preserving Retrieval-Augmented Generation

> cloud-hosted RAGでserverからdocument corpusとuser queryの双方を秘匿するため、CKKS homomorphic encryption上でsemantic retrievalを実行するend-to-end privacy-preserving framework。non-interactive PRAG-Iとclient-assisted PRAG-IIを用意し、encrypted K-means + HNSW、Operation-Error Estimation (OEE)、dummy traversal / periodic rebuildによってretrieval accuracy・efficiency・access-pattern privacyを両立する。

## 概要

RAGをcloudへoutsourcingすると、private knowledge baseだけでなくuser queryもcloud providerへ露出する。通常のRAG privacy研究では、authorized userがgenerator outputからprivate corpusを抽出するconfidentiality riskを扱うことが多いが、PRAGが想定するattackerは異なる。

PRAGでは**RAG infrastructureを運用するcloud server自体をsemi-honest adversary**とみなし、serverがprotocolを正しく実行しても、保存されたdocument embeddings、query embeddings、similarity scores、retrieval pathsなどからprivate informationを推定できないようにする。

中心的な課題は、単純にembeddingsを暗号化するだけではRAGに必要なTop-k semantic searchを効率的に行えないことである。特にANN searchではcomparison、ranking、graph traversalが必要だが、CKKSのようなapproximate HEは加算・乗算には向く一方、比較演算を直接扱いにくい。

PRAGはこの問題に対して、

1. encrypted K-means + encrypted HNSWによるhierarchical ANN index
2. fully homomorphicなnon-interactive PRAG-I
3. clientがcomparisonを補助するinteractive PRAG-II
4. CKKS / polynomial approximation errorによるranking inversionを制御するOEE
5. HNSW traversalから生じるaccess-pattern leakageへのdummy traversal + periodic rebuild

を組み合わせる。

## 問題設定 / Threat Model

### Parties

主に二者を想定する。

- **Client / Data Owner**: private documentsとqueryを保持し、secret keyを管理するtrusted party。
- **Cloud Server**: encrypted indexとciphertextsを保存し、retrieval computationを実行する。

serverはsemi-honest / honest-but-curiousであり、protocolには従うが、観測できる情報からdocumentsやqueriesを推測しようとする。

### Serverが観測できる情報

serverは、

- encrypted document embeddings
- encrypted query embeddings
- encrypted similarity / distance values
- public HE parameters
- encrypted index structureに対するoperation
- HNSW traversal / access patterns
- communication timing / request sequence

等を観測し得る。

secret keyは持たず、clientとのcollusionは想定しない。

### Security Goal

主な目標は、

- document confidentiality
- query confidentiality
- intermediate score confidentiality
- retrieval access-pattern leakageの低減

である。

暗号学的なdata confidentialityはCKKSのIND-CPA securityを基礎とし、access patternについては別途obfuscation mechanismを導入する。

## 先行研究からの改善点

### Differential Privacy系との違い

[Privacy-Preserving Retrieval-Augmented Generation with Differential Privacy](2024-2412.04697-privacy-preserving-rag-differential-privacy.md) はdocument-level DPによって、RAG outputから個別documentのmembershipを推定しにくくする。

[DP-SynRAG](2025-2510.06719-dp-synrag.md) はprivate corpusをDP synthetic corpusへ変換する。

これらはauthorized RAG userに対する**output-side / statistical privacy**を主に扱う。一方PRAGは、cloud serverがoriginal corpus/queryを見ること自体を防ぐ**infrastructure-side cryptographic confidentiality**を対象とする。

### Piscesとの関係

[Pisces](2026-pisces-private-rag.md) もserver-side knowledgeとqueryを暗号学的に保護するprivate RAGであり、PRAGと最も近いrepo内Defenseである。

PiscesはMPC / PIR / PSI等を組み合わせてsemantic retrievalとlexical retrievalのdual pathをprivateに実行する。

PRAGはCKKS homomorphic encryptionを中心に、**K-means + HNSWというANN index自体をencrypted domainで利用する**ことでlarge-scale semantic retrievalを高速化する点が特徴である。

### Secure Similarity SearchからRAGへ

既存secure kNN / similarity retrievalはencrypted vectorsのnearest-neighbor searchを可能にするが、RAG deploymentで必要な、

- scalable ANN
- ranking fidelity
- dynamic update
- low online latency
- access-pattern protection

を同時に満たさない場合が多い。

PRAGは単なるsecure similarity primitiveではなく、RAG retrieval pipelineとしてend-to-end designを行う。

## Architecture

PRAGは二段階indexを用いる。

```text
Encrypted document embeddings
        ↓
Encrypted K-means clustering
        ↓
Cluster 1 ─ encrypted HNSW
Cluster 2 ─ encrypted HNSW
   ...
Cluster C ─ encrypted HNSW
```

query時にはまずcandidate clustersを絞り、その内部HNSWだけを探索する。これにより全encrypted documentsとのlinear comparisonを避ける。

## Encrypted K-means

large corpusを複数clustersへ分割し、queryが探索すべきsearch spaceを縮小する。

plaintext K-meansではdistance比較からnearest centroidを決めるが、encrypted settingではcomparisonが難しい。

PRAG-Iではhomomorphic-friendly polynomial approximationを使ってsoft assignment / selectionを近似し、centroid updateまでciphertext domainで行う。

PRAG-IIでは必要なcomparisonをclientへ委譲できるため、より正確なcluster assignmentを得られる。

cluster-level routingによって、後段の高価なencrypted HNSW searchを少数clustersへ限定する。

## Encrypted HNSW

各cluster内ではHierarchical Navigable Small World (HNSW) graphを構築する。

通常のHNSWはcurrent nodeとneighborsのdistanceを比較し、queryに近いnodeへgreedy traversalする。

PRAGではnode embeddingsとquery embeddingsが暗号化されているため、serverはCKKS上でinner product / distanceを計算する。

問題は、

```text
which encrypted score is smaller / larger?
```

というcomparisonである。

ここでPRAG-IとPRAG-IIが分岐する。

## PRAG-I: Non-Interactive Retrieval

PRAG-Iはonline client interactionを必要としない。

serverはChebyshev polynomial等のhomomorphic-friendly approximationを利用してcomparison / rankingを近似する。

conceptually、step function / sign functionをpolynomial $P(x)$ で近似し、二つのencrypted scores $s_i,s_j$ に対して、

$$
P(s_i-s_j)
$$

を評価することでどちらが優位かをsoftに判定する。

### 利点

- query送信後のclient-server round tripが少ない。
- communication costが小さい。
- cloud-side retrievalを自律的に完結できる。

### 欠点

- polynomial approximation error
- CKKS numerical noise

によって、scoreが近いcandidatesのrankingが逆転する可能性がある。

この問題をOEEで扱う。

## PRAG-II: Client-Assisted Retrieval

PRAG-IIではencrypted distance / candidate scoresをserverからclientへ送り、secret keyを持つclientがdecryptしてexact comparisonを行う。

clientは、例えば次に探索すべきcluster / HNSW nodeのindexだけをserverへ返す。

serverはplaintext query/document embeddingsを見ることなく、clientのdecisionを使ってgraph traversalを続ける。

### 利点

comparison approximationが不要になり、plaintext HNSWに近いranking fidelityを得られる。

### 欠点

- client-server interactionが増える。
- latencyがnetwork round tripsに依存する。
- communication volumeが大きくなる。

したがってPRAG-Iはlatency / bandwidth重視、PRAG-IIはretrieval fidelity重視というtrade-offになる。

## Operation-Error Estimation (OEE)

CKKSはapproximate arithmeticなので、encrypted similarity scoreはtrue plaintext scoreと完全には一致しない。

さらにPRAG-Iではcomparison polynomial approximation errorも加わる。

PRAGはretrieval errorを単なるabsolute numerical errorではなく、**Top-k orderingを壊すかどうか**という観点から分析する。

概念的にはobserved encrypted-domain scoreを、

$$
\tilde{s}_i = s_i + e_{HE,i} + e_{poly,i} + e_{path,i}
$$

のように、

- true similarity $s_i$
- HE approximation/noise
- polynomial approximation error
- graph traversalに伴うerror

へ分解する。

二candidate間のtrue score margin

$$
\Delta_{ij}=|s_i-s_j|
$$

がtotal error boundより十分大きければorderingは維持される。

逆にmarginが非常に小さい場合はrankingがambiguousになるが、semantic retrieval上も両documentsが近いためutility impactが限定的である可能性が高い。

OEEによってparameter selectionとranking stabilityを結び付けるのが本論文の重要なsystem contributionである。

## Query Processing

clientはuser queryをembeddingへ変換し、CKKSでencryptする。

さらにcomplex queryを複数subqueriesへdecomposeし、それぞれをencrypted retrievalへ投入する構成も用いる。

serverはcandidate clustersを選び、各cluster内のencrypted HNSWを探索する。

retrieved encrypted candidatesはclient側へ返され、clientがdecryptして後段のRAG generationへ利用する。

したがってcloud serverはsemantic searchを実行するが、query/document plaintextを直接得ない。

## Dynamic Updates

実運用RAGではcorpusが固定ではないため、PRAGはencrypted indexへのinsert / updateも扱う。

新document embeddingをencryptし、cluster assignmentとHNSW link updateをsecurely実行する。

実験ではmillisecond-orderのupdate latencyを報告しており、static secure searchだけでなくdynamic RAG knowledge baseを意識している。

## Access-Pattern Leakage

HEでvectorsを暗号化しても、serverが「どのHNSW nodesへアクセスしたか」を観測できる場合、繰り返しqueryからgraph topologyを推定できる。

この点はPRAGの重要なsecurity analysisである。

### Graph Reconstruction Attack

adversaryは複数queryにおけるnode co-access / traversal transitionsを集計し、encrypted HNSWのedge relationを推定する。

plaintext embeddingsを直接読めなくても、graph structureが復元されればsemantic neighborhoodに関するside informationを得る可能性がある。

### Dummy Traversal

real HNSW traversalにrandom dummy walksを混ぜる。

real pathに対するdummy ratioを $\rho$ とすると、serverから見たaccess sequenceには偽edgesが多数混入する。

### Path Padding

queryごとのreal path lengthからinformationが漏れないよう、traversal lengthをpaddingする。

### Periodic Rebuild

一定epochごとに、

- ciphertext re-encryption
- re-clustering
- HNSW reconstruction

を行い、長期間のaccess observationsを同一graphへaggregateできないようにする。

論文はgraph reconstruction advantageをquery budget $Q_E$、dummy ratio、dataset size等との関係でboundし、概ね

$$
O\left(\frac{Q_E}{(1+\rho)|D|}\right)
$$

の形でattack advantageが抑えられることを議論する。

## Experiment Setup

### Dataset

主評価では **TriviaQA 100,000 samples** を利用する。

### Cryptographic Setting

- CKKS homomorphic encryption
- 128-bit security
- Microsoft SEAL 4.1ベース
- pure C++ implementation

### Retrieval / Generation

- OpenAIEmbeddings
- encrypted K-means + HNSW
- Top-10 retrieval
- Qwen3 response generator

### Hardware

Ubuntu 24.04環境で、代表的には、

- 8 Intel Xeon Gold vCPUs
- 200 GB RAM

を用いる。

### Baselines

secure similarity / kNN schemesとして、

- SESR
- FSkNN
- MSecKNN
- PDQ

等と比較する。

### Metrics

- Recall@10
- retrieval latency
- update latency
- communication cost
- graph edge recovery rate
- adversarial false-positive rate

を測定する。

## Main Results: Retrieval Performance

### Recall

Top-10 retrieval recallは、

- PRAG-I: **72.45%**
- PRAG-II: **74.45%**

となる。

PRAG-IIはexact client-assisted comparisonによりPRAG-Iより高いretrieval fidelityを得る。

### Retrieval Latency

代表結果では、

- PRAG-I: **1.29 s**
- PRAG-II: **7.91 s**
- SESR: **166.11 s**
- FSkNN: **1978 s**
- MSecKNN: **2137.65 s**
- PDQ: **4107.111 s**

と報告される。

PRAG-Iはhierarchical ANNとnon-interactive approximationによって、secure baselinesより大幅に低いonline latencyを実現する。

PRAG-IIはclient interactionによりPRAG-Iより遅いが、それでも比較baselineより大幅に高速である。

## Update / Communication Cost

update latencyは、

- PRAG-II: **5.44 ms**
- PRAG-I: **7.28 ms**

程度。

communication costは、

- PRAG-I: **4.12 MB**
- PRAG-II: **78.55 MB**

で、interactive comparisonを多用するPRAG-IIはcommunicationが大幅に増える。

この結果から、PRAG-I / IIの設計trade-offが明確になる。

```text
PRAG-I
  low latency / low communication
  approximate ranking

PRAG-II
  higher communication / interaction
  higher ranking fidelity
```

## Access-Pattern Defense Evaluation

無防御のencrypted HNSWに対するIHOP-style graph reconstructionでは、attackerが約 **34.7%** のedgesをrecoverする。

### Dummy Traversal

$\rho=0.3$ のdummy traversalを入れるとedge recoveryは約 **6.8%**へ低下する。

### Periodic Rebuild

epoch=1000のperiodic rebuildだけでもedge recoveryは約 **5.1%**まで低下する。

### Combined Defense

両方を組み合わせると、

- edge recovery: **1.1%**
- attacker false-positive: **83.5%**

となる。

このときRecall@10は約 **71.9%**、latency overheadは約 **1.28×**であり、access-pattern protectionによるutility / performance degradationを比較的小さく抑える。

## Security / Utility Trade-offs

### PRAG-I Polynomial Degree

comparison polynomialを高精度化するとranking errorは減るが、homomorphic multiplication depthとlatencyが増える。

OEEを使って必要なscore marginに応じたapproximation precisionを選ぶことが重要になる。

### PRAG-II Interaction

client-assisted comparisonはaccuracyを改善するが、network latencyとcommunication costが増える。

### Dummy Ratio

$\rho$を増やすほどgraph reconstructionは困難になるが、dummy traversal computationが増える。

### Rebuild Frequency

epochを短くするとlong-term access correlationを抑えられるが、index reconstruction costが増える。

## Differential Privacy DefenseとのThreat Model差

repo内のDP系Defenseとの違いは重要である。

```text
Malicious / curious RAG user
        ↓
DPVoteRAG / DPSparseVoteRAG
DP-SynRAG
  → responseからprivate document presence/contentを推定しにくくする

Semi-honest cloud infrastructure
        ↓
PRAG
  → corpus/queryをserverからcryptographically hideする
```

したがってPRAGを導入しても、authorized userがRAG APIへ大量queryしてCopyBreakRAG等を実行する問題は直接解決しない。

逆にDPVoteRAGだけでは、cloud serverがplaintext private corpusを保存しているdeploymentでserver自体を信用できない問題は解決しない。

両者は競合ではなくcomplementary defenseである。

## Knowledge-Base Extraction Attackとの関係

[Feedback-Guided Extraction / CopyBreakRAG](../Attack/2024-2411.14110-feedback-guided-extraction-copybreakrag.md)、[Silent Leaks / IKEA](../Attack/2025-2505.15420-silent-leaks-ikea.md)、[Connect the Dots / RAGCrawler](../Attack/2026-2601.15678-connect-the-dots.md) は、authorized external userがRAG generatorへqueryしてknowledge baseをreconstructする。

PRAGのencryption boundaryはcloud retrieval infrastructureとclientの間にあるため、正規RAG clientへdecryptされたretrieval resultがgeneratorに渡され、そのgenerator outputへattackerがアクセスできるなら、これらのextraction attacksは別途成立し得る。

したがってPRAGは**storage/retrieval confidentiality defense**であり、generator-side extraction defenseではない。

RAGFort / CanaryRAGのようなruntime extraction defenseと組み合わせる余地がある。

## Limitations / 成立条件

### Semi-honest Server

serverがprotocolから逸脱するmalicious adversaryは主threat modelではない。ciphertext manipulation、active fault injection等を扱うには追加mechanismが必要になる。

### Non-collusion

client / serverや複数service componentsのcollusionを想定しない。

### Single-key / Single-client Setting

基本設計は単一client trust domainを前提とする。複数organizationsが異なるkeysで同じRAG indexを共有するmulti-key settingはfuture workとなる。

### Offline Cost

encrypted K-means / HNSW constructionはplaintext indexingより大幅に重い。online retrievalは高速化されているが、large-scale encrypted index preparation costは残る。

### PRAG-II Communication

PRAG-IIは78 MB/query級のcommunicationを必要とするsettingがあり、WAN deploymentではnetwork costが大きい。

### Generator Privacyは別問題

retrieval後にclient側でplaintext contextをLLM providerへ送る場合、そのgeneration providerに対するprivacyはPRAGだけでは保証されない。end-to-end deploymentではgenerator execution boundaryも検討する必要がある。

## RAG Security Taxonomyでの位置づけ

PRAGは **Defense / confidentiality / cryptographic private retrieval / infrastructure-side privacy** に位置づけられる。

```text
RAG Confidentiality Defense

Corpus transformation / statistical privacy
  SAGE
  DP-SynRAG

Query-time output privacy
  DPVoteRAG / DPSparseVoteRAG

Cryptographic private retrieval
  Pisces
  PRAG ← 本論文

Generator-side extraction defense
  RAGFort
  CanaryRAG
  SD-RAG
```

同じ「private RAG」でも、誰から何を守るかによって必要なDefenseが大きく異なることを示す例である。

## 実装・研究上の示唆

PRAGの重要な示唆は、encrypted vector searchをRAGへ導入する際に**embedding confidentialityだけでは不十分**という点である。

ANN indexではqueryごとのgraph traversal自体がside channelになるため、

- ciphertext security
- ranking stability
- access-pattern privacy

を同時に考える必要がある。

またCKKSではabsolute numerical precisionよりTop-k ordering preservationがRAG utilityに直結する。OEEのようにerror analysisをranking marginへ変換する設計は、他のencrypted retrieval systemsにも応用可能である。

一方、RAG security全体ではPRAGとRAGFort / CanaryRAGは異なるtrust boundaryを守る。enterprise deploymentでは、

```text
cloud storage/retrieval → cryptographic protection
RAG API/generator      → extraction prevention/detection
output                 → privacy policy / DP
```

のようなlayered defenseが必要になる。
