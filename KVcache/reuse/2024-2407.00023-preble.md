# Preble — Distributed Prompt Scheduling for KV Reuse

> **要点**：prefix cacheを持つGPUへrequestを集めればprefillを省略できるが、人気prefixへの集中でqueueが長くなる。Prebleは**cache localityとload balancingを同じ目的関数で扱う**。モデルのattentionを近似せず、requestをどのGPUへ送るかを変えるsystem-level reuse手法である。

## 1. 概要・問題設定

RAG・tool calling・agent・document QAなどでは、長いsystem prompt、tool仕様、文書の冒頭が多数のrequestで共通する。論文が調べた5 workloadでは、promptはoutputの37〜2494倍の長さで、prompt tokenの85〜97%が別requestと共有可能だった。単一GPUのprefix cachingはこうした重複を削減するが、data-parallelなクラスタでround-robin routingすると、同じprefixが別GPUへ散らばり、再計算が発生する。

逆に、同じprefixのrequestを常に同じGPUへ集約すると、人気のsystem promptやtool prefixがあるGPUに過負荷を作る。**cache hit率を上げるだけでは平均遅延・p99遅延が最適にならない**。Prebleはこの相反する目的を、GPU間request routingとGPU内batch schedulingの両方で解く。

分類：**`reuse` → exact-prefix reuse / distributed cache-aware scheduling**。KV内容の近似・圧縮は行わず、token単位の再計算位置も選ばない。

## 2. 既存法とのギャップ

- **Single-GPU prefix caching**：RadixAttention型のradix treeはGPU内のKVを効率的に再利用できるが、クラスタ全体の配置は考慮しない。
- **Round-robin / least-loaded routing**：計算負荷は均される一方、長いprefixのcache localityを失い、各GPUで同じKVを生成し直す。
- **Cache-only routing**：最長一致prefixのあるGPUへ常に送ると、人気prefixでqueueingとtail latencyが悪化する。
- **GPU内のFCFS / reuse優先**：FCFSは共有可能なprefixを活用しにくく、reuse優先のみでは長く待つrequestが生じる。

したがって、どのGPUがどのprefixを保持しているかだけでなく、**cache evictionの将来コスト、GPU負荷、prefill/decodeの計算特性、fairness**を組み合わせる必要がある。

## 3. 手法

### 3.1 Two-level scheduler

Prebleは二層構成で、**global scheduler**がrequestをGPU/model instanceへ割り当て、**local scheduler**がiterationごとのbatch形成・KV evictionを行う。Global側は全GPUのprefix cache情報とloadを把握し、各GPUのlocal側は待機request queueとradix treeを持つ。

Global radix treeのnodeには、prefix token長、当該KVを保持するGPU集合、履歴windowでそのnodeを使ったrequest数を保持する。新規requestのtoken列をprefix treeと照合し、共通prefix長を得る。nodeの一部しか一致しない場合はradix nodeをsplitする。保持GPUがなく、最近のrequestもないnodeは削除する。

### 3.2 E2：Exploitation + Exploration

Request $R$のprompt長を$n$、cache済みprefix長を$c$、未cache長を$m=n-c$とする。E2の大きな分岐は次のとおり。

$$\mathrm{route}(R)=\begin{cases}
\mathrm{Exploit}, & c>m\\
\mathrm{Explore}, & c\le m
\end{cases}$$

**Exploit**では、prefix再計算を省く利益が大きいため、最長一致prefixを保持するGPU集合から、推定loadが小さいGPUを選ぶ。**Explore**では、今後のrequestが利用できる新しいprefixを別GPUに配置する余地を作り、次節のcostが最小のGPUを選ぶ。この分岐は簡潔なheuristicであり、cache hit長と未cache長の比を厳密なTTFT最適解とみなすわけではない。

### 3.3 Prompt-aware load cost

GPU $i$への割当コストを概念的に次の3項へ分解する。

$$C_i=L_i+M_i+P_i$$

- **$L_i$：最近の計算負荷**。履歴window（default 3分）内でのprefillとdecodeの推定GPU時間。cached prefixは再計算不要として差し引く。
- **$M_i$：cache evictionの将来損失**。新requestのKVのために追い出すnode集合$E$に対し、各nodeの再計算時間$PT_j$と履歴hit率$N_j$を用いて$M_i=\sum_{j\in E}PT_jN_j$と見積もる。
- **$P_i$：新requestの未cache部分のprefill費用**。request自身のdecodeは候補GPU間で共通と近似し、比較時には除く。

GPU計算時間はtoken数を説明変数とするoffline profiling/regressionで推定する。実際の計算時間を全requestごとに測定せず、schedulerの管理負荷を小さくする。

### 3.4 Hot-prefixの動的replicationとprefill/decode balancing

一度prefixを割り当てても、後から人気が変わり得る。GPU間のload差が閾値を超えると、以降のrequestを軽いGPUへre-routeする。特定prefixへのqueueingが大きくなればprefix subtreeを複数GPUへ**replicate**し、人気のあるprefixを一箇所に固定しない。

さらに、長いuncached promptはprefill-heavy、ほぼ全体がcache hitするrequestはdecode-heavyとみなせる。Explore時にdecode負荷が高いGPUへprefill-heavyなrequestを組み合わせるなど、phaseの性質を考慮したload balancingを行う。これはprefill/decodeノードを完全に分離するMooncakeとは異なる発想である。

### 3.5 Local scheduling：cache hit率とfairness

Local schedulerは各requestのcache hit率に基づき複数のpriority groupへ振り分ける。hit率が高いrequestを優先しつつ、各groupから比例的にbatchへ採用することでstarvationを緩和する。KV容量不足時にはlocal radix treeのLRU nodeをevictし、global側へ非同期に通知する。長いuncached promptにはchunked prefillも使用する。

モデルの重みやattention構造を変更しない。既存serving engine（論文ではvLLMとSGLang）へのrouting/scheduling layerとして実装できるが、global/local metadataとqueue制御は必要となる。

## 4. Experiment Setup

- **ワークロード**：ToolBench/tool use、embodied agent、programming、video QA、LooGLE/long-document QAの5種。加えてAzure LLM request arrival traceで非Poissonの到着を再現。
- **モデル**：Mistral 7B、Llama-3 70B。
- **GPU**：2〜4×NVIDIA A6000、8×H100（70Bはtensor parallelismを併用）。
- **比較対象**：data-parallelなSGLang/vLLMをround-robin load balancerで構成し、各instanceのprefix cacheは有効化。比較は**クラスタレベルのrouting**を中心とする。
- **指標**：average end-to-end request latency（scheduling、queue、prefill、decodeを含む）、p99 latency、request/s。本文の主指標はTTFT/TPOTではなくrequest latencyである。
- **到着分布**：基本はPoisson、mixed workloadではAzure trace。cache共有の分布と人気の偏り（Zipf）も変える。

## 5. Main Results

**End-to-end**：SGLang round-robin baselineに対し、5 workload・GPU構成を通して平均request latencyが**1.5〜14.5倍改善**、p99 latencyが**2〜10倍改善**。この最大値は特定workload/負荷での比較であり、どのrequestでも14.5倍速いことを意味しない。

**Workload依存**：tool use、embodied agent、video QA、LooGLEではprefillが支配的で利益が大きい。Programmingは生成tokenが比較的長く、decodeが占める割合が高いため平均改善は**1.56〜1.8倍**程度、p99は**3〜4倍**の条件がある。Preble自体はdecode kernelを高速化しない。

**Azure trace mixed workload**：4×A6000でtool useとvideo QAを混ぜた場合、SGLang比で平均latency **6.02倍**、p99 **4.61倍**、平均TTFT **2.42倍**、平均TPOT **5.60倍**の改善（Fig.4）。この条件ではTPOTも改善するが、主にGPU混雑・queueingの変化でありattention演算自体の改善ではない。

**Global schedulerのscale**：論文はprefix treeとGPU負荷の管理をasync handler/lock-free read主体で実装し、数百GPUまでのrequest dispatch rateを検証する。各GPUのKVそのものをglobal schedulerへ集約する方式ではない。

## 6. Ablation・分析

論文Fig.5ではToolBench（Zipf 1.1のprefix人気）を使い、以下を順に追加して平均/p99 latencyを比較する。

1. **E2 routing**：round-robinからcache-awareなExploitation/Explorationへ変更するだけでも平均とp99が改善。
2. **Post-assignment rebalancing / prefix replication**：時間変動によるホットスポットを緩和し、とくにp99へ寄与。
3. **Prefill/decode-aware routing**：GPUのphase混合を改善し、平均とp99を追加改善。
4. **Priority-based local queue**：平均よりも**p99とfairness**を改善するのが主目的。

各componentの効果はworkloadの共有率・人気の偏り・GPU台数で変わる。長いprefixがほぼないworkloadではcache-aware routingの効果は小さく、既存servingと同程度に近づく。

## 7. Limitations / 実装上の注意

- **Exact prefix前提**。同義語の別表現や異なる位置へ移動したdocument KVをそのまま共有するものではない。semantic alignment/repairは行わない。
- **履歴依存のload推定**。$H$、requestの出力長予測、prefill regressionが実際のworkloadとずれるとroutingが悪化し得る。
- **Global metadata管理**。GPUのcache evictionやreplicaの変化を反映する必要があり、非常に大きなクラスタでは複数global schedulerへ分割する設計が課題。
- **Network転送とKV placement**。主に既存GPU上のcache localityを利用する方式であり、Mooncakeのような分散DRAM/SSDからの大量KV転送は中心機能ではない。
- **Accuracyではなくlatency**。モデルのforwardは同じなので品質維持が前提だが、KVのcross-document再利用時の品質劣化を検証した論文ではない。
- **Venue表記**。arXiv PDFのフッタに「ICLR 2024」と表示される箇所があるが、**ICLR公式proceedingsは2025**である。metadataでは公式採択記録を優先。
