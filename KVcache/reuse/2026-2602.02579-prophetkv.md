# ProphetKV: User-Query-Driven Selective Recomputation for Efficient KV Cache Reuse in Retrieval-Augmented Generation

> CacheBlend系のselective recomputationを発展させ、**「full prefillとの差が大きいtoken」ではなく「最終user queryにとって重要なtoken」を再計算する**。限られたrecomputation budgetをquery-relevant tokenへ集中させることで、$20\%$ recomputationでもfull-prefillに近いaccuracyを維持する。

## 概要

RAGでは複数のretrieved documentsを長いcontextとしてLLMへ入力するため、prefillがTTFTの主要bottleneckになる。

この問題に対し、各documentを独立にprefillしてKV cacheを保存し、request時にそれらを再利用する方法がある。しかし独立計算したKVは、本来のfull prefillで存在するdocument間のcross-attentionやpreceding contextからのhidden-state更新を欠くため、単純にconcatするとaccuracyが低下する。

[CacheBlend](2024-2405.16444-cacheblend.md)やKVShareは、一部tokenだけをfull-context条件で再計算してこの差を補う。

ProphetKVの問題意識は、その**token selection criterion**にある。

従来法では、

- KV deviation
- global attention saliency
- low-layerで観測したimportance

などから「full prefillとの差が大きいtoken」を選ぶ。しかし、そのtokenが最終user queryにとって重要とは限らない。

globalにはsalientでもqueryに無関係なtokenがrecomputation budgetを占有し、本当にquery-criticalなtokenがselectionから押し出される。論文ではこれを **crowding-out effect** と呼ぶ。

ProphetKVはselection objectiveを、

```text
global importance
      ↓
query relevance
```

へ変更し、user queryからcached contextへのattentionを使ってrecomputation対象を決める。

## 問題設定

RAG promptを、

```math
S = [D_1, D_2, \ldots, D_m, Q]
```

とする。$D_i$ はretrieved document、$Q$ はuser query。

各documentは独立prefillされ、

```math
K'_i, V'_i
```

としてcacheされている。

request時にはこれらをconcatするが、full prefill時の

```math
K, V
```

とは一致しない。

そこで一部token集合 $\mathcal{R}$ だけをfull-context条件で再計算し、残りはcached KVをそのまま使う。

recomputation ratioを

```math
r = \frac{|\mathcal{R}|}{s}
```

とすると、目的は小さい $r$ でfull-prefillに近いaccuracyを得ること。

ProphetKVの中心課題は、

> **どのtokenを $\mathcal{R}$ に入れるべきか**

である。

## Crowding-out Effect

recomputation budgetが $20\%$ なら、全tokenのうち1/5しか修復できない。

既存global saliency型selectionでは、

```text
globally important / query-irrelevant
globally important / query-irrelevant
globally important / query-irrelevant
...
query-critical
```

という順位になる場合がある。

このとき上位20%だけを取ると、queryに必要なtokenが落ちる。

特に、

- MultiValue
- MultiQuery
- long-context QA

のように、大量contextからqueryに対応する狭いevidence spanを拾うtaskで問題が大きい。

ProphetKVは、selective recomputationでは

> full KVとの差を最小化すること

よりも、

> query-conditioned semantic lossを小さくすること

の方が重要だと考える。

## 手法

### 1. Query-driven Token Importance

ProphetKVではtoken $t$ のimportanceを、

> user query tokenからcontext token $t$ へどれだけattentionが向くか

で測る。

layer $l$ におけるscoreを、

```math
\alpha_l(t) = \hat{\Phi}'^{(l)}_{Q_s,t}
```

とする。

直感的には、

```math
\mathrm{importance}(t)
\approx
\sum_{q \in Q_s}\mathrm{Attention}(q,t)
```

である。

つまり、

```text
Is this token globally important?
```

ではなく、

```text
Will this user query actually attend to it?
```

を見る。

論文ではfull-prefill時のquery outputとcached-KV利用時のquery outputとの差からsemantic lossを考え、query-weighted output errorへ大きく寄与するtokenを再計算すべきだと導出する。

ただしfull-prefillを行わず真のattentionは得られないため、cached KVに対するquery attentionをobservable proxyとして使う。

### 2. Query-only Layer Pass

token importanceはlayerごとに変わる。

浅いlayerではlocal token中心、高いlayerではdistant evidenceやsemantic answer spanへattentionが移るため、low-layer importanceだけで全layerを近似するとdeep layerで重要なtokenを落とす可能性がある。

ProphetKVではcontext全体を再forwardせず、

> **query tokenだけを全layerへ通す**

軽量passを行う。

cached context K/Vは固定したまま、各layerで

```math
A_l(Q_s, K'_l)
```

を計算し、query→context attentionから $\alpha_l(t)$ を得る。

計算量は概ね、

```math
O(|Q_s|s)
```

で、通常 $|Q_s| \ll s$ なのでcontext全体のfull prefillより小さい。

### 3. Layer-wise Fusion

全layerで得たscoreをfusionし、

```math
\bar{\alpha}(t)
=
\frac{1}{L}\sum_{l=1}^{L}\alpha_l(t)
```

のようなaggregate importanceを作る。

その後、

```math
\mathcal{R}
=
\mathrm{TopK}_t \bar{\alpha}(t)
```

として全layer共通のrecomputation対象を選ぶ。

共通token setにすることで、

- layerごとのdynamic shapeを避ける
- gather / scatterを固定できる
- GPU kernelを単純化できる

という実装上の利点もある。

### 4. Selective Recomputation

選ばれたtokenだけをfull-context条件で全layer再計算する。

全体は、

```text
Cached document KV
       ↓
Query-only pass
       ↓
Per-layer query relevance
       ↓
Layer-wise fusion
       ↓
Top-k query-relevant tokens
       ↓
Selective full recomputation
       ↓
Generation
```

となる。

## Experiment Setup

主なmodelは、

- Llama-3.1-8B-Instruct
- Qwen2.5-14B-Instruct
- Qwen3-14B

である。

benchmarkは、

- RULER
- LongBench

を使用する。

RULERではMultiValue / MultiQuery等、LongBenchではHotpotQA、NarrativeQA、Musique、QMSum等のlong-context taskを含む。

contextは512-token chunkへ分割し、各chunkを独立prefillしてKV cacheを保存する。

主要baselineは、

- FullRecomp
- NaiveReuse
- CacheBlend
- EPIC
- KVShare

である。

main settingではrecomputation ratioを **$20\%$** とする。

TTFTはH100で測定し、実験全体ではA100 / H100 / L20を使用する。

## Main Results

### $20\%$ recomputationでfull-prefill accuracyの96–101%

中心結果は、$20\%$ のtokenだけ再計算しても、

> **full-prefill accuracyの約96–101%**

を維持すること。

RULERでは既存SOTAに対して **8.8–24.9%**、LongBenchでは **18.6–50.9%** のaccuracy改善を報告する。

特にMultiValue / MultiQueryのようなquery-specific retrievalが重要なtaskで差が大きく、crowding-out仮説と整合する。

### Qwen3-14Bの代表値

| Method | RULER Avg. | LongBench Avg. |
|---|---:|---:|
| Full recomputation | 91.79 | 61.06 |
| CacheBlend | 71.99 | 50.17 |
| EPIC | 67.94 | 45.23 |
| KVShare | 70.64 | 48.90 |
| **ProphetKV** | **89.89** | **59.52** |

$20\%$ recomputationでもfull prefillとの差が小さい。

単にCacheBlendを数point改善するだけでなく、**full recomputationとのgap自体を大きく縮めている**点が特徴。

## Recomputation Ratio / Selection Ablation

recompute ratioを変えると、ProphetKVは$10\%$–$30\%$程度でnear-full accuracyへ近づく。

一方baselineは同accuracyまで戻すためにより高いrecompute ratioを必要とする。

selection criterion自体をoracleと比較した実験でも、

- Oracle: 約 $2\%$
- ProphetKV: 約 $4\%$
- CacheBlend: 約 $6\%$

程度でaccuracyが回復するcaseが示される。

これはProphetKVのquery-driven importanceが、CacheBlendのglobal importanceよりoracle selectionに近いことを示す。

## TTFT

16K contextでの代表値は、

| Model | FullRecomp | EPIC | ProphetKV | CacheBlend |
|---|---:|---:|---:|---:|
| Llama-3.1-8B | 5.23 s | 1.08 s | 1.13 s | 1.29 s |
| Qwen2.5-14B | 9.94 s | 2.03 s | 2.12 s | 2.31 s |
| Qwen3-14B | 8.70 s | 1.76 s | 1.84 s | 2.05 s |

full recomputationに対して約4.6〜4.7×高速で、論文全体では最大約5×のTTFT speedupを報告する。

ProphetKVの位置づけは、

```text
accuracy ≈ full prefill
latency  ≈ EPIC
```

に近い。

EPICより少しcomputeを使う代わりにaccuracyを大幅に回復し、CacheBlendより高accuracyかつ低latencyとなる。

4K程度ではselection passやkernel launch等のfixed overheadが相対的に大きく、長contextほどbenefitが大きい。

## CacheBlendとの違い

[CacheBlend](2024-2405.16444-cacheblend.md)は最も直接的なpredecessor。

CacheBlendは、

```math
KV_{\mathrm{reuse}} \rightarrow KV_{\mathrm{full}}
```

を目標とし、full prefillとの差が大きいtokenを修復する。

ProphetKVは、

```math
\text{preserve query-relevant semantics}
```

を優先する。

| | CacheBlend | ProphetKV |
|---|---|---|
| Selection objective | KV / global attention recovery | Query relevance |
| Importance | global | user-query-conditioned |
| Deep-layer signal | low-layer approximationあり | query-only passで取得 |
| Recomputation budget | query無関係tokenにも使われる | query-critical tokenへ集中 |

ProphetKVの主要な新規性は、selective recomputationのobjectiveを**state reconstructionからquery-conditioned utilityへ変えたこと**にある。

## EPIC / Block-Attentionとの違い

[EPIC](2024-2410.15332-epic.md)はposition-independent reuseをlightweight linkingで実現するためruntime costは低いが、query-specific repairは行わない。

[Block-Attention](2024-2409.15355-block-attention.md)はさらに別方向で、fine-tuningによってmodel自体をindependent KV reuseへ適応させる。

整理すると、

- EPIC: lightweight position-independent reuse
- CacheBlend: inference-time repair
- ProphetKV: query-aware inference-time repair
- Block-Attention: reuse-aware fine-tuning

となる。

## Limitations

1. **Query attention自体もcached KVに依存する**  
   independent cachingによるrepresentation errorが極端に大きい場合、importance scoreも誤る可能性がある。

2. **Query-centric workload向き**  
   RAG QAのように明確なuser queryがあるtaskでは自然だが、summarizationなどquery relevanceが曖昧なtaskでは効果が弱まる可能性がある。

3. **$20\%$とはいえrecomputationは必要**  
   EPICのようなほぼrepair-free方式よりcompute costは大きい。

4. **Cache I/Oは別問題**  
   CPU / SSDからGPUへKVをloadするstorage hierarchy costは別途最適化が必要。

5. **Short contextではfixed overheadが目立つ**  
   4K程度ではfull prefill自体が短く、selection overheadの相対比が大きくなる。

## KV-cache taxonomyでの位置づけ

ProphetKVは **query-aware inference-time selective recomputation** に分類できる。

reuse系は、

- **Exact Prefix Reuse**
- **Position-independent / Modular Reuse** — EPIC
- **Inference-time Repair** — CacheBlend
- **Query-aware Inference-time Repair** — ProphetKV
- **Reuse-aware Fine-tuning** — Block-Attention

と整理できる。

特にProphetKVはCacheBlend系の自然な発展として、

> 「どのKVが壊れているか」ではなく「どのKVがこのqueryに必要か」

をselection criterionにした点が重要。

## まとめ

ProphetKVはRAG KV reuseにおけるselective recomputationを、

```text
Which cached tokens are most corrupted?
```

から、

```text
Which cached tokens matter most for this query?
```

へ切り替える。

中心componentは、

| Component | Role |
|---|---|
| Query-only layer pass | full prefillせず全layerのquery relevanceを取得 |
| Layer-wise fusion | deep / shallow layerのimportanceを統合 |
| Top-k recomputation | query-critical tokenへbudgetを集中 |

$20\%$ recomputationでfull-prefill accuracyの96–101%を維持し、RULER / LongBenchでCacheBlend、EPIC、KVShareを大きく上回る。

KV reuse研究としては、CacheBlendが「壊れたKVを効率よく修復する」方向を開いたのに対し、ProphetKVは**すべての壊れたKVを直す必要はなく、queryに必要なtokenだけ直せばよい**ことを示した後継研究として位置づけられる。
