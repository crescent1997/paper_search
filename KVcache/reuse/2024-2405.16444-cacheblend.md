# CacheBlend: Fast Large Language Model Serving for RAG with Cached Knowledge Fusion

> exact-prefix cachingを、RAGのような**複数chunkを任意順序で組み合わせるprompt**へ拡張する代表的研究。単純なKV concatenationでは失われるcross-chunk attentionを、影響の大きいtokenだけ再計算して部分的に回復する。

## 概要

LLM servingでは同じdocumentやcontext chunkが複数requestで繰り返し使われる。prefix cachingなら、同じtextがprompt先頭に現れる場合、そのKV cacheを安全に再利用できる。

しかしRAGでは、複数documentを連結するため、後ろのdocumentのKVは前に置かれたdocumentへattentionした結果を含む。たとえばDoc Bを単独でprefillしたKVと、Doc Aの後ろに置いてfull prefillしたKVは一致しない。

[
KV(B mid A) 
eq KV(B)
]

既存方式には、full recomputation、prefix caching、独立chunk KVの単純reuseがあるが、それぞれTTFT、reuse範囲、qualityのいずれかを犠牲にする。

CacheBlendは、

> すべてのtokenを再計算する必要はなく、cross-chunk interactionの影響が大きいtokenだけ直せばよい

という中間解を取る。

## 問題設定

複数chunkのprecomputed KVをrequest時に連結すると、RoPE positionは補正できてもcross-attentionは復元できない。

```text
Chunk 1
   ↓
Chunk 2 ← 本来はChunk 1を見る
   ↓
Chunk 3 ← 本来はChunk 1, 2を見る
```

full reuseではこのinteractionが欠落し、その誤差が後続layerへ伝播する。

論文では、precomputed KVとfull recompute KVの差を **KV deviation**、attention matrixとの差を **attention deviation** として捉え、少数tokenのKV更新でattention deviationを最小化する問題として整理する。

## 手法

### 1. Precomputed KV reuse

document chunkごとにKV cacheを事前計算して保存する。request時にはretrieved chunkのKVを読み出し、prompt順に連結する。

RoPE modelでは、chunkがrequest内で置かれるglobal positionに合わせてKeyのrotationを補正する。

ただしposition correctionだけではcontext dependencyは戻らない。

### 2. Selective recomputation

各layerですべてのtokenを再計算せず、重要なtoken subsetのみQ/K/Vを再計算する。残りのtokenはprecomputed KVをそのまま使う。

recompute ratioを (r%) とすると、full prefillより大幅にcomputeを減らせる。

### 3. High-KV-Deviation token

中心となるのは、どのtokenを再計算するか。

論文ではKV deviationが大きいtokenほど、そのtokenを再計算した際にattention deviationを大きく減らせることを観察する。

このtokenを **High-KV-Deviation (HKVD) token** として優先する。

重要なのは、全tokenが同程度に壊れるわけではない点である。実験では約10〜15%程度のtokenに大きなdeviationが集中し、それ以外は比較的小さい。

これはattention sparsityとも整合し、他chunkとのcross-attentionが強いtokenほど影響を受けると解釈できる。

### 4. Layer間でのHKVD追跡

真のKV deviationを求めるためにfull recomputeしてしまえば本末転倒である。

CacheBlendは、HKVD tokenの順位が隣接layer間でかなり相関することを利用する。

前layerでdeviationが大きかったtokenを次layerの候補として残す **gradual filtering** により、毎layer全tokenを検査する必要を減らす。

```text
Layer 1
  ↓ broad candidate selection
HKVD tokens
  ↓
Layer 2
  ↓ narrow / rerank
smaller candidate set
  ↓
...
```

## KV LoadingとのPipeline

CacheBlendはselective recomputationとKV loadingをoverlapさせる。

```text
Layer i:     selective recomputation
Layer i+1:   KV loading
              ↑ overlap
```

KV cacheをCPU memoryやNVMeへ置いた場合、I/Oが長いとrecomputeをその裏に隠せる。

論文ではLlama-7B、4K contextの例で、15% tokenのrecomputeがlayer当たり約3 ms、NVMeからの1 layer分KV loadingが約16 msとなり、recompute delayをI/Oでほぼ隠せることを示す。

一方、modelが大きい場合はrecompute側が支配的になることもあるため、model / context / storageに応じてrecompute ratioとcache placementを変える。

## Experiment Setup

CacheBlendはvLLM上に実装される。

複数sizeのopen-source LLMとQA / RAG / summarization workloadを用い、

- Full KV recompute
- Prefix caching
- Full KV reuse
- CacheBlend

を比較する。

主なmetricはF1 / Rouge-L、TTFT、serving throughput、storage / loading overhead。

## Main Results

CacheBlendはfull recomputeとほぼ同等のgeneration qualityを維持しながら、

- **TTFT: 2.2〜3.3×改善**
- **throughput: 2.8〜5×改善**

を報告する。

full KV reuseと比べると速度は近いがqualityが大きく改善する。

代表的にはQAでabsolute F1を約0.1〜0.2、summarizationでRouge-Lを約0.03〜0.25改善する。

つまり狙いは、

> full reuse並みの速度とfull recompute並みのquality

である。

## Recompute RatioのAblation

recompute ratioを増やすほどqualityは改善するが、改善は線形ではない。

最初の少数HKVD tokenを直す段階で大きく改善し、10〜20%付近で飽和しやすい。

論文では15%をdefaultとして多く用い、速度とqualityのバランスが良いことを示す。

同じtoken数をrandomに選ぶより、HKVD selectionの方が明確に優れる。

## Prefix Caching / Full Reuseとの違い

| Method | Non-prefix reuse | Cross-chunk interaction | Extra compute |
|---|---|---|---|
| Prefix caching | × | 正確 | 少 |
| Full KV reuse | ✓ | ほぼ無視 | ほぼなし |
| CacheBlend | ✓ | selective repair | 約10〜20% |
| Full recompute | ✓ | 完全 | 最大 |

CacheBlendはnon-prefix reuseを可能にしつつ、cross-chunk attentionを完全には捨てない点が特徴。

## Block-Attentionとの違い

[Block-Attention](2024-2409.15355-block-attention.md)もdocument KV reuseを狙うが、解き方は逆。

CacheBlendはpretrained modelを維持し、

[
KV_{reuse} ightarrow KV_{full}
]

へ近づける。

Block-Attentionはfine-tuningにより、

[
Model ightarrow 	ext{reuse-friendly representation}
]

へ適応させる。

したがって、

- CacheBlend: **inference-time repair**
- Block-Attention: **reuse-aware fine-tuning**

と整理できる。

## EPICとの違い

[EPIC](2024-2410.15332-epic.md)はCacheBlendのdynamic selective recomputationを主要baselineとし、そのselection overheadをさらに削減する。

CacheBlendがHKVD tokenを動的に追跡するのに対し、EPICはchunk先頭のattention sinkへ誤差が集中することを利用し、固定少数tokenだけをlinkする。

## Limitations

1. **Recomputeは残る**  
   tuning-freeだが、defaultで15%程度のtokenをforwardし直す。

2. **token selection overhead**  
   HKVD追跡やattention計算はlong contextで無視できない。

3. **storage / I/O依存**  
   cacheをGPU外へ置く場合、speedupはCPU-GPU / NVMe bandwidthに左右される。

4. **full prefillとの厳密一致ではない**  
   selective repairは近似であり、taskごとに必要recompute率が異なる。

5. **chunk interaction依存**  
   強いcross-document reasoningが必要なpromptでは、full reuseとの差が大きくなりやすい。

## KV-cache taxonomyでの位置づけ

CacheBlendは **non-prefix reuse + inference-time partial repair** の代表手法。

```text
Exact prefix caching
      ↓
Full non-prefix reuse
      ↓ quality loss
Selective recomputation
      ↓
CacheBlend
```

という位置にある。

特に、position correctionだけでは解決できない**context dependencyそのもの**を扱った点が重要。

## まとめ

CacheBlendは、documentごとにprecomputeしたKVを任意順序でreuseしたい一方、full-attention modelではKVが前文脈に依存するという問題を、selective recomputationで解決する。

| Component | Role |
|---|---|
| Precomputed chunk KV | documentごとのreuse |
| RoPE correction | request内positionへ再配置 |
| HKVD selection | cross-chunk影響の大きいtokenを特定 |
| Selective recompute | 少数tokenだけfull-contextで更新 |
| KV-load pipeline | recompute delayをI/Oの裏へ隠す |

約10〜20%、default 15%程度のtoken再計算でfull recomputeに近いqualityを維持し、TTFT 2.2〜3.3×、throughput 2.8〜5×改善を報告する。

reuse研究では、**「cached KVをそのまま使う」のではなく「壊れた部分だけ直して使う」**という系統の代表例である。
