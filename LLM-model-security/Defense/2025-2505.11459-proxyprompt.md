# ProxyPrompt: Securing System Prompts against Prompt Extraction Attacks

## 概要

ProxyPromptはsystem prompt extractionに対し、「modelへ秘密のsystem promptを渡したまま漏らさないようinstructionする」のではなく、**同等のtask behaviorを実現するがoriginal promptを復元しにくいproxy prompt**へ置き換えるDefenseである。

attackが成功してsystem prompt fieldを出力させても、得られるのはproxyであり、developerが保護したいoriginal promptではない。

## 問題設定 / Threat Model

system promptにはproprietary instruction、application logic、prompt-engineering know-how、policy、hidden workflow等が含まれうる。attackerは通常userとしてqueryし、prompt extraction attackでsystem promptをrecoverしようとする。

Defenseの目的はextraction requestを常に拒否することだけでなく、**仮にmodelが保持するpromptを完全に漏らしてもoriginal promptの秘密性を維持する**ことである。

## Security Goal

original promptを (P)、proxyを (	ilde P) とすると、

[
Utility(	ilde P) approx Utility(P)
]

を維持しつつ、original/proxy間の類似性とattackerによるoriginal recovery可能性を下げる。

つまりtask utility preservation、information dissimilarity、extraction resistanceを同時に扱う。

## 先行研究からの改善点

### Refusal-based Defense

「system promptを開示するな」とsystem prompt自身へ追記する方法は同じLLMのinstruction-following robustnessへ依存する。未知のprompt injection / jailbreakで回避されればoriginalがそのまま露出する。

ProxyPromptは**leak preventionからleak consequence reductionへsecurity objectiveを移す**。

### Instruction Hierarchy

[The Instruction Hierarchy](2024-2404.13208-instruction-hierarchy.md)はsystem > userを学習してextraction requestを拒否させるmodel-level Defenseである。ProxyPromptはhierarchy failureが起きる可能性を前提に、漏洩対象そのものを変換する。

### CaMeL

[CaMeL](2025-2503.18813-defeating-prompt-injections-by-design-camel.md)がcapability / provenanceをsystem architectureで制御するのに対し、ProxyPromptは**prompt information assetのrepresentation**を防御する。

## Method / Algorithm

1. 保護対象のoriginal system prompt (P) とtask behaviorを用意する。
2. LLMを利用してoriginalとは表現・情報的に異なるcandidate proxyを生成する。
3. candidateをsystem promptとして実行し、task utilityを測る。
4. originalとのsimilarity / recoverabilityを評価する。
5. utilityとprotectionのtrade-offを満たすproxyを選び、deploymentではproxyのみを使用する。

```text
Original system prompt
        ↓
proxy generation / optimization
        ↓
utility check + protection check
        ↓
Proxy prompt
        ↓
deployment
```

## なぜ単純Paraphraseではないか

表面語を置き換えただけでは、extracted proxyからoriginalの意味を容易に推測できる。目的はtask semanticsの必要部分を保持しつつoriginal promptとのlinkabilityを下げることであり、**functionally equivalent surrogate instruction**を作る問題に近い。

## Experiment Setup

評価は **264 LLM × system-prompt pairs** の組合せで行う。複数のprompt extraction attackに対し、prompt protection success、extracted contentとoriginalの類似度、utility retention、query budget増加時のrobustnessを比較する。

utility評価にはGSM8K、CoLA、SST-2等を含み、security改善の代わりに本来機能を失っていないかを測る。

## Main Results

ProxyPromptは評価したsystem promptの **94.70%** を保護し、比較対象の次善Defenseの **42.80%** を大幅に上回る。

これはattack requestを完全に防いだという意味ではなく、attackがdeployment promptを引き出しても、**original assetのrecoveryに直結しない**ようにした結果である。

## Utility / Query-budget Robustness

複数taskでoriginal promptとproxyのperformanceを比較し、prompt protectionを大きく改善しながらtask utilityを概ね維持する。

またquery budgetを100から400へ増やす評価でもprotectionが大きく崩れないことを確認する。ただし無制限adaptive attackerに対するformal secrecy guaranteeではない。

## Just Askとの関係

[Just Ask](../Attack/2026-2601.21233-just-ask.md)はblack-boxで複数queryを繰り返し、targetごとに有効なsystem-prompt extraction strategyをonline探索する。

```text
Just Ask:
  assume prompt can be queried repeatedly
  → improve extraction strategy

ProxyPrompt:
  assume stored prompt may eventually leak
  → make leaked representation less valuable
```

という対応関係にある。

## Instruction Hierarchyとの関係

priority followingとprompt confidentialityは同一ではない。

```text
Instruction Hierarchy:
  prevent lower-priority override

ProxyPrompt:
  reduce damage if higher-priority prompt leaks
```

modelが未知attackでsystem promptを出力した場合、originalを保持している限りassetが漏洩する。ProxyPromptはこのresidual riskを別layerで扱う。

## StruQ / SecAlign / Meta SecAlignとの関係

[StruQ](2024-2402.06363-struq.md)、[SecAlign](2024-2410.05451-secalign.md)、[Meta SecAlign](2025-2507.02735-meta-secalign.md)はtrusted promptとuntrusted dataを分離し、低権限instructionによるbehavior overrideを防ぐ。

ProxyPromptはbehavioral overrideではなく**trusted prompt自体のconfidentiality**を扱うため、これらと併用できる。

## ISEとの関係

[Instructional Segment Embedding](2024-2410.09102-instructional-segment-embedding.md)はsource identityをlearnable embeddingとしてmodelへ伝えてpriority enforcementを強化する。一方ProxyPromptはmodel architectureを変更せずprompt representationを変換するため、closed modelにも適用しやすい。

## White-box / Black-box Attackへの位置づけ

特定attack stringに依存しないためblack-box prompt extractionに対して自然なDefenseである。一方、attackerがproxy generation processやoriginal/proxy pairにアクセスできるstrong white-box settingではthreat modelが変わる。

## Limitations

- originalとproxyのfunctional equivalenceを完全保証しない。
- task distributionが変わるとproxy utilityが低下しうる。
- task behaviorからoriginal semanticsが本質的に推測可能なら完全秘匿はできない。
- proxy自体にもproprietary valueが生じうる。
- formal cryptographic secrecyではない。
- credential等の真のsecretをsystem promptへ置く設計を正当化しない。
- prompt confidentialityを守ってもtool authorization / prompt-injection integrityは別途必要。

## LLM Model Security Taxonomyでの位置づけ

```text
Model-level priority Defense
  Instruction Hierarchy / SecAlign / ISE
        ↓
prevent lower-priority override

System-level capability Defense
  CaMeL
        ↓
prevent unauthorized effects

Prompt confidentiality Defense
  ProxyPrompt
        ↓
reduce value of extracted prompt
```

## 実装・研究上の示唆

system promptを知的財産として保護するapplicationでは、originalをoffline assetとして保持し、utility-equivalent proxyを生成してdeploymentにはproxyのみを配置し、query-budget付きextraction testとoriginal recoverabilityのred-teamを行う設計が考えられる。

credentialやprivate user dataはproxy化以前にsystem promptへ置かず、外部secret store / authorization layerで管理すべきである。
