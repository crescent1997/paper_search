# QUEST: Query-Aware Sparsity for Efficient Long-Context LLM Inference

> long-context decodeでKV cache全体を毎step読む代わりに、**current queryに重要なKV pageだけを選んでロードする**。SparQのtoken-level query-aware accessから、PagedAttentionと相性のよいpage-level selectionへ進めた代表的access手法。

## 概要

long-context LLMのdecodeでは、過去tokenのK/Vをcacheして再計算を避けても、self-attentionのたびに巨大なKV cacheをHBMから読み出す必要がある。contextが長くなるほどattentionはcomputeよりmemory movementに支配される。

一方、実際のattention outputは少数のcritical tokenに強く依存する。しかし重要tokenは固定ではなく、**current queryによって変化する**。H₂OやStreamingLLMのようにhistorical importanceからtokenを永久evictすると、後のqueryで突然重要になるold tokenを失う可能性がある。

QUESTはKV全体を保持したまま、各decode stepでquery-dependentに重要pageを推定し、そのpageだけを実際のattention計算へロードする。

## 問題設定

KV cacheをpage size Sで分割する。page数をPとすると、dense attentionではP pageすべてについてfull K/Vを読む。

理想的にはcurrent query qに対してattention scoreが高くなり得るpageだけを読みたい。しかしselectionのために全Keyを読めばdense attentionと同じmemory trafficが発生する。

QUESTの中心課題は、

> **full Keyをロードせず、非常に小さいmetadataだけから重要pageを安全側に推定する**

こと。

## Query-aware page criticality

### Page metadata

各KV pageについてKeyのdimensionごとの最小値と最大値を保持する。

dimension jについて、

- min K_j
- max K_j

だけをmetadataとして保存する。

pageにS tokenあってもmetadata sizeはtoken数に比例せず、各dimensionにつき2値だけで済む。

### Query-dependent upper bound

current query q_jの符号に応じて、そのdimensionでdot productを最大化するKey boundを選ぶ。

q_jが正ならmax K_j、負ならmin K_jを使い、dimensionごとの寄与を足すことで、そのpage内の任意tokenが取り得るattention scoreのupper boundを推定する。

つまりpageのcriticalityは固定importanceではなく、**そのdecode stepのQueryに依存する**。

このupper-bound型scoreにより、本当に高attentionになり得るpageを候補として残しやすい。

## Top-K page selection

全pageのmetadataだけをscanしてcriticalityを計算し、Top-K pageを選択する。

その後初めて、選ばれたpageのfull K/VをHBMから読み、通常のattentionを計算する。

selection granularityはtokenではなく**page/block level**。PagedAttention型serving systemで既に使われるKV pageをそのままaccess unitとして利用できる。

## Memory load

dense attentionではP個のpageすべてのfull K/Vを読む。

QUESTでは概ね、

1. 全P pageの小さいmetadata
2. Top-K pageのfull K/V

だけを読む。

page sizeをSとするとmetadata scanの相対costは概ね1/S、selected pagesのcostはK/Pなので、dense KV loadに対する比率は直感的に

```text
1 / S + K / P
```

程度になる。

したがってlong contextでPが大きく、Kを小さく保てるほどbenefitが大きい。

## H₂O / StreamingLLMとの差

[H₂O](../compress/2023-2306.14048-h2o.md)や[StreamingLLM](../compress/2023-2309.17453-streamingllm.md)はKV capacityそのものを減らすcompress手法。

| | H₂O / StreamingLLM | QUEST |
|---|---|---|
| category | compress | access |
| old KV | evictionする | 保持する |
| selection | historical / structural | current query |
| granularity | token | page |
| future importance | evicted後は復元不可 | 毎step再選択可能 |
| 主目的 | cache capacity削減 | decode memory load削減 |

long-dependency taskでは、非常に古いtokenが後で突然重要になる。QUESTはcacheを保持しているため、その時点のqueryに応じて再び選択できる。

## SparQ Attentionとの差

[SparQ Attention](2023-2312.04985-sparq-attention.md)は最も近いpredecessorの一つ。

SparQはcurrent queryの絶対値が大きい上位dimensionだけを使い、全tokenのKeyを低次元で粗くscoreしてtop-k tokenを選ぶ。

QUESTはKeyのfull/partial vectorをselection時に直接scanする代わりに、**pageごとのmin/max metadata**からcriticality upper boundを計算する。

| | SparQ | QUEST |
|---|---|---|
| selection granularity | token | page |
| metadata / coarse read | selected Key dimensions | per-page Key min/max |
| relevance | current query | current query |
| KV eviction | なし | なし |
| serving affinity | sparse gather | PagedAttention / block access |
| bottleneck target | KV bandwidth | KV bandwidth |

技術系譜としては、

```text
query-aware sparse KV access
        ↓
SparQ: dimension pruning → token selection
        ↓
QUEST: compact page metadata → page selection
```

と整理できる。

## Long-dependency accuracy

QUESTの重要な評価は、単にperplexityを保つだけでなく、遠い過去の特定tokenを後から参照するtask。

passkey retrievalでは非常に小さいtoken budgetでも高accuracyを維持する。代表的には10K contextで64-token budgetで約99%、100K contextで1024-token budgetで約96%となり、budgetを少し増やすとfull-cache相当へ近づく。

historical eviction型手法は必要tokenを既に捨てている可能性があるため、このsettingで大きく崩れやすい。

## LongBench

LongChat-7B-v1.5-32Kを用い、NarrativeQA、Qasper、MultiFieldQA、HotpotQA、GovReport、TriviaQA等を評価する。

QUESTは約2K-token budgetでfull KV cacheに近いLongBench performanceを示し、同等またはより大きなbudgetを使うeviction baselineよりgapを小さくする。

これは「どのtokenが重要かは過去の平均importanceよりcurrent queryで決めるべき」という中心仮説を支持する。

## Implementation

QUESTはFlashInferをベースに専用CUDA kernelを実装する。

decode pathは概ね、

```text
Query
  ↓
page criticality estimation
  ↓
Top-K filtering
  ↓
selected-page KV load
  ↓
sparse attention
```

となる。

metadataはKV page更新時にmaintainし、decodeではfull K/Vをselectionのために読む必要がない。

Top-K filtering自体のoverheadはlong-contextでは小さく、128K未満で数µs〜10µs程度の範囲と報告される。

## Main Results

論文本文・公式実装で報告される代表値は、

- **self-attention speedup: 最大7.03×**
- **end-to-end inference speedup: 最大2.23×**

である。

特に30K前後のsequence、2048-token budget、4-bit weight quantizationでend-to-end 2.23×を報告する。

32K context / 2048-token budgetでは、full-cache FlashInferと比べて大幅にattention latencyを削減する。

注意点としてarXivの一部abstract表示では2.23×と7.03×の対応が逆転している版があるが、ICML本文・公式repositoryでは **7.03× self-attention / 2.23× end-to-end** とされている。

## Ablation / trade-off

### Page size

pageを小さくするとselection granularityが細かくなり不要tokenを読み込みにくいが、metadata割合とpage管理overheadが増える。

大きいpageはmetadata costを下げるが、1つ重要tokenがあるだけでpage全体を読むためread amplificationが増える。

### Token budget / Top-K pages

budgetを増やすほどaccuracyはfull attentionへ近づく一方、KV memory trafficとattention latencyが増える。

QUESTはlong-dependency taskで比較的小さいbudgetでも必要pageをquery-awareに回収できる点が強み。

### Query awareness

固定importanceやhistorical attentionと比べ、query-aware criticalityはqueryごとに参照先が変わるretrieval taskで特に有効。

## GQA / model architectureとの関係

[GQA](../model/2023-2305.13245-gqa.md)はKV head数を構造的に減らすmodel-level optimizationであり、QUESTとは直交する。

- GQA: head axisのKV量を減らす
- QUEST: sequence axisで実際に読むpageを減らす

したがって原理上は併用できる。

初期実装ではGQA対応が限定的だったが、公式repositoryでは後にLlama-3.1やMistral-v0.3 familyへのsupportも追加されている。

## Limitations

1. **KV cache容量そのものは削減しない**。全KVを保持できるmemory capacityは必要。
2. **page selection overhead**があり、short contextではdense attentionとの差が小さくなる。
3. **page-level read amplification**がある。page内に1個だけ重要tokenがあってもpage全体を読む。
4. accuracyはTop-K budgetに依存し、attentionが広く分散するtaskではより多くのpageが必要。
5. speedupはattentionがend-to-end latencyで占める割合、weight quantization、GPU kernel efficiencyに依存する。

## KV-cache taxonomyでの位置づけ

**access / query-aware page selection / sparse KV fetch / training-free**。

QUESTはKV cacheを「何token残すか」ではなく、

> **current queryに対して、どのKV pageをこのdecode stepでHBMから読むか**

を最適化する。

SparQとともに、capacity compressionとdecode-time bandwidth reductionを分けて考える上で重要な代表例。

## まとめ

QUESTはlong-context decodeでのKV memory movementを、per-page min/max metadataを使ったquery-aware criticality estimationで削減する。

| Component | Role |
|---|---|
| per-page min/max Key | full KVを読まない軽量metadata |
| Query-aware upper bound | current queryに重要なpageを推定 |
| Top-K page filtering | actual KV read setを削減 |
| sparse page attention | HBM bandwidthとlatencyを削減 |

最大7.03×のself-attention speedup、最大2.23×のend-to-end inference speedupを報告し、long-dependency taskでもsmall budgetでfull-cacheに近いaccuracyを維持する。

技術的にはSparQのquery-aware sparse accessを、**page-level metadata + PagedAttention-friendly selection**へ発展させた研究として位置づけられる。
