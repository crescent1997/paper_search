# KVComm: Online Cross-context KV-cache Communication for Efficient LLM-based Multi-agent Systems

## 概要と選定理由

**reuse → multi-agent / cross-context reuse / offset alignment**。複数agentが同じモデルcheckpointを使い、role-specific system promptや他agentの応答を異なる順序・位置に挿入する場合、重複するテキストを毎回prefillするのは無駄になる。単なるprefix cacheは先頭一致しか利用できず、別のprefixの下で作ったKVを直接連結すると**RoPE位置ずれだけでなく、先行文脈によるhidden-state変化**が残る。

KVCommは共有contentを単に「同じ位置へ移動」するのでなく、**base cacheと実際のagent文脈下のcacheの差（offset）**を類似した過去事例から予測し、再prefillなしに近似KVを組み立てる。従来のselective recomputationとは異なり、reuse可能と判定したplaceholderは**全KVを補正して再利用**する。学習やモデル改変を必要としないと主張する。NeurIPS 2025 Main採択を公式proceedingsで確認。

## 問題設定・前提

agent $m$ のpromptは固定prefix $p_{m,i}$ と動的placeholder $\phi_{m,i}$ の交互列：

$$
s_m=[p_{m,0},\phi_{m,1},p_{m,1},\ldots,\phi_{m,i},p_{m,i}].
$$

同じ$\phi$でも前に付くsystem instruction・message・token数が違えば、各layerの$K,V$は変わる。KにはRoPEによる位置回転もある。KVCommが仮定するのは、**同一のRoPEベースdecoder checkpointを各agentが使用**する構成であり、異種モデル間のcache転用を一般に保証するものではない。動的placeholderを抽出できるprompt templateも必要となる。

論文はtoken embeddingが近い入力ほど、異なるprefixによって生じるKVの差分も似ると観察する。残差経路とattention/FFNのLipschitz仮定に基づく2つの上界を示すが、これらは**下流accuracyの厳密な保証ではなく、anchor類似度によるoffset推定の動機**と捉えるのが適切。

## 手法

### 1. Base KVとRoPE位置補正

動的segment $\phi$ の**base KV**を、そのsegment単体のprefillなどから保持する。元の位置$n$で得たKeyを新しい位置$n+\delta$で使うには、回転後のKeyをそのまま流用せずRoPE回転差を補正する：

$$
K^{\mathrm{aligned}}_{n+\delta}\approx R_{\delta}K_n,
$$

ここで$R_\delta$はRoPEの位置差に対応する回転（論文は比較前にde-rotationする説明も用いる）。ValueはRoPEを受けない。**位置補正は必要条件だが十分条件ではない**。異なるprefixによるcontext-dependentなKV変動は残る。

### 2. Anchor poolとoffsetの記録

placeholderごとにanchor poolを持ち、anchor $\psi$ に対して、(a) base KV、(b) agent $m$ の実際の文脈下でのplaceholder offset $\Delta_{m,\psi}^{\phi}$、(c) 直後の固定prefix segmentに生じるoffset $\Delta_{m,\psi}^{p}$ を保存する。**placeholderだけでなく、その後続prefixのKVも修正する**点が重要。これは過去のsegmentが後続tokenのhidden statesへ与える影響を部分的に復元するためである。

新しい入力が既存anchorより長い場合や、長さ条件を満たすanchorに対するembedding類似度が十分でない場合は、reuseを諦めて通常prefillを行い、新anchorとして登録する。pool上限$\mathcal V$に達したらアクセス頻度の低い古いanchorを削除する。オンラインにcoverageを増やすので、**初期warm-upとrequest順序**に依存する。

### 3. Anchor matchingとweighted offset interpolation

token embeddingから得たsegment表現の距離で候補anchorを検索する。長さ条件を満たすanchor集合$\mathcal A_\phi$上で重みを

$$
w_{\phi\to\psi}=\mathrm{softmax}_{\psi\in\mathcal A_\phi}\bigl(-\lVert h_\phi-h_\psi\rVert\bigr)
$$

とし、placeholderのKVを

$$
\widehat{KV}_{m,\phi}=KV^{\mathrm{base}}_{\phi}
+\sum_{\psi\in\mathcal A_\phi}w_{\phi\to\psi}\,\Delta^{\phi}_{m,\psi}
$$

で近似する（Kは適切なRoPE位置整合後に適用）。後続prefixにも同様に$\Delta^p$を足す。offsetは**層別・位置別のKVベクトルに作用する近似**であり、単一のtoken埋め込みを置き換えるだけではない。これらをprompt順に連結してdecodeへ進む。

### 4. Matching thresholdとfallback

論文のanchor追加判定にはsegment長とembedding類似度に基づく重みのentropyを利用し、$\gamma$でreuseとprefillを調節する。閾値を緩めるとreuse率は増えるがoffset誤差でaccuracyが落ちる。学習不要という利点の代わりに、**pool構築用の通常prefill・anchor保存量・lookup負荷**を負う。

## Experiment Setup

- **Model / hardware**: Llama-3.1-8B-Instruct（MMLU、GSM8K）、Qwen2.5-Coder-7B-Instruct（HumanEval）。単一NVIDIA H100。Hugging Faceベースのmulti-agent再現環境。
- **Agent構成**: fully-connected 2–5 agents、role-specific prompt、各agentの生成上限512 tokens。
- **Dataset**: MMLU（論文ではRAG系の評価）、GSM8K（数学推論）、HumanEval（code）。
- **Baselines**: full-prefill Original、CacheBlendの選択的再計算を再実装した比較（差分の大きいtop 20% tokenを再計算）。
- **Default**: $\gamma=0.3$、最大anchor数$\mathcal V=20$。accuracy/pass@1、TTFT、reuse rate。
- **Reuse rate定義に注意**: KVCommは「cache reuseを使うagentの割合」、比較CacheBlendは「reuseしたtokenの割合」。**両者の70–80%を直接比較してはいけない**（論文Table 1注記）。

## Main Results

### Accuracy / reuse（論文Table 1）

| Dataset（agent数） | Original | CacheBlend | KVComm | KVComm reuse率 |
|---|---:|---:|---:|---:|
| MMLU（4）accuracy | 68.0% | 65.4% | **68.0%** | 70.1% |
| GSM8K（4）accuracy | 82.1% | 65.1% | **80.6%** | 73.4% |
| HumanEval（4）pass@1 | 84.5% | 30.4% | **83.2%** | 81.1% |
| GSM8K（5）accuracy | 81.7% | 57.1% | **79.6%** | 71.0% |

「quality degradationなし」は全条件で厳密に同一精度という意味ではない。GSM8K 4-agentでは82.1→80.6%、HumanEval 4-agentでは84.5→83.2%と小幅な低下がある。一方、この再現条件のCacheBlendは特にcode/mathで大きく低下する。

### TTFT（論文Table 2、**改訂版の定義**）

5-agent、prefix 512 / output 512の設定では、Agent 5のfull-prefill TTFT **428.6 ms**に対して、KVCommの内訳はKV処理 **17.5 ms** + first-token decode **21.1 ms** + others **16.2 ms**、合計**54.8 ms**で**7.82×**。**428.6→17.5 msではない**。Agent 1はupstream cacheが少ないため1.11×、Agent 2–5は5.06×、6.14×、6.85×、7.82×。3-agentの平均speedupは短い設定で2.24×、長い設定で6.72×（Table 3）。

論文HTMLには「初稿のTTFTではfirst-token decodeを計上し忘れ、最終版で修正」と明記される。引用時は必ず最終版の数字を使う。

## 主要ablation（Table 4–6）

- **3つの補正は全て必要**：MMLU 4-agentで、RoPE位置補正のみ43.1%、placeholder offsetのみ58.8%、後続prefix offsetのみ60.1%。3つを併用すると**68.0%**。RoPE+placeholder offsetだけだと38.6%と逆効果になる組合せもあり、単純な独立改善ではない。
- **Request order**：MMLU 4-agentでrandom 68.0/72.5%、ascending 67.3%、descending 66.0%（full-prefill baseline 68.0%）。pool構築順が品質に影響する。
- **$\gamma$**：GSM8K 4-agent、$\gamma=0.1$でaccuracy83.1%、reuse34.3%；$\gamma=0.3$で80.6%、73.4%；$\gamma=0.9$で78.8%、98.2%。
- **Pool size**：$\mathcal V=5/10/20$でreuse 44.0/60.3/73.4%、accuracy 82.0/81.4/80.6%。poolを増やせば精度が単調改善するわけではない。

## Limitations・研究上の検討点

1. **同一checkpoint前提**。モデルやtokenizerが違うagent間のKV translationではない。GQA/RoPEのlayoutやposition IDsを変えた場合の検証が必要。
2. **誤差保証なし**。embedding近傍性がKV offset近傍性を示す実験的根拠はあるが、後続attentionと生成結果の近さを保証しない。Lipschitz boundは非常に緩くなり得る。
3. **Warm-up / memory**。anchorのbase KVとagent別offsetを持つため、poolのGPU/CPU配置、lookupとcopy、prompt template変化に依存。
4. **実験範囲**。主な結果は単一H100、7–8B級、定型multi-agent prompt。異種agent checkpoint、大規模分散、複雑なmulti-document RAGの一般性は未実証。
5. **比較の注意**。CacheBlendはvLLM実装をそのまま比較したのではなく、Hugging Face環境への再実装。reuse率の定義も異なる。

## Taxonomy・既存研究との技術的差分

| 手法 | reuse単位 / signal | repair方式 | model更新 | 最適化対象 |
|---|---|---|---|---|
| [CacheBlend](2024-2405.16444-cacheblend.md) | chunk内token、KV差分 | 選択的token再計算 | 不要 | full-prefill品質近似 |
| [KVShare](2025-2503.16525-kvshare.md) | semantic span / similarity | semantic alignment・differential editing | 論文条件に依存 | semantic sharingのhit率と品質 |
| [ProphetKV](2026-2602.02579-prophetkv.md) | query-attention重要token | selective recomputation | 不要 | query関連の品質修復 |
| [A³](2025-2511.17560-a3.md) | question-relevant chunk/token | attention-aware KV fusion | 論文条件に依存 | task utilityとTTFT |
| **KVComm** | agent placeholder、embedding距離、prefix | **RoPE位置整合 + anchor offset補間** | 不要 | cross-contextでprefillを極力省略 |

KVCommの独自性は**差分の大きいtokenを再計算する代わりに、過去の類似文脈からその差分を予測**する点。KVShareのsemantic matchingと「類似性を利用する」点は共通だが、同一手法ではない。ProphetKV/A³のquestion relevanceによる選択とも別軸。
