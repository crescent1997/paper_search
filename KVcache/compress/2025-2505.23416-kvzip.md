# KVzip: Query-Agnostic KV Cache Compression with Context Reconstruction

## 概要と選定理由

**compress → query-agnostic KV token eviction（reuse-compatible compression）**。SnapKV/PyramidKV等は、prefill末尾や質問に関連したattentionから「今のqueryに重要なtoken」を残す。ところが同じ文書を複数の異なる質問で使うと、**最初のquery向けに削ったKVを次のqueryに流用するだけでは性能が落ちる**。KVzipはqueryをまだ知らない段階で、後の任意のqueryにも有用な情報を残すという目的に変更する。

中心となる仮説は、**圧縮後のKVだけを見て元のcontextを復元できるなら、多様な下流queryにも必要な情報を保持できている**というもの。追加の学習ではなく、同じLLMによるcontext reconstructionのattentionからKV重要度を測定する。NeurIPS 2025 Main採択。

## 問題設定と従来法との差

Context $c$ を一度prefillして得た$KV_c$から、cache budget $r$で部分集合$KV'_c$を作る。目的は特定の$q_1$だけでなく、将来の複数queryに対して

$$
f_{\mathrm{LM}}(q\mid KV'_c)\approx f_{\mathrm{LM}}(q\mid KV_c),\quad \forall q
$$

が経験的に成り立つこと（論文Eq. 1）。「すべてのquery」の厳密保証を与えるものではない。単一queryでSnapKVが良くても、別queryに流用すると90%のcache budget（10% eviction）でも劣化する例を示す（Figure 2）。

**KVShare/CacheBlendとの違い**：KVzipは「異なる文書のKVを結合して壊れた表現を修復」するのではなく、**既に正しく計算済みの1つのcontext KVから汎用性を損ねにくい要素を選んで捨てる**。複数requestで同じ圧縮cacheを再利用できるが、prefixが変わることによるcontext dependencyの補正は対象外。

## 手法

### 1. Context reconstructionでattentionを取得

最初にcontext $c$ を通常prefillし、$KV_c$を得る。次に`Repeat the previous context:`というrepeat promptと元contextをつないだ系列を、**teacher forcingの単一forward**で処理する。自由生成でcontextを1tokenずつ再現する必要はない。新しいquery tokenが、元context側のKeyへ与えるattentionを抽出する。

GQAのKV head $h$、layer $l$、query head群$g$、再構成入力のquery位置$i$、元contextのKey位置$j$に対し、元context領域へのattention $\bar A_{l,h}[g,i,j]$を取り出す。元contextのtoken $j$の重要度は

$$
S_{l,h,j}=\max_{g,i}\bar A_{l,h}[g,i,j]
$$

（論文Eq. 2）。つまり**「再構成中に一度でも強く参照された元contextのKV」を残す**。平均attentionでなくmaxを使うことで、特定の箇所を再現するのに不可欠な位置を拾う。Layer/Head/Tokenごとに$S$を持つ。

### 2. Head間budget allocationとeviction

$S$の高いKV pairを残す。論文の主評価は**head間で非一様budget**を配り、全headの重要度から上位$r$%を保持する。System promptのKVは保持。DuoAttentionのようなhead単位のevictionにも拡張でき、その場合は各headのtoken方向max scoreを使う。

これはtoken-level evictionであり、**保存するbit幅を変える量子化でも、K/Vを再計算する修復でもない**。QServeの4-bit KV量子化と組み合わせた実験がある。

### 3. 長文に対するchunked scoring

再構成系列全体に対してattentionをmaterializeすると、$O(n_c^2)$のscore matrixが必要になる。KVzipは元contextを$m=2K$ token程度のchunkに分割し、各chunkについてrepeat prompt+chunkをteacher forcingして、元contextの当該chunkに対するscoreを計算する。2つ目以降のchunkでは前chunk末尾8 tokensをrepeat promptに入れる（Figure 7）。

score matrixを作る部分の複雑度は、chunkごと$O(m^2)$、全chunkで$O(mn_c)$、peak score memory $O(m^2)$。**ただしモデルのforward自体は既存context KVにattentionするため、全体計算量が$O(n_c)$になるわけではない**。論文はfull prefillに対してscoring処理の計算量がおよそ2倍と分析する。実際の初期prefillとscoringの合計では一回限りのsetup overheadが大きい。

### 4. Context-independent head-level variant

一つの代表context（88K tokenの英語書籍）でhead重要度を事前計算し、モデル共通のhead scoreとして再利用するvariantも提案。DuoAttentionのpasskey向けhead profilingを、自然文書のreconstruction scoreで置き換える。contextごとのscoringが不要になる代わりに、細かなtoken-level適応性は弱まる。

## Experiment Setup

- **Model**：Qwen2.5-7B-1M、Qwen2.5-14B-1M、Llama-3.1-8B、Gemma3-12B等。Gemma3はglobal attention層のみevict。
- **Dataset**：SQuAD、GSM8K、Needle-in-a-Haystack、SCBenchの9タスク（RULER/∞Bench由来を含む）、計12 benchmark。multi-query設定を重視。context 100〜170K tokens。
- **Baseline**：H2O、SnapKV、PyramidKV。head-level版はDuoAttention。全baselineにも非一様head budgetを適用して公平性を確保。
- **Hardware**：NVIDIA A100 80GB、BF16、greedy decode。FlashAttention-2 variable-length実装。
- **Metrics**：各taskのaccuracy/pass@1/ROUGE、cache budget、decode attention latency、cache memory、scoring setup時間。

## Main Results

### Query-agnostic multi-query品質

Qwen2.5-7B-1MのFigure 9では、retrieval-intensiveなNIAH/Retr.KV等で**30% cache retention**でも比較的良い精度を維持（Retr.Prefix-Suffixは例外）。QAやGSM8K等のcontextual understandingでも20–30% retentionで劣化が小さい条件が多い。冗長性の高いtaskは10%まで保持率を下げても耐える例がある。ただし、**全12タスクで30%が無損失という意味ではない**。

### Decode memory / latency（Figure 8、A100）

124K-tokenのLlama-3.1-8Bでcache retentionを100%→40%に下げると、KV memoryは**16.3→6.5 GB**、layer当たりattention latencyは**0.39→0.22 ms**。20% retentionでは3.3GB / 0.17ms。**約2×はdecode attention kernelの速度改善**であり、追加のscoring/prefillまで含めたend-to-end TTFTの高速化ではない。

### 量子化併用（Figure 10）

Llama3-8B、124K inputで、FP16 KV 16.3GBから、4-bit KV + 70% evictionで**1.2GB**まで削減した例を報告。これは**eviction単独の効果ではなく、量子化併用**の結果。

## 主要ablationと注意点

1. **Scoring input（Figure 12）**：reconstructionはfirst token、last token、一般promptからのattention scoringよりSQuAD multi-queryで優位。単なる長文末尾Queryでなくcontext全体を再構成することが効く。
2. **Chunk size（Figure 8b）**：0.5K/1K/2K/4K/8Kでscoring時間は約95.8/75.4/**65.9**/71.9/87.2秒、peak memoryは約30.5/30.7/**31.1**/32.5/38.8GB（124K、A100）。2Kはこの条件で良好なバランス。
3. **Scoring overhead**：2Kで約65.9秒のscoring。論文は初回prefillの約2倍の計算量、追加peak memoryは2%未満と報告。**短寿命context・1回限りqueryでは回収しにくい**。
4. **Context-independent mode（Figure 11）**：DuoAttentionのhead score最適化（8 GPUで数時間）に対し、KVzipは数forward・1分以内の事前計算でより高い平均相対性能を報告。
5. **Head allocation / kernel**：非一様head budgetは圧縮効率を高めるが、実装ではheadごとの可変KV長とmetadataが必要。FlashAttention-2のvarlenなどに依存する。

## Limitations・研究上の示唆

- **Query-agnosticの代償**：future queryの分布に関する厳密保証はない。reconstructionが取り出さない情報を問う特殊queryでは失敗し得る。
- **初回コスト**：reconstruction scoringのforwardは重い。reuse回数$N$が少ないと、削減したdecode時間よりsetup costが大きい。粗く$T_{\mathrm{score}} < N\cdot\Delta T_{\mathrm{decode}}$を満たすかが重要。
- **KV位置の整合性**：元contextの一部KVをevictする方式であり、別々にprefillした複数chunkを連結してfull-prefillを再現する方法ではない。
- **Behavior変化**：論文Table 1では、full KVで拒否した個人情報への質問に、圧縮後cacheで応じる例を報告。**compressionでsafety behaviorが変わる可能性**を明記すべき。
- **Kernel実装依存**：variable-length head KV、metadata、scoring kernelのI/Oを含む実測が必要。

## Taxonomy・既存研究との差分

| 手法 | Cacheを作るsignal | reuse可能な範囲 | 操作 |
|---|---|---|---|
| [SnapKV](2024-2404.14469-snapkv.md) | prefill末尾Query attention | 主にそのquery | token eviction |
| [PyramidKV](2024-2406.02069-pyramidkv.md) | layer別attention | 主にそのquery | layer budget付きeviction |
| [DuoAttention](../access/2024-2410.10819-duoattention.md) | profilingでretrieval headを同定 | モデル横断的なhead選択 | streaming head化 |
| **KVzip** | **context reconstruction attention** | **同一contextへの多様なquery** | token/head eviction |
| [KVShare](../reuse/2025-2503.16525-kvshare.md) | semantic similarity | 異なるsemantic span/request | alignment・editing |
| [ProphetKV](../reuse/2026-2602.02579-prophetkv.md) | query attention | queryに関係する再利用token | selective recomputation |
| [A³](../reuse/2025-2511.17560-a3.md) | question-relevant chunk | RAG query向け | KV fusion |

KVzipの独自性は**圧縮を先に行い、質問を知らない段階で汎用性を確保する**点。KVShare/ProphetKV/A³の「再利用KVをどう修復するか」とは目的関数が異なるが、**KVzipで保存容量を減らしたcacheを別のreuse手法が読み込む**という併用は研究余地がある。
