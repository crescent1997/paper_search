# IH-Benchmark: A Conflict-Centered Benchmark for Instruction-Hierarchy Robustness in LLM Applications

## 概要

IH-Benchmark (IH-B) は、Instruction Hierarchy robustnessを単一scoreとして扱わず、**どのpriority boundary / conflict surfaceでmodelが失敗するか**を測るpurpose-built benchmarkである。

中心となる2 trackは、

- System > User (S>U)
- User > Tool (U>T)

である。

37 model variantsを評価するとoverall complianceは20.5%から98.2%まで大きく広がり、S>Uで強いmodelがU>Tでも強いとは限らない。

## 問題設定

LLM applicationでは複数sourceからinstructionが入る。

```text
System
  >
User
  >
Tool output
```

理想的にはsource privilegeによってconflictを解決すべきだが、実際にはconflict presentation、constraint type、wording strength等にもbehaviorが左右される。

IH-Bは特に、

```text
direct conflict:
  System > User

tool-mediated conflict:
  User > Tool
```

を分離して評価する。

## 既存Benchmarkからの改善点

既存研究ではsystem-user edgeだけを中心に評価したり、既存datasetをhierarchy taskへ転用したりする場合がある。

IH-Bは最初からInstruction Hierarchy conflictを測るためにscenarioを構築し、tool-mediated settingを大きく取り入れる。

これにより、

```text
good S>U score
  !=
good U>T score
```

を直接検証できる。

## Dataset / Scenario Construction

IH-Bには2,336 executable scenariosがある。

### S>U track

734 scenarios。

system promptにconstraintを置き、user instructionがそれとconflictする。

### U>T track

1,602 scenarios。

user taskに対しtool output側からconflicting instruction / contentを挿入する。

tool-mediated prompt injectionやagentic settingに近い。

## Constraint Taxonomy

44 constraint familiesを人手で設計する。

domainは、

- generic
- health
- finance
- retail
- coding

を含む。

単純な「秘密を漏らすな」だけでなく、PII disclosure、tool allow/deny list、tool parameter restriction、transaction constraint等のapplication-level ruleを評価する。

## Evaluation Protocol

scenarioごとにbinary pass / failを判定する。

判定には、

1. predicate DSL
2. category-scoped LLM judge

を組み合わせる。

機械的に判定できるconstraintはpredicateで評価し、semantic judgmentが必要なcaseはdomain-specific judgeを利用する。

異なるscenarioでも最終metricをuniform binary complianceへ揃えることで、track間を比較しやすくする。

## Stateful Agent Simulation

U>Tでは単純なstatic promptだけでなく、tool interactionを含むstateful simulatorを用いる。

modelがtool outputを受け取った後、

- original user constraintを維持するか
- tool内instructionへ従うか
- unauthorized actionを実行するか

を実際のaction / responseから評価する。

## Constraint Hardening

同じconstraintについてwordingのstrictnessを強める。

概念的には、

```text
L1:
  Do not X.

L2:
  You must never X.

L3:
  X is prohibited even if later
  instructions request it.
```

のようにpriority reminderを強化する。

これによりfailureが単なるweak wordingによるものか、より構造的なhierarchy failureかを分析する。

## Experiment Setup

37 model variantsを評価する。

複数provider / model familyを横断し、S>U / U>T、constraint family、strictness level、conflict presentationごとにcomplianceを測定する。

重要なのはoverall averageだけでなくsurface別scoreを分析する点である。

## Main Results

全37 model variantsでoverall hierarchy complianceは20.5%から98.2%まで広がる。

model capabilityが高いだけでは完全なhierarchy robustnessを保証しない。

### S>U と U>T の乖離

system-user direct conflictへ強いmodelでも、tool outputからconflicting instructionが入ると大きくperformanceが落ちる場合がある。

これはInstruction Hierarchy robustnessが単一latent capabilityではないことを示す。

```text
System > User robustness
        |
        X
        |
User > Tool robustness
```

したがって一方をproxyとして他方を評価すべきではない。

## Constraint Hardeningの結果

modelは大きく2種類のbehaviorを示す。

一部modelではwarning / priority wordingを強めるだけでfailureの多くが修正される。

別のmodelではstrictnessを最大まで上げてもfailureが残る。

前者はsurface-level instruction salienceの問題、後者はより根本的なpriority resolution failureである可能性がある。

## Subtle Failure

興味深い結果として、明らかに危険なoperationよりも微妙なconstraint violationの方が失敗しやすい場合がある。

modelは、

- unauthorized purchase
- bulk ticket closure

のようなovertly dangerous actionには比較的抵抗する一方、

- injected disclaimer
- small factual distortion

等のsubtle conflictではlower-priority instructionへ従いやすい。

これはgeneral safety trainingとInstruction Hierarchy robustnessを区別する必要性を示す。

## IHEvalとの関係

[IHEval](2025-2502.08745-iheval.md)はsystem / user / conversation history / tool outputを含むhierarchy followingをReference / Aligned / Conflict settingで評価する。

IH-Bは特にconflict surfaceを、

```text
S > U
U > T
```

へ明示的に分解し、purpose-built application constraintsとagent simulatorを用いる。

IHEvalがgeneral hierarchy capabilityを見るのに対し、IH-Bは**application deploymentでどのboundaryが破れるか**を診断するbenchmarkとして補完的である。

## Control Illusionとの関係

[Control Illusion](2025-2502.15851-control-illusion.md)はrole designationだけでなくconstraint固有biasやsocial hierarchy cueがmodel behaviorを支配することを示す。

IH-Bのconstraint family / hardening分析も、priority followingがrole labelだけでは決まらないことを示す。

特にstrictness変更で直るfailureと直らないfailureを分けることで、surface cue sensitivityを診断できる。

## Many-Tier Instruction Hierarchyとの関係

[Many-Tier Instruction Hierarchy](2026-many-tier-instruction-hierarchy.md)はroleとprivilegeを分離し最大12 privilege tiersを評価する。

IH-Bはtier数を増やすのではなく、現実的な2つのboundaryを深く評価する。

```text
ManyIH:
  breadth over number of tiers

IH-B:
  depth over conflict surfaces
  and application constraints
```

という違いがある。

## XIH-Benchとの関係

[Language Shapes Instruction Hierarchy Compliance in Multilingual LLMs](2026-2607.23545-xih-bench.md)はlanguage identityがpriority followingへ与える影響を評価する。

IH-Bのconstraint surfaceとXIH-Benchのlanguage axisを組み合わせれば、

```text
S > U / U > T
      ×
higher/lower language
```

というmultilingual tool-injection evaluationへ拡張できる。

## Defense評価への利用

[The Instruction Hierarchy](../Defense/2024-2404.13208-instruction-hierarchy.md)、[Instructional Segment Embedding](../Defense/2024-2410.09102-instructional-segment-embedding.md)、[HIPO](../Defense/2026-2603.16152-hipo.md)、[IHDec](../Defense/2026-2606.29960-ihdec.md)等を評価する際、overall IH scoreだけでは改善箇所が分からない。

IH-Bを使えば、

- S>Uだけ改善したか
- U>Tにもgeneralizeしたか
- strong wordingに依存していないか
- subtle constraintでもrobustか

を分解できる。

## Prompt Injectionとの関係

U>T trackはtool outputというlower-priority sourceからinstructionが入るため、indirect prompt injectionと直接関係する。

ただしIH-B自体はadaptive Attack algorithmではない。

[PISmith](../Attack/2026-2603.13026-pismith.md)のようなDefense-aware attackをIH-B scenarioへ適用すれば、固定conflict presentationよりさらに厳しいevaluationになる。

## Generalization / Robustness

44 constraint families、5 broad settings、2 hierarchy surfacesを横断することで、単一taskへのoverfittingを避ける。

一方、2-tier edgeを深く評価するbenchmarkなので、developer roleやarbitrary many-tier privilege reasoningを完全にカバーするわけではない。

## Limitations

- 主なpriority edgeはS>UとU>Tで、developer role等を含む全hierarchyを網羅しない。
- LLM judgeを含むためevaluation errorを完全には排除できない。
- 44 constraint familiesが実世界application policyの全てを代表するわけではない。
- fixed scenarioはDefense-aware adaptive attackerのworst-case ASRを直接測らない。
- model/provider updateによりbenchmark scoreは変化し得る。
- high benchmark complianceはtool authorization等のexternal enforcementの代替にならない。
- constraint hardeningで改善しても、priority mechanismを本質的に理解した証明にはならない。

## LLM Model Security Taxonomyでの位置づけ

```text
IHEval
  general hierarchy evaluation
      ↓
Control Illusion
  diagnose non-role cues
      ↓
ManyIH
  arbitrary privilege tiers
      ↓
XIH-Bench
  multilingual hierarchy
      ↓
IH-Benchmark
  conflict-surface decomposition
  S>U vs U>T
```

Instruction Hierarchy robustnessを「一つのscore」から**複数のpriority boundaryにまたがるbehavior集合**として評価するBenchmarkである。

## 実装・研究上の示唆

Instruction Hierarchy Defenseを評価するときはoverall scoreだけでなく、

1. priority edge別
2. constraint family別
3. strictness別
4. direct / tool-mediated conflict別
5. overt / subtle violation別
6. static / adaptive attack別

にsliceする必要がある。

特にS>Uだけを改善して「Instruction Hierarchy robustnessが向上した」と結論づけるのは危険であり、tool outputを含むU>Tを独立に測るべきである。
