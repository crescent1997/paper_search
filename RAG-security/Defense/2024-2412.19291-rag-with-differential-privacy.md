# RAG with Differential Privacy

> **要点**：RAGの検索文書をそのままLLMのpromptへ連結すると、回答が特定個人の文書に依存し、PII・機密情報を再出力する可能性がある。DP-RAGは、**retrieval stageとtoken generation stageの双方にDifferential Privacy（DP）を導入**し、1人分の文書が有無を変えても回答分布が大きく変化しないことを目指す。多数の文書で共有される集約的知識は残し、少数の文書にしかない個人固有情報を出しにくくする。

## 概要と研究上の位置づけ

RAGでは、検索されたprivate documentsを単純にcontextへ追加する。generatorが強いinstruction following能力を持つほど、retrieved textをそのまま回答へ含めるriskがある。Output filter、redaction、query-based guardなどは個別の漏洩パターンには有効でも、未知のquery・連続したqueryへの統計的なprivacy保証を与えるとは限らない。

本論文のDP-RAGは、privacy-sensitive dataを使ってLLMを再学習するのではなく、**inference-timeにprivate documentsからtoken分布を集約**する。ここで重要なのは、DP generationだけでなく、retrievalの文書選択が非DPであれば個人の有無によってcontext構成が変わるという問題を考慮している点である。

提案は次の二段階である。

1. **Privacy-unit preserving retrieval**：queryと各documentのsimilarityから、exponential mechanismでDPな選択閾値をサンプリングする。上位文書を直接公開せず、選択が1 privacy unitに過度に依存しないようにする。
2. **Differentially private in-context generation**：選択文書を1つの長いpromptにまとめず、**文書ごとに独立したLLMのnext-token distribution**を計算し、clipping後に集約してDPなnext-token samplingを行う。

原論文は個人の医療情報に関する**集約的な質問**を想定しており、特定の患者の固有情報を正確に答えることを目指していない。個人単位のprivacyを守るなら、そのような回答はむしろ抑制すべきだからである。

## Threat Model / Privacy Model

### 保護対象

- **秘密**：retrieval database内のprivacy unit（通常は個人）に紐づくprivate documents。
- **観測者**：RAGへqueryを送り、生成された回答を観測する外部利用者。出力から特定個人の記録の有無や内容を推定しようとする。
- **Defenderの権限**：retrieval処理、LLMへのprompt構成、token sampling ruleを変更できる。document embeddingsとLLM token distributionsを計算できる。
- **目標**：隣接database `D, D'` が1 privacy unitの有無で異なる場合、回答分布が大きく変化しないようにする。

Differential Privacyは、任意の観測event `S`について

\[
\Pr[\mathcal A(D)\in S]\le e^{\varepsilon}\Pr[\mathcal A(D')\in S]+\delta
\]

を要求する。`ε`が小さいほどprivacyが強く、`δ`は近似DPの例外確率を表す。**個人情報を必ず1文字も出さない**という決定論的保証とは異なり、出力分布の統計的な変化を制限する保証である。

### 最も重要な成立条件：1 document = 1 privacy unit

原論文は、簡単化のため1 documentが1人分の情報だけを含むと仮定する。同一個人の情報が複数documentにまたがる場合、それらを1 privacy unitにgroupingしないと、文書単位DPを個人単位DPとして解釈できない。複数患者を含む共有文書や、重複した記録がある場合も注意が必要である。

また、本文で保護するのは**出力として観測される情報**であり、運用環境の検索ログ、embedding storeへの直接アクセス、外部LLM APIへ送信するprivate context、サーバー側のaccess-pattern leakageをすべて暗号学的に保護する設計ではない。

### 従来RAGとの違い

通常のRAGはtop-k文書を連結し、単一のLLM forward passでtokenを生成する。この方式では、ある患者の1文書がcontextへ追加されるだけで生成確率が大きく変わりうる。

DP-RAGは各文書の寄与を個別に計算・制限するため、**文書間のaggregationがprivacy accountingの単位になる**。その代償として、文書数に比例するLLM計算と、tokenごとのDP budget消費が生じる。

## Method / Algorithm

### 全体構成

```text
User query q
     │
     ▼
Query / document embedding + similarity scores
     │
     ▼
Exponential mechanismでretrieval thresholdをsample
     │
     ▼
Privacy-unitを保ったdocument subset {d_i}
     │
     ├── LLM(q, d_1, generated_prefix) -> token logits/probs
     ├── LLM(q, d_2, generated_prefix) -> token logits/probs
     ├── ...
     └── LLM(q, d_k, generated_prefix) -> token logits/probs
     │
     ▼
各distributionのnormalization / clipping + public prior
     │
     ▼
Exponential mechanismによるDP next-token sampling
     │
     ▼
Prefix更新・privacy budgetのaccounting・次tokenへ
```

### Step 1: RetrievalをDPにする必要性

通常のtop-k検索はdeterministicである。ある文書を1件追加するとtop-kの構成が不連続に変化するため、その後段のDP aggregationを形式的に議論する際、選択された集合の変化も考慮しなければならない。

原論文は、各documentのquery similarity `s_i`を計算し、閾値`τ`以上の文書を選ぶ方式へ置き換える。`τ`をexponential mechanismで選ぶことで、retrieval側にもprivacy costを割り当てる。

### Step 2: DP top-k threshold

候補閾値`τ`に対して、閾値以上の文書数が目標`k`からどれだけずれるかをutilityとする。

\[
U_{top-k}(\tau)=-\left|\sum_i\mathbf1[s_i\ge\tau]-k\right|
\]

原論文ではこのutilityのsensitivityを1として、

\[
\Pr(\tau)\propto \exp\left(\frac{\varepsilon U_{top-k}(\tau)}{2}\right)
\]

からthresholdをsampleする。これにより「厳密にk件を返す」よりも、privacyを保ちながら**k件程度**を選ぶことを目指す。最終的には`τ`以上のsimilarityを持つdocumentを抽出する。

この段階では、scoreそのものを利用者に見せることは想定していない。公開される情報とprivacy unitの関係を明確にすることがDPの成立に重要である。

### Step 3: DP top-p threshold

top-k方式ではqueryの選択性が高くても低くても文書数がほぼ固定される。そこで、類似度の集中度に応じて選択文書数を変える**weighted top-p** variantも提案する。

\[
U_{top-p}(\tau)=-\left|\sum_i\mathbf1[s_i\ge\tau]w(s_i)-p\sum_iw(s_i)\right|
\]

で、重み`w(s)`は類似度の相対位置を指数関数的に変換する。`p`は取得したい重みの比率、`α`はscore差の強調度を制御する。これにより、関連文書がごく少ないqueryでは少数、関連文書が広く分布するqueryではより多くのdocumentを選べる。

**理論上の注意**：重みの正規化にdataset依存の`max/min`を使う場合、隣接databaseでのutility sensitivityの扱いを実装と証明で厳密に確認する必要がある。top-kのsensitivity 1という主張を、そのままtop-pの全実装へ自動的に拡張してよいわけではない。

### Step 4: 文書別next-token distribution

選択した`k`文書を連結するのではなく、各文書を独立にcontextへ入れ、共通のgenerated prefixを条件として次token分布

\[
L_{j+1,i}(r)=P(r\mid q,d_i,r_{1:j})
\]

を得る。1文書を追加・削除したときに、主としてその文書に対応するdistributionが変化するように分離するためである。

この設計は通常のRAGと異なり、各tokenで**複数のcontextからのlogit計算**を必要とする。複数文書に共通する事実は多数のdistributionで支持される一方、1文書だけの固有情報はaggregation後に優勢になりにくい。

### Step 5: Distribution normalization / clipping

個々のtoken log-probabilityをそのまま足し合わせると、極端に低い確率値などがutilityのsensitivityを大きくする。そこで原論文は、各document由来のtoken scoreをnormalizationし、範囲をclippingして寄与を制限する。

例えば、各文書のtoken確率をその文書で最も高いtoken確率で割ってshiftする形や、対数確率差へ近づく変換を使い、変換の鋭さを`α`で制御する。小さい`α`ではlog-probability differenceに近く、大きい`α`ではargmaxに近い指示的なscoreとなる。

最終的なutilityは、概念的には

\[
U_{ICL}(r)=\theta\log L_{public}(r)+\sum_i \operatorname{clip}(l_i(r))
\]

の形で、**public prior**と各private documentのbounded contributionを組み合わせる。`θ`はprivate data以外で既に知っている知識をどれだけ重視するかの係数である。

### Step 6: DP next-token sampling / composition

utilityのsensitivity上界を`C`として、next tokenを

\[
\Pr(r_{j+1}=r)\propto\exp\left(\frac{\varepsilon U_{ICL}(r)}{2C}\right)
\]

に従ってsampleする。実際にはretrieval stageと各generation stepのprivacy lossを合成してaccountingする必要がある。原論文はGoogleの`dp_accounting` libraryを利用する。

この方式の本質的なtrade-offは、**長い回答ほどtoken単位のprivacy budgetが蓄積する**ことにある。総budgetを固定するとtokenあたりのprivacy予算が小さくなり、長文回答のqualityが落ちやすい。逆に同じtoken-level予算で長く生成すれば総privacy lossが増える。

## 先行研究からの改善点

### DP fine-tuning / synthetic corpusとの比較

- DP-SGDでLLMをfine-tuneする方式はprivate knowledgeが頻繁に更新される環境で再学習が重い。
- DP synthetic dataを事前生成してRAGに使う方式は、one-timeでprivacy costを払って以後のqueryを通常RAGとして処理できるが、生成されたsynthetic corpusのcoverageとqualityに依存する。
- DP-RAGはprivate original documentsを直接検索し、**queryごとにDP retrieval + DP decoding**する。そのため新しいdocumentを取り込めるが、queryごとにbudgetと推論コストを消費する。

関連する既登録論文：[DP-SynRAG](2025-2510.06719-dp-synrag.md)はprivate corpusをone-timeでDP synthetic corpusへ変換する方式。[Privacy-Preserving Retrieval-Augmented Generation with Differential Privacy](2024-2412.04697-privacy-preserving-rag-differential-privacy.md)はretrieval groupsとvotingを使ってtoken budget消費を抑える方式であり、同じdocument-level privacy問題への別の設計解である。

### Non-DP privacy defenseとの比較

- [SAGE](2024-2406.14773-sage.md)：pure synthetic corpusによるprivacy mitigation。DP-RAGは形式的なprivacy parameterを明示する。
- [RAGFort](2025-2511.10128-ragfort.md)：corpus stealingのexploration/exploitationを検知・抑止するheuristic defense。DP-RAGは個々の文書の寄与を制限するため、特定のattack query patternへの依存が小さい。
- [RAG-CT](2026-2609.16095-rag-ct.md)：retrieval similarity分布からPII extraction queryを検知するtraining-free defense。DP-RAGは異常queryを判定するのではなく、回答生成の確率分布を保護する。
- [ABack](2025-2508.06087-adaptive-backtracking-aback.md)：decoding時のPII兆候を検知してbacktrackingする。DP-RAGはPII検出器を前提とせず、privacy unitの統計的な寄与を制限する。

### Attackとの関係

[The Good and The Bad](../Attack/2024-2402.16893-the-good-and-the-bad.md)、[Follow My Instruction and Spill the Beans](../Attack/2024-2402.17840-follow-my-instruction-and-spill-the-beans.md)、[RAG-Thief / CopyBreakRAG](../Attack/2024-2411.14110-feedback-guided-extraction-copybreakrag.md)のような攻撃は、retrieved private dataが生成へ反映されることを利用する。DP-RAGはその情報経路に直接制限をかける設計だが、**これらのattackに対するend-to-end ASR/coverageを原論文が比較したわけではない**。形式的なprivacy guaranteeと、実測のcorpus reconstruction成功率は別の評価軸である。

## Experiment Setup

### Dataset / Task

原論文は約**5,000件のsynthetic medical documents**を用いる。データは医師・患者間の質問応答に類する文書で、特定の症状と疾患の関係を含む。synthetic dataを使う理由は、LLMが事前学習で正解を知っていることによる混同を減らし、private documentsの寄与を評価しやすくするためである。

公開dataset：`sarus-tech/medical_dirichlet_phi3`（Hugging Face）。実装：`sarus-tech/dp-rag`（GitHub）。

主なtaskは、文書集合に含まれる症状や疾患の**集約的な情報を質問し、どの程度正しく回答できるか**を測ること。1人の患者の氏名や個別診断をそのまま復元することはutility目標ではない。

### Privacy setting / Metrics

- 文書数：約5,000。
- 代表的privacy parameters：**ε ≈ 5、δ = 10⁻³**。
- utility：特定の疾患情報を回答できるaccuracy。横軸は同じ知識を含むdocument数（knowledge specificity / frequency）。
- private retrieval：top-kまたはtop-pのthreshold sampling。
- private generation：文書別token distributionのaggregationとDP sampling。

**実験上の制約**：本文で中心となる評価は、document frequencyと回答accuracyの関係であり、現代の多様なRAG attackに対するASR、long-context throughput、低FPRでのMIA resistanceを網羅的に比較するものではない。これらの指標を測ったと誤読しない。

## Main Results

### Privacy–utility trade-off

Figure 6では、同じ情報を含むdocumentが増えるほどaccuracyが向上する。原論文は**約100文書以上が類似の情報を持つと、accuracyが実用的な水準になる**と報告している。

逆に、情報を含むdocumentが少数であれば、DP aggregationはその知識を回答へ出しにくくする。これは医療情報のようなprivate datasetでは望ましい場合がある。特定の個人だけが持つ情報を生成することは、privacy保護の観点では抑制すべきだからである。

この結果は、privacy-preserving RAGの評価で**一般的なQA accuracyだけでなく、答えのsupporting-document frequencyを明示する必要**があることを示す。元々1件しかない事実と、100件に共通する事実を同じaccuracy目標で評価すると、privacyとutilityのtrade-offを誤解する。

### なぜ文書数が重要か

各privacy unitのtoken utility寄与がclippingされるため、同じ答えを支持するdocumentが多数ある場合、そのtokenはaggregate utilityで優勢になる。一方、ある患者の記録だけに含まれる固有のtokenは、1文書分の寄与しか得られず、DP samplingで支配的になりにくい。

ここで`ε`を増やすと出力分布がutility最大化へ近づく一方、privacy lossも増える。`θ`を大きくしてpublic priorを重視すると、private dataがなくても答えられる部分の生成は安定するが、private documentsだけに依存する知識の反映は弱くなる。

### 報告結果の解釈上の注意

本論文のaccuracy結果を、**「すべてのprivate documentsからのverbatim extractionがゼロになる」**という主張へ拡張することはできない。DPの保証は隣接dataset間の出力分布に関するものであり、実際のprivacy lossはbudget accounting、privacy unitのgrouping、出力以外のside channelsの有無に依存する。

また、原論文ではDP budgetの下での集約的QAを中心に評価しているため、retriever/generatorを変えたときの精度、攻撃者が大量queryを行ったときのprivacy accountantの運用、商用RAGでのlatencyとcostの定量比較は追加検証が必要である。

## Ablation / Robustness / Additional Evaluation

### Top-kとtop-pの役割

Top-kのutilityは「ほぼk件を選ぶ」ことに最適化される。一方top-pはsimilarity distributionの形に応じて選択数を変える。selective queryでは少数、broad queryでは多数を集められる可能性がある。privacyの強さはthreshold samplingのsensitivityとbudgetに依存するため、query adaptivityを強くするときはprivacy analysisも同時に見直す必要がある。

### Public priorの役割

private documents由来のtoken distributionだけでなくpublic priorをutilityに混ぜることで、private corpusに頼る必要のないtokenを安定化する。これは後続のDPSparseVoteRAG等が、private knowledge不要なtokenのbudget消費を抑えようとする設計とも問題意識が近い。

### Response length

原論文の結論では、短い回答へ制限することをprivacy–utility trade-off改善の一つとして挙げる。autoregressive生成ではtokenごとのprivacy costを合成するため、回答長が長いほどbudget設計が厳しくなる。long-form RAGを対象とする場合、短答型の実験結果をそのまま当てはめない。

### Defense evaluationの欠落

原論文はDP mechanismの構成とsynthetic medical dataset上のutility評価が中心であり、RAG-Thief、IKEA、MEntA等の具体的なattackを用いたlarge-scale benchmarkは報告していない。特に**multi-turn adaptive attacker**に対する累積budget運用は、本手法を現代のRAG security evaluationへ組み込む際の必須課題である。

## Limitations / 成立条件

1. **Privacy unit assumption**：1 documentが1人分の情報であること。同一人物が複数documentに出るとgroup privacyが必要。
2. **Utility depends on redundancy**：複数documentに支持される知識は保持できるが、稀少な事実は抑制される。専門的・固有情報のQAではutility低下が大きい。
3. **Token-level cost**：選択した各documentに対するnext-token distributionを計算するため、通常RAGより高い計算負荷を持つ。
4. **Repeated-query composition**：単発回答の`ε`だけでなく、利用者が繰り返しqueryを投げる際の累積privacy budgetを管理しなければならない。
5. **Output vs infrastructure privacy**：外部APIへのprivate document送信、index access patterns、operatorのログ閲覧、retrieval embeddingsの直接流出はこの機構だけでは防げない。
6. **DP threshold implementation**：score normalization、top-p weighting、privacy unit grouping、公開されるintermediate stateが理論仮定に一致しているかを確認する必要がある。
7. **Synthetic-only evaluation**：医療風のsynthetic corpusでのaggregate QA中心であり、実データの長文・重複・複数患者文書で同等の性能になる保証はない。
8. **DP is not an absolute refusal policy**：DPは統計的な個人の寄与を制限するが、特定の禁止文字列を絶対に出さないというcontent policyではない。

## RAG Security Taxonomyでの位置づけ

| 軸 | DP-RAG |
|---|---|
| Category | Defense |
| Protected asset | Private retrieval datastore内の個人単位情報 |
| Attacker access | 外部query / output観測、繰り返しqueryの可能性 |
| Defense layer | Retrieval-time + Decoding-time |
| Primitive | Exponential mechanism / clipping / private token aggregation |
| Formal objective | `(ε,δ)`-DP（privacy-unit単位） |
| Primary utility target | 多数の文書に共有されるaggregate knowledge |
| 対象外 | 直接DBアクセス、API送信時の秘匿、side-channelの全面保護 |
| 実装上の課題 | k文書×生成tokenの計算、privacy accounting、grouping |

## 実装・研究上の示唆

### vLLM / KV-cache / FlashAttentionとの接点

DP-RAGでは、同じqueryとgenerated prefixに対し、異なるprivate document contextを与えた`k`本のnext-token distributionを計算する。通常のRAGと違い、**単一contextのKV cacheだけでは足りず、文書別branchのKV state**が必要となる。

実装候補としては、(i) query prefixの共有可能な部分のKV再利用、(ii) 文書別forwardのbatched execution、(iii) logitsだけを集めて大きなattention tensorを保持しない構成、(iv) tokenごとのprivacy samplingをhost/device間の同期を抑えて実行する構成が考えられる。ただしこれらは**本論文で検証された最適化ではなく、推論基盤へ適用する場合の研究課題**である。

### Evaluation protocolへの示唆

DP-RAGを評価する際は、一般QA accuracyだけでなく、(1) 1個人にしかない情報の漏洩、(2) 10/100個人に共通する情報のutility、(3) multi-turn adaptive extractionの累積privacy loss、(4) 1回答あたりのforward回数とlatency、(5) near-duplicateや同一個人の複数文書、を分けて測るべきである。

特にRAG-CTやRAGFortのようなattack detection型defenseと比較するときは、**DPの形式的なguarantee**と**実測のattack success rate**を別々に報告する必要がある。検出器が正常queryを誤って遮断するfalse-positive問題と、DPが稀少な知識を出せなくするutility低下は異なるtrade-offである。
