# Defeating Prompt Injections by Design

## 概要

本論文はCaMeL（Capabilities for Machine Learning）を提案し、prompt injectionを「LLMがuntrusted textをinstructionとして誤解するclassification problem」として完全に解決しようとするのではなく、**仮にLLMが騙されてもuntrusted data由来のdecisionに危険なprivilegeを与えない**architectureを設計する。

したがって[StruQ](2024-2402.06363-struq.md)、[The Instruction Hierarchy](2024-2404.13208-instruction-hierarchy.md)、[SecAlign](2024-2410.05451-secalign.md)とは異なり、model-level alignmentよりOS / programming-language securityに近いprivilege separationである。

## 問題設定 / Threat Model

agentic LLMがemail、web、documents、tool outputs等のuntrusted dataを読みながら、send email、database update、file access等のprivileged toolを実行できる状況を考える。

攻撃者はuntrusted contentへprompt injectionを埋め込める。従来agentでは同じLLMがdataを解釈し、次のactionを決定し、tool argumentsまで生成するため、injected instructionがagentのauthorityをそのまま利用できる。

CaMeLはLLMがinjectionを見分けられることをsecurity assumptionにしない。代わりに、**untrusted valueから派生したdecisionがどのprivileged operationへ影響できるか**をsystem側で追跡・制限する。

## 先行研究からの改善点

prompt filtering、instruction hierarchy、adversarial training等は「modelが正しくinstruction sourceを識別する」ことに依存する。このbehavioral guaranteeはadaptive attackに対して破られる可能性がある。

CaMeLはSaltzer & Schroeder型のleast privilege、capability security、information-flow controlの考え方をLLM agentへ持ち込み、model predictionが誤ってもsecurity boundaryを越えにくい構造を作る。

## Method / Architecture

### Privileged LLM (P-LLM)

trustedなuser requestを読み、taskを実行するprogram / planを生成する。重要なのは、P-LLMにはuntrusted tool outputを直接見せないことである。したがってexternal data内のprompt injectionがprivileged planning logicを書き換える経路を減らす。

### Quarantined LLM (Q-LLM)

untrusted dataの解析、抽出、分類等を担当する。Q-LLMはattacker-controlled instructionを見る可能性があるためcompromisedであると仮定するが、privileged toolへ直接アクセスするauthorityを持たない。

### Capability / Provenance Tracking

program中のvalueについて由来と許可された利用範囲を追跡する。例えばemail本文から抽出された文字列が、そのまま別recipientへのsend-email destinationとして使用される場合、untrusted provenanceを持つvalueがsensitive sinkへ流れたことを検出できる。

### Security Policies

tool invocation時に、argumentのprovenance / capabilityがpolicyを満たすか検証する。つまりsecurity decisionをLLMの自然言語判断だけに委ねず、deterministic enforcement layerへ移す。

## Experiment Setup

AgentDojo等のagent benchmarkを用い、benign user taskをどの程度完了できるかと、prompt injection下でsecurity policyを守れるかを同時に評価する。

比較対象は通常のLLM agentやprompt-injection defenseを含み、securityだけでなくutility loss、token overheadも測定する。

## Main Results

undefended agentが処理できるtaskの約84%に対し、CaMeLは約**77%のtaskをsecurity guarantee付きで解決**できると報告する。すなわち完全なutility維持ではないが、かなりのtask coverageを保ちながらprivilege separationを導入できる。

一方、architectureの複雑化によりtoken overheadが発生し、代表値ではmedian input token costが約**2.82×**、output token costが約**2.73×**になる。

このtrade-offはmodel-only defenseと大きく異なる。CaMeLは追加inference / program execution costを払ってsecurity boundaryをsystem側へ移す。

## Security Properties / Robustness

CaMeLの強みは、未知のprompt injection文字列に対するclassifier generalizationをsecurityの中心に置かない点である。Q-LLMが完全にattackerのinstructionへ従ったとしても、そのoutputにprivileged capabilityがなければsensitive actionを直接実行できない。

これはInstruction Hierarchy型の

```text
model should ignore lower-priority instruction
```

に対し、CaMeLでは

```text
lower-trust computation must not possess higher privilege
```

をsystem invariantとして実装する違いである。

## Limitations

CaMeLはすべてのagent taskを容易に表現できるわけではない。特にuntrusted dataに依存してcontrol flowやprivileged actionを動的に決定しなければならないtaskでは、strict information-flow policyとutilityが衝突する。

またside channel、implicit flow、policy specification error、tool semanticsの不完全なmodeling等は別問題として残る。

さらに複数LLM call、provenance tracking、program executionを必要とするため、latency / token cost / implementation complexityがmodel-only defenseより大きい。

## LLM Model Security Taxonomyでの位置づけ

本repositoryではDefenseに置くが、厳密には**model-level defenseではなくsystem-level architectural privilege separation**である。

```text
Model-level
  StruQ / Instruction Hierarchy / ISE / SecAlign
      modelにtrust hierarchy遵守を学習

System-level
  CaMeL
      modelを完全には信用せずcapabilityで権限を強制
```

この対比は重要で、両者は排他的ではない。hierarchy-aware modelをCaMeLのP-LLM/Q-LLMに用いればdefense in depthになる。

## 実装・研究上の示唆

LLM model側のinstruction hierarchyが100% reliableでない限り、金銭送金、メール送信、credential access等のhigh-impact toolではexternal enforcementを併用する設計が合理的である。

研究上は、model-level benchmarkのASRだけでなく、compromised modelを仮定した際にsystemがどのauthorityを保持するかを評価する必要がある。Instruction Priority研究とcapability securityの接点を示す比較対象として価値が高い。
