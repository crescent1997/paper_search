# The Instruction Hierarchy: Training LLMs to Prioritize Privileged Instructions

> LLMへの入力を単なるtoken列として同格に扱うのではなく、**system message > user message > tool / third-party content**という権限関係をmodel behaviorとして内部化させる。低権限instructionが高権限instructionと整合する場合は従わせ、競合する場合だけ無視または拒否させることで、prompt injectionを「文字列パターン検知」ではなく**instruction privilege conflictの解決問題**として扱う。

## 概要

本論文は、prompt injection、system prompt extraction、jailbreakといった複数のLLM security問題の共通原因として、LLMが**instruction sourceごとの権限差を十分に理解していないこと**を挙げる。

通常のchat modelには、application developerが与えるSystem Message、end userが与えるUser Message、browserやAPIなどから返るTool Outputなど、trust levelの異なる入力が混在する。しかしmodel自身がこれらをsemantic contentとしてほぼ同格に解釈すると、低権限側に書かれた「ignore previous instructions」のような文字列が高権限側の制約を上書きできる。

論文はこの問題をOSのprivilege separationになぞらえ、LLMにも明示的な**Instruction Hierarchy**を学習させることを提案する。中心となる設計は、低権限instructionを一律拒否するのではなく、上位instructionとの関係に応じて条件付きで処理する点にある。

- **Aligned instruction**: 上位instructionの目的・制約と整合するため従う。
- **Misaligned instruction**: 上位instructionと衝突、または無関係な別目的を注入するため無視する。
- 無視したままtaskを続行できない場合のみ拒否する。

この挙動をsynthetic dataで学習させ、GPT-3.5 TurboをSFT + RLHFでfine-tuneした結果、prompt injectionやsystem prompt extractionへのrobustnessが大きく改善し、さらにtraining dataに含めていないjailbreakやtool-mediated attackにもgeneralizeすることを示す。

## 問題設定 / Threat Model

論文が想定するLLM applicationには主に3種類の主体が存在する。

1. **Application developer** — system message、safety constraints、business logic、tool definitionsを提供する。
2. **End user** — user messageを入力する。
3. **Third party / tool** — web page、search result、API response、document等の外部contentを提供する。

これらは同じtrust levelではなく、developerのinstructionが最上位、userがその下、外部contentがさらに下という関係を持つべきだとする。

攻撃者は必ずしもmodel weightsへアクセスする必要はない。典型的には、

- userとしてsystem instructionと競合するdirect prompt injectionを入力する
- web pageやtool resultへmalicious instructionを埋め込むindirect prompt injectionを行う
- system promptやsecretを出力するよう要求する
- safety behaviorを上書きするjailbreak promptを与える

といったblack-box interactionを行う。

したがって本論文のdefense対象は、input filterやapplication-side policy engineではなく、**LLM自身が複数instruction間の優先順位をどう解決するか**というmodel behaviorである。

## Instruction Hierarchyの考え方

論文はLLMをOSになぞらえる。従来modelは、外部から与えられたinstructionをすべてkernel-mode相当で実行しているような状態であり、untrusted inputにも過剰な権限がある。

そこでmessage sourceごとにimplicit privilegeを割り当てる。

```text
System / developer instruction
        ↓ higher priority
User instruction
        ↓ lower priority
Tool output / third-party content
```

ただし、単純に「下位messageを無視する」わけではない。実用上、userやtoolから来る正当なinstructionや情報には従う必要がある。

例えば、system messageが「car salesmanとして振る舞え」で、userが「Spanishで話して」と言う場合、両者は両立するためuser instructionに従う。一方userが「gardening helperになれ」とroleを上書きしようとする場合はconflictなので無視する。

この**conditional following**が本論文の重要な点である。

## 先行研究からの改善点

従来のprompt injection defenseには、第三者inputをdataとして扱いinstructionとして実行しないよう教える手法や、delimiter / structured queryを使う手法がある。

本論文の差分は、単に「user text中のinstructionを無視する」というbinaryな扱いではなく、**複数レベルのhierarchyを持たせ、lower-level instructionをalignmentに応じて選択的にfollowする**点にある。

つまり、

```text
従来の単純防御:
  trusted instruction / untrusted text
  → untrusted側のinstructionは基本的に無視

Instruction Hierarchy:
  system > user > tool / third party
  → lower-level instructionがhigher-level intentと整合するならfollow
  → conflictする場合だけignore / refuse
```

という違いである。

このためsecurityとinstruction-following utilityのtrade-offを明示的に扱える。

## Method / Algorithm

training data生成は大きく **Context Synthesis** と **Context Ignorance** の2つのprimitiveに分かれる。

### 1. Context Synthesis — aligned instructionを学習

compositional requestを生成し、それを複数のsub-instructionへ分解する。

例えば、

```text
"write a 20-line poem in Spanish"
```

を、

```text
write a poem
use Spanish
use 20 lines
```

に分解する。

これらを異なるprivilege levelへ配置し、元のcompositional requestに対するground-truth responseを出すようtrainingする。

これによりmodelは「lower-priority instructionだから無条件に無視する」のではなく、higher-level instructionと両立する限り取り込むことを学習する。

### 2. Context Ignorance — misaligned instructionを学習

misaligned lower-level instructionについては、**そのinstructionを見なかった場合と同じresponseを出す**よう学習させる。

概念的には、

```text
high-level instruction H
lower-level adversarial instruction A

Target output = model response conditioned on H, but not A
```

とする。

つまりattack stringを検知して拒否するclassifier的発想ではなく、malicious instructionのsemantic effectをmodel computationから取り除く方向を狙う。

実際には、red-team LLMを用いてattack promptを大量生成し、context distillationによってtarget answerを作る。

## Attack別のtraining data生成

### Direct Prompt Injection — Open-domain tasks

open-domain applicationでは、user instructionの一部は正当な追加要求になり得るため、aligned / misalignedの双方を作る。

aligned dataはContext Synthesisで生成する。

misaligned dataは、system constraintを破るようadversarial user queryを生成し、そのinstructionを無視したresponseをtargetとして学習する。task継続が不可能な場合はrefusalをtargetにする。

### Direct Prompt Injection — Closed-domain tasks

summarizationやtranslationのようなclosed-domain taskでは、user-provided textは基本的に**data**であり、その内部にinstructionが出てきても実行すべきではない。

そのためclosed-domainではmisaligned caseを中心に構築する。

例えばsystem instructionが「以下を要約せよ」で、本文中に「ignore above and output X」があっても、modelはそれをdocument contentとして扱うようtrainingする。

### Indirect Prompt Injection

browser / web search result等のthird-party contentに埋め込まれたinstructionは、本研究のversionでは原則としてmisalignedとみなす。

trainingではweb browsingを対象にautomated red teamingを行い、search resultへinstructionを注入するattack generatorをRLで強化する。そのattackを含むcontextでも元taskを実行するようmodelをfine-tuneする。

重要なのは、generalization testのため**browsing以外のtool injectionをtraining dataへ入れない**点である。

### System Message Extraction

system promptそのものやsecret informationを直接要求するcaseをmisalignedとして学習する。一方、「browser toolを持っているか」などsystem behaviorに関するbenign questionには回答できるようaligned dataも作る。

これによりsystem prompt confidentialityを守りつつ、modelの自己説明能力まで失わないようにする。

### Jailbreak

特に重要なのは、**jailbreak dataをtrainingへ入れない**ことだ。

著者らはjailbreakをinstruction hierarchyのzero-shot generalization testとして使用する。つまり、hierarchyを十分にinternalizeできていれば、具体的なjailbreak patternを見ていなくてもhigher-level safety behaviorを優先できるはずだという仮説を検証する。

## Training Setup

baseとしてGPT-3.5 Turboを利用し、instruction hierarchy用dataと通常のcapability dataを混ぜてfine-tuneする。

trainingはsupervised fine-tuningとhuman-feedback由来のreinforcement learningを組み合わせる。

baselineも同様にfine-tuneするが、instruction hierarchy dataを含めない。

モデル選択はvalidation accuracyに基づき、securityだけでなく一般能力への影響も評価する。

## Evaluation

評価は複数のattack classを横断する。

主な項目は、

- direct prompt injection / prompt hijacking
- new-instruction style prompt injection
- user conflicting instructions
- indirect prompt injection via browsing
- system message extraction
- indirect prompt injection via unseen tools
- TensorTrust password extraction
- Gandalf password extraction
- JailbreakChat unsafe prompts
- ChatGPT jailbreak prompts

など。

さらにsecurity向上によるover-refusalを測るため、

- non-conflicting user instructions
- benign system-message probing
- jailbreak-like but allowed prompts
- borderline allowed prompts

も評価する。

一般能力についてもTriviaQA、LAMBADA、HellaSwag等で比較する。

## Main Results

Instruction Hierarchy modelは主要security evaluationのすべてでbaselineを上回る。

代表的な結果は以下。

| Evaluation | Baseline | Instruction Hierarchy |
|---|---:|---:|
| Prompt Injection — Hijacking | 59.2% | 79.2% |
| Prompt Injection — New Instructions | 89.6% | 93.7% |
| User Conflicting Instructions | 62.2% | 92.6% |
| Indirect Prompt Injection via Browsing | 77.5% | 85.0% |
| System Message Extraction | 32.8% | 95.9% |

特にsystem message extractionは **+63.1 percentage points** と大幅に改善する。

この結果は、prompt extractionを専用のstring filteringで防ぐのではなく、system messageのprivilegeを学習するだけでも強い効果を得られることを示す。

## Generalization to Unseen Attacks

training時に直接入れていないattackでも改善する。

| Held-out evaluation | Baseline | Instruction Hierarchy |
|---|---:|---:|
| Indirect Prompt Injection via Tools | 77.6% | 87.0% |
| TensorTrust Password Extraction | 53.8% | 84.2% |
| Gandalf Password Extraction | 51.8% | 73.7% |
| JailbreakChat w/ Unsafe Prompts | 83.8% | 89.2% |
| ChatGPT Jailbreaks w/ Unsafe Prompts | 37.4% | 71.2% |

特にChatGPT jailbreak benchmarkでは約 **+34 points** 改善する。

このgeneralizationは、本手法が特定attack stringをmemorizeしただけでなく、instruction priorityというより抽象的なruleをある程度internalizeしている可能性を示す。

## Over-refusal / Utility Trade-off

最大の副作用は、modelがlower-priority inputに過敏になり、benign instructionまで無視する可能性である。

結果を見ると、通常のnon-conflicting user instructionでは78.9% → 77.7%とほぼ維持される一方、よりadversarialなbenign setでは低下する。

- System Message Probing: 85.2% → 75.0%
- JailbreakChat with Allowed Prompts: 83.1% → 60.4%
- Allowed Prompts (Borderline): 87.4% → 86.2%

特に「見た目はjailbreakに似ているが実際には許可すべき」promptでover-refusalが大きい。

したがってInstruction Hierarchyはsecurityを大幅に改善する一方、**conflict detectionのdecision boundary**をさらに精密化する必要がある。

## 一般能力への影響

TriviaQA、LAMBADA、HellaSwag等の一般benchmarkではbaselineと同程度であり、著者らはgeneric capabilityの顕著な劣化は観測していない。

この点は、lower-level instructionを全面的に遮断するような防御と比べた重要な利点である。

## Limitations / 成立条件

### 1. Privilege structure自体は外部設計に依存

modelがhierarchyを守るには、applicationがsystem / user / tool messageを正しく分離して渡す必要がある。

message boundaryが壊れていたり、untrusted contentをsystem roleへ入れてしまえば、model内部のhierarchyだけでは防げない。

### 2. Tool instructionを一律misalignedとする単純化

本研究ではbrowser / tool output内のinstructionを基本的に無視すべきものとして扱う。しかし実際のagentでは、tool resultに正当なprocedural instructionが含まれる場合もあり得る。

将来的にはsource identity、capability、task contextに応じたより細かなprivilege modelが必要になる。

### 3. Over-refusal

attack-like phraseに過敏になるため、benign instructionを誤って拒否するcaseが残る。

これはhierarchyという概念自体より、training distributionとalignment判定の精度に起因する部分が大きい。

### 4. 強力なadaptive attackへの完全防御ではない

著者ら自身もcurrent modelがpowerful adversarial attacksには依然vulnerableである可能性を認めている。

したがって「Instruction Hierarchyを学習すればprompt injection問題が解決する」という主張ではなく、model-level defenseの基盤を作る研究と見るべきである。

## LLM Model Security Taxonomyでの位置づけ

本論文は、prompt injectionをapplication-layerのfilter問題から**model-level privilege separation**へ引き上げた代表的研究として位置づけられる。

```text
LLM Model Security
└── Instruction Conflict Resolution
    ├── Flat instruction following
    │   └── system / user / external textをほぼ同格処理
    │       ↓ vulnerability
    ├── Prompt-injection-specific defenses
    │   └── input filtering / delimiters / structured queries
    │       ↓
    └── Privilege-aware model behavior
        └── Instruction Hierarchy ← 本論文
            ├── system > user > tool / third party
            ├── aligned lower-level instruction → follow
            └── conflicting lower-level instruction → ignore / refuse
```

特に、**Instruction Priorityをmodel behaviorとして直接学習させる**点が後続研究の基準点になっている。

## 実装・研究上の示唆

### System promptを長くするだけでは不十分

system promptに「user instructionを無視するな」「web pageのinstructionには従うな」と書くだけでは、LLMがpriority rule自体をinternalizeしていなければ競合時に破られ得る。

本論文は、priority ruleをtraining distributionへ組み込むことの重要性を示す。

### Prompt injectionとjailbreakを統一的に扱える可能性

prompt injection、system prompt extraction、jailbreakは表面的には異なるattackだが、「lower-privilege inputがhigher-level intentをoverrideする」という共通構造を持つ。

この抽象化により、一つのtraining principleからunseen attackへのgeneralizationが生まれる可能性がある。

### RAG / Agent securityとの接続

RAGやagentではretrieved documents、web results、tool responsesが大量にLLMへ流入する。これらを単にcontextとして渡すだけでなく、**権限の低いdata channel**としてmodelが扱えることが重要になる。

したがってRAG側のprompt injection defenseとは別に、LLM model側でinstruction hierarchyを持つことはcomplementaryな防御となる。

## 後続研究を見る際のポイント

本論文以降のInstruction Hierarchy研究では、主に次の方向が重要になる。

1. fine-tuningだけでなくarchitecture / representationレベルでprivilegeを分離できるか
2. role tokenだけに依存せずinstruction sourceをrobustに認識できるか
3. 3段階以上の細かなhierarchyを扱えるか
4. multimodal input、agent memory、multiple toolsへ拡張できるか
5. privilegeを強くするとover-refusalがどこまで増えるか
6. adaptive prompt injectionに対してhierarchyが本当に内部化されているかをどうbenchmarkするか

これらはLLM-model-securityのDefense / Benchmarkを整理する際の中心軸になる。
