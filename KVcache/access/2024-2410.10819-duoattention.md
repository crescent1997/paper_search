# DuoAttention: Efficient Long-Context LLM Inference with Retrieval and Streaming Heads

> attention headごとにlong-range retrievalの必要性が異なることを利用し、**full-history KV accessを必要とするheadだけを残す**。SparQ/QUESTがtoken/page axisをquery-awareに疎化するのに対し、DuoAttentionはhead axisでfull-history accessを疎化する。

## 概要

long-context LLMでは全attention headについて全tokenのKV cacheを保持・参照するため、context lengthに比例してmemory footprintとdecode memory trafficが増える。

DuoAttentionの観察は、すべてのheadがlong-range informationを必要としているわけではないというもの。少数の**Retrieval Heads**は遠い過去から情報をretrieveするためfull contextが必要だが、多数の**Streaming Heads**はrecent tokensとattention sinksだけを参照すればほぼ同じ役割を果たせる。

そこで各layerを、

- Retrieval Heads: full KV cache / full attention
- Streaming Heads: sink + recent tokensだけのconstant-length KV cache / streaming attention

に分割する。

既存model parameterは変更せず、synthetic dataを使った軽量optimizationでhead roleを同定する。

## 問題設定

StreamingLLMのように全headへ一律にstreaming cacheを適用するとmemoryは大きく減るが、long-range retrieval能力を失う。一方、全headにfull KVを残せばaccuracyは維持できてもmemory/bandwidth benefitが小さい。

DuoAttentionは、

> **どのKV headだけがfull historyを本当に必要としているか**

を特定し、必要なheadだけに高価なfull attentionを割り当てる。

これはtoken importanceではなく**head role specialization**を利用する点が特徴。

## Retrieval Heads / Streaming Heads

### Retrieval Heads

long context中の任意位置から情報をretrieveするhead。passkey retrievalのようにqueryから遠く離れたtokenを後で参照するには、これらのheadのfull KV historyが必要。

### Streaming Heads

主にrecent tokensとsequence先頭付近のattention sinksを見るhead。middle contextのKVを削除してもmodel outputへの影響が小さい。

Streaming Headsには固定長cacheだけを与えるため、context lengthが伸びてもそのheadのKV memoryはほぼ一定になる。

## Retrieval Headの同定

DuoAttentionは単純なattention-pattern thresholdではなく、**KVを落とした結果としてmodel outputがどれだけ変化するか**を直接利用する。

各KV headにgateを導入し、

- gate = 1: full attention
- gate = 0: streaming attention

の間を連続的にmixする。

synthetic passkey-style dataを使い、元のfull-attention modelとのoutput deviationを抑えながら、できるだけ多くのgateをstreaming側へ寄せるようoptimizationする。

model weights自体はfreezeされ、学習対象は小さいgate parameterだけ。

optimization後にgateをthresholdし、各headをRetrieval / Streamingへ二値化する。

このため単なる「平均attentionが高いhead」ではなく、

> middle-context KVを取り除いたときに**model behaviorを維持するため不可欠なhead**

を抽出する。

## GQAの場合

[GQA](../model/2023-2305.13245-gqa.md)では複数query headsが1つのKV headを共有する。

DuoAttentionでは共有KV unitに合わせてRetrieval / Streamingを判定するため、GQA modelにも適用できる。

GQAがhead数自体を減らし、DuoAttentionが残ったKV headsのうちfull-history cacheを必要とするheadを限定するので、両者は直交的。

## KV cache構成

各Transformer layerに論理的に2種類のcacheを持つ。

### Full cache

Retrieval Heads用。全past tokenのK/Vを保持し、通常のfull attentionを実行する。

### Streaming cache

Streaming Heads用。attention sink tokenと直近のwindowだけを保持する。

context length N、retrieval-head fractionをrhoとすると、長contextではKV footprintの主要部分は概ねrhoに比例する。Streaming Heads部分は固定windowなのでNに対してconstant。

## StreamingLLMとの差

[StreamingLLM](../compress/2023-2309.17453-streamingllm.md)はattention sink + recent windowを基本的に全headへ適用する。

DuoAttentionはこのstreaming patternをhead-specificに使う。

| | StreamingLLM | DuoAttention |
|---|---|---|
| unit | 全head共通 | KV headごと |
| full-history head | なし | Retrieval Heads |
| streaming cache | 全head | Streaming Headsのみ |
| long-range retrieval | 弱くなり得る | Retrieval Headsで維持 |
| head identification | 不要 | optimizationで学習 |

したがってDuoAttentionはStreamingLLMのbounded-memory ideaを、**head heterogeneityを利用してaccuracyを維持する形へ拡張**したと整理できる。

## SparQ / QUESTとの差

[SparQ Attention](2023-2312.04985-sparq-attention.md)と[QUEST](2024-2406.10774-quest.md)はいずれもcurrent queryに応じて毎decode stepでread setを変える。

| | SparQ | QUEST | DuoAttention |
|---|---|---|---|
| sparsity axis | token | page | head × history |
| selection signal | current query | current query | offline learned head role |
| selection timing | each decode step | each decode step | profiling/calibration |
| full KV storage | 原則保持 | 保持 | Streaming Headsでは削減 |
| dynamic query dependence | あり | あり | なし |
| 主な利点 | fine-grained sparse fetch | page-friendly sparse fetch | selection overheadが小さい |

技術的には競合というより異なるaxisのsparsityであり、原理上はRetrieval Head内部へtoken/page sparse accessを適用する組み合わせも考えられる。

## Experiment Setup

Llama-2、Llama-3、MistralなどMHA/GQA modelを対象に、passkey retrieval、LongBench等のlong-context workloadでaccuracyを評価する。

system efficiencyではA100 GPU上でKV memory、prefill latency、decode latencyを測定する。

Retrieval Head identificationにはsynthetic dataを使い、full modelのweightsはfine-tuneしない。

さらにweight/KV quantizationと組み合わせ、million-token contextへのscalabilityを評価する。

## Main Results

ICLR 2025版で報告される最大値は以下。

| Architecture | KV memory reduction | Decode speedup | Prefill speedup |
|---|---:|---:|---:|
| MHA | 2.55× | 2.18× | 1.73× |
| GQA | 1.67× | 1.50× | 1.63× |

full attentionと比べてlong-context accuracyの低下を小さく保ちながらmemoryとlatencyを同時に削減する。

GQAでは元々KV head数が少ないため、MHAより追加削減余地が小さくなる。

## Million-token scaling

8-bit weight quantizationと4-bit KV cache quantizationをDuoAttentionと組み合わせることで、Llama-3-8Bをsingle A100上で約**3.3M token context**までdecode可能と報告する。

standard FP16 full-attention deploymentとの比較では約**6.4×のcontext capacity increase**。

これはDuoAttention単独の圧縮率ではなく、

- head-wise streaming
- weight quantization
- KV quantization

を組み合わせた結果である点に注意が必要。

## Ablation / analysis

### Retrieval Head fraction

Retrieval Headsを増やすほどfull attentionへ近づきaccuracyは安定するが、KV memoryとlatency benefitが減る。

逆に強く圧縮するとlong-range retrievalに必要なheadまでstreaming化し、accuracyが急落する。

### Identification method

attention patternだけでhead importanceを推定する方法より、実際にtokenをdropした際のoutput deviationをoptimization objectiveへ入れる方法の方が、同等accuracyでより多くのheadをstreaming化できる。

### Synthetic calibration

実taskの大量training dataを必要とせず、synthetic retrieval dataでhead roleを特定できる点がdeployment上の利点。

## Compressとの境界

DuoAttentionはStreaming Headsについてold KVを保存しないため、storage capacityも実際に削減する。その意味では`compress`にも属する。

一方、論文の中心的な設計判断は、

> **どのheadがfull-history KV accessを必要とするか**

というhead specializationであり、Retrieval Headsはfull cacheを維持する。

このrepositoryでは主categoryを`access`とし、taxonomy上は

**access / head-specialized access + head-wise KV compression**

と整理する。

## Limitations

1. Retrieval / Streaming classificationは基本的にstaticであり、requestごとにhead roleを動的変更しない。
2. Retrieval Headsでは依然としてfull-history KVを保持・参照するため、context lengthに対するlinear costは残る。
3. benefitはmodel内のRetrieval Head割合に依存し、GQAではMHAより削減余地が小さい。
4. deployment前にsynthetic calibration / gate optimizationが必要。
5. million-token capacityはquantizationとの併用結果であり、DuoAttention単独の効果とは分離して読む必要がある。

## KV-cache taxonomyでの位置づけ

**access / head-specialized full-history access / streaming KV compression / calibration-based / model-weight frozen**。

これまでのaccess系をaxisで整理すると、

```text
SparQ        : query → important tokens
QUEST        : query → important pages
DuoAttention : learned head role → full-history or streaming cache
```

となる。

DuoAttentionは「どのtokenを読むか」ではなく、より上位の

> **どのheadにlong-context access能力を残す必要があるか**

を選択する点が新しい。

## まとめ

DuoAttentionはattention headsの役割が均一ではないことを利用し、long-range retrievalに不可欠な少数headだけにfull KV cacheを残す。

中心componentは、

| Component | Role |
|---|---|
| synthetic retrieval data | head role calibration |
| continuous gate | full / streaming importanceを最適化 |
| Retrieval Heads | full-history KV accessを保持 |
| Streaming Heads | sink + recentだけのconstant cache |
| head-wise kernels | prefill/decodeの実latency削減 |

MHAで最大2.55×、GQAで最大1.67×のmemory削減、最大2.18×/1.50×のdecode speedupを報告する。

SparQ/QUESTがsequence axisのread setを疎化するのに対し、DuoAttentionは**head axisでfull-history accessを疎化する**ため、long-context KV optimizationを複数axisへ広げる重要なhistorical paper。
