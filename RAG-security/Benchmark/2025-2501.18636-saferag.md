# SafeRAG: Benchmarking Security in Retrieval-Augmented Generation of Large Language Model

> RAG securityを単一attackや単一componentではなく、**knowledge base → retriever → filter/compressor → generator**というpipeline全体で評価するため、4種類のdata injection attackとcomponent-wise evaluation frameworkを整備したbenchmark。

## 概要

RAGは外部knowledgeを利用することでfactualityやfreshnessを改善できる一方、外部knowledge sourceがuntrustedである場合、malicious contentがRAG pipelineへ混入する新しいattack surfaceを持つ。

従来のRAG security研究では、knowledge poisoning、prompt injection、adversarial retrieval、misinformation injectionなど個別attackが提案されていた。しかし評価settingが異なり、

- retrieverがどこで失敗したのか
- filter/compressorがattack contentを除去できたのか
- generatorがconflicting / malicious contextをどの程度無視できたのか

を統一的に比較しにくかった。

SafeRAGはこの問題を、**RAG pipelineの各componentに対するsecurity stress test**として定式化する。

## Threat Model

attackerはRAG knowledge sourceまたはretrieved contextへmalicious contentを注入できる。

攻撃目標はprivate data extractionではなく、主にRAG responseの**Integrity / Availability**を損なうことである。

つまり今回のrepositoryで中心に追っているknowledge-base stealingとはattack directionが異なる。

```text
Confidentiality attack:
Knowledge Base → Attacker

SafeRAGが主に扱うattack:
Attacker → Knowledge Base / Context → Generator → Corrupted Response
```

この点では[PoisonedRAG](../Attack/2024-2402.07867-poisonedrag.md)と近いが、PoisonedRAGがtargeted answer injectionを中心にするのに対し、SafeRAGは複数種類のattack scenarioを同一frameworkで比較するbenchmarkである。

## SafeRAGの4 Attack

### 1. Silver Noise

retrieval対象とsemanticに関連しているが、回答には不要または誤誘導的なcontentを混ぜる。

完全に無関係なnoiseではretrieverが落としやすいため、attackerは**relevant-looking noise**を作る。これによりretriever rankingを占有し、generatorへ本当に必要なevidenceが届きにくくなる。

このattackは主にretrieval robustnessを測る。

### 2. Inter-context Conflict

benign contextと矛盾するcontentを注入する。

例えばcorrect factとopposite factを同時にretrieved contextへ入れ、generatorがどちらを採用するかを見る。

これはRAGの「retrieved contentをground truthとして信頼する」という性質を直接突く。高性能LLMでも、複数context間のconflict resolutionが常に安定するとは限らない。

### 3. Soft Ad

advertisement / promotional contentをretrieval corpusへ自然に混ぜ、回答にproduct / service recommendationを滑り込ませる。

露骨なspamではなく、query-relevantな文章に広告contentを埋め込むためretrieverやfilterが落としにくい。

RAGがweb searchやuser-generated contentをknowledge sourceに利用するproduction settingでは現実的なriskである。

### 4. White DoS

malicious contextによってgeneratorを正常回答不能にし、answer qualityを大きく低下させるAvailability attack。

traditional DoSのようにservice自体を停止させるのではなく、RAG pipelineは動いているが**useful answerを返せない状態**を作るためWhite DoSと呼ぶ。

## Attack Injection Stage

SafeRAGの特徴はattack contentを複数stageへ入れて比較する点にある。

概念的には、

```text
Knowledge Base
   ↓
Retriever
   ↓
Retrieved Context
   ↓
Filter / Compressor
   ↓
Filtered Context
   ↓
Generator
```

の各地点でattack surfaceが変わる。

knowledge base段階のpoisonはretrieverを突破する必要がある。一方、retrieved contextやfiltered contextへ直接attack contentが到達するとretrieval defenseをskipできるため、一般にattack effectivenessが高くなる。

## Evaluation Pipeline

### Retriever

代表的なsparse / dense / hybrid retrievalを比較する。

- BM25
- DPR系dense retriever
- Hybrid retrieval
- Hybrid + reranking

retrieverごとにattack susceptibilityが異なり、dense retrieverなら常に安全、rerankerを入れれば安全という単純な関係にはならない。

### Filter / Compressor

retrieved contextへpost-processingを入れ、attack contentを除去できるかを見る。

- NLI-based filter
- selective knowledge / relevance filtering
- context compression系component

などを評価する。

ここで重要なのは、filterは「不要情報を減らす」だけでなく、**evidence structureそのものを変えてしまう**ことがある点である。conflicting evidenceの一部だけを残すと、かえってgeneratorがmalicious factを採用しやすくなる場合がある。

### Generator

GPT系、DeepSeek、Qwen、Baichuan、ChatGLMなど複数LLM familyを比較する。

LLMのinstruction-following能力やreasoning能力が上がっても、retrieved malicious contextを常に正しく識別できるわけではない。

## Evaluation Metrics

SafeRAGではtaskごとにattack成功を定義する。

- Silver Noise: benign evidenceがretrieval / generationでどれだけ維持されるか
- Inter-context Conflict: conflicting malicious contextに回答が引っ張られるか
- Soft Ad: promotional contentがresponseへ反映されるか
- White DoS:正常回答abilityがどの程度失われるか

つまり単一ASRだけでなく、attack目的に応じたrobustnessを測る。

## Main Results

### Attack stageがgeneratorへ近いほど危険

knowledge-base poisoningではretrieverが自然な防波堤になるが、attack contentがretrieved context / filtered contextまで到達すると効果が大きくなる。

これはsecurity設計上、**knowledge ingestionだけ守ればよいわけではなく、retrieval後contextのprovenance / sanitizationも必要**であることを意味する。

### Retrieverごとにfailure modeが異なる

Hybrid + rerankingのような強いretrieval pipelineでも全attackにrobustではない。

conflict contentやquery-relevant adversarial textはrerankingで高scoreになり得る。逆にdense retrieverはsemanticに近いDoS / noiseを拾いやすい場合がある。

したがってretrieval accuracy benchmarkで強いretrieverがsecurity benchmarkでも強いとは限らない。

### Filter / Compressorは常にDefenseにならない

一見するとcontext filterはsecurityを改善しそうだが、結果はattack-dependentである。

特にInter-context Conflictでは、benign / malicious evidenceをまとめたり一部を除去することで、元々存在した「複数evidenceを比較するための情報」が失われる場合がある。

filtering / compressionはutility optimization componentであって、security guaranteeではないことが分かる。

### Advanced LLMでもmalicious contextを完全には無視できない

高性能generatorでも、retrieved contentをtrusted evidenceとして扱う傾向そのものは残る。

RAG promptは通常「与えられたcontextに基づいて回答せよ」とinstructionするため、generator側alignmentだけでuntrusted retrieval contentを識別するのは難しい。

### Attack typeごとに最適なDefenseが異なる

- noise: retrieval/reranking強化が比較的効く
- conflict: evidence consistency checkingが重要
- advertisement: source provenance / content policyが重要
- DoS: malicious context detectionとgenerator robustnessの両方が必要

単一filterだけで4 attackを一括防御するのは難しい。

## 先行研究からの改善点

SafeRAG以前のRAG security研究は、個別attackを強く示すものが多かった。

例えば[PoisonedRAG](../Attack/2024-2402.07867-poisonedrag.md)は、少数のpoisoned textsを使ってtarget answerへ誘導できることを体系的に示す。一方SafeRAGは、特定の新attack性能を最大化することより、**attack categoryとRAG componentを直交軸にして比較できるbenchmarkを作ること**を目的とする。

```text
Individual RAG attacks
  ├─ knowledge poisoning
  ├─ conflicting evidence
  ├─ advertising injection
  └─ availability attack
        ↓
Unified pipeline-level evaluation
        ↓
SafeRAG
```

このため「どのRAG componentを改善すればどのattackに効くのか」を分析しやすくなった。

## Knowledge Extraction Benchmarkとの違い

[Benchmarking Knowledge-Extraction Attack and Defense on RAG](2026-2602.09319-benchmarking-knowledge-extraction-attack-and-defense.md)とは補完関係にある。

- SafeRAG: **Integrity / Availability**中心
- Knowledge-Extraction Benchmark: **Confidentiality / knowledge stealing**中心

両方を見ることでRAG securityの主要CIA propertiesをかなり広くカバーできる。

## Experiment上の示唆

production RAGのsecurity evaluationでは、final answer accuracyだけでは不十分である。

最低でも、

- malicious documentがtop-kに入ったか
- filterが残したか
- generatorが採用したか

をcomponent-wiseにloggingしないと、defenseがどこで効いたのか分からない。

SafeRAGの価値はこのevaluation decompositionにもある。

## RAG Data Extraction Riskとの関係

SafeRAG自身はknowledge-base stealingを直接扱わない。

しかし今回のrepositoryでRAG securityを整理する上では重要である。RAGは外部knowledge interfaceを持つことで、

- Confidentiality: knowledge extraction
- Integrity: knowledge poisoning / conflict / advertisement
- Availability: White DoS

という複数riskを同時に持つ。

特に[PoisonedRAG](../Attack/2024-2402.07867-poisonedrag.md)と並べて読むと、「RAG knowledge baseへ書き込めるattackerが何をできるか」をより広く理解できる。

## Limitations

1. **Knowledge extractionを直接benchmarkしない**  
   private corpus reconstructionやverbatim context leakageは主対象ではない。

2. **Textual RAG中心**  
   multimodal retrieval、code RAG、agentic RAGにはそのまま一般化できない。

3. **System-level controlsは範囲外**  
   document ACL、tenant isolation、identity-aware retrieval、source authenticationなどproduction defenseは十分扱わない。

4. **Attack taxonomyは完全ではない**  
   backdoor、membership inference、knowledge stealing、tool injection等は別途評価が必要。

5. **LLM / retriever updateへの依存**  
   closed APIのbehaviorやretrieval modelが変わるとrankingも変化し得る。

## 重要なポイント

- ACL 2025 Long PaperのRAG security benchmark。
- Silver Noise / Inter-context Conflict / Soft Ad / White DoSの4 attackを統一frameworkで評価。
- knowledge base → retriever → filter/compressor → generatorの各stageを分離して分析する。
- attack contentがgeneratorへ近いstageまで到達するほど危険になる。
- retriever / rerankerのaccuracy向上はsecurity向上を保証しない。
- filter / compressorもattackによっては逆効果になり得る。
- advanced LLMでもmalicious retrieved contextを完全には識別できない。
- PoisonedRAGのような個別attack研究を、pipeline-level benchmarkへ拡張した位置づけ。
- knowledge extraction benchmarkとは補完的で、RAGのIntegrity / Availability sideを理解する基準になる。
