# 概要とスコープ
**区分: Benchmark。** CarryoverBenchは、外部データからの一回限りのindirect prompt injection (IPI)が、agent自身による**永続ファイルへの書き込み**を経て後続sessionで実行される問題を評価する。一般的な単発のsystem/user/tool conflictとは異なり、低信頼tool outputが`MEMORY.md`や`HEARTBEAT.md`へ保存され、runtimeが次回起動時に高い権威を持つ文脈として再提示する**cross-session authority laundering**が中心。**モデル内部のIH学習ではなくagent harnessとモデルの相互作用が主対象**なので、本repositoryでは関連benchmarkとして位置づけ、model-only robustnessの数値と混同しない。

一次資料: [arXiv:2610.28425](https://arxiv.org/abs/2610.28425)、[ACL Anthology](https://aclanthology.org/2026.emnlp-main.1996/)、[PDF](https://aclanthology.org/2026.emnlp-main.1996.pdf)。arXiv初回2026-10-20、ACL会議録2026年10月、著者6名を照合。

# Problem / Threat Model
攻撃者はagentが読むメール、Webページ、document、tool returnなど**低信頼コンテンツ**を一度だけ改変できる。runtime、OS ACL、persistent memoryを直接変更する権限は持たず、攻撃者はplant後に退出する。攻撃が成功するにはagent自身が悪意ある内容をpersistent stateへ書き込み、後続sessionでそれを再び参照して不正actionを実行する必要がある。target LLMのgradient/logit accessは不要。payload生成の詳細なquery budgetはこのbenchmarkの主要指標ではない。

- **Instant:** 従来の同一session IPI。
- **Autonomous:** `HEARTBEAT.md`に登録された定期taskがユーザー不在の後続tickで実行される。
- **Latent:** `MEMORY.md`に保存された内容が、後の関連user requestで再浮上する。

形式化: `ASR = P(Plant) × P(Trigger | Plant)`。この分解は**植付け防御と再発火防御を別々に評価**するために重要。`N-TrigRate`は植付けに成功したtask集合に対する第N後続sessionの実行率。正常task utilityを別指標として記録し、全面拒否による見かけのASR改善を避ける。

# Benchmark Construction / Algorithm
- **12 personal-assistant task families**（メール、銀行、コードレビューなど）。**101 attack tasks** = Instant 35 + Autonomous 30 + Latent 36。benign task、containerized environment、攻撃目標と挿入場所、検証器を組にしたschema。
- `MEMORY.md`は次回sessionでsystem promptに暗黙に前置される長期記憶、`HEARTBEAT.md`はruntimeが30分ごとに読ませるscheduled taskという設定。
- verifierはLLM-as-judgeではなく**deterministic rule-based**。tool callの宛先/URL/path等をmarker registryと照合し、tool種類をmessaging/HTTP/write/read/execへ正規化。attack successとutilityを別々に採点する。
- Autonomous/Latentは**各5 trigger rounds**をfresh agentで評価。Autonomousはuser requestなし、Latentは同一の自然なfollow-up promptを繰り返す。後者はtopic-match条件を固定するため、現実のランダムな将来要求分布を表さない。

# Experiment Setup
主runtimeはNanobot、比較runtimeはHermes。5 targetモデルはGPT-5.4、Claude-Sonnet-4.6、Gemini-3.1-Pro、GLM-5、Qwen3-235B-A22B。temperature 0、共通system promptとtool-call template。Main resultのASRはAutonomous/Latentで**5 round中のいずれかで発火した割合**、Instantではsingle shot。task単位cluster bootstrap 10,000回の95% CIを報告。

# Main Results（論文Table 1）
| Model | Instant ASR | Autonomous ASR | Latent ASR | Overall ASR | No-attack Utility | Attacked Utility |
|---|---:|---:|---:|---:|---:|---:|
| GPT-5.4 | 22.9% | 3.3% | 8.3% | **11.9%** | 97.2% | 91.4% |
| Claude-Sonnet-4.6 | 22.9% | 10.0% | 22.2% | **18.8%** | 89.3% | 87.9% |
| Gemini-3.1-Pro | 60.0% | 56.7% | 38.9% | **51.5%** | 100.0% | 94.2% |
| GLM-5 | 34.3% | 40.0% | 11.1% | **27.7%** | 97.2% | 93.1% |
| Qwen3-235B-A22B | 57.1% | 83.3% | 52.8% | **63.4%** | 92.4% | 91.6% |

**重要:** AutonomousのASRがInstantより高いQwen等もあり、「2段階だから常に安全」とは言えない。QwenのAutonomous Plant率は93.3%、第5roundでも70.0%が発火。GPT-5.4のLatentは8.3%が第1〜第5roundで変わらない。これは**条件付きで同じ記憶が再入力され続ける**ことを示すが、自然環境で毎日8.3%の確率で発火するという意味ではない。

# Robustness / Transfer / Defense Evaluation
## Plant vs Trigger
モデルによってplant率は大きく違うが、plant成功後のtriggerはしばしば高確率。論文はAutonomousで条件付き発火率が多くのモデルで約1に近いことを報告。低信頼データを一度persistent fileへ取り込んだ後は、**次sessionでモデルが元のsource trustを再判定しない**ことが本質的な問題。

## Defenses D1–D3
D1はsystem promptによるpersistent-state注意喚起、D2はedit authorityの明示、D3はpersistent fileを`<untrusted_persistent_state>`で包むSpotlighting型provenance表示。QwenでNo DefenseのAuto/Latent ASR 83.3/52.8%→D3 60.0/38.9%。Claudeでは10.0/22.2→3.3/2.8%。ただし大半の効果は**plant率の低下**によるもので、すでに植え付けられた内容のtrigger gateはほぼ閉じない。

## Cross-runtime（Hermes）
36 Latent variantsを同じモデル・検証器で移植。Qwen ASR 52.8→27.8%、Claude 22.2→5.6%、GLM-5 11.1→8.3%、GPT-5.4 8.3→2.8%。runtime差で低下するがゼロにはならない。Hermes側のpattern scannerは0/89 payload filesを検出、memory review pipelineも削除・置換を発火させていない。差を特定のscanner成功へ帰属させない。**Autonomousはheartbeatとcronの意味が異なるため、matched runtime比較を行っていない**。

# Limitations / Generalization
1. **Verifier false negatives:** tool引数の指定フィールドとaliasを一致判定するため、本文への漏洩や別表記の成功を見逃しうる。ASRは絶対的な実世界被害率ではない。
2. **Latent triggerの分布:** 同じtopic-aligned follow-upを5回反復。現実の多様な次回質問に対する`P(Trigger|Plant)`の上限的な評価である。Autonomousにはこの制約がない。
3. **Runtime依存:** NanobotとHermesのmemory再注入方法が重要。別のsystem prompt composition、capability sandbox、永続状態の読み込み設計ではASRが変わる。
4. **Model family:** Hermesの比較はGemini reasoning modeを除外。5モデルの差を純粋な「モデル内IHの優劣」と解釈できない。
5. **攻撃primitive:** 低信頼text→state write→再読込。GCG suffix optimizationやtarget modelへのwhite-box accessではない。StruQ/SecAlign/Meta SecAlign/ISE/CaMeLを同条件で直接比較していない。

# LLM Model Security Taxonomy / 実装・研究上の示唆
**Benchmark > Cross-session trust-boundary failure / persistent-state authority laundering.** 直接のmodel-level defenseではないが、Instruction Hierarchyを実運用で評価する際の「**tool outputが永続化され、次のsystem-contextとして復活する**」重要な境界事例を提供する。評価設計では、(1) original provenanceを保存したままmemoryへ書く、(2)後続sessionでsystem messageとuntrusted stateを分離、(3)plant/triggerを独立に測定、(4)tool authorizationとegress policyをruntimeで強制、(5)benign utilityとASRを同時測定、を推奨する。CaMeLのような明示的なcapability制御の必要性を補強するが、**CaMeLを実測で破った論文ではない**。
