# 概要

**FastGen**は、LLMのattention headが同じ情報を必要とするわけではないことを利用し、**各headに異なるKV保存規則を適用する**KV cache圧縮手法である。入力promptのprefillで観測したattention patternからheadの役割を推定し、decode中はそのheadに対応するpolicyでcacheを更新する。モデルの重みを変えず、追加fine-tuningも不要である。主対象は保存するKV token数の削減であり、カテゴリは`compress`。

論文の新規性は単なるheavy-hitter evictionではなく、**「どのtokenを残すか」以前に「どの種類のcache policyをそのheadに適用するか」を選ぶ**点にある。2023年の[H2O](2023-2306.14048-h2o.md)や[Scissorhands](2023-2305.17118-scissorhands.md)を固定的に全headへ適用する方式と対照的である。

## 問題設定と既存法の問題

通常のautoregressive decodeは過去tokenのK/Vをすべて保持するため、cache memoryはsequence length、batch size、layer/head数に比例して増加する。全headに同じlocal window、頻度上位tokenなどの規則を課すと、特定のtoken種別しか見ないheadでは無駄が残り、広範囲を見るheadでは重要情報を落とす。

著者らはLlama 1のattention mapを観察し、初期・終盤layerではfull contextを見るheadが比較的多い一方、中間layerではspecial tokenに集中するheadが多いことを示す（Figure 3）。さらに、同一request内ではprefill時に見られたheadの傾向がdecodeの10/20/30 stepでもおおむね維持される（Figure 4）。この**headごとの異質性と時間的安定性**がone-shot policy selectionの根拠となる。

## 手法

### 1. Prefill時のhead-wise profiling

各headのprompt attention mapを`A = softmax(QK^T)`とする。候補policy `C`を適用して残るKeyを`K_C`とし、元のattention mapを所定の閾値`T`以上で再現できる候補の中から、KV memory costが最小のものを選ぶ（Section 3.3, Eq. 1）。ここでのattention recoveryは**過去attention分布の近似指標**であり、将来の質問に対する正答率を直接最適化しているわけではない。

### 2. 候補policyとその組合せ

| Policy | 保持するKV | 意味 |
|---|---|---|
| `C_special` | `<s>`、`[INST]`等 | special token中心のhead向け |
| `C_punct` | `.`, `:`, `?`等 | 句読点に注目するhead向け |
| `C_local` | 直近の相対距離window内 | local attention head向け |
| `C_frequent` | 累積attention scoreが大きいtoken | heavy-hitter head向け |
| `C_full` | 全token | 遠距離依存を落とせないhead向け |

実装ではすべての組合せを探索せず、special tokenを常に含むgreedyなpolicy chainを使う（Eq. 2）。`C_special`、`C_special+punct`、`C_special+punct+frequent`、`C_special+punct+frequent+local`、`C_full`が基本候補。和は**保持するtoken集合のunion**である。論文の図表と式で一部候補の表記が異なるため、正確な再実装ではコードと照合する必要がある。

### 3. Decode時のcache更新

Prefillで選んだpolicyをheadごとに固定し、生成tokenが増えるたびにそのpolicyに従ってKVを保持・evictする（Algorithm 2）。`C_frequent`には累積attention scoreの管理が必要だが、policy選択を毎stepやり直さない。full-cache headではKVをそのまま維持する。

## Experiment Setup

- **Model**: Llama 1の7B / 13B / 30B / 65Bとinstruction fine-tuned版。比較のため元のMHAを採用し、**GQAを使うLlama 2 Chatは対象外**（Section 5.1）。論文中のfine-tunedモデルは評価用であり、FastGenを適用するための学習ではない。
- **Quality**: GSM8K、HumanEval、Natural Questions、TriviaQA、instruction-followingを測るAlpacaEval。固定policy（frequency / locality / combination）およびfull cacheと比較。
- **Efficiency**: Llama 1-7B、Hugging Face Accelerate、DeepSpeedを比較。FastGenはDeepSpeed系のcustomized sparsity kernelを使用。KV memory表はbatch=16、sequence=512、FP16重みという条件で測定。
- **Trade-off**: attention recovery threshold `T`、locality/frequency比率を変えてcache量・quality・latencyを比較。

## Main Results

**Quality-memory trade-off**（Table 1, Figures 2/5）: 65B fine-tunedモデルでは、`T=95%`に相当する設定でfull-cache 21.5 GBに対して11.8 GB（約45%削減）、AlpacaEvalでfull cacheに対するwin rate 44.9%。7Bではfull 4.3 GBに対し2.6 GB、win rate 39.8%。著者らは、同程度の品質を保つ際の削減余地が大きいモデルほど広がると観察している。**win rateは正答率ではなくfull-cache出力との相対的な比較**である。

**Latency**（Table 2）: Llama 1-7Bのbatch=1、prompt 32 / generation 16,384でHF 799.14 s、DeepSpeed 435.74 s、FastGen 359.83 s。HF比で約55%のlatency削減、DeepSpeed比で約17.4%削減。batch=8、prompt 4,096 / generation 4,096ではDeepSpeed 127.94 sに対してFastGen 82.16 s（約35.8%削減）。**この55%はlatency削減率であり、55% throughput向上という意味ではない**。

**Profiling overhead**（Table 3）: Llama 1-65Bではpolicy探索が約0.11秒。generation 128 tokenで全体の0.35%、1,024 tokenで0.07%。累積attention scoreの追加メモリは、head dimension=128を仮定するとKV memoryの約0.78%相当と試算する。これは評価環境依存の値であり、任意のlong-context/GQA環境で保証されるものではない。

## 主要ablation

Appendix A.1、Table 4では`T=0.98`でpolicyを一つずつ除去した。全候補では**36.04% pruning / 49.75% win rate**。`C_frequent`を除くと**21.26% pruning / 46.08% win rate**、`C_special`を除くと**31.16% / 47.64%**。前者は圧縮率と品質、後者は品質の両面で重要。policyの探索順序を変えたTable 5でも、同じpolicy群でwin rateが49.75%から47.64%へ変化し、greedy探索の順序依存がある。locality/frequency比率の感度分析もFigure 6に示される。

## Limitations / 実装上の論点

1. **MHA中心の評価**: GQA/MQAのshared KV headに対してQuery headごとの異なるpolicyをそのまま適用できない。Llama 2への適用は今後の課題として明記される。
2. **Prompt依存のpolicy推定**: 後続queryや生成中の話題が大きく変化すると、prefill時のattention patternの安定性が崩れうる。
3. **Attention-map依存**: Profilingはattention mapを用いるため、FlashAttention系でfull mapをmaterializeしない実装では計測・再設計が必要。
4. **Head別可変長cache**: 不均一なtoken保持をpaged KV layoutやbatch servingに統合するには追加のkernel・metadata設計が必要。論文のlatencyはcustom kernel込みであり、標準vLLMで同じ値が出るとは限らない。
5. **Quality指標の限界**: 元のattention分布の近似は、将来のquery/task utilityを直接保証しない。

## Taxonomy / 関連研究との差分

| 項目 | FastGen |
|---|---|
| Category | `compress`（保存KV token数を減らす） |
| Selection granularity | policy選択は**head-level**、evictionはtoken-level |
| Relevance signal | prompt中のhead別attention pattern、累積attention頻度 |
| Timing | prefillで診断、decodeで継続eviction |
| Model modification / fine-tuning | 不要 |
| Full-prefill approximation | 該当しない（prefill計算の再利用ではない） |
| Main trade-off | KV memory / generation quality / runtime |

[Scissorhands](2023-2305.17118-scissorhands.md)と[H2O](2023-2306.14048-h2o.md)はtoken importanceに基づく保持規則を中心とする。FastGenは**headごとに複数の保持規則を選び分ける**点を加えた。後続の[RazorAttention](2024-2407.15891-razorattention.md)はretrieval headを重視し、[HeadKV](2024-2410.19258-headkv.md)はheadごとに異なる**数値的KV budget**を配分する。FastGenはpolicy type、HeadKVはbudget allocationが主たる自由度である。
