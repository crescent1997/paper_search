# Detecting RAG Extraction Attack via Dual-Path Runtime Integrity Game

> RAG knowledge-base extractionをsemantic similarityで事後評価するのではなく、retrieved chunksへcanary tokensを挿入し、generation中のcanary behaviorを監視する **runtime integrity violation detection** として再定式化する。Target pathとOracle pathに相反するintegrity条件を課すことで、canary suppressionやoutput obfuscationを行うadaptive attackerにも対応するCanaryRAGを提案する。

## 概要

RAGではgeneratorがretrieved proprietary contentを参照して回答するため、「正常な回答」と「knowledge-base leakage」のsemantic boundaryをonlineで定義することが難しい。[The Good and The Bad](../Attack/2024-2402.16893-the-good-and-the-bad.md) や [Feedback-Guided Extraction / CopyBreakRAG](../Attack/2024-2411.14110-feedback-guided-extraction-copybreakrag.md) が示すように、attackerはretrieved contextを直接・反復的に引き出し、private knowledge baseをreconstructできる。

既存Defenseの多くはretrieval resultを変える、responseをsummarizeする、あるいはgeneration leakageを減らすことでattack successを下げるpassive mitigationである。特に [RAGFort](2025-2511.10128-ragfort.md) はknowledge-base extractionをinter-class explorationとintra-class exploitationへ分解し、retrieval / generation双方をhardeningする。

CanaryRAGは別の方向を取る。knowledge leakageを完全に発生させないことだけを目指すのではなく、**retrieved contextを不正に外部へ再現しようとするbehaviorをruntimeでmachine-verifiableに検知し、generationを停止する**。

発想はsoftware securityのstack canaryに近い。retrieved chunksへ通常のbenign outputには現れないrandom canary tokenを挿入し、generation中にcanaryの露出・消失を監視することで、曖昧なsemantic leakage detectionを明確なintegrity checkへ変換する。

## 問題設定 / Threat Model

victimはprivate / proprietary knowledge baseをretrieverで検索し、取得したchunksをLLM contextへ組み込む一般的なRAG systemである。

attackerはblack-box query interfaceのみを持ち、以下にはアクセスできない。

- private knowledge base
- retriever / embedding index
- system prompt
- retrieved chunk IDs / similarity scores
- generator parameters / hidden states

attackerはmulti-turnでresponseを観測しながらqueryをadaptiveに更新し、knowledge baseを高忠実度でreconstructすることを目的とする。

重要なのは、論文が **canary-aware adaptive attacker** まで考慮する点である。attackerは防御にcanary mechanismが使われていることを知り、canary suppression、encoding、paraphrase、deferred task injection等を利用して検知を回避しようとしてよい。

defenderはretrieved chunksがgenerator contextへ入る直前のcontext composition layerと、streaming generationを監視・停止できる必要がある。一方でretriever、knowledge base、LLM本体の再学習やarchitecture変更は要求しない。

## 先行研究からの改善点

### Semantic / Content-Based Detectionの問題

通常RAG answerもretrieved documentの意味内容を利用するため、responseとretrieved chunksのsemantic similarityが高いだけではbenign QAとextractionを区別できない。

逆にexact string matchingだけでは、attackerがparaphrase、encoding、translation、reverse等を行えば容易に回避できる。

CanaryRAGはこの曖昧さを避けるため、semantic contentではなく **synthetic integrity anchor** を導入する。canaryはbenign answerには本来不要だが、retrieved contextそのものを再現すると露出しやすい。

### RAGFortとの差

[RAGFort](2025-2511.10128-ragfort.md) はattackのexploration / exploitation能力そのものを弱めるpassive defenseである。一方CanaryRAGはattackがknowledge extraction behaviorを示した瞬間をruntime integrity violationとして検知する。

したがって技術的系譜は概念的に、

```text
CopyBreakRAG / RAG-Thief
        ↓
RAGFort: extractionを困難化
        ↓
CanaryRAG: extraction behaviorをruntime検知・停止
```

となる。

## Method / Algorithm

### 1. Canary Injection

user queryを $q$、private knowledge baseを $K$ とし、retrieverが

$$
C=R(q,K)=\{c_1,\ldots,c_n\}
$$

を返すとする。

通常RAGではsystem instruction $s$、query、retrieved chunksを結合してgenerator inputを作るが、CanaryRAGではcanary集合

$$
\tau=\{\kappa_1,\ldots,\kappa_m\}
$$

を用意し、各retrieved chunkを

$$
\tilde c_i=\Phi(c_i,\tau)
$$

へ変換してからcontextへ入れる。

canaryは通常textに自然出現しにくいrandom / non-semantic token sequenceとして設計される。benign userが通常QAを行う限りanswerへcanaryを出す必要はないが、attackerがretrieved contextを忠実に再現させようとするとcanaryも一緒に生成される可能性が高くなる。

### 2. Target Path

Target pathではoriginal user query $q$ をそのまま実行する。

期待されるintegrity conditionは単純で、**benign executionではcanaryを出力してはいけない**。

生成tokenをstreamingで監視し、canary sequenceが検出された時点でextraction attemptと判定する。canaryが複数tokenへtokenizeされる場合を考慮し、sliding buffer上でsequence matchingする。

重要なのは検知したtokenをuserへ送ってから止めるのではなく、bufferをreleaseする前に検査する点である。したがってcanary exposureを検知した時点でgenerationをabortし、漏洩responseを外部へ出さない運用が可能になる。

### 3. Target Pathだけでは不十分

canary mechanismを知るadaptive attackerは、

- special/random tokenを出力しない
- retrieved contextからmarkerだけ削除する
- base64 / ROT13等へencodeする
- reverse / translate / paraphraseする
- extraction instructionを後段へ遅延させる

などの方法で、private contentを取得しながらcanaryだけをTarget pathから消そうとできる。

このためCanaryRAGはTarget pathとは逆の期待動作を持つ **Oracle path** を並列実行する。

### 4. Oracle Path

Oracle pathでは同じcanary付きretrieved contextを使うが、queryを

$$
q_{\mathrm{orc}}=\Psi(q,\ell)
$$

のように変換し、leakage-inducing instruction $\ell$ を追加する。

Oracleでは **canaryが出力されることが正常** である。

oracle outputから回収されたcanary集合を $R(y)$ とすると、一定数以上のcanaryが観測されなければintegrity violationとする。概念的には

$$
E_{\mathrm{orc}}(y)=\mathbb{I}[|R(y)|<\kappa_{\mathrm{orc}}]
$$

であり、典型的には $\kappa_{\mathrm{orc}}=|\tau|-1$ を用いる。

adaptive attackerが「canaryを削除せよ」「markerをencode / suppressせよ」というinstructionを仕込んでいる場合、そのinstructionはOracle pathにも影響し、本来出るはずのcanaryが消える。そのためTarget pathを回避してもOracle pathで検知できる。

### 5. Dual-Path Runtime Integrity Game

2 pathの期待条件は相反する。

```text
Target Path : canaryを出してはいけない
Oracle Path : canaryを出さなければならない
```

直接contextを再現すればTarget pathで捕まり、canary suppression / obfuscationを強制すればOracle pathで捕まる。

CanaryRAGはこの相反するconstraintを **dual-path runtime integrity game** として利用する。

## Experiment Setup

評価では異なるretriever / generator / corpusを持つ3つのRAG agentを構築する。

- **Agent A**: Llama-3.1-8B-Instruct + BGE-v1.5-large + ChatDoctor
- **Agent B**: Qwen3-8B thinking + E5-large-v2 + Mini-Wikipedia
- **Agent C**: Llama-3.2-3B-Instruct + GTE-large-en-v1.5 + Mini-BioASQ

各knowledge baseから500 chunksをsamplingする。

AttackにはPiratesと [RAG-Thief / CopyBreakRAG](../Attack/2024-2411.14110-feedback-guided-extraction-copybreakrag.md) を利用する。最大1,500 attack attemptsを許可し、さらにdomain-aware attackerへtopic-related initial promptsを与える強いsettingで評価する。

Defense baselineは、

- No Defense
- Reranker
- Summarization
- [RAGFort](2025-2511.10128-ragfort.md)

である。

主指標はChunk Recovery Rate (CRR)。reconstructed chunkがoriginal chunkに対して **ROUGE-L > 0.5 かつ embedding cosine similarity > 0.85** を満たす場合にrecoveredとする。

## Main Results

CanaryRAGは全agent / attackでCRRを大幅に低減する。

| Agent / Attack | No Defense | RAGFort | CanaryRAG |
| --- | ---: | ---: | ---: |
| ChatDoctor / Pirates | 97.4% | 50.2% | **1.6%** |
| ChatDoctor / RAG-Thief | 73.4% | 37.8% | **2.4%** |
| Mini-Wikipedia / Pirates | 78.4% | 42.4% | **5.4%** |
| Mini-Wikipedia / RAG-Thief | 49.6% | 37.0% | **8.8%** |
| Mini-BioASQ / Pirates | 71.0% | 53.8% | **0.4%** |
| Mini-BioASQ / RAG-Thief | 63.4% | 38.0% | **0.2%** |

No Defenseの平均CRRを1.00×と正規化すると、Reranker 0.98×、Summarization 0.67×、RAGFort 0.60×に対し、CanaryRAGは **0.04×** まで低下する。平均約96% reductionである。

しかも評価では検知後にattackerをbanせず、最大1,500回queryを続けさせるworst-case条件を採用している。実運用で最初の高confidence detection後にsession / userをblockすれば、cumulative reconstructionをさらに抑えられる。

## Adaptive Attack Evaluation

本論文で特に重要なのがcanary-aware adaptive attackである。

主なstrategyは、

- **A1: Canary Suppression**
- **A2: Output Obfuscation** — base64、ROT13、reverse、translation、paraphrase等
- **A3: Deferred Task Injection**

である。

Oracle pathを無効化したTarget-only defenseでは、Detection TPRはnon-adaptive attackで98.2%だが、A1+A3で **51.8%**、A2+A3で **23.4%** まで低下する。

一方dual-path CanaryRAGでは、

- Non-adaptive: **99.2%**
- A1+A3: **94.1%**
- A2+A3: **95.6%**

となる。

したがってOracle pathは単なる冗長なcheckではなく、canary mechanismを理解したattackerに対するrobustnessの中心componentである。

## Benign Utility / False Positive

CanaryRAG導入前後のBERTScoreは、

- ChatDoctor: 0.517 → 0.515
- Mini-Wikipedia: 0.473 → 0.470
- Mini-BioASQ: 0.654 → 0.652

とほぼ変化しない。

False Positive Rateもそれぞれ **0.13% / 0.08% / 0.15%** と低い。

つまりcanary injectionが通常QAのsemantic qualityをほぼ壊さず、benign responseをattackとして誤検知する割合も小さいことを示す。

## Efficiency

Relative Mean FLOPsはCanaryRAGで約 **1.90×**。Oracle pathを追加するためNo Defenseより計算量は増えるが、RAGFortの3.25×、Summarizationの4.80×より小さいと報告される。

また実測end-to-end latency distributionはNo Defenseとほぼ重なり、runtime overheadは小さい。これはdual pathの追加計算が必ずしもuser-visible latencyへ同じ比率で反映されないためである。

## Limitations / 成立条件

CanaryRAGの主対象は **large-scale, high-fidelity knowledge-base reconstruction** である。document membership inferenceやside-channel attack、単一PII / secret / attributeを狙うfine-grained extractionにformal privacy guaranteeを与えるものではない。

またcontext composition layerでcanaryを挿入し、streaming generationをbufferして途中停止できる必要がある。generatorが完全な外部black-box APIでcontext preprocessing / streaming controlを持てない構成では、そのまま導入できない可能性がある。

adaptive evaluationはcanary suppression、obfuscation、deferred injectionを含み強力だが、すべての将来attack strategyへのformal robustness guaranteeではない。特にcanary behaviorを保ったままknowledgeだけを別channelへ移す高度なstrategyは今後の検討対象となる。

さらにFPRが低くても、非常に大量のbenign requestsを扱うproduction systemでは単発判定だけでaccount blockするとfalse blockingが蓄積する。そのため論文ではwindow / thresholdを用いた運用も議論する。

## RAG Security Taxonomyでの位置づけ

本論文は **Defense / confidentiality / knowledge-base extraction / runtime detection** に位置づけられる。

RAG security defenseの系譜としては、

```text
Attack: CopyBreakRAG / RAG-Thief
          ↓
Defense: RAGFort
  retrieval / generationをhardeningしてextractionを困難化
          ↓
Defense: CanaryRAG
  extractionをruntime integrity violationとして検知・停止
```

と整理できる。

RAGFortとCanaryRAGは競合するだけでなく、原理的には組み合わせることも可能である。前者でattackerのcoverage / recovery rateを下げ、後者で残ったextraction behaviorを検知するdefense-in-depth構成が考えられる。

## 実装・研究上の示唆

CanaryRAGの重要な示唆は、RAG privacy defenseを「出力内容がprivate informationと似ているか」というsemantic classification問題だけとして扱わなくてもよいことである。

retrieval pipeline内部にdefender-controlled markerを導入できるなら、曖昧なconfidentiality propertyを明確なruntime integrity propertyへ変換できる。

実運用では、

- retrieved chunkごと / requestごとのcanary rotation
- streaming bufferでのpre-release detection
- Target / Oracle violationのsession-level aggregation
- detection後のrate limit / account suspension
- RAGFort等のpassive defenseとの併用

が自然な拡張になる。

一方、membership inferenceやsingle-fact leakageはcanaryを露出させず成立し得るため、[Riddle Me This!](../Attack/2025-2502.00306-riddle-me-this.md) のようなattack classには別の防御が必要である。
