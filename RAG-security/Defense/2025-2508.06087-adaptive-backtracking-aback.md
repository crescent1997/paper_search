# Adaptive Backtracking for Privacy Protection in Large Language Models（ABack）

> **読むべきポイント**：RAGのprivate corpusを事前にsanitizeせず、generatorが出力する段階でPII漏洩を止める **inference-time defense**。単純なoutput redactionでは同じ機密情報を後続tokenで再び漏らしうる、という問題意識から、漏洩に先行する文章まで遡って再生成する。主要評価ではprivacy/utilityの合成scoreを0.74（最良baseline）から0.88（hard）/0.90（soft）へ改善するが、**明確なPII entity抽出と漏洩検知に依存し、2倍超の生成遅延がある**。隠れ状態を実際のmodel activationから測定するわけではない点にも注意。

## 概要

RAGでは、ユーザーの質問に応じて非公開databaseから文書をretrieveし、その内容をLLMのcontextに渡す。このとき、retrieved documentsに患者情報、氏名、住所、職業、金融情報などのPIIが含まれていると、攻撃者がqueryやprompt injectionを工夫することで、モデルが回答内に機密情報を再現する危険がある。

従来の防御には、retrieval後のdocument sanitization、system promptによる非開示指示、生成後のPII masking、出力全体のsafety classificationがある。しかし、(i) sanitizationは本来の回答に必要な情報まで落とす、(ii)単純なmaskingは生成済み文面の意味を損ね、後続文で同じ情報を言い換えて漏らす可能性がある、(iii) system promptだけでは攻撃的queryに弱い、という課題がある。

提案する **ABack（Adaptive Backtracking）** は、retrieved contentからPII候補を抽出し、出力中にそれらが現れそうになったら生成を中断する。単にそのtokenを削除するのではなく、漏洩につながる記述方針が文章中に現れ始めた位置を、テキスト片に対する **Reverse Mental State Reasoning（RMSR）** で推定し、その位置からprivacy-awareに再生成する。モデル重みのfine-tuningを必要としない。

併せて、医療・金融のPIIを含み、ユーザー属性を反映した回答を要求する **PriGenQA（5,000 Q&A）** と、GRPOで強化したadaptive prompt-injection attackerを提示する。

## 問題設定・Threat Model

### 守る対象と攻撃者の能力

- **保護対象**：RAGがretrieveした非公開文書内のprivacy entities。論文の中心は、documentそのものの逐語的な完全復元ではなく、回答へ露出する**個別PII entityの漏洩**。
- **攻撃者**：外部のquery interfaceを利用するblack-box user。非公開database、retriever index、generator重みへのアクセスはない。悪意あるuser query / prompt injectionによって、検索された機密内容を回答に混ぜようとする。
- **防御者**：RAG operator。retrieve済みdocumentを読み、privacy entityの抽出、generatorのtoken-level monitoring、生成停止・巻き戻し・再生成を実行できる。したがって**decoderを制御できるmiddleware/serving integration**を前提とする。
- **防御目標**：private entity集合 $E$ をretrieved context $D$ から抽出したうえで、回答 $r$ の有用性を保ちながら、$e\notin r$（全 $e\in E$）を目指す。これは実験上の運用目標であり、形式的なDP保証ではない。

**重要な範囲の違い**：本論文のdefenseは、正規ユーザーに必要な機密情報を権限に応じて出し分けるaccess controlではない。許可されたPIIの開示と禁止された開示を識別するpolicy layerを別途要する。また、PIIに該当しない社内機密文書・技術仕様のstealingまで防ぐと実証したものではない。

### 想定する漏洩経路

```text
Attacker query
    ↓
Retriever → private documents D
    ↓
LLM generator → response tokens
    ↓
PII entity appears in response (or paraphrase)
```

防御は**retrieval後・出力前**に位置する。retrieverがどのdocumentを返すかを変更せず、RAGのcontextに入るprivate text自体も変更しない。generatorが機密内容を参照できるという利点を残す一方、最終出力への漏洩を止める設計である。

## Method / Algorithm

### 全体フロー

```text
Query → Retrieve top-k documents
                ↓
       Privacy entity extraction
                ↓
         E = {PII entities}
                ↓
      Autoregressive generation
                ↓
    Monitor current token + lookahead
          ├─ safe → continue
          └─ risk → Reverse Mental State Reasoning
                         ↓
                Earliest risky segment
                         ↓
                  Privacy-aware rewrite
                         ↓
                 Resume generation
```

論文のAlgorithm 1は、このloopをend-of-sequenceまで繰り返す。以下の3段階が実装の中核となる。

### 1. Retrieved contextからprivacy indicatorを作る

Retrieverが返した文書集合 $D$ に対してLLMを使い、氏名、職業、年齢、住所などのprivacy entity集合 $E$ を抽出する。以後のtoken monitorはこの集合を参照する。

この段階は、LLMがretrieved documentからすべての機密entityを抽出できるという仮定に依存する。抽出されなかったPIIは原理的にmonitorできない。組織独自の機密識別子や複数documentの組み合わせで初めて機密になる情報を検出するには、entity extractionの拡張が必要となる。

### 2. Generation-time monitor：hard / softの2方式

生成prefixを $r_{\le i}$ としたとき、漏洩指示関数 $P(r_{\le i},E)$ が1になったら防御を起動する。

**Hard String Matching**：PIIが複数tokenに分割されるため、現在のtokenがentity文字列のprefixに一致した段階で、さらに $m$ tokenをlookaheadしてentityの出現を確かめる。例えば `AI developer` という機密属性について、`AI` だけで即座に漏洩と判定せず、後続tokenを検証する。

**Soft Semantic Matching**：生成されたlookahead文と各privacy entityを `bge-large-en-v1.5` で埋め込み、最大cosine similarityが閾値 $\delta$ を超えた場合に検知する。言い換えによる**inference-based leakage**を拾うことが目的。

$$s=\max_{e\in E}\cos\bigl(\mathrm{Emb}(h),\mathrm{Emb}(e)\bigr).$$

hardはstructured identifierの直接漏洩に強く低コスト、softは意味的な言い換えに対応する代わりにembedding計算・閾値調整が必要になる。論文の主なablationはhard版を使用する。

### 3. Reverse Mental State Reasoning（RMSR）とrewriting

漏洩を検知した位置 $i$ より前の $d$ tokenを取り、$l$ tokenごとに区切ったobservation segments $o_1,\ldots,o_n$ とする。各segmentには以下の**自然言語で定義した状態**を割り当てる。

| State | 意味 | 防御上の役割 |
|---|---|---|
| $S_1$ Neutral Description | 非機密な一般記述 | 巻き戻し不要な候補 |
| $S_2$ Obfuscated Privacy Avoidance | 機密を避ける記述 | 安全側の文脈 |
| $S_3$ Privacy-Leakage Tendency | 機密を開示しそうな記述方針 | **巻き戻し開始候補** |
| $S_4$ Disclosed | 既に機密を露出 | 検知位置の既知状態 |

最後の漏洩segmentを $S_4$ として固定し、過去方向へ $p(s_j\mid s_{j+1:n+1},o_{1:n+1},q,D)$ を推定する。推定には、LLMに過去segmentの状態を判定させる**reverse reasoning**を利用する。状態遷移の理論式を示すが、実際のLLM hidden activationから真の「意図」を読み取るわけではなく、**生成テキストとpromptを使った状態分類**である。

状態分類を安定化するため、$S_1$〜$S_3$ ごとにGPT-4oで200個のprototype textを事前生成し、`bge-large-en-v1.5` embeddingの平均ベクトルをprototypeとする。各observationとのcosine similarityをsoftmaxして得たpriorを、逆向きのLLM状態推定へ与える。これは**offlineに一度作り、異なるgenerator間で再利用可能**な設計。

最も早く $S_3$ が出現したsegmentをbacktracking point $i^*$ とし、$i^*$〜検知位置とlookaheadをprivacy-aware promptで書き直す。その後、rewritten prefixからautoregressive generationを再開する。既に開示したentityだけでなく、**その前にある「この患者の状況を詳述する」といった漏洩誘発文脈まで修正する**点がpost-processingとの差分となる。

### Implementation details

- 実験設定は $l=5$ tokens/segment、lookahead $m=5$、trace window $d=15$、soft threshold $\delta=0.95$（本文§4.2）。
- 2 documents/queryをretrieve。出力上限512 tokens、greedy decoding。
- AppendixではLinux Ubuntu 22.04.3 / NVIDIA A100 80GB 1枚、5 runsの平均。RetrieverのembeddingはL2 normで比較する設定が記されている。
- 遅延比較はvLLM batch size 1、**KV cache disabled**で実施されている。実サービスのpaged KV cacheやcontinuous batchingを利用したときのoverheadは未測定。

## 先行研究からの改善点

| 先行class | 弱点 | ABackでの変更 | 残る限界 |
|---|---|---|---|
| System Protect / Instruct Guide | 強いprompt injectionに従ってPIIを出す | 生成中にPII候補を監視し、危険なtrajectoryを中断 | monitor対象のPII抽出に依存 |
| Post Process（出力mask） | 文章が壊れやすく、言い換え再漏洩も起こりうる | 危険文脈に遡って書き直す | detectionが遅い場合、streamed tokenは既に送信済みになりうる |
| Data Sanitization（context加工） | private dataを除去するとpersonalized answerのutilityが落ちる | 元のretrieved contextを保持し、出力のみ制御 | model内部では依然private contextを参照 |
| Llama Guard（生成後判定） | 生成結果を丸ごと拒否するとutilityが低下する | 一部を書き換えて回答継続 | 再生成回数・遅延増大 |
| 既存Backtracking for Safety | unsafe textの削除や専用tokenを出すためのtrainingを要する | LLMによるsegment-state推定でtraining-free化 | hidden-state推定の正しさに形式保証なし |

関連するrepository内の論文として、[Follow My Instruction and Spill the Beans（PIDE）](../Attack/2024-2402.17840-follow-my-instruction-and-spill-the-beans.md) と [The Good and The Bad（TGTB）](../Attack/2024-2402.16893-the-good-and-the-bad.md) が本論文のattack baseline。Privacy-preserving corpus置換では [SAGE](2024-2406.14773-sage.md)、生成段階以外の機密保護では [DP-SynRAG](2025-2510.06719-dp-synrag.md) や [SD-RAG](2026-2601.11199-sd-rag.md) と対比できる。

**Threat model上の注意**：論文はblack-box extractionを主にprompt injectionでモデル化しているが、[RAGCrawler](../Attack/2026-2601.15678-connect-the-dots.md) や [IKEA](../Attack/2025-2505.15420-silent-leaks-ikea.md) のようなbenign-looking multi-turn explorationも存在する。ABackは個別PIIを抑制するものであり、**非PIIのknowledge-base stealing全体を止める評価ではない**。

## Experiment Setup

### Dataset：PriGenQA

既存のHealthcareMagicには個人情報が少ない（著者による1万件の検査でPIIあり約38%）こと、Enron EmailはQ&A形式でないことを理由に、医療・金融の**5,000 Q&A**からなるPriGenQAを構築。

| Domain / source | 件数 | 平均privacy entity数 | 特徴 |
|---|---:|---:|---|
| Medicine: HealthcareMagic（PII未注入） | 1,000 | 1.616 | 既存の個人属性を利用 |
| Medicine: HealthcareMagic（PII注入） | 2,000 | 2.931 | 合成PIIを注入し回答をpersonalize |
| Finance: synthetic investment Q&A | 2,000 | 4.0 | 職業・収入・住所・リスク許容度などを生成 |

平均約3件のprivacy entityを含み、queryとreference answerが個人属性に依存するため、**privacyを守るために情報を全部消すと回答の質が落ちる**状況を意図的に作っている。PIIは主として合成データで、実患者の機密情報を使う評価ではない。

### Generator / Retriever / Attack

- **Generator**：Qwen2.5-7B-Instruct、Qwen2.5-14B-Instruct、Gemma-2-9B-It、Gemini-2.0-Flash。
- **Retrieval**：1 queryあたり2 documents。論文Appendix Bにretrieval実装詳細。retrieverを大きく切り替えた頑健性評価は主眼ではない。
- **Attacks**：PIDE、TGTBのstatic prompt injectionと、著者が追加学習した**GRPO adaptive attacker**。
- **GRPO attacker**：固定したQwen2.5-7B target（強いsystem safeguard付き）と、LoRAで学習するQwen2.5-7B attack model。別途1,500件のtraining setを使用し、PriGenQAの評価データとは分離。LoRA rank 32、alpha 128、dropout 0.1、AdamW lr 2e-4、1 epoch。学習後のattackerを他generatorへtransfer。
- **Defenses**：Boundary1（RAGなし）、Boundary2（無防御RAG）、System Protect、Instruct Guide、Post Process、Data Sanitization、Llama Guard、ABack(hard/soft)。

### Metricsと解釈

Privacy側は、**ALR**（retrieved文書中のprivacy entityのうち回答で漏洩した割合）、**ASR**（1件以上漏洩したqueryの割合）、**CLR**（少なくとも一つのretrieved文書のprivacy entityがすべて漏洩したqueryの割合）。いずれも**低いほど良い**。

Utility側はROUGE-L、METEOR、GPT-4o-mini judgeによるaccuracy / conciseness / relevanceを合成。各metricをBoundary1/2で正規化し、

$$\mathrm{PrivacyScore}=\frac{\mathrm{ALR}+\mathrm{ASR}+\mathrm{CLR}}{3},\qquad
\mathrm{UtilityScore}=\frac{\mathrm{ROUGE\!\mbox{-}L}+\mathrm{METEOR}+\mathrm{GPTJudge}}{3},$$

$$\mathrm{OverallScore}=\frac{1-\mathrm{PrivacyScore}+\mathrm{UtilityScore}}{2}.$$

ここで表のPrivacy/Utilityは正規化済みの値。**Overall Scoreの差分はpercentage points（0.74→0.88で0.14ポイント）**として読むべきであり、ASRが14%下がったという意味ではない。

## Main Results

### GRPO攻撃はstatic templateより強い（Table 2 / Appendix Table 8）

| Generator | PIDE Privacy Score | TGTB Privacy Score | GRPO Privacy Score |
|---|---:|---:|---:|
| Qwen2.5-7B | 0.06 | 0.46 | **0.96** |
| Qwen2.5-14B | 0.05 | 0.54（Appendixでは0.57） | **0.89** |
| Gemma-2-9B | 0.02（Appendixでは0.04） | 0.04（Appendixでは0.02） | **0.85** |
| Gemini-2.0-Flash | 0.03 | 0.60 | **0.83** |

GRPO attackerはQwen2.5-7B targetで学習されているにもかかわらず、他の3モデルにも強い漏洩を誘発した。例えばAppendix Table 8のGRPOのASRは、Qwen2.5-7B **93.33%**、Qwen2.5-14B **90.73%**、Gemma-2-9B **81.26%**、Gemini **80.93%**。一方、PIDEのASRはそれぞれ7.40%、6.07%、2.26%、4.80%。

**資料上の注意**：本文Table 2とAppendix Table 8で一部のTGTB/PIDE値が一致していない。上表では本文値を主に記し、差分を併記した。比較を厳密に再利用する際には再現実験が望ましい。

### Defense比較（Table 3）

| Defense | Qwen2.5-7B（Privacy / Utility / Overall） | Qwen2.5-14B（Privacy / Utility / Overall） | 4モデル平均Overall |
|---|---|---|---:|
| System Protect | 0.96 / 0.94 / 0.49 | 0.89 / 0.98 / 0.54 | 0.52 |
| Instruct Guide | 0.98 / 0.86 / 0.44 | 0.99 / 0.90 / 0.45 | 0.43 |
| Post Process | 0.17 / 0.56 / 0.70 | 0.17 / 0.69 / 0.76 | **0.74** |
| Data Sanitization | 0.16 / 0.57 / 0.71 | 0.16 / 0.70 / 0.77 | 0.70 |
| Llama Guard | 0.92 / 0.95 / 0.52 | 0.90 / 0.99 / 0.55 | 0.52 |
| **ABack(hard)** | **0.11 / 0.83 / 0.86** | **0.13 / 0.92 / 0.90** | **0.88** |
| **ABack(soft)** | **0.12 / 0.84 / 0.86** | **0.11 / 0.98 / 0.93** | **0.90** |

ABack(hard)の平均Overallは0.88で、最良baseline Post Process（0.74）より**0.14ポイント高い**。ABack(soft)は0.90。単純なmaskingよりutilityを維持し、system promptやLlama GuardよりPII漏洩を抑える。

Qwen2.5-7BではPost ProcessがPrivacy 0.17、Utility 0.56であるのに対し、ABack(hard)はPrivacy 0.11、Utility 0.83。**privacyをさらに下げながらutilityも改善**したことが重要。ただし、これはPriGenQAと特定のGRPO attackerに対する結果である。

### Human evaluation（Table 4）

3人のannotatorがQwen2.5-7Bの応答を10点満点で評価。ABackの**privacy 9.28 / utility 9.16**に対し、Post Processは7.97 / 5.59、Data Sanitizationは8.16 / 5.67、Llama Guardは4.37 / 9.32。人手評価でも、PII削除だけに頼る手法より高い両立性能が報告された。

## Ablation / Robustness / Cost

### RMSRとembedding priorの寄与（Table 6）

| Qwen2.5-7B setting | Privacy ↓ | Utility ↑ | Overall ↑ |
|---|---:|---:|---:|
| Full ABack | **0.11** | **0.83** | **0.86** |
| w/o Prior | 0.14 | 0.78 | 0.82 |
| w/o RMSR（LLMが直接backtrack点を選ぶ） | 0.21 | 0.71 | 0.75 |

RMSRを省くとOverallが0.86→0.75まで低下し、priorを省くと0.82に下がる。単なるPII detection＋再生成ではなく、**巻き戻し位置の推定**が有効性に寄与するという主張を支える。ただし「潜在意図」が実際に正しく推定されたかを独立に検証したground-truthラベルは示されていない。

### 言い換え攻撃（Table 7）

Qwen2.5-7BにPIIを逐語的に出さずparaphraseするよう誘導した場合、ABack(hard)のPrivacy Scoreは**0.11→0.49**へ悪化。ABack(soft)は**0.13→0.14**にとどまる。Post Processは**0.20→0.94**と大幅に悪化。ここではGPT-5に応答からprivacyを推定させて評価している。

この結果は、**出力を正規表現・文字列一致でredactするだけでは、意味的な機密開示を止められない**ことを明瞭に示す。一方、soft matchingでもentity間の推論や複数応答の突き合わせによる再識別まで網羅したわけではない。

### Hyperparameter robustness（Figure 4）

$l\in\{3,5,7\}$、$m\in\{5,10,15\}$、$d\in\{10,15,20\}$、$\delta\in\{0.9,0.95,0.99\}$でOverall Scoreの変動は小さいと報告。これは小範囲の感度検査であり、他言語・長いPII・高負荷servingへの一般化を保証しない。

### Latency / Serving overhead（Table 5）

| Model | Standard RAG | Post Process | ABack | ABack / Standard |
|---|---:|---:|---:|---:|
| Qwen2.5-7B | 2.424 s | 5.816 s | **6.023 s** | **2.48×** |
| Qwen2.5-14B | 2.968 s | 6.343 s | **6.397 s** | **2.16×** |
| Gemma-2-9B | 2.252 s | 5.801 s | **5.876 s** | **2.61×** |
| Gemini-2.0-Flash | 1.439 s | 4.831 s | **4.798 s** | **3.33×** |

ABackはPost Processとほぼ同等の実測時間で、baselineのutility低下を避けている。ただし**無防御RAG比では2.2〜3.3倍**であり、paper本文の「約2×」を無条件に一般化すべきではない。実験はvLLMのKV cacheを無効化しているため、KV reuse/partial rollbackが効く通常servingでの比較は別途必要。

## Limitations / 成立条件

1. **PII extractor依存**：retrieved contextから列挙できない秘密、暗黙の個人情報、社内IPなどを漏洩monitorが見逃しうる。
2. **先読み・出力バッファの必要性**：lookaheadした機密tokenをclientへ先にstreamすると防御は手遅れになる。output streamingを一時保留する実装が必要。
3. **Soft detectorのfalse positive**：cosine similarityの閾値で一般的な語句までPIIとみなすと、合法な回答が不要にrewindされる可能性。benign false-positive rateの体系評価は不足。
4. **RMSRは説明用のlatent-state仮説**：4状態は人手定義、priorはGPT-4o生成文のembedding、posteriorはLLM prompt推定。modelの真の内部状態を観測したわけではなく、巻き戻し点の正確性に証明はない。
5. **Synthetic PriGenQA中心**：現実のアクセス権、組織ごとの秘匿規則、long document、cross-document inference、継続的multi-turn extractionは十分検証されていない。
6. **Adaptive attackerの範囲**：GRPO attackerは強いsystem promptを攻撃するが、ABackのmonitor/RMSR自体を知ったうえで最適化した**defense-aware attacker**の評価は示されない。
7. **生成コストと再試行**：LLM-based entity extraction、状態推定、rewriting、regenerationに複数passが必要。高QPS、continuous batching、KV cacheを有効にした条件でのTTFT/TPOTは未評価。
8. **Metricの性質**：PII漏洩をALR/ASR/CLRで測り、utilityをreference-based metricで評価。PIIを回答から隠すべきかどうかのauthorization correctnessとは別問題。

## RAG Security taxonomy上の位置づけ

| Axis | ABackの位置 |
|---|---|
| Attack/Defense | **Defense** |
| Security property | Retrieved-document confidentiality / PII non-disclosure |
| 防御層 | Post-retrieval **generation/decoding-time** |
| Attacker access | Black-box user query / prompt injection |
| Protected data | Retrieved document中の個別PII entity |
| 主な防御対象 | PIDE、TGTB、GRPO prompt-injection型PII exfiltration |
| 明示的な非対象 | Whole-corpus reconstruction、GraphRAG edge extraction、非PII知識のstealing、retriever indexの侵害 |
| 保証 | 実験的なprivacy/utility改善。DP等の形式保証なし |

RAG-CT（retrieval score distributionからqueryをblock）とは防御位置が異なる。ABackは**悪意queryを事前判定するのではなく、生成中の機密露出を抑制**する。これらは原理上組み合わせられるが、論文内でその組み合わせは評価されていない。

## 実装上・研究上の示唆

- **KV cacheとの相性**：backtrack後に再生成する場合、prefix $[0,i^*)$ のKVは原理上再利用でき、$i^*$以降だけdiscard/recomputeする設計が考えられる。ABack自身はこの最適化を実装・測定しておらず、vLLM実験はKV cache disabled。KV cache reuse/partial recomputation研究との接点が大きい。
- **TTFTとTPOTの切り分け**：PII抽出はprefill前の追加処理、lookahead・rewind・rewriteはdecode中の追加処理。実運用評価ではTTFT、平均TPOT、tail latency、rollback回数、再生成token数を分離すべき。
- **Defenderの正当な知識アクセス**：PIIに限定した単純なdenylistでは、ユーザー自身の個人情報を正当に使うユースケースを阻害する。entityごとにrole/consent/authorizationを付ける設計が必要。
- **評価の拡張**：IKEA/RAGCrawler型のbenign-looking multi-turn corpus stealing、同義語・属性推論による漏洩、非PIIの企業秘密、context windowの大きさを変えた攻撃、defense-aware optimizationを組み合わせると本手法の守備範囲が明確になる。
- **Detectorとbacktrackingの分離評価**：PII extractor recall、monitor FPR/FNR、state boundary accuracy、rewriting後の再漏洩率を個別に測ると、性能向上の原因を同定できる。

## まとめ

ABackは、retrieved documentsの情報をLLMから奪うのではなく、**private contextを利用しつつ、漏洩につながる生成trajectoryを検知・巻き戻す**という立場のdefenseである。PII漏洩に対して高いprivacy–utility scoreを示し、特に単純なPost Processがparaphrase attackで破綻する状況を改善した。PriGenQAとGRPO attackerも、privacy-focused RAG evaluationの再利用可能な要素である。

一方で、データ抽出の包括的防御ではなく、PII entity検知に依存し、真のhidden stateを利用した保証もない。**KV cache有効化時のrollbackコスト、authorization-aware PII policy、multi-turn extractionへの耐性**が、後続研究で検証すべき論点となる。
