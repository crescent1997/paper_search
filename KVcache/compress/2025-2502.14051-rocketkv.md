# RocketKV — 二段階のKV eviction + sparse access

## TL;DR / taxonomy

**Primary category: `compress`**（副次的に `access`）。**保存するKV token数**を減らす第一段階と、**decode stepで実際に読むKV量**を減らす第二段階を明確に分離する。モデルの再学習は不要で、cross-request KV reuseやposition-independent cachingを対象としない。2025年のICML採択論文。重要なのは「400×圧縮」が全GPUメモリを400分の1にする意味ではなく、元の系列長に対する**KV traffic-equivalent token budget**の比であること。

## 1. 問題設定と観察

KV eviction（[H2O](../compress/2023-2306.14048-h2o.md)、[SnapKV](../compress/2024-2404.14469-snapkv.md)）は一度捨てたtokenを後のqueryで参照できない。一方、[Quest](../access/2024-2406.10774-quest.md)や[SparQ](../access/2023-2312.04985-sparq-attention.md)のdynamic sparse attentionは全KVを保持するため、HBM容量を減らせず、索引やmin/maxなどの補助情報が必要になる。

Mistral-7BのQasper実験では、各decode stepでexact top-256を選べば高い品質を保てるが、実用的なeviction/selection方式はbudget 1024未満で精度が低下する。一方、全decode stepのexact top-256の**和集合**は最大系列長25Kに対して約1200 token程度であり、まず広めの候補集合を保存し、そこからstepごとに狭める構成が有望だと示した。この和集合のサイズは観測例であり、一般的な上限ではない。

## 2. Method: Stage 1 — permanent KV eviction

第一段階では[SnapKV](../compress/2024-2404.14469-snapkv.md)を拡張したSnapKV++を用いる。prompt末尾のobservation windowから過去tokenへのattentionを集計し、重要tokenを残す。sequence方向のpoolingで近傍tokenを同時に残し、情報の連続性を維持する。元のSnapKVの小さいpooling kernelに対して、RocketKVは**coarse-grain filtering**を意図してkernel size **63**を採用する。

GQAモデルでは、query headごとに異なるtokenを保持すると同じKV headのcacheを複製する恐れがある。RocketKVは[Ada-KV](../compress/2024-2407.11550-adakv.md)を参考に**query group単位でattention scoreを集約**し、group全体で同一token集合を共有する。MHAとGQAの両方を実験対象とする。

この時点で未選択tokenのKVは**物理的に破棄**され、保存容量が削減される。第二段階はこの縮小済みKV集合の上で実行する。

## 3. Method: Stage 2 — Hybrid Sparse Attention (HSA)

HSAは[Quest](../access/2024-2406.10774-quest.md)のsequence方向のpage代表値と[SparQ](../access/2023-2312.04985-sparq-attention.md)のhead dimension方向のquery sparsityを組み合わせる。

1. 残存keyを連続pageへ分割し、各page・各dimensionのelement-wise `K_max`, `K_min` を保存する。新しいkeyが増えるたびに代表値を更新する。
2. Decode queryの絶対値が大きい上位 `k1` dimensionsだけを抽出する。GQAではquery group方向の和を用いて、KV group内で同じ選択を実現する。
3. 選択dimensionの符号に応じてpageの `K_max` または `K_min` を取り、各pageが到達し得る大きいattention scoreを**近似**する。
4. 上位 `k2` page/token候補を選び、そこから**元の高次元K/V**を読み出して正規のattentionを実行する。代表値はselection専用であり、final attention valueの代替ではない。

```text
Input: q, compact K/V, pagewise K_min/K_max
idx_dim = topk_dim(sum_group(abs(q)), k1)
page_score = score(q[idx_dim], select_minmax(K_min, K_max, sign(q)))
idx_seq = topk_page(page_score, k2)
y = attention(q, gather(K, idx_seq), gather(V, idx_seq))
```

Page-levelのmax/minは厳密なtoken scoreではないため、候補pageのover-selectionやtop-k missが起こる。近似計算自体にもKV trafficがあるので、論文では**selection + final sparse attention**の合計readをtoken budgetへ換算して公平に比較する。

## 4. Adaptive compression decomposition

系列長を `S`、attention readの等価token budgetを `t` として全体圧縮率 `c=S/t` を定義する。二段階の分担を `r` とすると第一段階 `c^r`、第二段階 `c^(1-r)`。著者らの経験式は

$$
r = \min(0.2 + 0.06\log_2 c,\ 0.8).
$$

HSA内部では第二段階の削減をsequence/head両方向へ分ける。例えば `c=64` なら `r=0.56`、第一段階約10.3×、第二段階約6.2×、さらにsequence約3×・head約2.1×に分解される。固定のsplitでは最適値が系列長やbudgetにより変わるが、経験式は大半の設定で最良の固定値に近い精度を示した。

**Storageとtrafficの区別:** full-KVを1とすると、論文の概算はRocketKVのstorageが `1/c^r + 2/c^((1+r)/2)`、trafficが `1/c`。補助的なpage min/maxを含めた式であり、`1/c`はstorageではない。モデル重み・activation・allocator overheadは別に残る。

## 5. Multi-turn: RocketKV-MT

Single-turnの永続evictionは、次の質問で重要tokenが変わると回復不能になる。RocketKV-MTでは**第一段階で選ばれなかったKVも保持**し、各turnのdecode時には第一段階で絞った集合だけにHSAを適用する。次のturnでは全履歴を使ってSnapKV selectionをやり直す。結果としてdecode trafficは減るが、全履歴を保存するので**storage削減効果は消える**。disaggregated prefill/decode構成では選択された部分のみdecode側へ転送する設計が考えられるが、CPU/HBMの総保持量とは分けて評価する必要がある。

## 6. Experiment Setup

- Models: Llama-3.1-8B-Instruct（GQA）、Mistral-7B-Instruct-v0.2（GQA）、LongChat-7B-v1.5-32k（MHA）。
- Quality: LongBench、Needle-in-a-Haystack（NIAH）、RULER、SCBench（multi-turn）。
- Baselines: Full-KV、Exact-TopK oracle、DuoAttention、SnapKV、Quest、SparQ、HSA-only。
- Efficiency: Llama-3.1-8B FP16、batch size 1、NVIDIA A100/H100、gpt-fast上のend-to-end decode実験。KV traffic換算budgetを揃える。
- Version: **arXiv v3 / ICML 2025版**。初期arXiv v1のH100最大3×/31%と、最新版のA100最大3.7×/32.6%を混同しない。

## 7. Main Results

Llama-3.1-8B LongBench（Table 2）では、Full-KV平均 **52.2**、budget 256のSnapKV **42.6**、HSA-only **49.5**、RocketKV **51.1**。budget 512ではRocketKV **51.9**。NIAHはLlama-3.1-8Bの最大109K context・budget 256で**100%**を報告し、`109K/256 > 400`の等価traffic圧縮に相当する。ただしこの値は**特定のsynthetic retrieval benchmark**であり、LongBenchやRULER全体の400× near-losslessを意味しない。

GPU実験ではFull-KV比、**A100最大3.7×、H100最大3.3× end-to-end speedup**、peak GPU memory **最大32.6%削減**。A100の改善幅が大きいのは、H100よりmemory-bandwidth制約が強いためと説明する。ここでいうend-to-endは論文が測ったdecode処理系の指標であり、RAGのTTFTやpreprocessingを含むとは限らない。

SCBench multi-turnでは通常RocketKVに精度低下が残り、**RocketKV-MTはExact-TopKに近づく**。これは永久evictionがquery changeに弱いという問題の直接的なablationである。

## 8. Ablationと検証ポイント

- **HSA-only vs two-stage:** HSAだけでも近似選択を改善するが、前段のSnapKVで候補を絞ると同じtraffic budgetで精度が高くなる。二段階の補完性が主張の核。
- **Split factor:** 固定 `r=0.3–0.7` とadaptiveを比較。最適な固定値は条件に依存する。
- **GQA aggregation:** group単位のtoken index共有はKV複製を避けるが、group内のquery headで異なる重要度を平均化するtrade-offを伴う。
- **Multi-turn:** `RocketKV`と`RocketKV-MT`を別手法として記録。storage削減の有無が異なる。
- **Token budget:** HSAのmetadata fetchやselection readも計上する。TopK演算・index gather・page layoutのGPU実装コストを測る必要がある。

## 9. Limitations / 実装上の含意

1. PrefillでKVを計算した後に削除する方式であり、**prefill FLOPs自体を減らさない**。CacheBlend/ProphetKVのようなinter-document recomputation削減とは目的が異なる。
2. Multi-turnではstorage節約とfuture queryへの頑健性が衝突する。RocketKV-MTは保持容量を犠牲にする。
3. HSAはpage min/maxの補助cache、top-k、gatherを必要とする。batch=1のgpt-fast実験から、vLLM continuous batchingで同等のspeedupを保証できない。
4. FlashInfer paged attentionに載せる場合、page candidateと実際のphysical pageの対応、GQA group単位のindex共有、index重複と連続性、metadata更新を設計する必要がある。
5. NIAHの成功率を多段推論や複数証拠集約の品質と同一視しない。RULERでは長文ほど精度低下が大きくなる。
