# Differentially Private Synthetic Text Generation for Retrieval-Augmented Generation (RAG)

> Private corpusをquery-timeに毎回DP処理するのではなく、**一度だけdifferentially private synthetic text corpusへ変換し、そのsynthetic corpusを通常のRAG databaseとして再利用する**DP-SynRAGを提案する。

## 概要

RAGはprivate documentsを外部databaseへ保持し、必要な情報だけをretrieveすることで、LLM本体へprivate dataを直接trainingするより柔軟なprivacy managementを可能にする。しかし、retrieved passagesがgeneratorへ渡される以上、membership inference、context leakage、knowledge-base extractionなどを通じてprivate corpusの情報が外部へ漏れる可能性がある。

Differential Privacy (DP)を使えばindividual recordの寄与を制限できるが、典型的なprivate RAGではqueryごとにDP retrievalやprivate aggregationを実行するため、query数が増えるほどprivacy budgetがcompositionによって消費される。またquery-time noiseはretrieval qualityを直接悪化させる。

本論文の基本発想は、private corpusそのものへ何度もDP mechanismを適用するのではなく、**最初に一度だけprivate corpusからDP synthetic corpusを生成し、その後はsynthetic corpusだけを使う**というものである。

これにより、

- synthetic corpus生成時にprivacy budgetを一度だけ消費
- その後のRAG query回数にprivacy costが依存しない
- standard retriever / reranker / generatorをそのまま利用できる

という利点を得る。

## Threat Model / Privacy Goal

対象は、複数のsensitive recordsからなるprivate text corpus $D$ を持つRAG systemである。

attackerはRAG APIへ繰り返しqueryを送ることができ、responseやretrieval behaviorから、特定recordがcorpusに含まれていたか、あるいはprivate recordの内容を推測しようとする可能性がある。

本論文は、attack-specific detectionではなく、database construction stageで **differential privacy guarantee** を与えることで、任意のdownstream attackerに対するinformation leakageを制限することを目指す。

生成されるsynthetic corpus $\tilde D$ が $(\epsilon,\delta)$-DPを満たせば、元dataset中の1 recordを追加・削除しても、synthetic corpusのdistributionが大きく変わらない。

その後のretrievalやLLM generationはDP outputに対するpost-processingなので、追加のprivacy lossを発生させない。

## DP-SynRAGの全体構成

概念的なpipelineは以下である。

```text
Private Corpus D
   ↓
DP Keyword Statistics
   ↓
Topic / Cluster Construction
   ↓
Embedding-based Refinement
   ↓
Private Prediction / Text Synthesis
   ↓
Synthetic Candidate Documents
   ↓
Self-filtering / Quality Control
   ↓
DP Synthetic RAG Corpus D~
   ↓
Standard Retriever + LLM
```

重要なのは、private dataに触れる操作をsynthetic corpus生成stageへ閉じ込める点である。

## Method

### 1. DP Keyword Histogram

private corpus中に現れる重要keyword / termのfrequencyを集計する。ただしraw countを公開するとrare termからsensitive recordを推測できる可能性があるため、DP noiseを加えたhistogramを構築する。

このhistogramはcorpus全体のtopic distributionを保持しつつ、individual documentの寄与を隠す役割を持つ。

### 2. Soft Clustering

DP keyword statisticsからtopic / semantic groupを作る。

hard clusteringでは一つのdocumentを一つのclusterへ固定するが、text dataは複数topicを跨ぐことが多い。そこでsoft assignmentを使い、synthetic text生成時に多様なsemantic combinationを維持する。

### 3. Embedding Refinement

keyword-level clusterだけではsemantic coherenceが不足するため、embedding spaceでcluster representationをrefineする。

ここでは、公開またはpretrained embedding modelを利用し、synthetic generationに使うsemantic anchorを改善する。

### 4. Private Prediction / Synthetic Text Generation

各clusterについて、private informationを直接copyしないようDP mechanismを用いながら、LLMへsynthetic textを生成させる。

生成textは元documentのverbatim replicaではなく、cluster-level patternsや頻出conceptを保つsynthetic documentとなる。

論文ではprivacy accountingにzCDPを利用し、各private mechanismのcostを合成した上で $(\epsilon,\delta)$-DPへ変換する。

### 5. Self-filtering

生成されたsynthetic documentの中には、

- topicとの関連性が低い
- semantic qualityが低い
- retrieval corpusとして不適切

なcandidateも含まれる。

そこでLLM / scoringによるself-filteringを行い、retrieval utilityの高いdocumentだけをsynthetic corpusへ残す。

このfilteringはDP mechanismのoutputに対するpost-processingなので、追加privacy costを必要としない。

## なぜQuery数に依存しないのか

従来型private RAGでは、queryごとにprivate corpusへアクセスしてnoisy retrieval / aggregationを行う。

query $q_1, q_2, ..., q_T$ がそれぞれprivacy costを持つ場合、compositionによってoverall privacy lossが増える。

DP-SynRAGでは、

```text
Private Corpus
   ↓ one-time DP mechanism
Synthetic Corpus
```

の時点でprivate accessが終わる。

その後のqueryはすべてsynthetic corpusだけを参照するため、$T$が増えても元private corpusに対するprivacy costは増加しない。

この性質は、長期間運用され大量queryを受けるproduction RAGで特に重要である。

## 実験

Medical Synth、MovieLens-1M、SearchQAなど複数domainで評価する。

比較対象には、private retrievalやprivate generationをquery-timeに行う既存DP-RAG methodが含まれる。

評価軸は主に、

- downstream QA / recommendation utility
- retrieval relevance
- privacy budget $\epsilon$
- rare / frequent informationへの性能

である。

## Results

DP-SynRAGは複数dataset・privacy budgetで既存private RAG baselineを上回るutilityを示す。

特にquery数が多いsettingでは、query-time DP methodがprivacy compositionの制約を受ける一方、DP-SynRAGは一度作ったsynthetic corpusを繰り返し使えるため有利になる。

またsynthetic corpusを通常のRAG pipelineへ投入できるため、retrieverやLLMをspecial DP implementationへ置き換える必要がない。

### Rare informationの問題

一方、support documentが非常に少ないtopicでは性能が大きく落ちる。

論文では、あるtopicをsupportするdocumentsが30件以下程度になると、そのtopicを十分なqualityでsynthetic corpusへ再現することが難しくなることを示す。

これはDPの本質的trade-offである。rare informationはindividual recordの影響が大きく、privacyを守るためnoise / suppressionが強く働く。

したがってDP-SynRAGは、

- common facts / aggregate patternsには強い
- unique / rare factsには弱い

という性質を持つ。

## Defense Modelとしての位置づけ

DP-SynRAGは、RAG-ThiefやRAGCrawlerを検知してblockするdefenseではない。

その代わり、**攻撃者に盗まれる可能性があるdatabase自体をDP synthetic dataへ置き換える**。

仮にattackerがsynthetic corpusを大量に抽出しても、DP guaranteeによりoriginal private recordへの依存度が制限される。

attack-defense relationは、

```text
Original Private Corpus
     ↓ DP synthesis
Synthetic RAG Corpus
     ↓ extraction attack
Attacker obtains synthetic text
     ↓
Limited inference about any one original record
```

となる。

これはoutput filteringやprompt guardrailとは異なる、**data-layer defense** である。

## RAG Data Extraction Riskとの関係

knowledge-base stealing attackでは、attack successを「original private corpusをどれだけ復元できたか」で評価する。

DP-SynRAGはこのsecurity boundaryを根本から変える。

RAGのinternal datastoreにoriginal recordsを置かず、DP synthetic documentsのみを置くことで、

- verbatim extraction
- corpus reconstruction
- membership inference
- repeated adaptive querying

が成功しても、元private recordに対するprivacy leakageをboundedにすることを目指す。

特にRAGCrawler / CopyBreakRAGのような大量adaptive query attackに対して、query数とprivacy budgetが独立している点は大きな利点である。

## Limitations

1. **Rare factsのutilityが低下する**  
   少数recordにしか含まれないknowledgeはDPで保持しにくい。

2. **Synthetic hallucinationの可能性**  
   generated corpusなので、元corpusにないinformationを作る可能性がある。

3. **Exact-document retrievalには向かない**  
   legal contractやmanualなど、原文そのものを正確にretrieveする必要があるapplicationではsynthetic replacementが難しい。

4. **Privacyとutilityのtrade-off**  
   小さい $\epsilon$ ほどprivacyは強くなるが、retrieval utilityは下がる。

5. **Attack-specific leakage controlではない**  
   sensitive attributeやorganization policy上絶対に出してはいけないfactがある場合、DPだけでなくaccess controlやoutput filteringも必要である。

## 重要なポイント

- private RAG corpusをone-time DP synthetic corpusへ変換するDefense。
- query-time DPではないため、query数が増えても追加privacy budgetを消費しない。
- standard RAG retriever / generatorをそのまま利用できる。
- zCDPを用いてprivacy accountingを行い、最終的に$(\epsilon,\delta)$-DP guaranteeを与える。
- DP keyword histogram、soft clustering、embedding refinement、private prediction、self-filteringから構成される。
- 多くの設定で既存private RAG baselineより高いutilityを示す。
- rare informationの再現が弱く、support documentが少ないtopicで性能低下が顕著。
- RAG extraction attackを止めるのではなく、「盗まれてもoriginal record privacyを守れるdatabaseを作る」というdata-layer defense。
