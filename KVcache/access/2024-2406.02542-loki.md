# Loki — PCA低次元scoreでdecodeのKVアクセスを絞る

## TL;DR / taxonomy

**Primary category: `access`**。保存済みKVを消すのではなく、各decode stepで**全tokenの低次元Key**から近似scoreを計算し、選んだtop-k tokenの**full-dimension K/V**だけを使ってattention outputを得る。Model weightを再学習しないが、PCA用のoffline calibrationは必要。**保存KVサイズは基本的に減らない**。NeurIPS 2024採択。

## 1. 問題設定とKeyの低rank性

Dense decode attentionでは系列長 `S`、head dimension `D` に対しQK scoreとweighted Vに概ね `O(DS)` の計算・KV memory readが必要。H2Oなどのevictionはcapacityを減らせる一方、後のqueryで必要なtokenを失う。Exact TopKは正確なscoreを全KVに対して計算してから絞るので、選択時のread/compute削減が限定的。

Lokiは各layer/headのkey matrixの実効rankが`D`より小さいことをPCAで検証する。複数モデルで`D=128`に対し、90%のvarianceを説明するrankが概ね80程度という観察がある。**これはattention scoreが必ずrank 80で再現できるという証明ではなく、PCA reconstruction errorが小さいという統計的観察**である。

PCAはcalibration datasetで計算し、layer/headごとに主成分行列を求める。WikiText-103、C4、BookCorpusで得た変換の汎化も比較する。

## 2. Orthogonal transformでexact attentionを保つ

`K ∈ R^(S×D)`、query `q ∈ R^D`、PCA直交行列 `P ∈ R^(D×D)` とする。全dimensionの変換は

$$
\widehat K=KP,\quad \widehat q=qP,
\qquad \widehat q\widehat K^T=qPP^TK^T=qK^T.
$$

したがって**全主成分を使う限りattention scoreは厳密に同一**である。LokiはKeyをPCA座標へ回転して保存し、queryも同じbasisへ回転する。

Top-kを決める段階だけ先頭 `d < D` の主成分に切り詰める。

$$
\widetilde s_t = \sum_{j=1}^{d}\widehat q_j\widehat K_{t,j},
\qquad I=\mathrm{TopK}_t(\widetilde s_t,k).
$$

最後は**選ばれた `I` のfull-D KeyとValue**で通常のsoftmax attentionを計算する。

$$
 y=\mathrm{softmax}\!\left(\frac{\widehat q\widehat K_I^T}{\sqrt D}\right)V_I.
$$

**注意:** これは全tokenへのdense attentionと同一ではない。選択したtoken集合上のattentionをexactに計算するのであって、落としたtokenのsoftmax massは再正規化される。PCAの直交変換自体はexact、**low-rank rankingとtop-k truncationはapproximation**という二段階を分けて理解する。

## 3. PCAを採用する理論的根拠

任意のorthogonal `P` ではfull-D scoreが不変。`d`次元でのQK score誤差について、Cauchy–Schwarzから

$$
\|qK^T-q(KP_{:d}P_{:d}^T)^T\|_2^2
\le \|q\|_2^2\,\|K-KP_{:d}P_{:d}^T\|_F^2.
$$

PCAは右辺のKey reconstruction errorを最小化する。よってscore誤差の**上界**を小さくするが、top-k順位やsoftmax output誤差を直接最小化するとは限らない。論文も別のtransformがscore誤差をより小さくする可能性を認めている。

特にRoPEがある場合、**pre-RoPE KeyでPCAを学ぶか、post-RoPE Keyで学ぶか**で汎化が大きく異なる。Llama-3/Mistralではpost-RoPE PCAでperplexityが大きく悪化することがあり、pre-RoPE PCAが有利。実装では推論時の実際のRoPE後attentionとの整合を維持する必要があり、単にRoPE前のKを直接scoreに入れることはできない。

## 4. Decode algorithmとmemory traffic

```text
Offline:
    for each layer/head:
        collect calibration keys
        P = PCA(keys)

Decode token t:
    q_hat = q_t @ P
    k_hat = k_t @ P
    append k_hat and v_t to full KV cache
    score_approx = q_hat[:d] @ K_hat[:, :d].T
    I = topk(score_approx, k)
    score_exact = q_hat @ K_hat[I, :].T / sqrt(D)
    y = softmax(score_exact) @ V[I, :]
```

Full attentionはquery-key productとvalue weighted sumに約`2DS`の計算を要する。Lokiは近似scoreに`dS`、選択後attentionに`2Dk`、query/key basis変換に`O(D²)`を使う。TopK overheadを無視し、`S≫D`なら

$$
\mathrm{ideal\ speedup}\approx\frac{1}{d/(2D)+k/S}.
$$

`d/D=0.25`、`k/S=0.25`なら理想約**2.67×**。これは**計算量に基づく理論比**であり、実測end-to-end throughputではない。実際はTopK sort、gather、KV append、kernel launch、memory layoutにより小さくなる。

保存するのはfull-Dのrotated Keyとfull-D Valueで、さらにPCA matrixを保持する。したがって**KV storage削減は0**に近い。`K_hat[:,:d]`を読むだけでscoreを計算できるようなmemory layout、full-Dを選択的にgatherするTriton kernelが重要。

## 5. Triton implementation

単純なPyTorch実装では`K_hat[:, :d]`や`K_hat[I, :]`をindexingしたときにdense intermediate tensorが作られ、read削減が相殺される。著者らはTritonで、低次元QK・top-k後のfull-D QK・V weighted sumの各演算に適したkernelを実装し、**必要なdimension/tokenだけをregisterへロード**する。

[SparQ](2023-2312.04985-sparq-attention.md)もquery dimension sparsityを利用するが、Lokiはraw dimensionの絶対値で選ぶのではなく、**calibrationで得たPCA basis**に変換する。PCAの前処理とbasis rotationのcostを払う代わりに、ranked dimensionsがkey分布の主要方向を表す。

Lokiと[Quest](2024-2406.10774-quest.md)の違いは、Questが**sequence pageのmin/max envelope**を使ってcandidate pageを選ぶのに対し、Lokiは**feature dimension**を減らして全tokenのscoreを近似すること。RocketKVのHSAはこの二つの方向を組み合わせる。

## 6. Experiment Setup

- Models: Llama-2-7B/13B、Llama-3-8B/70B、Mistral-7B、Mixtralなど複数モデル。
- Tasks: WikiText-2 perplexity、LM Evaluation Harnessのshort-context tasks、LongBench English tasks。
- Calibration: WikiText-103（主）、C4、BookCorpus。
- Baselines: Full attention、Exact-TopK oracle、H2O。SparQ kernelとの比較もAppendixに含む。
- Budgets: `k_f=k/S` = 0.125/0.25、`d_f=d/D` = 0.125/0.25/0.5等。TopK budgetとdimension budgetは独立。
- Hardware: Perlmutter上の**NVIDIA A100 40/80GB**。大きいモデルではAxoNNでshard。
- Speed: Llama-2-13B-like setupのattention microbenchmark、batch16、prompt 3072、generation 512など。論文が比較するvanilla attentionはHugging Face実装であり、FlashAttention-2/vLLMのend-to-end baselineではない。

## 7. Main Results

Llama-2-7Bのshort-contextでは、pre/post-RoPE PCAのどちらも比較的良い一方、**Llama-3-8Bではpost-RoPE PCAのperplexityが約5から10超に悪化**する場合がある。Llama-3/Mistralはpre-RoPE PCAの方が良い。変換方式の選択は単なる実装詳細でなく、accuracyを左右するablationである。

Llama-2-7B-ChatのLongBenchでは、summarization、few-shot、synthetic、code completionでfull attentionに近いか一部上回る。single/multi-document QAではやや劣り、**HotpotQAで約3ポイント低下**。`k_f=0.25,d_f=0.25`は`k_f=0.125,d_f=0.5`より多くのtaskでaccuracyが良い。

Top-k agreementのJaccard similarityは、比較した代表設定で**約0.9**。これはPCA scoreによる候補選択がExact-TopKに近いことを示すが、attention outputの厳密一致を保証しない。

Attention計算だけを測ると、Llama-2-13B・prompt 3072・generation 512でvanilla attention比**約45%短縮**。一方、Hugging Face TransformersのKV appendが**総実行時間の80%以上**を占める設定があり、end-to-endの改善は限定的。したがって「45%高速化」は**attention部分**の指標として記録する。

## 8. Ablation / sensitivity

**PCA rank (`d_f`) とselected token fraction (`k_f`):** どちらを減らしてもscore推定やattention outputが劣化し得る。`k_f=0.25,d_f=0.25`は`k_f=0.125,d_f=0.5`より精度寄り。前者の理論speedupは2.67×。

**Pre/post-RoPE PCA:** RoPE適用後のposition依存keyをcalibrationすると、位置分布にoverfitする可能性。モデルごとにpre/postを検証して最良を採用するため、1種類のuniversal projectionではない。

**Calibration corpus:** WikiText-103/C4/BookCorpusのPCAで大きな性能差が出ないという観察は、Key subspaceが特定のcalibration textに強く依存しないことを示唆する。

**Exact-TopK比較:** Full-D exact scoreで上位kを選ぶoracleとの差が小さい。したがって主なerrorはtop-k truncationであり、PCA rankingの追加errorは小さい設定が存在する。

**TopK kernel:** 論文はTopK自体の処理時間が縮小したGEMMに近いことを指摘。Triton fusionをさらに進めてもselection costが残る。

## 9. Limitations / 実装検討

1. **KV容量は減らない。** A100でHBM capacityが不足する長文・大batchでは、CPU offloadingやKV quantizationとの併用が必要。
2. **選択後のsoftmax renormalization**により、長いattention tailを捨てる影響がある。[MagicPIG（未登録・前回要約済み）](https://arxiv.org/abs/2410.16179)が扱うimportance samplingの問題意識と対照的。
3. RoPE後のscoreを正しく近似するにはprojectionの適用順とpositionの扱いを検証する必要がある。pre-RoPE PCAが良いという観察は、position-free scoreで代用してよいという意味ではない。
4. GQA/MQAでは複数query headが同一KVを共有する。headごとのtop-k indexをそのままgatherするとKV重複fetchが起こる可能性があり、group-level union/budgetを設計する必要がある。
5. Hugging Face append overheadが支配的な設定での結果であり、PagedAttention/FlashInfer/FlashAttention-2の実測を別途行う必要がある。
6. PCA basisをlayer/headごとに保存し、query/keyを回転するため、KV cache formatの変更が必要。既存prefix cacheとの互換性は保存形式・RoPE処理に依存する。
