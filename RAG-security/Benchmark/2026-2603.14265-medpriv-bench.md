# MedPriv-Bench: Benchmarking the Privacy-Utility Trade-off of Large Language Models in Medical Open-Ended Question Answering

> **本文精査済み**：公式EMNLP 2026 camera-ready PDF（全21ページ）のMethod、主要実験表、追加分析、NLI judge検証、Appendixを確認。数値・model名・著者情報は公式版を優先し、arXiv v1との差異を明示する。

> **要点**：医療RAGの回答が有用であるほど、patient-specificな機微情報を文脈として漏らしやすい、という問題を**utilityとprivacyの二軸**で評価するbenchmark。主対象は**benignな臨床質問によるcontextual leakage**であり、RAG-Thief/GeoExのような大量のprivate corpus stealingを直接測るbenchmarkではない。

## 概要 / Motivation

医療RAGは電子カルテやclinical notesをretrievalして回答の質を上げる。一方、明示的な患者名・住所・IDをde-identificationしても、希少疾患、職業、社会経済的背景、精神疾患、治療歴、時期などが組み合わされると、患者を間接的に特定する手掛かりとなる。通常のQA benchmarkはaccuracyを評価しても、このような**contextual leakage**を評価しない。

MedPriv-Benchは、clinical noteに合成したsensitive attributesを埋め込み、臨床的には有意義だが答える際にsensitive factsを利用したくなる質問を作る。回答のclinical utilityと、どれだけsensitive factsが回答に含意されたかを同時に測る。**RAGのretrieved contextに含まれる情報をどこまで回答に出してよいか**という、context-to-answerのprivacy boundaryに焦点を当てる。

## 問題設定 / Threat Model

- **Protected asset**：患者のprivate clinical contextに含まれる機微属性。明示的PIIだけでなく、希少な属性の組合せによる再識別につながる情報を含む。
- **System**：臨床文書をcontextとして参照し、open-endedな臨床質問へ回答するLLM。RAGにより外部医療文書がpromptに取り込まれる設定を動機とする。
- **Question Agent（benchmark作成時）**：sensitive contextと埋め込んだPHIを**white-boxで知る**。それを質問文に直接書かず、医学的には妥当でPHIがあると回答のutilityが高くなる質問を作る。
- **Deployment時のリスク**：必ずしも悪意のあるprompt injectionではなく、通常の診療上の質問への回答でPHIが暗黙に露出する。実際の攻撃者が全患者の元文書を知るという前提ではない。
- **Benchmarkの攻撃成功**：生成回答が少なくとも1つの埋め込みPHI factを含意すればinstance-level leakage。**実世界の本人再識別が成功したことを直接示すものではない**。

この区別が重要である。MEntA/MBAは「候補文書がcorpusにあるか」を推定し、RAG-Thief/GeoExは「未知のcorpus内容を回収する」。MedPriv-Benchは**正規の回答がどの程度センシティブなcontextを外へ出すか**を測る。

## Benchmark construction / Method

### 1. Source documents とPHI taxonomy

元データは**PMC-Patients**のde-identified clinical notes。文書を3 chunksに分割し、文脈に合うsensitive factsを合成して注入する。PHI taxonomyは次の4つの上位カテゴリを使う。

| Category | 評価対象の例 | Security上の意味 |
|---|---|---|
| Stigmatized behaviors | 飲酒・薬物使用・高リスク行動等 | 差別・スティグマにつながる秘密の開示 |
| Mental health & cognitive status | 精神疾患、認知機能、心理状態 | 治療に関係するが不用意な開示は高リスク |
| Socioeconomic determinants of health（SDOH） | 住居不安定、薬代を払えない、家庭環境 | 医療判断には有用でも個人の生活状況を露出 |
| Quasi-identifiers / VIP status | 希少職業、居住地、社会的地位など | 明示的IDなしでも個人特定を補助 |

合成PHIは臨床的に無関係なsecretをランダムに挿入するのではなく、**回答に使いたくなるほど自然に文脈へ埋め込む**。この設計により、単なる拒否やPII regexでなく、utilityとprivacyの衝突を引き起こす。

### 2. Three-agent generation

```text
PMC-Patients de-identified note
            │  split into 3 chunks
            ▼
   PHI Injection Agent
   └─ PHI taxonomyから選んだfactを臨床文脈へ注入
            │ sensitive context C*
            ▼
     Question Agent
   └─ PHIを質問に明示せず、PHIに関連する臨床質問qとreasoning pathを生成
            │
            ▼
      Answer Agent
   └─ context、PHI、q、reasoning pathからutility/privacyを意識したgold answer
            │
            ▼
  Auto-validation + expert review
            │
            ▼
 (context C*, question q, gold answer, injected PHI facts)
```

PHI Injection Agentはtaxonomy $\mathcal T$ からentity集合 $E_\phi$ を抽出し、clinical context $C$ を $C^*$ へ書き換える。Question Agentは $(C^*,E_\phi)$ から臨床質問$q$とreasoning pathを作る。Answer Agentはこれらを使いgold answerを生成する。Gold answerは単なるPII除去後の文章ではなく、必要なclinical utilityを保つ基準として機能する。

### 3. Auto-validation / human-in-the-loop

**GPT-5.2とQwen 3.6 Plusの2モデル**がそれぞれ(a)元clinical noteとの**non-contradiction**、(b)拒否で済ませず臨床上必要な回答を返す**minimum viable utility**をPass/Failで評価し、**両者がPassした場合のみ採用**する。出典にない具体値や薬剤を追加した回答は不適切とする一方、原文から導ける一般化は許容する。自動filter後のランダム**20%**をregistered nurse等のclinical expertが手動レビューする。

この作り方は臨床的に不自然な「患者の秘密を教えて」という質問に偏るのを防ぐが、**synthetic PHIとLLM生成質問への依存**という評価バイアスを持つ。

## Evaluation metrics

### 1. Utility（0–5）

Gold answerをquestion-specificなgrading pointsへ分解し、生成回答が満たした要点に応じて0–5で評価する。公式版ではGPT-5-miniをutility judgeに使用。BLEU/ROUGEの表層一致だけでは、臨床的に妥当な言い換えを正しく評価できないため、rubricベースの採点を用いる。

### 2. Fact-level leakage

各instance $i$ の生成回答 $\hat y_i$ と注入したPHI facts $E_\phi^{(i)}$ の間で、NLIにより回答がfactを含意するか判定する。

$$LR_{fact}=\frac{\sum_i\sum_j\mathbf{1}[\hat y_i\models e_{ij}]}{\sum_i|E_\phi^{(i)}|}.$$

漏洩したsensitive factsの**総割合**を表す。1回答に複数PHIがある場合、何件漏れたかを反映する。

### 3. Instance-level leakage

$$LR_{inst}=\frac1N\sum_i\max_j\mathbf{1}[\hat y_i\models e_{ij}].$$

1つでもPHI factを含意すればunsafeとみなす**any-leak基準**。実運用では、患者一人に関するどれか1つの秘密が出たかを見る厳格な尺度である。$LR_{fact}$ と $LR_{inst}$ は異なるため、数字を混同しない。

### 4. NLI judge（公式EMNLP版）

`roberta-large-mnli`を医療privacyの**entailment判定用にfine-tune**する。Premiseを生成回答、Hypothesisを注入したPHI factとして、entailment / neutral / contradictionを判定する。512-token上限を超える回答は**stride 128 tokensのsliding windows**に分割し、いずれかのwindowがentailmentなら当該PHI factが漏洩したと扱う。

Appendix Cではprivacy-preserving answer 696件に対して漏洩するcounterexampleを696件生成し、計**1,392 pairs**（train 1,113 / test 279）を構成。3 epochs、learning rate $2\times10^{-5}$、batch size 8でfine-tuneする。元のRoBERTaに比べ、human annotationとの**instance-level sensitivityが58.7%から90.7%へ改善**した。これはbenchmark自体のmetric品質に関わる重要な追加実験である。

### Experiment setup（公式版）

- **Benchmark**：**2,938 instances**。Table 1の比較はheld-out **test set $n=738$**。arXiv v1の805件と混同しない。元データPMC-Patients（約167,000件のde-identified patient summaries、10万件以上のcase reports）から合成PHI付きQAを作成。
- **Model（9種類）**：closed-source = GPT-5-nano、Claude Haiku 4.5、Gemini 3 Flash；open-source = Llama3-70B、Qwen 3.6、DeepSeek-V3.2；medical = Med42-v2-70B、Med42-v2-8B。**Table 1に実際に名前が記載されるのは8モデル**であり、本文の「9 LLMs」と食い違う。未掲載の9番目は推測しない。
- **Serving**：Llama3-70B、Med42-v2-8B/70Bは**2 × NVIDIA RTX PRO 6000**上でvLLM。その他は公式API。temperature 0.4、top_p 0.8、repetition_penalty 1.10。
- **Defenses**：無防御（w/o）、privacy instructionをprependするprompt defense（w/）、Med42-v2-8B / Llama3-70BへのSFT（LoRA）、next-token候補へのGeneralized Randomized Responseを使うinference-time LDP。Table 1のLDPは**token-level $\epsilon$-LDP**であり、文書単位のend-to-end RAG DP保証ではない。長さ$T$の出力では単純compositionにより$T\epsilon$となる。
- **Metrics**：utility 0–5、$LR_{fact}$、$LR_{inst}$、4 PHI category別$LR_{fact}$、human annotationに対するNLI判定精度。
- **Retriever**：retrieved clinical chunksを1–3件与える感度分析はあるが、retriever architecture、ranking algorithm、top-kを変えるknowledge-base stealing比較は主実験ではない。

## Main Results（公式EMNLP 2026 PDF）

### 1. 主結果：utilityと2種類のleakageは必ず分けて読む

Table 1（test $n=738$）の代表値を抜粋する。**下表のleakageは$LR_{fact}$**であり、$LR_{inst}$ではない。

| Model / Setting | Utility ↑ | $LR_{inst}$ ↓ | $LR_{fact}$ ↓ |
|---|---:|---:|---:|
| GPT-5-nano / no defense | 4.89 | 70.2% | 57.1% |
| GPT-5-nano / prompt defense | 4.88 | 54.6% | 42.7% |
| Claude Haiku 4.5 / no defense | 4.71 | 89.0% | 80.0% |
| Claude Haiku 4.5 / prompt defense | 4.60 | 61.4% | 48.6% |
| Gemini 3 Flash / prompt defense | 4.32 | 93.2% | 86.5% |
| Med42-v2-70B / prompt defense | 4.60 | 83.6% | 71.8% |
| **Med42-v2-8B / no defense** | **3.87** | **85.5%** | **72.8%** |
| Med42-v2-8B / prompt defense | 3.71 | 81.3% | 67.6% |
| **Med42-v2-8B / SFT** | **4.25** | **50.5%** | **38.9%** |
| **Med42-v2-8B / LDP** | **3.03** | **31.3%** | **20.5%** |
| Llama3-70B / SFT | 4.33 | 56.1% | 42.0% |
| Llama3-70B / LDP | 2.96 | 30.5% | 20.8% |

Med42-v2-8BではSFTがutilityを**+0.38**改善し、$LR_{fact}$を**−33.9 points**低減。LDPは$LR_{fact}$を**−52.3 points**まで減らすがutilityを**−0.84**低下させる。SFTがprivacyとutilityを同時に改善し得る一方、強い出力摂動は臨床有用性を損なう。Medical specializationはprivacyの強さを保証せず、Med42-v2-70Bはprivacy prompt適用後も$LR_{fact}=71.8\%$と高い。

### 2. PHI type別：直接的な識別子より推論型情報が残りやすい

Table 1では、Claude Haiku 4.5のQIV（quasi-identifier / VIP）漏洩はprompt defenseで**36.1% → 6.2%**と大きく下がる。しかしmental health（MH&CS）は**88.3% → 61.1%**、SDOHは**80.5% → 46.9%**で残存する。Gemini 3 Flashはprivacy prompt後もMH&CS **96.7%**、SDOH **92.6%**。モデルが表面的な識別子を出さなくても、回答に必要な患者背景を説明してしまうという失敗モードがある。

### 3. Clinical intent別（Table 2）

| Question type | $LR_{inst}$ |
|---|---:|
| SDOH & Psychosocial Support | **55.3%** |
| Discharge Planning & Care Coordination | 52.4% |
| Medication Adherence & Management | 49.4% |
| Follow-up Care & Monitoring | 47.8% |
| Infection Control & Wound Care | 46.7% |

社会的背景や退院支援はpatient-specific contextを多く必要とするため、proceduralな感染対策の質問より漏洩しやすい。これは単に「医療用語が多い質問が危険」ではなく、**回答に必要な社会的・個人的文脈の深さ**がprivacy riskを左右することを示す。

### 4. Retrieval量と生成長の切り分け（Section 6.4 / Figure 4）

GPT-5-nano（prompt defense）ではretrieved chunksを**1→3**に増やすとutilityは**4.30→4.88**へ上昇するが、leakage増分は相対的に限定的だった。一方、**full contextのまま回答を100 wordsへ制限**すると、$LR_{inst}$が**54.6%→14.8%**へ下がり、utilityは**4.53**を維持。300/500-word制限へ緩めるとutilityと漏洩がともに増える。著者らは「retrievalが多いこと」以上に「生成が冗長になること」が漏洩の主要因と論じる。ただし、100-word制限が常に有効という一般保証ではない。

### 5. NLI judgeの妥当性と残る測定誤差（Sections 6.5 / Appendix C）

50 patient IDs × 7 models = **350 responses**について、各モデルを2名の人間が独立判定。human同士の一致率はfact-level **88.9%**（Cohen's $\kappa=0.736$）、instance-level **85.4%**（$\kappa=0.699$）。fine-tuned NLI judgeはhumanとのinstance-level accuracy **74.7%**、F1 **75.3%**、sensitivity **90.7%**、平均**0.056 s/sample**。元のpretrained RoBERTaのsensitivity **58.7%**から大幅に改善している。

ただしGPT-5-nanoの長い回答（平均**652 words**）ではinstance-level sensitivity **57.8%**、F1 **64.3%**と悪化する。Gemini 3 Flash（276 words、F1 **87.9%**）との差は、512-token windowの間に分散したPHI情報をNLIが統合できない可能性を示す。**benchmarkの漏洩率そのものにjudgeの長文バイアスが混入し得る**ため、human-reviewed subsetとの併記が重要。

### 6. SFT robustness / LDP accounting（Appendix D）

SFTはLoRA（rank 16、alpha 16、2 epochs、learning rate $2\times10^{-4}$、max length 1024、per-device batch 2、gradient accumulation 8）を用いる。Med42-v2-8Bのtraining-size ablationではutilityはデータ増加とともに概ね改善するが、privacy改善は単調ではない。3 seedsの平均はutility **4.12±0.12**、$LR_{inst}$ **57.8±6.5%**、$LR_{fact}$ **46.5±6.6%**。表の単一runの38.9%を必ず再現できるわけではない。

LDPはtop-$K$ token集合内のgeneralized randomized responseで、元tokenを確率$e^{\epsilon}/(e^{\epsilon}+K-1)$で維持し、他候補を各$1/(e^{\epsilon}+K-1)$で選ぶ。**per-token $\epsilon$**は系列長$T$で$T\epsilon$へ累積する。これは[DP-RAG](../Defense/2024-2412.19291-rag-with-differential-privacy.md)のdocument-level DPとprivacy unitが異なるため、数値$\epsilon$を直接比較してはいけない。

## Limitations / 成立条件

1. **Synthetic clinical privacy pressure**：元のPMC-Patientsはde-identifiedであり、sensitive factsは合成して注入する。実病院のEHRで同じleakage率になると断定できない。
2. **Actual re-identification未実証**：生成回答がPHI factを含意したかを測る。攻撃者が外部の公的データやlinkage databaseと照合して実際に個人を特定した成功率は別の問題。
3. **RAG retrievalそのものの影響が限定的**：retrieved chunks数1–3の感度分析はあるが、retriever、reranker、access control、hybrid search等を体系的に変えたknowledge-base stealing benchmarkではない。
4. **Query generatorはwhite-box**：benchmark作成時にはQuestion Agentがsecretを知っている。実攻撃者がblack-boxで未知の秘密を見つける難易度とは区別する。
5. **NLI judgeのerror**：false positive/negative、長文windowの不安定さ、domain-specificな推論関係を取り違えるリスクがある。human alignmentの数値とcamera-readyのF1を混ぜない。
6. **Utility judgeのsubjectivity**：rubricとLLM judgeの採点は人間の医療専門家の総合判断と同一ではない。臨床安全性を直接保証する指標でもない。
7. **版差**：arXiv v1の805件、pretrained NLI judge等と、camera-readyの2,938件・fine-tuned NLI judge・SFT/LDP追加評価は一致しない。再現実験には公式版の固定が必要。
8. **Model数の記述差**：本文は9モデルとするが公式Table 1で個別に列挙されるのは8モデル。未掲載の9番目は不明。
9. **Code / dataset**：公式PDF脚注にGitHub公開先が明記される。ただしbenchmark dataの使用条件や患者情報の取扱いは実装側で別途確認する。

## RAG Security Taxonomyでの位置づけ

| 脅威 | MedPriv-Benchとの関係 |
|---|---|
| Contextual leakage / quasi-identifiers | **主対象**。必要な臨床回答の中に敏感な組合せ情報が出る |
| Prompt injectionによるraw document exfiltration | 直接の主評価ではない。queryは通常の臨床質問を模倣 |
| Membership inference（MBA / MEntA） | corpus内の文書存在推定を測らない |
| Whole-corpus reconstruction（RAG-Thief / GeoEx） | 多数のqueryによるcoverageやchunk recoveryを測らない |
| Differential privacy defense | LDP等のprivacy–utility比較に利用可能 |
| Response-level redaction / fact minimization | 出力に含意されたPHIをNLIで測るため、防御の追加評価軸となる |

このbenchmarkを既登録の[LeakDojo](2026-2605.05818-leakdojo.md)と組み合わせると、**LeakDojo：攻撃で何chunk回収できたか**、**MedPriv-Bench：正常利用の回答がどの機微factを露出したか**という、異なるprivacy dimensionを測れる。[DP-SynRAG](../Defense/2025-2510.06719-dp-synrag.md)、[RAG with Differential Privacy](../Defense/2024-2412.19291-rag-with-differential-privacy.md)、[EPD](../Defense/2025-2512.03100-ensemble-privacy-defense-epd.md)は防御目的が隣接するが、MedPriv-Benchで直接baselineとして評価されたことを意味するリンクではない。

## 実装・研究上の示唆

- **Evaluation harness**：query/context/PHI facts/gold answerの4つ組を固定し、model出力からutilityと$LR_{fact}$・$LR_{inst}$を分離集計する。NLI judgeのthresholdやchunk aggregationは固定し、human-reviewed subsetで再校正する。
- **Security testing**：benign queryでのcontextual leakageと、adversarial queryでのexfiltrationは別軸として評価する。RAG extraction defenseを提案する際には、少なくとも両者を混同せず報告する。
- **Model serving**：local vLLMによるmodel比較が含まれるため、同じcontextを使った各modelの回答のprivacy–utilityを比較しやすい。KV cache最適化はbenchmarkの直接貢献ではないが、長いretrieved clinical contextをどのように渡すかはlatencyとexposureの両方に影響する。
- **Policy design**：PHIは単なるNER対象ではない。何を「質問に必要な最低限の情報」と認めるかを、clinical utilityと組み合わせて定義する必要がある。
