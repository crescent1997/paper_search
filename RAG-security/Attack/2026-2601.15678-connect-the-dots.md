# Connect the Dots: Knowledge Graph-Guided Crawler Attack on Retrieval-Augmented Generation Systems

> RAGから得られた情報をKnowledge Graphとして蓄積し、未探索領域を選択しながら次のqueryを生成することで、RAGの内部Knowledge Baseを効率的に盗み出す攻撃手法 **RAGCrawler** を提案する。

## 概要

RAGではモデル本体だけでなく、Retrieverが参照する非公開corpusにも企業固有文書、専門知識、ライセンス文書、社内手順などの重要な情報が保存される。そのため、外部ユーザが多数のqueryを繰り返すことで、回答に現れる断片情報から内部Knowledge Baseを徐々に復元できる可能性がある。

既存のknowledge-base stealing attackは、直前のRAG responseからキーワードやentityを抽出し、それについて再度質問するという**局所的な探索**が中心である。この方式では、一度見つけたsemantic regionの周囲を何度も掘ってしまい、query budgetを消費する割に新しいdocumentへ到達しにくい。その結果、corpus coverageが早期に飽和しやすい。

本論文ではこの問題を **Adaptive Stochastic Coverage Problem (ASCP)** として捉える。各queryを「未知のcorpus領域を確率的に新しくcoverするaction」とみなし、過去のquery / response履歴を踏まえて、次のqueryによるexpected marginal gainを最大化することを目標とする。

しかしblack-box RAGでは、攻撃者は実際にどのdocumentがretrieveされたか、retrieval scoreはいくつか、corpus全体がどのような構造を持つかを観測できない。

そこで提案手法 **RAGCrawler** は、過去の全responseから攻撃者側のKnowledge Graphを逐次構築し、このgraphを「これまでどこを探索したか」を表すproxy stateとして使う。Knowledge Graph上で未探索または情報利得の高そうなentity / relationを選び、それを次の自然言語queryへ変換することで、local query chainingではなく**global planningに基づくcorpus exploration**を行う。

## 問題設定

攻撃対象はAPIやchat interfaceとして公開される **black-box RAG system** である。攻撃者は通常ユーザと同じquery interfaceしか利用できず、内部構造へのアクセスは持たない。

攻撃者が直接観測できないものは、例えば以下である。

- 内部corpus
- retrieveされたdocument ID
- retrieval score
- Retriever / rerankerの内部構造
- retrieval pipeline

攻撃者が利用できるのは基本的に、入力したqueryとRAGから返されるresponseだけである。

本論文では特に、内部documentの生textを直接要求するような露骨なprompt injectionではなく、**自然な質問を多数繰り返して知識を少しずつ回収するimplicit stealing attack** を想定する。個々のqueryは通常のinformation-seeking queryに見えるため、単純なmalicious prompt detectionだけでは見つけにくい。

目的は、query budget $B$ の中で可能な限り広いcorpus情報を取得することである。理想的には、各stepで「まだ得ていない情報をどの程度増やせるか」を表す **Conditional Expected Marginal Gain (CMG)** が最大となるqueryを選びたい。

このとき、query $q$ の価値は、これまでの観測履歴 $\psi$ を条件として、そのqueryによって新たに得られるcoverageの期待増分として考えることができる。

理論的には、coverage functionがadaptive monotoneかつadaptive submodularであれば、各stepで最大CMGを選ぶadaptive greedy policyは、最適policyに対して $(1-1/e)$ 近似を持つ。

ただし実際のRAG attackでは、

1. 真のcoverageを直接観測できない
2. 自然言語queryのaction spaceが非常に大きい
3. 過度に攻撃的なqueryはguardrailに拒否される可能性がある

という問題がある。

RAGCrawlerはこの巨大なquery spaceを直接探索する代わりに、Knowledge Graph上のentity / relationを中間表現として使い、探索問題を扱いやすくしている。

## 手法

RAGCrawlerは主に3つのcomponentからなる。

1. **KG-Constructor**
2. **Strategy Scheduler**
3. **Query Generator**

全体の流れは、

```text
Query
  ↓
Victim RAG
  ↓
Response
  ↓
KG-Constructor
  ↓
Global Knowledge Graph
  ↓
Strategy Scheduler
  ↓
Entity / Relation Anchor
  ↓
Query Generator
  ↓
Next Query
```

となる。

各turnで得られたresponseをKnowledge Graphへ取り込み、そのgraphを使って次に探索するsemantic anchorを選び、自然言語queryを生成する。このループをquery budgetの範囲で繰り返す。

### 1. KG-Constructor

KG-Constructorは、black-box環境では観測できない「真のcorpus coverage」を、攻撃者側から追跡可能なgraph stateへ置き換える役割を持つ。

各RAG responseから、

- entity
- relation
- entity間のtriple

を抽出し、過去の全responseを統合したglobal Knowledge Graphを構築する。

例えば、あるresponseから特定の薬剤、疾患、治療法、研究機関などのentityと、それらの関係を抽出してgraphへ追加する。次のturn以降は、このgraphを参照することで「どのentityは十分掘ったか」「どのrelationはまだ情報が少ないか」を判断できる。

単純に文字列一致でnodeを作ると、同一概念が異なる表記で複数nodeに分かれてしまう。そこでentityやrelationをembedding化し、cosine similarityが閾値を超える場合にsemantic mergeする。

これにより、例えば表記揺れや同義語を別々の探索領域として数えることを防ぐ。

このKnowledge Graphは、単なるquery historyではなく、**攻撃履歴そのものを構造化したglobal memory** として働く。

### 2. Strategy Scheduler

RAGCrawlerの中心となるcomponentである。

自然言語queryそのものを探索するとaction spaceが大きすぎるため、RAGCrawlerでは **Entity → Relation** という2段階で次のsemantic anchorを選択する。

Entityは、

> どのknowledge regionへ移動するか

を決定し、Relationは、

> そのregionをどの方向へ掘るか

を決定する。

例えば、ある薬剤entityを選んだ後、`side_effect`、`clinical_trial`、`mechanism` など、まだ十分に探索していないrelation方向へqueryを生成するイメージである。

Entityのscoreには、主に次の2種類の情報を組み合わせる。

- **Empirical payoff**: 過去にそのentity周辺を探索したとき、どれだけ新しいknowledgeが得られたか
- **Graph prior**: graph構造上、そのentityがどれだけ新しい領域へ接続しそうか

つまり、単にdegreeが高いentityを選ぶのでも、直近で情報が多く出たentityだけを選ぶのでもなく、**過去の実績とgraph上の未探索可能性の両方を見る**。

Relationについても、既に多く探索した方向を避け、まだ情報が少ないrelationを優先する。

有望なrelationが見つからない場合は、entityのみをanchorとしてqueryを生成することもできる。

また、各turnでgraph全体のscoreを再計算するとコストが大きいため、scoreをcacheし、graph更新の影響を受けたnodeだけを再計算するlazy updateも導入している。

この設計により、直前のresponseに含まれていた単語をそのまま次のqueryへ使うのではなく、**攻撃履歴全体を見て、次に最もcoverageが伸びそうな場所を選ぶ**ことができる。

論文の重要な発想は、RAG stealingを「どんなpromptを書けば情報が漏れるか」というprompt engineering問題ではなく、**未探索領域を効率良く巡回するexploration problem** として捉え直した点にある。

### 3. Query Generator

Strategy Schedulerが選択したentity / relationを自然なqueryへ変換する。

生成するqueryは、

- 過去queryと重複しにくい
- target entity周辺の別documentをRetrieverに引かせやすい
- 明示的なdata extraction requestにならない
- victim側のguardrailに拒否されにくい

ように作られる。

例えばSchedulerが、

```text
Entity: remdesivir
Relation: adverse_effect
```

を選んだ場合、それをそのまま内部情報抽出命令として使うのではなく、

```text
What adverse effects have been reported for remdesivir?
```

のような通常の質問へ変換する。

ここでLLMは主にsemantic anchorから自然言語queryへの変換を担当する。長期的な探索方針そのものはKnowledge GraphとSchedulerが担当するため、attacker側に非常に強力なLLMを置かなくても性能を維持できる。

## 評価

TREC-COVID、SciDocs、NFCorpus、Healthcareなど複数corpusを用い、既存のRAG extraction attackである **RAGThief**、**IKEA** と比較する。

代表的な実験ではBGE Retrieverを使い、複数のgenerator modelを組み合わせて評価している。

主な評価指標は、

- **Coverage Rate (CR)**: 元corpusのどの程度まで情報を回収できたか
- **Semantic Fidelity (SF)**: 抽出内容が元情報をどの程度意味的に保持しているか
- **Target-Coverage Query Complexity $Q_\gamma$**: coverage $\gamma$ に到達するまでに必要なquery数
- 抽出knowledgeから構築したsurrogate RAGのanswer similarity

である。

### Corpus Coverage

1,000 query budgetでは、RAGCrawlerは平均 **66.8%のcorpus coverage** を達成し、最大で **84.4%** に達する。

strongest baselineに対するcoverage improvementは **44.9%**。

またSemantic Fidelityでも平均 **0.605** を達成し、IKEAの0.559、RAGThiefの0.417を上回る。

特に高coverage領域で差が大きい。baselineは同じsemantic regionを何度も掘るためcoverage curveがplateauしやすい一方、RAGCrawlerはKnowledge Graphを使って未探索regionへ移動し続けることができる。

### Query Efficiency

70% coverageへ到達するまでのquery数 $Q_{0.7}$ を比較すると、RAGCrawlerだけが全datasetで70%へ到達する。

代表値は、

- TREC-COVID: 4,040 queries
- SciDocs: 1,163 queries
- NFCorpus: 595 queries
- Healthcare: 568 queries

である。

baselineに対して、70% coverageへ到達するまでのquery数を平均で少なくとも **4.03×削減**している。

つまり本手法の利点は最終coverageだけでなく、**同じcoverageへより少ない問い合わせで到達できること**にもある。

### Surrogate RAG Reconstruction

抽出したknowledgeからattacker側にsurrogate RAGを構築し、victim RAGの応答をどの程度再現できるかも評価している。

RAGCrawler由来のsurrogateはdatasetによって **38.1%–52.6%** のsuccess rateを示し、answer similarityは最大 **0.6992**、ROUGE-Lは最大 **0.2408** に達する。

これは単なる断片的なinformation leakageではなく、十分に広いcorpus情報を抽出できれば、**victim RAG serviceの振る舞いをある程度複製できる**ことを意味する。

Knowledge Base自体がサービス価値の大きな部分を占めるRAGでは、model stealingとは別に、retrieval corpus stealingが独立した知的財産リスクになることを示している。

### Retriever Switching

RetrieverをBGEからGTEへ変更してもRAGCrawlerは高い性能を維持し、平均coverage **76.6%** を達成する。

IKEAは53.9%、RAGThiefは28.2%であり、RAGCrawlerの優位性は特定のRetriever architectureだけに依存していない。

### Query Rewriting / Multi-Query Retrieval

RAG側でquery rewritingを導入した場合でも、RAGCrawlerは平均coverage **74.1%** を維持する。

つまり、

```text
User Query
   ↓
Query Rewriter
   ↓
Retriever
```

という構成だけではknowledge-base stealingへの十分な防御にはならない。

またmulti-query retrievalでも高いcoverageを維持する。

興味深い点として、retrieval diversityを高めるためのmulti-query retrievalは、1回のqueryから複数semantic clusterの情報を返す可能性があるため、global graphを構築するRAGCrawlerにはむしろ有利に働く場合がある。

つまり、retrieval qualityを高めるための仕組みが、information leakageの観点では攻撃面を広げる可能性がある。

### Smaller Attacker LLM

攻撃側LLMを比較的小さい **Qwen2.5-7B-Instruct** へ変更しても、平均coverage **71.3%**、Semantic Fidelity **0.585** を達成する。

この結果から、RAGCrawlerの性能向上は単純に「強いLLMが巧妙なpromptを書くから」ではなく、

- global Knowledge Graph
- Strategy Scheduler
- query redundancy control

に大きく依存していることが分かる。

これは防御上も重要で、高性能なfrontier modelを攻撃者が使わなくても、**探索状態を適切に管理するだけで高効率なcorpus extractionが可能**であることを意味する。

## まとめ

RAGCrawlerは、RAG Knowledge-Base Stealingを単なるprompt engineeringではなく、**「限られたquery数で未知corpusをどれだけ広く探索できるか」**というcoverage optimizationとして捉えた攻撃手法である。

従来手法では、

```text
Response
  ↓
Keyword / Entity Extraction
  ↓
Next Query
```

という局所的なquery chainingが中心であり、現在いるsemantic regionから抜け出しにくかった。

RAGCrawlerでは、

```text
All Previous Responses
        ↓
Global Knowledge Graph
        ↓
Unexplored Region Selection
        ↓
Next Query
```

というglobal planningを導入する。

各componentの役割は明確である。

| Component | Role |
|---|---|
| KG-Constructor | 過去のresponseから得たknowledgeをglobal stateとして構造化する |
| Strategy Scheduler | 未探索かつinformation gainが高そうなentity / relationを選ぶ |
| Query Generator | semantic anchorを自然で非冗長なqueryへ変換する |

結果として、1,000 queriesで平均66.8% coverage、最大84.4% coverageを達成し、strongest baselineに対して44.9%改善している。また70% coverageへ到達するまでのquery数も平均4.03×以上削減する。

特に重要なのは、個々のqueryは自然な質問に見えるため、**1 query単位のprompt filteringだけでは防御しにくい**点である。

RAGの防御では、

- user単位でのmulti-turn semantic exploration監視
- query budget / rate limit
- retrieval結果からresponseへ渡す情報量の制御
- response-level information leakage detection
- semantic coverageの拡大速度を利用した異常検知

など、**複数turnをまたいだinformation extraction全体を監視する設計**が重要になることを示唆している。

## 関連文献

### RAGThief

RAGから内部Knowledge Baseを抽出する代表的な既存attack。本論文の主要baselineの一つ。

複数turnで得られたresponseを利用して次のqueryを生成するが、RAGCrawlerほど明示的なglobal exploration stateを持たないため、同一semantic regionを繰り返してcoverageが飽和しやすい。

### IKEA

iterativeなquery generationによってRAGからknowledgeを抽出する既存attack。

RAGCrawlerとの主要な違いは、Knowledge Graphをglobal memoryとして持ち、**「次にどこを探索すべきか」をcoverage optimizationとして扱う**点にある。

### Membership Inference against RAG

特定documentがRAGのretrieval corpusに含まれているかを推定するprivacy attack。

Membership inferenceが主に「このdocumentは入っているか」というbinary / probabilistic inferenceを目的とするのに対し、RAGCrawlerは**corpusそのものを広く復元すること**を目的とする。
