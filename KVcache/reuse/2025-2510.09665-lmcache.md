# LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference

## 概要と選定理由

**reuse → serving infrastructure / cross-query prefix caching / cross-engine KV transfer**。KV cache reuse研究の多くは「どのKVを再利用すれば正確か」を考えるが、実用上は**GPU paged KVをどう取り出し、CPU・SSD・remote storageに置き、次requestのGPUへ効率よく戻すか**も同程度に重要。LMCacheはこのdata movementを独立したcache layerとして実装し、vLLM/SGLangとstorageの間のinterfaceを標準化する。

主用途は (1) 複数requestの**同一prefix**の再利用、(2) prefillとdecodeを別engine/GPUへ分離する**PD disaggregation**。論文が直接実現するのは**転送・配置・lookupの効率化**であり、異なるcontextのKVを連結した際のaccuracy劣化を修復するアルゴリズムではない。vLLM/LMCache上にCacheBlend/ProphetKV型のblenderを組み込む研究にとって、基盤となる論文。

## 問題設定と既存法の問題

GPU内prefix cacheだけでは容量が限られ、GPUから追い出されたcontextを再利用できない。長文promptのKVをCPU/remote storageへ移すと、従来の`torch.save/torch.load`や小さなtensor copyは遅い。vLLM等は**paged KV memory**を使うため、論理的に連続するtokenでもGPU上では小さな不連続pageに分散する。

論文の例ではLlama-3.1-8B-InstructのvLLM pageは約62.5KB。多数の小pageをそのまま送るとNIC/PCIeの帯域を使い切れない。従来のCPU offloadや独立storage backendは、engine側の頻繁なAPI/layout変更にも追随しづらい。さらにschedulerやrouterがcacheの位置・hit数を知らなければ、再利用の機会を活かせない。

## System architecture

**Inference engine (vLLM/SGLang) ↔ KV connector ↔ LMCache token processor / storage manager / transfer channel ↔ GPU・CPU・disk・remote storage**。

- **Store path**：scheduler/connectorがtoken列とGPU page位置を収集し、既存backendにないKV部分を判定。GPU上のpaged KVを連続bufferへpackし、chunk単位でoffloadする。
- **Load path**：token prefixを照合し、external cacheのhit token数をschedulerへ返す。該当chunkをGPU bufferへloadし、kernelでpaged KVへunpackしてからモデル実行を継続。
- **PD disaggregation**：prefill engineで生成したKVをdecode engineへ転送。単なるprefix hitとは異なり、同一request内で異なるengineへKVを受け渡す。
- **Management plane**：controllerが各instance・storage tierのKV所在を管理し、lookup/move/clear/pin/compress等のAPIを提供する。

### 1. Configurable chunk sizeとpaged↔contiguous変換

vLLMのnative page単位でI/Oを起こさず、複数layer・pageをまとめた**default 256-token chunk**を使う。GPU上の散在pageからCUDA kernelで連続**streaming GPU buffer**へ集約し、DMAでCPU/remote storageへ送る。読み戻しでは逆にbufferからpaged layoutへscatterする。これは**論理的cache chunk**と**GPU物理page**のgranularityを分離する設計。

`LMCACHE_CHUNK_SIZE`は単なるdisk fileサイズでなく、hash/lookup/transferの粒度と、部分一致prefixの扱いに影響する。chunkが大きいほどI/O効率は良いが、小さなprefix差分に対して無駄な転送が生じやすい。

### 2. Batched/parallel store-loadとdecode遅延書込

CPU DRAM、local disk、remote DRAM/disk、object storage等への転送をまとめ、複数device間で並行store/loadする。生成した1 tokenごとにoffloadすると小さいwriteが多発するため、**decode KVはchunkが溜まるまでbuffering**して遅延保存する。PCIe等がfull-duplexなら上り下り転送を並列化する。

### 3. Compute–I/O overlapとprefetch

Layer-wise pipelineでモデル演算とKV転送を別CUDA streamで進める。論文は**current layerの演算中に次layerのKVを読み込む**構成を説明する。またschedulerで待機しているrequestのKVを事前に遅いtierから速いtierへprefetchできる。これにより、`load全層 → compute`という直列化を避ける。

### 4. Minimum-copyとdynamic offloading

同じKVを複数destinationへ送る場合はreference countingで余分なhost copyを避ける。GPU free pagesをすべて即座にCPUへ複製するのではなく、start/current/end pointerで**必要な範囲のみdynamic offload**する。重複量を減らすと新requestがpageを取得する際にstallし得るため、複製window幅はmemory節約とlatencyのtrade-off。

### 5. Connectorと管理API

vLLMのscheduler側で`get_num_new_matched_tokens`、`update_state_after_alloc`、`build_connector_meta`などを用いてexternal hitとallocationを扱い、model runner側で`start_load_kv` / `wait_load_kv` / `start_store_kv` / `wait_store_kv`を実装する。これは**engineのscheduler状態とGPU transferを分離**するための境界。

Controllerは`lookup(tokens)`で(instance_id, storage_device, hit_tokens)を返し、`move`、`clear`、`pin/unpin`、`compress/decompress`等を提供する。`compress` APIがあることは、論文本体が特定のlossy KV compression法を新規提案したことを意味しない。

## Experiment Setup

- **Model**：Llama-3.1-8B/70B-Instruct、Qwen2.5-Coder-32B、Qwen2.5-72B、Qwen3-Coder-480B-A35B FP8など。
- **Hardware**：single-node 8×H100サーバ（モデルごとに必要なGPU数を割当）。central remote storageは15Gbps接続。PD disaggregationではNVLink等を使用。
- **Workload**：emulated multi-round QA、LongBench/TriviaQA、vLLM random benchmark、企業traceに基づく入出力長分布。
- **Baselines**：vLLM GPU-only prefix caching、vLLM native CPU offloading、native PD disaggregation、commercial API（black-box比較）。
- **Metrics**：TTFT、ITL（inter-token latency）、throughput/QPS、cache hit、remote loading overhead。

## Main Results

### Single-node CPU offload（Figure 8）

5モデルのmulti-round workloadで、低QPSではTTFTが**1.9–8.1×短縮**。同一TTFT条件のthroughputは最良baseline比**2.3–14×**。ITLはQPS=1で7–92%低減（各モデル・条件に依存）。Abstractの「最大15×」は異なる条件をまとめた上限値で、全ケース共通ではない。

### Real trace（Figure 9）

企業traceに合わせた複数モデルの実験で、high QPSにおけるTTFTを**4.4–6.6×**短縮、ITLを**34–58%**短縮した条件を報告。hit率の改善と効率的なchunk転送の両方が効いている。

### Centralized remote storage（Figure 11）

15Gbpsのcentral backendに置いたKVを利用し、TriviaQAで**1.3–3×のthroughput改善**。remote backendはより多くのKVを保持できるが、CPU-localよりloadが遅く、**短いcontextではprefillの方が速い**場合がある。常にexternal hitを優先すべきではない。

### PD disaggregation（Figure 12）

8K input / 200 outputの設定で、vLLM native PD disaggregation比でmean TTFT **1.53–1.84×**、mean ITL **1.12–1.66×**の改善を報告。これはcross-request semantic reuseではなく**同一requestのprefill→decode KV転送**の改善。

## 主要ablation・システム分析

1. **Transfer granularity**：小pageを逐次送る方式はPCIe/network帯域を使い切れない。256-token chunkへのpack/unpackで大きなDMAを実現する。比較ではpage size、layer数、head数、token数によりbyte量が変わる。
2. **Overlap**：layer-wise load/storeとGPU computeの並列化、queue待機時間を使ったprefetchがstallを減らす。GPU演算がI/Oを隠せるかは層ごとのcompute時間とstorage bandwidthに依存。
3. **Dynamic offloading**：複製windowが小さいほどCPU容量節約になる一方、GPU page allocationがoffload進行待ちでstallする。pointer管理がそのtrade-offを制御。
4. **Hit率**：企業運用ではcontext truncationがprefixの先頭一致を壊し、hit率を大幅に下げ得ると指摘。長文RAGでchunk順序が変わる場合も同様。
5. **Network vs recompute**：remote KVの転送コスト$T_{load}$と、miss部分のprefill $T_{prefill}$を比較する判断が必要。CacheGenのtransport圧縮と組み合わせる余地がある。

## Limitations・実装上の注意

- **Semantic/position-independent reuseを自動実現しない**。基本は同一prefixをhash等で照合し、既存の正しいKVを転送する。異なるdoc境界の再RoPEやattention修復は別手法。
- **速度の条件依存**。throughput 15×をどのモデル・contextでも再現できるわけではない。GPU cache hit、storage帯域、chunk size、同時実行数、CPU pinned memory、CUDA stream競合に左右される。
- **Accuracy評価は主目的ではない**。正しいprefix KVの再利用が前提。lossy compressionやblenderで部分再計算した際の品質保証は提供しない。
- **Integration drift**。vLLM v1 scheduler、paged layout、attention backend、model architectureの変更でconnectorのhookとcache layoutを保守する必要がある。
- **Memoryとcost**。host/storageへKVを大量に保存するため、GPU節約と引き換えにCPU RAM・network・storage costを支払う。request間reuse頻度が低い場合は不利。

## Taxonomy・関連研究との差分

| 手法 | 主に解決する問題 | 単位 | 修復・再計算 |
|---|---|---|---|
| **LMCache** | KVの**保存・検索・転送** | token chunk / paged KV / request | 原則なし（同一prefixを復元） |
| [Prompt Cache](2023-2311.04934-prompt-cache.md) | 定型prompt segmentのprecompute | module / prompt span | position-independent再利用設計 |
| [CacheGen](../compress/2023-2310.07240-cachegen.md) | external KVのnetwork byte圧縮 | transport chunk | bandwidth次第で再prefill |
| [CacheBlend](2024-2405.16444-cacheblend.md) | 非prefix document結合時の品質 | token | KV差分に基づく再計算 |
| [KVLink](2025-2502.16002-kvlink.md) | 独立doc KV連結時の品質 | document / special token | positional adjustment + fine-tuning |
| [KVShare](2025-2503.16525-kvshare.md) | semantic overlapを跨ぐ共有 | semantic span | differential editing |
| [ProphetKV](2026-2602.02579-prophetkv.md) | query重要tokenのreuse品質 | token | selective recomputation |
| [A³](2025-2511.17560-a3.md) | question-aware KV fusion | chunk / token | fusion |

**研究上の位置づけ**：LMCacheの外部cache layerを下位基盤とし、上位で「KVをどこから探すか」「cacheをどう修復するか」「どこまで再計算するか」を実装する分離が自然。特にvLLM/LMCacheでselective recomputationを実験する際は、(1) schedulerが既存tokenをhitとして扱う区間、(2) blenderが実際に再計算するquery位置、(3) store/load時の物理KV page layout、(4) CUDA stream同期、を混同しないこと。
