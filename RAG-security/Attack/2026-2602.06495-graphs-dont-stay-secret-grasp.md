# Graphs Don't Stay Secret: Practical Subgraph Reconstruction Attacks on Defended Graph RAG

> **GRASP**（Graph RAG Reconstruction Attack for Subgraph Profiling）は、Graph RAGが外部API経由で提供する関係情報を利用して、非公開knowledge graphのtarget entity周辺の**型付き関係**を再構成するclosed-box attack。GraphRAGのsafe system promptが禁止する単純なcontext dumpを回避しても、構造化された関係処理能力そのものがprivacy leakageの経路になり得ることを示す。

## 概要

Graph RAGは通常のtext-chunk RAGと異なり、entity、relation、source textを表形式・リスト形式に正規化してgeneratorに渡す。これはmulti-hop reasoningに有効だが、非公開corpus由来のrelation type、source/destination、組織固有ontologyを外部から推定できる危険も作る。

従来のdata extractionはretrieved contextをそのまま列挙させる方式が多く、Graph RAGで「contextの逐語開示やgraph構造を出さない」というsafe system promptを入れると、拒否・抽象化・relation typeの言い換えにより失敗しやすい。特にentity pairだけでなくrelation typeも正確に復元する場合、この問題が顕著になる。

本論文は**targeted one-hop subgraph reconstruction**に焦点を絞り、(1) 明示的なdump要求を避けるtask reframing、(2) relation recordの混同を防ぐinstance-grounded representation、(3) 同じ関係ばかり取得する飽和を抑えるadaptive query diversificationを統合したGRASPを提案する。単なる回答中のPII抽出ではなく、**structured knowledge assetの再構成**という攻撃目標が重要である。

## 問題設定 / Threat Model

- **Victim**: 企業文書や医療会話などからprivate KGを構築し、Graph RAGで質問に回答するサービス。GraphRAGのsafe promptはretrieved tableの逐語開示とgraph構造の開示を禁止する。
- **Attacker**: 通常のquery API/UIにアクセスできる悪意あるユーザ（内部ユーザ、認証情報を得た外部者、公開サービスの利用者を含む）。target entityの識別子と粗いdomain知識を持つが、retriever、embedding、LLM内部、KG/schema、retrieved relationsを観測できない。
- **Goal**: target entity `t` に接続するtyped edges `E_t = {(u, r, v) ∈ E | u=t or v=t}` を推定し、`G_t=(V_t,E_t)` を再構成する。単なるentity共起ではなく、source/destinationの方向とrelation typeの一致が必要。
- **Budget**: target entity当たり最大10 queriesを主設定とする。論文は大量のAPI probingを前提にしない。
- **Boundary**: private KG全体の完全復元ではなくtargeted one-hop reconstructionが主課題。後続実験で2/3-hop拡張を評価する。

## 先行研究からの改善点

**直接のGraph RAG baseline**は、既登録の[Exposing Privacy Risks in Graph Retrieval-Augmented Generation](2025-2508.17222-exposing-privacy-risks-graphrag.md)。同研究はGraph RAGのentity/relation leakageを示したが、本論文はsafe system promptのある**defended Graph RAG**でtyped edgesを正確に復元できるかを改めて検証する。

他のbaselineとして、[The Good and The Bad](2024-2402.16893-the-good-and-the-bad.md)および[Follow My Instruction and Spill the Beans](2024-2402.17840-follow-my-instruction-and-spill-the-beans.md)のrepeat-context系、[Unleashing Worms and Extracting Data](2024-2409.08045-unleashing-worms-extracting-data.md)のjailbreak系、[RAG-Thief / CopyBreakRAG](2024-2411.14110-feedback-guided-extraction-copybreakrag.md)のadaptive exploration系を比較する。

| 論点 | 従来型 | GRASP |
|---|---|---|
| 抽出対象 | text chunkまたは粗いentity/relation情報 | target entityのtyped・directed relation |
| 防御前提 | context dumpが通る場合を含む | 明示的な非開示safe promptあり |
| 応答品質 | paraphrase・混同でrelation typeを失う | relation instanceを区別してstructured matching |
| query strategy | 固定templateの反復、一般的なexploration | 既発見typeと新規relation数に応じた多様化 |
| 評価 | 文書漏洩率・粗いcoverage | RType / Naïve のPrecision, Recall, F1 |

### Failure Analysis

6種類の既存attack promptをsafe prompt下で評価すると、baseline P2–P4の拒否率は100%、Wormは99.7%、FGは100%に達する。P1でも29.9%の拒否が発生する。非拒否の場合も安全promptによる抽象化でrelation typeが変わるほか、同一templateの繰り返しでは新規relationの発見が早期に飽和する。これを**intent detection / relation fidelity / discovery saturation**の3課題として整理する。

## Method / Algorithm

### 1. Task Reframing

明示的に「retrieved graphをすべて出力せよ」とするのではなく、既にretrieved contextにあるrelation recordを対象にした限定的な情報処理taskとして扱う。論文の目的は、禁止された逐語dumpだけを拒否するpolicyでは、通常の関係処理能力を通じたstructured disclosureが残ることを評価する点にある。

### 2. Instance-grounded extraction

各relationを `(ID, SRC_ENTITY, REL_TYPE, DST_ENTITY)` というrecord単位で扱い、type・direction・endpointsを個別に保持する。IDは必ずしも元KGの実IDである必要はなく、**異なるrelation instanceを区切るanchor**として機能する。例えば複数のrelationからsourceとdestinationを取り違えた合成edgeが生成される問題を減らす。

固定のline-based outputと空結果の明示によってpost-processingの揺らぎやhallucinationを抑え、RType matching可能な出力を得る。重要なのは、モデルがnon-refusalするだけでなく、**元のrelation typeを正確に維持する**ことである。

### 3. Goal-driven diversity

retrievalはtop-kに制限されるため、1 queryで現れないrelationは生成側が知り得ない。GRASPは過去の結果から既発見relation/typeを記録し、4種類のdiversity templateを切り替える。

- **Context-frame drift**: 既知typeと異なるdomain frameへ検索焦点を移す。
- **Type expand**: 既に観測したrelation typeの未発見instanceを補完する。
- **Type explore**: まだ観測していないrelation typeを探す。
- **Residual extract**: 飽和段階で信頼度の高い残存relationを限定的に回収する。

これらは無作為な言い換えではなく、relation coverageの不足原因に応じてretrieval/extractionの焦点を変えるための役割分担である。

### 4. Discovery-aware Scheduler

各turnの新規relation数 `e_q` のEMAを `μ_e ← α e_q + (1-α)μ_e`（α=0.6）で追跡し、**SURGE (>2)、STEADY (0.5–2)、STALL (<0.5)** に分類する。templateごとの新規発見成功率もEMAで記録し、効果のあったtemplateへ重みを寄せる。

早期停止にはGood–Turingに基づくunseen mass推定を利用し、window内のsingleton数 `f1` とwindow長から次turnの新規発見数を `ŷ=f1/|W|` と見積もる。5 turn以上で `ŷ<0.3` なら停止、`ŷ<0.9` でdiversity phaseを開始する。ここでは**残りqueryをどの探索モードへ配分するか**がアルゴリズム上の主要な貢献となる。

## Experiment Setup

- **Graph RAG**: Microsoft GraphRAGのlocal search。KG作成にGPT-4o-mini、embeddingに`text-embedding-3-small`、query当たりtop-10 entities / top-10 relations。
- **Datasets**: Enron emails、HealthCareMagic（HCM）から各5,000 documentsをsampleしてKG構築。各KGでdegree≥5のtarget entitiesを50件抽出。
- **Generators**: GPT-4o-mini、GPT-5-mini、Claude Haiku 4.5、Qwen3 30B。
- **Baselines**: P1/P2（repeat-context）、P3/P4（Graph RAG向けrepeat/list）、Worm、Feedback-Guided (FG)。baselineは必要に応じてLLM post-processorでtyped edge listへ正規化し、同一budgetの10 queriesで比較。
- **Metrics**: macro-averaged Precision / Recall / F1。**RType**は `(src, relation_type, dst)` の完全一致、**Naïve**はrelation typeを無視してentity pairのみ一致。

## Main Results

### Typed Relation Reconstruction

安全prompt下のRType F1（%）は以下。単にentity pairを当てるNaïve F1より厳しいmetricである。

| Dataset | GPT-4o-mini | GPT-5-mini | Claude Haiku 4.5 | Qwen3 30B |
|---|---:|---:|---:|---:|
| Enron / GRASP | 65.6 | 71.2 | **82.9** | 73.3 |
| HCM / GRASP | 51.4 | 63.1 | 82.4 | 74.9 |

Enron / GPT-5-miniではFG・WormともRType F1=0.0だが、GRASPは71.2。安全promptによりbaselineがrelation typeを復元できない状況でも、GRASPはtyped edgesを再構成する。Enron / Claude Haiku 4.5の82.9が論文で強調される最大RType F1である。

### CoverageとRetrievalの上限

Enron / GPT-4o-mini、50 targetsに含まれる634 relationsについて、GRASPの累積coverageは**54.1%**。Worm 35.0%、FG 33.6%、P4 0.8%、P1 0.2%を上回る。ただし191/634（約30%）は**どのattackでも未到達**で、top-kにほとんど出現しないlong-tail relationが抽出可能性の上限を作る。

## Ablation / Transferability / Robustness

### Component Ablation

Enron / GPT-4o-mini / RTypeでfull GRASP F1 **65.6**に対し、instance IDを除くと**40.1**へ低下し、precisionは64.9→34.4。これは単なるformattingではなく、relation-instance混同によるhallucinationを抑える重要componentであることを示す。diversityを除くとF1は約4.9ポイント低下し、recallが56.0へ落ちる。schedulerを外した場合も適応的な探索配分が失われる。

### Graph RAG Framework Transfer

GraphRAGに加えてLightRAG、nano-GraphRAGを評価。Enron / GPT-5-miniではRType F1がそれぞれ**71.2 / 81.8 / 83.7**。後2者はundirected graphであり、direction matchingの負担が小さくなる点を考慮する必要がある。

### Multi-hop Extension

one-hopの結果を新しいtargetへ再利用する2/3-hop拡張では、true-positive relationsをそれぞれ**2,754 / 23,916**回収し、F1は**52.5 / 33.8**。hopが増えるほど誤差伝播と探索空間拡大が効き、完全なKG reconstructionとは距離がある。

## Defense Evaluation

### 比較するDefense

Safe prompt、Abstractive / Extractive summarization、detected extractionのReject、Privacy-Aware Decoding（PAD）、提案するcontext-construction defenseの**ID Alignment**と**Decoy**を比較する。さらにruntime controlsとしてquery intent screening、retrieval filtering、rate/repetition limitsも評価する。

### 提案Defenseの機構

- **ID Alignment**: retrieved relation tableのIDを共通値へ揃え、instance anchoringを壊す。benign QAは通常IDを参照しないためutilityへの影響を抑える設計。
- **Decoy**: 真のsrc/dstとは異なる紛らわしいendpoint列をretrieved tableに追加し、benign queryでは参照しないようsystem instructionで区別する。structured extractionに対してfield attributionを曖昧にする。

### Defenseの数値

EnronのRType F1（低いほど防御成功）とbenign QA Rouge-L utilityを比較すると次の通り。

| Defense | GPT-4o-mini F1 | GPT-4o-mini utility | Qwen3 F1 | Qwen3 utility |
|---|---:|---:|---:|---:|
| Safe prompt | 65.6 | 27.5 | 73.3 | 28.0 |
| Reject | 60.1 | 27.8 | 70.9 | 27.4 |
| ID Alignment | 47.0 | 27.7 | 58.4 | 28.3 |
| Decoy | **14.5** | 27.4 | 27.4 | 28.0 |
| Decoy + ID Alignment | 16.8 | 27.7 | 15.5 | 27.2 |
| Decoy + ID Alignment + Reject | 17.8 | 27.7 | **14.8** | 27.4 |

PADはQwen3でF1=70.0を残したままutilityが23.2へ低下する（safe promptの28.0に対して）。著者の主張は、output-level noiseより**retrieved contextの構造表現**へ介入する方が、特定の攻撃機構には効率的な場合があるというもの。ただしDecoyでも残存F1はゼロではない。

### Runtime Monitoring

Enron / GPT-4o-miniのno-defense F1=66.1に対して、encoder intent screening 48.2、LLM-as-judge 51.8、Moderation API 65.2、Bedrock Guardrails 47.1、similarity filtering 42.9、PII masking 40.5、rate/repetition limits 65.2。通常のintent detectionやrate limitだけでは十分ではないことを示す。

## Limitations / 成立条件

1. **Targeted entityが既知**: 未知の全KGを探索する汎用crawlerとは異なる。target周辺のone-hop graphが主要評価対象。
2. **Graph-servingの形式依存**: retrieved contextがentity/relation tableとして正規化されることが重要。生textだけのRAGへ数値を直接外挿できない。
3. **Controlled evaluation**: 実サービスへの攻撃は行わず、ローカルのGraphRAG構成で検証する。API authorizationやdocument-level ACLが厳格な運用とはthreat modelが異なる。
4. **Defender adaptation**: Decoyは特定のfield attributionに依存する防御であり、adversaryがその仕組みを知った条件での完全な頑健性は保証されない。
5. **Metricsの厳しさ**: RType exact matchはparaphraseに弱く、逆にsemantic leakageを過小評価する場合もある。Naïveはrelation typeを無視するため漏洩リスクを過大評価し得る。

## RAG Data Extraction / Security Taxonomyでの位置づけ

**Attack → Knowledge-Base / Structured Graph Extraction → Targeted Subgraph Reconstruction**。text chunkのverbatim theftではなく、KGのtyped relationとdirectionを再構成する攻撃である。先行するGraph RAG privacy studyの実践的拡張として位置づけられ、[RAGCrawler](2026-2601.15678-connect-the-dots.md)のようなglobal corpus explorationとは探索対象と目標metricが異なる。

## 実装上・研究上の示唆

RAGの情報漏洩を「機密文章をそのまま返すか」だけで評価すると、Graph RAGのstructured leakageを見落とす。entity、relation type、directionの一致と、許可されていないgraph neighborhoodへのaccessを別々に検証すべきである。safe prompt、prompt filtering、rate limitを組み合わせても、**legitimate-looking relational reasoningとstructured extractionの境界**は残る。防御ではcontext構造の秘匿化と、retrieval authorization / schema exposure policyの明示的な分離が必要になる。
