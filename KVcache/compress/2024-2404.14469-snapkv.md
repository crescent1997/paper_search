# SnapKV: LLM Knows What You are Looking for Before Generation

> generation開始前のprompt末尾だけを見ても、各headが今後重視するprompt tokenをかなり予測できる、という経験則をKV evictionへ利用する。

## 概要

KV quantizationは1 token当たりのbytesを減らすが、context lengthに比例してtoken数は増え続ける。SnapKVは別方向から、**保持するKV tokenそのものを減らす**。

著者らは、generation中に各attention headが参照するprompt位置のpatternが比較的安定しており、そのpatternがprompt末尾の短いobservation windowで既に観測できることを示す。

## Method

### Observation window

promptの最後の数tokenをquery側の観測領域とし、そこから過去prompt tokenへのattention scoreを集計する。

### Head-wise selection

重要位置はheadごとに異なるため、全head共通のtoken集合ではなくhead-wiseにhigh-attention KV positionsを選ぶ。

### Clustering / pooling

単一点だけを残すと近傍情報が失われるため、attention peak周辺をcluster-awareに集約して局所的なcontextを保持する。

選定後、不要KVをcacheから除去し、generationでは圧縮後cacheだけを参照する。追加fine-tuningは不要。

## 先行研究からの改善点

StreamingLLM等の固定ruleはsink tokenやrecent tokenを残すが、task / queryごとのsemantic importanceを十分見ない。SnapKVはprompt固有・head固有のattention patternから選択するため、より強く圧縮しつつaccuracyを維持することを狙う。

## Experiment Setup

複数long-context benchmark、Needle-in-a-Haystack、長いpromptでのgeneration memory / latencyを評価。HuggingFace実装でも検証している。

## Main Results

16K inputでbaselineに対し約8.2×のmemory efficiency、約3.6×のgeneration speedupを報告し、16種類のlong-sequence datasetでbaselineに近い性能を維持する。またA100 80GB 1枚で最大約380K contextを処理できる例を示す。

## Limitations

- prompt末尾のattentionがfuture generationの重要tokenを予測できる、という仮定に依存する。
- generation途中で関心topicが大きく変化すると、prefill時に捨てたKVは復元できない。
- cache compression率を高めすぎるとmulti-hop / broad coverage taskで必要情報を失う可能性がある。

## KV-cache taxonomyでの位置づけ

SnapKVは**token-level compression / eviction**。KIVIのbit-level compressionとは直交する。一方、CacheBlendのselective recomputationは「どのtokenを再計算するか」を選ぶためattention importanceを用いる点で発想上の近さもある。

## 実装・研究上の示唆

KV cache削減では「1 tokenを小さくする」だけでなく「何token残すか」が大きな軸になる。head-wise sparsityを利用すると、同じtoken budgetでも全head共通evictionより柔軟に情報を残せる。
