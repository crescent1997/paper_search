# 概要

**R-KV**は、reasoning LLMが長いChain-of-Thought（CoT）を生成する間に増大するKV cacheを、**attention importanceとKey vectorの冗長性の両方**から圧縮する手法。特に同じ推論・自己検証を何度も繰り返すtoken列が、attention scoreだけでは過大評価される問題を扱う。

従来の[SnapKV](2024-snapkv.md)や[PyramidKV](2024-2406.02069-pyramidkv.md)は主に長い**入力promptのprefill後**の圧縮を想定する。R-KVは、promptより**生成出力が長い**reasoning modelの**decode中**に一定間隔でKVを整理する。KV自体を削除するためカテゴリは`compress`であり、再利用KVの品質を部分再計算で直す`reuse`研究ではない。

## 問題設定と既存法の問題

DeepSeek-R1系のdistilled reasoning modelは、短い数学問題に対しても何千〜何万tokenの推論過程を生成する。論文のFigure 2では、MATH-500でground-truth解答の平均約210 tokenに対してR1-Llama-8Bの生成が約2,979 token、AIME24で約1,547に対して約15,536 token。1-/2-gram反復も増える。**長い生成履歴のすべてをcacheへ保存する必要があるか**が問題となる。

Attention-based evictionは過去のattention scoreが高いtokenを重要とみなす。しかし同じ内容のself-reflectionを反復すると、**似た表現が互いにattentionを集めるため、冗長なtokenが重要tokenとして残りやすい**。その結果、必要な初期条件や異なる中間推論を落としてしまう（Figure 3）。R-KVは「注目されている」ことと「他のtokenでは代替できない」ことを分離して扱う。

## 手法

### 1. Decode-time periodic compression

KV領域を、過去から保持する`B_budget` tokenと、新しく生成する`B_buffer` tokenのbufferに分ける。`B_buffer`個のtokenを生成するたびに圧縮を実行する（Section 3.1）。直近`α` tokenはobservation windowとして強制保持し、残る`B_budget - α`枠を、以前のcacheとbuffer中の古いtokenから選び直す。

論文の主設定は`B_buffer=128`、`α=8`。毎tokenのglobal selectionではなく**128 tokenごとのバッチ処理**でselection overheadを抑える。`B_budget`と`B_buffer`に加えて直近query stateの保持が必要である。

### 2. Attention-based importance `I_i`

末尾`α`個のQueryから候補Keyへのattention scoreを計算し、tokenごとのimportanceを得る（Section 3.2）。局所的なscoreのばらつきを抑えるため、幅`2W`のmax-poolingをかけ、observation windowのquery方向で平均する（Eq. 4）。

**GQA対応**も記述される。1つのKV headに対応する複数Query headのscoreをgroup方向にmax-poolingして統合し、再正規化してからKV head単位のimportanceを求める（Eq. 2–3）。これはGQAで共有されるK/Vに異なるQuery headのimportanceをどう集約するか、という実装上の重要点である。

### 3. Key similarityからredundancy `R_i`を推定

候補KeyをL2 normalizeし、同一KV head内でcosine similarity matrix `S = K_norm K_norm^T`を計算する（Eq. 5）。対角を0にし、閾値`T`を超えて似ているtoken群について**比較的新しい`β`個の類似tokenの扱いを保護する**よう類似度を調整する。各tokenの平均similarityを計算し、softmaxで正規化して`R_i`を得る（Eq. 6）。`R_i`が大きいほど他のtokenと内容が重複しているとみなす。

注意点として、これは**自然言語の意味の同値性を明示的に検証するものではなく、各headのKey表現上のcosine similarityをproxyとして使う**方法である。RoPEを含むKey表現・layer差に対する頑健性は実装条件に依存する。

### 4. Joint scoreとTop-K retention

`Z_i = λ I_i - (1-λ) R_i`（Eq. 7）によりimportanceを加点、redundancyを減点する。各headで`Z_i`上位を残し、直近`α` tokenを併せて固定budgetに収める。`λ=1`ならattention-only、`λ=0`ならredundancy-only。主実験は`λ=0.1`。**重要だが重複するtokenより、重要かつ多様なtokenを残す**のが狙い。

## Experiment Setup

- **Models**: DeepSeek-R1-Distill-Llama-8B、DeepSeek-R1-Distill-Qwen-14B。観察にはQwen-7Bも使用。NeurIPS公式PDFの主評価は前者2モデル。
- **Tasks**: MATH-500、AIME 2024。公式PDFの本文に「three benchmarks」と書かれながら2件しか列挙されていない箇所がある。主Figure 4はこの2ベンチマークであり、AIME25への言及と混同しない。
- **Baselines**: FullKV、SnapKV。SnapKVは同じ128-step間隔・同じbudgetでdecode圧縮するよう改変して比較。HeadKVなどのbudget allocatorは直交技術として比較対象外。
- **Sampling**: temperature=0.6、top-p=0.95、各問題64 sampleでpass@1を推定。MATH-500は最大16,384 token、AIME24は最大32,768 token。
- **Efficiency**: NVIDIA A100 80GB。単一requestと最大batch時のthroughput、固定token budgetと生成長に対する比率budgetの両方を測定。

## Main Results

**Reasoning accuracy**（Figure 4 / Appendix B.2）: R1-Llama-8BではMATH-500で**KV budget約34%**、AIME24で**約10%**によりFullKVに近い性能を達成。AIME24ではbudget約16%でFullKVの約105%のaccuracyと報告。R1-Qwen-14BではMATH-500で約54%、AIME24で約25%がFullKV相当の目安で、AIME24の約33%で105%と報告。これは**各dataset/model条件での相対accuracy**であり、すべての問題でaccuracyが改善するという意味ではない。

**Fixed budget**（Section 4.2）: R1-Llama-8BはMATH-500で`B_budget=1024`、AIME24で`1536`程度がfull相当の目安。生成長が約2,979から約15,536へ5倍以上伸びても、必要な固定cache budgetは同程度の桁に留まる。本文には2モデルの名称を繰り返す誤植があり、Qwen-14Bのfixed-budget記述はFigure 4/Appendix表との照合が必要。

**Memory / throughput**（Table 1）: 16K generationのFullKV最大batch=30、throughput=347.03 token/sに対し、R-KVのratio 10%では最大batch=271、throughput=2,300.28 token/sで**約6.6×**。固定`B_budget=1024`では最大batch=402、throughput=3,188.82 token/sで**約9.2×**。この改善の主因は**cache圧縮でbatch sizeを大幅に増やせること**であり、batch=1の単純なdecode速度向上は小さい（FullKV 69.41 vs R-KV 80.95 token/s）。

**注意: 版間の不整合**: arXiv v4/NeurIPS公式PDF本文は「10% budget / 6.6× throughput」等を記載する一方、NeurIPS公式abstractページは「38% budgetで105% / 50% memory saving / 2× speedup」と異なる値を掲載している。**本要約は公式PDF本文の図表・条件を優先**し、abstractページの数字と混在させない。

## 主要ablation / Analysis

1. **`λ`の役割**（Figures 5–6）: `λ=0`のredundancy-onlyはinitial tokenを落としやすく、`λ=1`のattention-onlyは反復tokenを残しすぎる。`0.01≤λ≤0.1`付近が適切で、MATH-500の感度分析では`λ=0.1`が最良。両scoreの併用が重要。
2. **Token selectionの可視化**（Figure 7）: SnapKVが反復的な自己検証部分を大量に保持して誤答する例に対し、R-KVは異なる計算・条件を保持して正答する。単一case studyであり、一般的な因果効果の証明ではない。
3. **Budget ratio vs fixed budget**（Figure 4 / Table 1）: 出力長が長いほど、同じ絶対token数のcacheでも相対budget比率は小さくなる。従って「10% budget」の数字を別のgeneration lengthへそのまま外挿してはならない。
4. **Complexity**（Appendix C.1）: importance推定はおおむね`O(α B_budget)`、cosine similarityによるredundancy推定は`O(B_budget^2)`。decode中に圧縮するとはいえ、budgetを大きくするとselection自体がボトルネックになりうる。

## Limitations / 実装上の論点

- **Quadratic similarity overhead**: `B_budget^2`のKey similarity matrixが必要。長いcacheに対するapproximate nearest neighbor、block化、低rank近似などがなければ拡張しにくい。
- **数学reasoningへの評価集中**: MATH-500/AIME中心で、長文QA、coding、multi-turn agent、RAGの品質保証は未検証。
- **Accuracyとthroughputの条件差**: 6.6×はmax-batchのthroughputであり、単一request latencyが6.6×改善するわけではない。
- **Future dependence**: 今は冗長に見える過去の計算が後続stepで重要になる可能性がある。evictionは不可逆。
- **GQA実装**: Query-head scoreの集約、RoPE付きKey cosine、headごとのKV layoutと周期的なgatherが実装上の論点。
- **出版物の整合性**: official proceedingsのabstractとPDF、arXiv revisionでheadline数値が一致しない。比較表を再利用する場合は必ず版とFigure/Tableを明示する。

## Taxonomy / 関連研究との差分

| 項目 | R-KV |
|---|---|
| Category | `compress` |
| Reuse単位 | inter-request reuseはしない。decodeで生成したtokenのKVを保持・evict |
| Selection granularity | token-level / KV head-level、128-step周期 |
| Relevance signal | recent query attention `I_i` + Key cosine redundancy `R_i` |
| Repair / fusion | なし。重要かつ非冗長なtokenを直接retain |
| Model modification / fine-tuning | 不要 |
| Main objective | CoT reasoning accuracyを保ちながらKV memoryとbatch throughputを改善 |

[SnapKV](2024-snapkv.md)は観測窓からのattentionで重要tokenを選ぶ。R-KVは**attentionが高くても意味が重複するtokenを減点する**。[HeadKV](2024-2410.19258-headkv.md)はhead間のbudget配分を学習済みのimportanceで調整するが、R-KVは各head内の**tokenの重複度**をdecode中に再評価する。[ChunkKV](https://arxiv.org/abs/2502.00299)は連続chunkの意味保持を重視し、R-KVは離れた位置の似たKey同士を重複候補として扱う。[ProphetKV](../reuse/2026-2602.02579-prophetkv.md)や[A³](../reuse/2025-2511.17560-a3.md)はcached KVを別文脈で**再利用した後の品質修復**を目的とし、R-KVの保存量削減とは最適化対象が異なる。
