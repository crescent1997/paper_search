# ProphetKV: User-Query-Driven Selective Recomputation for Efficient KV Cache Reuse in Retrieval-Augmented Generation

> CacheBlend系のselective recomputationをさらに進め、**「full prefillとの差が大きいtoken」ではなく「最終user queryにとって重要なtoken」を再計算する**ことを中心に据えたquery-aware KV reuse手法。限られたrecomputation budgetをquery-relevant tokenへ集中させることで、20% recomputationでもfull-prefillに近いaccuracyを維持する。

## 概要

RAGでは、retrieverが返した複数document / chunkを長いcontextとしてLLMへ入力するため、長contextのprefillがTTFTの主要bottleneckになる。

この問題に対して近年は、各retrieved documentをあらかじめ独立にprefillしてKV cacheを保存し、request時にはそれらを連結して再利用する方法が提案されている。

しかしdocumentを独立計算したcached KVは、full prefill時に本来存在する

- document間のcross-attention
- preceding contextからのhidden-state更新
- queryを含む全contextに基づくrepresentation refinement

を欠いている。

そのため単純にcached KVをconcatenateするだけではfull-prefillと内部stateがずれ、accuracyが低下する。

[CacheBlend](2024-2405.16444-cacheblend.md)やKVShareは、この差を埋めるために**一部tokenだけをselective recomputation**する。

ProphetKVはここでさらに一歩踏み込み、

> どのtokenを再計算すべきか

というselection criterion自体に問題があると指摘する。

既存法では、

- global attention saliency
- cached KVとfull-context KVのdeviation
- low-layerで観測したimportance

などを用いて「full prefillとの差が大きそうなtoken」を優先する。

しかし、最終的なanswer generationに必要なのは、

> **user queryに答えるために重要なtoken**

である。

globalにはattentionが大きくてもqueryとは無関係なtokenが多ければ、そのtokenがrecomputation budgetを占有し、本当にqueryに必要なtokenが選ばれない。

ProphetKVはこの現象を **crowding-out effect** と呼ぶ。

そこで、selection objectiveを

```text
global saliency
        ↓
query relevance
```

へ変更する。

さらに、layerごとに重要tokenが変化する問題に対して、query tokenからcached contextへのattentionを全layerで軽量に計算し、そのscoreをfusionして1つのhigh-utility token setを作る。

最終的に、

```text
Independent cached document KV
            ↓
Query-only lightweight attention pass
            ↓
Layer-wise query relevance scores
            ↓
Cross-layer fusion
            ↓
Top-k query-relevant tokens
            ↓
Selective full recomputation
            ↓
Generation
```

というdual-stage pipelineになる。

## 問題設定

RAG promptを、

[
S = [D_1, D_2, ldots, D_m, Q]
]

とする。

ここで、

- (D_i): retrieved document / chunk
- (Q): user query

である。

各document (D_i) は事前に独立prefillされ、cached KV

[
K'_i, V'_i
]

として保存されている。

request時には、

[
K' = [K'_1, K'_2, ldots, K'_m]
]

を連結する。

しかしfull prefillした場合のKV

[
K, V
]

とは一致しない。

独立計算されたdocument tokenは、

- preceding documentを見ていない
- 他documentとのinteractionを持たない
- full context内で更新されたhidden stateを持たない

ためである。

そこで一部token集合

[
mathcal{R} subseteq {1,ldots,s}
]

だけをfull-context条件で再計算し、残りはcached KVをそのまま利用する。

recomputation ratioを

[
r = rac{|mathcal{R}|}{s}
]

とすると、目的は小さい (r) でfull-prefillに近いaccuracyを得ることである。

問題は、

> **どのtokenを (mathcal{R}) に入れるべきか**

である。

---

## 既存selective recomputationの問題

### CacheBlend

CacheBlendはindependently cached KVとfull-prefill KVの差が特定tokenへ集中することを利用し、importanceの高いtokenを再計算する。

その基本発想は、

[
	ext{large KV deviation}
Rightarrow
	ext{important to repair}
]

である。

これはfull-prefill stateの復元という観点では自然だが、

> KV差が大きいtokenが、最終user queryにとって重要とは限らない

という問題がある。

### KVShare

KVShareもattentionやKV deviationを組み合わせ、再計算価値の高いtokenを選ぶ。

しかしglobal attention-based scoreはquery-specificではないため、context全体ではsalientでもuser queryとのsemantic connectionが弱いtokenを高く評価する可能性がある。

### EPIC

[EPIC](2024-2410.15332-epic.md)はposition-independent cachingのartifact、特にsegment beginningのattention sink等を補正する。

ただしselectionはProphetKVのようなuser-query-conditioned importanceを中心には設計されていない。

---

## Crowding-out Effect

ProphetKVが強調する中心的なfailure mode。

recomputation budgetが例えば20%しかない場合、

[
|mathcal{R}| = 0.2s
]

なので、selectionを誤るとquery-relevant tokenを簡単に落としてしまう。

既存global saliency型selectionでは、

```text
Globally salient token
Globally salient token
Globally salient token
...
Query-relevant token
```

という状態になり得る。

上位20%を取った結果、

```text
selected:
  global-important / query-irrelevant
  global-important / query-irrelevant
  ...

dropped:
  query-critical
```

となる。

著者らはこれを **crowding-out effect** と定義する。

特に、

- MultiValue
- MultiQuery
- Musique
- long-context QA

のように、大量contextの中からqueryに対応する狭いevidence spanを正確に見つけるtaskで影響が大きい。

これは単なる「重要token検出精度」の問題ではなく、

> selective recomputationにおけるimportance definitionそのものがgeneration objectiveとずれている

という指摘である。

---

## Query-driven Selectionの基本アイデア

ProphetKVでは、token (t) のimportanceを、

> **user query tokenから、そのcontext tokenへどれだけattentionが向くか**

で評価する。

query token集合を (Q_s) とし、layer (l) におけるquery→context attentionからtoken (t) のscore

[
hat{Phi}'^{(l)}_{Q_s,t}
]

を計算する。

直感的には、

[
	ext{importance}(t)
approx
sum_{q in Q_s}
	ext{Attention}(q,t)
]

である。

つまり、

```text
Is this token globally important?
```

ではなく、

```text
Will the user query actually look at this token?
```

を見る。

このquery-driven scoreによって、recomputation budgetをanswer generationへ直接寄与するtokenへ集中させる。

---

## Semantic Lossからの導出

論文ではquery-driven metricを単なるheuristicとして導入するのではなく、reuse時のsemantic errorからselection criterionを導出する。

full-prefill時のquery outputは、conceptually、

[
O_Q = Phi_{Q} V
]

と書ける。

ここで、

- (Phi_Q): queryからcontextへのattention
- (V): full-context Value

である。

cached KVを使う場合、

[
O'_Q = Phi'_Q V'
]

となる。

したがってquery semanticsのlossは、

[
| O_Q - O'_Q |
=
| Phi_Q V - Phi'_Q V' |
]

として捉えられる。

理想的には、

> query-weighted output differenceへの寄与が大きいtoken

を優先して再計算すべきである。

しかしfull-prefillを実行せずに (Phi_Q) や (V) の真値を得ることはできない。

そこでProphetKVは、独立cached KVを使ったquery attention

[
hat{Phi}'_{Q_s,t}
]

をobservable proxyとして利用する。

このscoreは、

- query-specific
- cached KVのみから取得可能
- full context再計算不要

という性質を持つ。

---

## Layer-wise Importanceの問題

token importanceはlayerごとに大きく変わる。

浅いlayerでは、

- local token
- near-neighbor
- syntactic relation

へattentionが集中しやすい。

一方高layerでは、

- distant evidence
- semantic answer span
- reasoningに必要なdocument

へattentionが移る。

論文ではQwen2.5-14B等でlayerごとのattention patternを可視化し、low layerだけを見たtoken selectionでは、deep layerで重要になるlong-range tokenを見逃すことを示す。

これはCacheBlend / KVShareのような手法で問題になる。

全layerで正確なimportanceを取得するためにfull hidden-state propagationを行うと、それ自体が高costになりKV reuseの利点を失う。

---

## ProphetKVの重要な工夫: Query-only Layer Pass

ProphetKVではcontext token全体を再forwardする代わりに、

> **query tokenだけを各layerへ通す**

軽量passを行う。

cached context K/Vは既に存在するので、各layerでquery tokenがcached contextへattentionするscoreだけを計算できる。

layer (l) で、

[
A_l(Q_s, K'_l)
]

を求め、context token方向のcolumn sum等から、

[
alpha_l(t)
=
hat{Phi}'^{(l)}_{Q_s,t}
]

を得る。

計算量は、

[
O(|Q_s| 	imes s)
]

となる。

通常、

[
|Q_s| ll s
]

なので、context全体を再計算するより圧倒的に小さい。

論文ではCacheBlend / KVShareのselectionに必要となる (O(s^2)) 系処理と比較しても軽いと説明する。

---

## Dual-Stage Recomputation Pipeline

ProphetKVは2段階で動作する。

### Stage I: Lightweight Query-Relevance Pass

全layerに対して、

- cached context KVは固定
- query tokenのみforward
- query→context attentionを取得

する。

各layer (l) についてtoken importance

[
alpha_l(t)
]

を得る。

重要なのは、この時点ではdocument token全体をfull recomputationしないこと。

つまり、selectionのためにfull prefill相当のcomputeを支払わない。

### Stage II: Layer Fusion + Selective Full Recomputation

layerごとのscoreをfusionする。

論文ではconceptually、

[
ar{alpha}(t)
=
rac{1}{L}
sum_{l=1}^{L}
alpha_l(t)
]

のようにlayer-wise attention metricをaggregateし、最終importanceを作る。

その後、

[
mathcal{R}
=
operatorname{TopK}_t ar{alpha}(t)
]

としてrecomputation対象token集合を決める。

選ばれたtokenだけを、full-context attention条件で全layer再計算する。

最終的な流れは、

```text
Cached Document KV
        ↓
Query-only pass
        ↓
α₁(t), α₂(t), ..., αL(t)
        ↓
Layer fusion
        ↓
ᾱ(t)
        ↓
Top-k tokens
        ↓
Full recomputation of selected tokens
        ↓
Generation
```

となる。

---

## なぜ全layer共通token setを使うか

layerごとに別々のtop-k tokenを選ぶ設計も可能である。

しかしProphetKVではfusion後に共通token setを作る。

これにはsystem上の利点がある。

- layerごとにtoken数・shapeが変わらない
- gather / scatter patternを固定できる
- GPU kernelを組みやすい
- dynamic sparsity管理costを抑えられる
- recomputation pathを単純化できる

つまりlayer fusionはaccuracyだけでなくimplementation efficiencyにも寄与する。

## Main Results: Full-prefill Accuracyの96–101%を維持

abstractで報告される中心結果。

20% recomputation ratioでProphetKVは、

> full-prefill accuracyの約96–101%

を維持する。

100%をわずかに上回るケースがあるのはbenchmark variance / selective denoisingの効果等により、必ずしもfull-prefill scoreが絶対上限ではないためと考えられる。

一方NaiveReuseではcross-chunk information不足により大きくaccuracyが落ちる。

CacheBlend / EPIC / KVShareも改善するが、taskやmodelによって不安定。

ProphetKVは3 model × 2 benchmark familyで一貫してfull-prefillへ近い。

---

## RULER Results

論文は20% recomputationで、

- 既存SOTA比 **8.8–24.9% accuracy improvement**

を報告する。

特にMV / MQの差が大きい。

これはProphetKVの設計仮説と一致する。

MV / MQでは大量contextの中でqueryに対応する特定entity / value / spanを見つける必要がある。

global saliencyだけでtokenを選ぶと、queryに無関係なhigh-attention tokenにbudgetを奪われやすい。

query attentionを直接selectionに使うProphetKVでは、必要evidenceを再計算対象へ残しやすい。

---

## LongBench Results

LongBenchでは既存SOTA比、

- **18.6–50.9% improvement**

を報告する。

RULER以上に改善幅が大きいcaseがある。

long-form QAではretrieved contextに大量のirrelevant textが含まれやすいため、query-conditioned selectionの利点がさらに大きいと解釈できる。

selection criterionそのもののqualityを見るため、oracle情報を使ったcomparisonも行う。

## Accuracy–Latency Trade-off

ProphetKVの重要な位置づけは、

```text
accuracy: full-prefillに近い
latency : EPICに近い
```

という点。

EPICは非常に低costだがtaskによってaccuracy lossが大きい。

CacheBlendはaccuracyを回復しやすいが、selection / recomputation overheadがProphetKVより大きいcaseがある。

ProphetKVは、

- query-only selection pass
- 20% recomputation

によって、EPICに近いTTFTを維持しながらaccuracyを大幅に改善する。

---

## 4KでSpeedupが小さい理由

4K contextでは、

- kernel launch
- cache management
- gather / scatter
- query selection pass
- runtime scheduling

といったfixed overheadの割合が大きくなる。

full-prefill computeそのものが小さいため、KV reuseで削減できるcomputeが相対的に少ない。

したがってProphetKVの利点は特に、

- 8K
- 16K+
- long-context RAG

で大きい。

---

## Cross-Model Robustness

ProphetKVのadvantageは、

- Llama 8B
- Qwen 14B
- reasoning-oriented Qwen3

で共通して確認される。

つまりquery-driven importanceが特定model familyだけの現象ではない。

また8B→14Bへscaleしてもselection policyが崩れないことから、

> query relevanceはKV reuseにおいて比較的model-agnosticなsignal

である可能性を示す。

---

## Cross-Dataset Robustness

RULERとLongBenchの両方で改善する。

RULERは比較的controlledなsynthetic long-context taskを含む。

LongBenchはrealisticなQA / summarization / retrieval taskを含む。

両方で改善することから、query-aware selectionは特定benchmarkへのoverfittingではないと主張できる。

---

## Chunk Sizeの影響

chunk sizeを変化させた評価でもProphetKVはbaselineを上回る。

512 token以上では特にnear-lossless accuracyへ到達しやすい。

chunkが小さすぎる場合、

- chunk数が増える
- boundary artifactが増える
- independent KV間interaction不足が増える

ためreuse difficultyが高くなる可能性がある。

一方chunkを大きくすると1 chunk内では通常のcausal interactionが維持されるため、cross-chunk repair量を抑えやすい。

---

## Selection Overhead

Stage Iのquery-attention computationは、

[
O(|Q_s|s)
]

である。

通常のRAGではquery長は数十〜数百token、contextは数千〜数万tokenなので、

[
|Q_s| ll s
]

となる。

したがってselection自体のcostはfull prefillに比べて小さい。

重要なのは、

> 全layerのimportanceを取得するためにcontext token全部をforwardしない

点。

この設計が「全layer informationを使う」と「selection overheadを抑える」を両立させる。

---

## CacheBlendとの本質的な違い

[CacheBlend](2024-2405.16444-cacheblend.md)はProphetKVの最も直接的なpredecessorとして見られる。

### CacheBlend

目的:

[
KV_{reuse}
ightarrow
KV_{full}
]

つまりcached KVをfull-prefill stateへ近づける。

selectionではKV deviation / attention重要度等から、

> full prefillとの差が大きいtoken

を選ぶ。

### ProphetKV

目的:

[
	ext{preserve answer-relevant semantics}
]

つまりfull state自体の完全再現より、

> user queryに必要なtokenを正しく修復する

ことを優先する。

違いをまとめると、

| | CacheBlend | ProphetKV |
|---|---|---|
| Selection objective | KV / attention recovery | Query relevance |
| Importance | global | user-query-conditioned |
| Deep-layer signal | approximationが必要 | query-only passで取得 |
| Crowding-out | 起こりやすい | 抑制 |
| Recompute budget | global-important tokenにも消費 | query-critical tokenへ集中 |

このobjective shiftがProphetKVの性能差の中心。

---

## EPICとの違い

[EPIC](2024-2410.15332-epic.md)はposition-independent cachingを軽量に実現することを目的とし、attention sink等のsystematic artifactを補正する。

EPICの利点は低overhead。

一方ProphetKVはselective recomputationを行うためEPICより多少computeが増える。

しかしuser queryに適応的にtokenを再計算するため、accuracy回復が大きい。

実験ではTTFTがEPICに近いままaccuracyでは大差をつけるcaseが多い。

---

## KVShareとの違い

KVShareはattention importanceとKV deviationを組み合わせたdynamic selectionを行う。

しかしProphetKV論文では、KVShareもquery-specific semantic objectiveではないためcrowding-outの影響を受けると位置づける。

またdeep layer importance取得にlow-layer approximationを使う制約がある。

ProphetKVはquery tokenだけを全layerに通すことで、このapproximationを避ける。

---

## Block-Attentionとの違い

[Block-Attention](2024-2409.15355-block-attention.md)はreuse problemを別方向から解く。

Block-Attentionでは、

[
	ext{model itself adapts to independent KV}
]

となるようfine-tuningする。

ProphetKVではmodel weightを変更せず、

[
	ext{cached KV} + 	ext{selective repair}
]

でfull-context semanticsを回復する。

したがって、

- Block-Attention: training-adapted reuse
- ProphetKV: inference-time repair

という異なるclass。

---

## Limitations

### 1. Query attentionが完全oracleではない

Stage Iで使うattentionはcached KVに基づく。

つまりfull-prefill時のtrue attentionではない。

independent cachingによるrepresentation errorが非常に大きい場合、query attention自体も誤る可能性がある。

### 2. Query-centric taskを前提とする

RAG QAのように明示的なuser queryがある場合に特に自然。

summarizationやopen-ended generationのように「どのcontextが重要か」がqueryから明確でないtaskでは効果が弱まる可能性がある。

### 3. Recomputationは依然必要

EPICのようなほぼrepair-free手法ではない。

20%とはいえselected tokenのfull-context recomputationを行う。

extreme-low-latency用途ではこのcostが問題になる可能性がある。

### 4. Cache I/Oは別bottleneckになり得る

長contextではstored KVをCPU / SSDからGPUへloadするcostがある。

論文の主眼はselection / recomputationなので、storage hierarchy全体のoptimizationは別問題。

### 5. 4K程度ではfixed overheadが支配的

短contextではselection passやkernel overheadがspeedupを相殺する。

---

## KV-cache reuse taxonomyでの位置づけ

ProphetKVは、

> **query-aware inference-time selective recomputation**

として分類できる。

reuse categoryを整理すると、

### Exact Prefix Reuse

```text
same prefix
→ exact cached KV
```

### Position-independent / Modular Reuse

代表: [EPIC](2024-2410.15332-epic.md)

```text
independent cache
→ reposition / lightweight linking
```

### Inference-time Repair

代表: [CacheBlend](2024-2405.16444-cacheblend.md)

```text
independent cache
→ identify globally important broken tokens
→ selective recomputation
```

### Query-aware Inference-time Repair

代表: ProphetKV

```text
independent cache
→ query-only attention pass
→ select query-critical tokens
→ selective recomputation
```

### Reuse-aware Fine-tuning

代表: [Block-Attention](2024-2409.15355-block-attention.md)

```text
change attention dependency
→ fine-tune model
→ direct reusable KV
```

ProphetKVはCacheBlend系の中でもselection objectiveをquery-conditionedへ変えた発展形と見るのが最も自然。

---

## 研究上の重要な示唆

ProphetKVの重要なメッセージは、

> selective recomputationで「full stateを最も正確に復元するtoken」と「answer accuracyに最も寄与するtoken」は同じではない

という点。

従来の考え方は、

[
min |KV_{reuse} - KV_{full}|
]

に近い。

ProphetKVは実質的に、

[
min 	ext{query-conditioned semantic loss}
]

へobjectiveを変える。

この違いはKV reuse以外にも一般化できる。

例えば、

- KV compression
- sparse attention
- context pruning
- token eviction
- retrieval reranking

でも、

> global importanceではなくcurrent queryへのmarginal utilityを使う

設計が有効である可能性がある。

---

## 実装上の示唆

ProphetKVを実装する場合、重要なのはStage Iのquery-only passをfull forwardとして実装しないこと。

各layerで必要なのは主として、

[
Q_{query} K_{context}^{T}
]

によるattention score。

context側K/Vはcached tensorをそのまま使える。

したがって実装上は、

1. cached context KVを読み込む
2. query hidden stateだけlayer-by-layerにforward
3. query-to-context scoreを収集
4. token scoreをreduce
5. top-k index決定
6. selected tokenだけfull recompute

というpipelineになる。

top-kが全layer共通なので、selected token indexをlayer間で使い回せる。

これはFlashAttention / FlashInfer / custom sparse kernelへ落とす際にも扱いやすい。

---

## CacheBlend研究との接続

CacheBlend系selective recomputationを研究する場合、ProphetKVから得られる直接的な示唆は大きい。

特に、

- KV deviationだけではtoken utilityを十分表せない
- query側attentionをselectionに含めるべき
- layer 0 / low-layerだけでimportanceを決めるとdeep semantic dependencyを見逃す
- 全layerimportanceを得る場合でもquery-only passならcostを抑えられる
- recomputation budgetが小さいほどselection objectiveの差がaccuracyへ大きく出る

という点。

部分再計算率が20%以下の領域でaccuracy degradationが大きい場合、単純にrecompute率を上げる前に、

> **selected tokenがquery-relevantか**

を調べる価値がある。

---

## まとめ

ProphetKVは、RAG KV reuseにおけるselective recomputationを、

```text
Which cached tokens are most corrupted?
```

から、

```text
Which cached tokens matter most for this user query?
```

へ切り替えた手法である。

全体は、

```text
Precomputed document KV
        ↓
Query-only layer pass
        ↓
Per-layer query→context attention
        ↓
Layer-wise fusion
        ↓
Unified top-k token set
        ↓
Selective full recomputation
        ↓
Generation
```

となる。

主要結果は、

- 20% recomputation
- full-prefill accuracyの96–101%
- RULERで既存SOTA比8.8–24.9%改善
- LongBenchで18.6–50.9%改善
- 8K / 16Kでfull recomputation比最大約5× TTFT speedup
- EPICに近いlatencyながら大幅に高いaccuracy

である。

特に重要なのは、性能数値以上に、**recomputation token selectionをquery-conditioned semantic utilityとして捉え直した点**にある。

CacheBlendが「壊れたKVを効率よく修復する」方向を開いたとすれば、ProphetKVは、

> すべての壊れたKVを同じ価値で修復する必要はなく、queryに必要なものだけ直せばよい

ことを示す後継研究として位置づけられる。
