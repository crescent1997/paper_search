# InfiniGen — 次layerのKVアクセスを先読みするoffloading system

## TL;DR / taxonomy

**Primary category: `access`**。CPU memoryにKVをoffloadしたLLM servingで、decode時に**次layerで必要になるKVだけをCPU→GPU転送**する。既存のKVを別promptへ転用する`reuse`でも、保存KVを不可逆に削除する`compress`でもない。主たる新規性は**layer i-1の計算中にlayer iのattentionを部分的に予測することでprefetch latencyを隠す**こと、そしてQ/Kの**直交変換によるoutlier集中**で予測を安価にすること。OSDI 2024採択。

## 1. 問題設定と従来法の限界

LLMのdecodeでは、各layerの過去token KVをGPUに読み込んでqueryとのattentionを計算する。長いsequenceや大batchではKVがGPUに収まらず、[FlexGen](https://arxiv.org/abs/2303.06865)などのCPU offloadingを用いる。ただし毎stepで全KVをPCIe転送すると、weight計算ではなく転送が支配的になる。

[H2O](../compress/2023-2306.14048-h2o.md)等の固定budget evictionはtransfer量を削減するが、過去に捨てたtokenを将来のqueryが参照できない。KVを全てCPUに置いてqueryごとに選べば情報は保てるものの、**queryが確定してから選択→fetch**すると転送がcritical pathに乗る。

InfiniGenはlayerごとの重要token数が一律ではないことも指摘する。OPT-13Bではscore `max-4`以上の重要token数が、系列長512/1024/1536/2048で平均37/60/66/73と増加が鈍い。全系列長の固定20%を転送するのは過剰になり得る。

## 2. Key observation: 隣接layerのattention入力は近い

Residual connectionとoutlier channelのため、Transformer block入力 `x_(i-1)` と `x_i` は高いcosine similarityを持つ。論文Table 1ではOPT-6.7B/13B/30Bで**0.95/0.96/0.97**、Llama-2-7B/13Bで**0.89/0.91**。対照的にattention output/FFN outputと次layer入力の類似度は低い。

これにより、layer `i-1` のattention入力 `x_(i-1)` を用いて、まだ得られていない `x_i` の代わりにlayer `i` のqueryを**近似的に生成**できる。重要な区別として、InfiniGenはlayer i-1のattention weightsをそのまま使うのではない。**layer iのquery projectionとkey cache**を、layer i-1の入力に適用してlayer iのattention scoreを予測する。

## 3. Offline skewing: 直交変換でQ/Kを疎な重要次元へ集約

部分dimensionだけのQK内積でselectionするには、重要な情報が少数dimensionに集中している方がよい。InfiniGenはquery/keyのweight matrixへ共通の直交変換 `A` を適用する。

$$
\widetilde Q = Q A,\qquad \widetilde K = K A,\qquad A A^T=I.
$$

したがって

$$
\widetilde Q\widetilde K^T = Q A A^T K^T = QK^T.
$$

**全dimensionを使ったattentionは変化しない**。モデルのfine-tuningや重み更新学習ではなく、数学的に等価なQ/K basis changeである。論文ではsample query matrixのSVD `Q=UΣV^T` から `A=V` を構築し、大きなsingular directionを前方の少数columnに集中させる。skewingしたQ/Kの絶対値を足し、column magnitude上位を選ぶことで、同じdimension indexをqueryとkeyで共有する。

重要なのは**SVDを毎decode stepで実行しない**こと。offlineでbasisを決め、weightに吸収する。Prefill時にpartial query weightsとpartial key cacheを構成する。実験では**30% dimension**を利用し、選択の近似と追加memoryを両立する。

## 4. Runtime speculative KV prefetch

Layer i-1の処理中に次layer i用の部分attentionを実行し、必要なKV token indexを予測する。

```text
# CPU: full K_i, V_i retained; GPU: partial K_i and partial W_Q_i
for each decoding token:
    for layer i:
        # while layer i-1 computes
        q_proxy = attention_input_(i-1) @ partial_WQ_i
        score_proxy = q_proxy @ partial_K_i.T
        idx_i = {t : score_proxy[t] > max(score_proxy) - alpha}
        async_prefetch(K_i[idx_i], V_i[idx_i], CPU -> GPU)
        # when layer i attention is ready
        y_i = attention(q_i, fetched_K_i, fetched_V_i)
```

このコードは概念図で、実際のCPU/GPU stream schedulingやlayer 0の扱いを省略している。論文ではoutlierがlayer 0の計算中に現れるため、**layer 1からspeculationを開始**する。各headのselected token数を調整してGPU kernelを実行しやすくする。

選択条件は `score >= max(score)-α`。`α=5`なら最大値との差5のtokenはsoftmax寄与が最大の `exp(-5)≈0.0067` 倍となる。これを利用して、固定top-kではなく**layer/queryごとに可変個数**をfetchする。OPTでは `α=4`、Llama-2では `α=5`、一層あたりfetchの上限はfull KVの20%とする。

**注:** score差に基づく閾値はsoftmax正規化後の相対重みを制限するが、多数の小さい重みが集積するケースの合計誤差を厳密に保証しない。実際のqualityは評価に依存する。

## 5. CPU KV pool管理とephemeral pruning

通常時はfull historyをCPUに残し、GPUへfetchしないtokenをそのstepのattentionから一時的に除外する（ephemeral pruning）。CPU容量にも制約がある場合、user-specified pool capacityを設け、FIFO・LRU・選択回数に基づくCounter evictionを比較する。

80% memory limitのWikiText-2/PTB実験では、**FIFOはperplexityを大幅に悪化**させるが、LRU/Counterはfull poolに近い。著者らはatomic update時のlinked-list lockを避けるためCounter方式を採用。ここで初めて過去KVを不可逆に捨てることになるため、通常のephemeral sparse accessと区別する必要がある。

## 6. Experiment Setup

- Models: OPT-6.7B/13B/30B、Llama-2-7B/13B。長文分析でLlama-2-7B-32K、Llama-3-8B-1048Kも使用。
- Hardware: **NVIDIA RTX A6000 48GB**、Xeon Gold 6136、DDR4-2666 96GB、**PCIe 3.0 ×16**。
- Serving baseline: FlexGen（明示的CPU KV offload）、CUDA UVM、FlexGen + H2O 20%、FlexGen + KV INT4。
- Quality: COPA、OpenBookQA、WinoGrande、PIQA、RTE（5-shot）、WikiText-2/PTB perplexity、PG-19から抽出した長文。
- Default: partial dimension ratio 0.3、`α=4`（OPT）/5（Llama-2）、一層fetch最大20%。
- Metrics: total inference latency（prefill+decode）、token/s、perplexity、relative KV fetch size、prefetch overhead。

## 7. Main Results

論文abstractの代表値は、**従来のKV管理方式比で最大3.00× speedup**と**最大32.6 percentage pointのaccuracy改善**。これは異なるbaselineとworkloadを横断した値であり、同じ条件のspeedup/accuracy対とは限らない。

OPT-13B・1920 input +128 output・batch20のFigure 14では、比較するUVM/FlexGen/INT4/H2Oの条件により**1.63–32.93×**のlatency差がある。最大値はUVM page-faultが多い条件を含むため、全ケースの一般的な改善率ではない。FlexGen比のsequence長実験（batch8）ではInfiniGen最大**5.28×**、H2O最大3.40×、INT4最大1.92×。

Batch 4→20のthroughputはInfiniGen **27.36→41.99 token/s**、INT4 12.22→14.02、H2O 21.31→25.70。FlexGenのKV全転送はbatch増加に対して伸びが悪い。

OPT-13B layerのlatency breakdownではFlexGenの**96.9%**、H2Oの**91.8%**がdata transfer。InfiniGenはIdeal（GPU常駐）比**1.52×遅い**水準に接近。KV全量を読む方式の3.90–18.55×より小さい。

Quality面では、**10%以下のKV fetch**でもH2O/INT4より良い傾向で、10%を超えるとfull KVに近いaccuracy。Long-context perplexityでも、permanent evictionによるH2Oの誤差累積を回避する。

## 8. Ablation / sensitivity

**Skewing有無:** OPT-6.7Bでskewingを外すと、少数dimensionから得たscoreがfull attentionを代表せず、accuracyが低下する。直交basis変換の導入により回復する。つまり「隣接layer入力の類似性」だけでは十分でなく、**近似scoreに適したcoordinate system**が重要。

**α:** 大きいほどKV fetch数・latency・accuracyが増える。`α>4`では精度改善が頭打ちになり、転送だけ増加する傾向。

**Partial ratio:** 0.3を超えてもqualityはほぼ改善しない一方、partial query/keyのGPU storageは増える。ratio 0.3で追加storageは**model weightの2.5%、KV cacheの15%**（論文の計測条件）。単純な「10% fetch = 10% memory」の解釈は不正確。

**Pool eviction:** FIFOよりCounter/LRUが良い。CPU memory limitを下げる場合は長期的な復元可能性が減る。

## 9. Limitations / 実装上の注意

1. **PCIe 3.0 offloading system**が主な評価対象。A100/H100のHBM内decodeやNVLink接続で同じspeedupになるとは限らない。
2. 予測には次layerのpartial K cacheが必要で、追加GPU memoryとindex managementが生じる。query/keyのbasis変更はattention値を保持するが、低次元のscore予測は近似である。
3. GQA/MLA/hybrid recurrent layersなど現代architectureで、per-head partial keyやlayer adjacencyをそのまま適用できるかは未検証。特にMLAのlatent cacheではquery/key projection absorptionとの整合が必要。
4. Layer i-1でnext-layerのKV indexを選ぶため、stream依存・async DMA・cache poolのlifetime管理が複雑。CPU page pinningやgather粒度で性能が変わる。
5. αで選んだtokenはsoftmax total massの保証を与えない。分散したlong-tail attentionでの品質低下を別途測る必要がある。
6. CPU poolを圧迫してCounter evictionを使うと、完全なfull-history再参照が不可能になり、query changeに弱くなる。
