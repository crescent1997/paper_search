# HiMe — Hierarchical Embodied Memory for Long-Horizon VLA Control

- [arXiv HTML](https://arxiv.org/html/2607.03449) / [PDF](https://arxiv.org/pdf/2607.03449) / [著者記載コード](https://github.com/HappyWaterXP/HiMe)
- **分類**: `KVcache/vla/` / hierarchical long-term memory + asynchronous control。Transformer KV tensor再利用ではない。

## 1. 概要・問題設定

高性能なVLM Plannerは遅く、低レイテンシのVLA Executorは長期履歴を保持しにくい。すべての制御stepでPlannerを実行すると、計算負荷と不安定なsubtask切替が生じる。HiMeはExecutor（高速制御）、Sentry（作業記憶と進捗監視）、Planner（長期記憶と再計画）を異なる時間粒度で動かし、必要な時だけ高価なPlannerを呼ぶ。長期記憶は画像・テキストを併用し、Add/Update/Deleteで古い状態を修正する。

## 2. 先行研究との差

- [MemoryVLA](2025-2508.19236-memoryvla.md): policy内部のperceptual-cognitive memory bank。HiMeは外部Plannerのepisodic memoryと進捗監視による再計画制御が中心。
- [MEM](2026-2603.03596-mem.md): 短期動画と長期言語記憶のpolicy入力。HiMeは外部DBの更新・削除とcontrol loopの階層化を重視。
- [ReMEmbR](2024-2409.13682-remembr.md) / [RAVEN](2026-2606.25206-raven.md): 長期ナビゲーションQA向け外部検索記憶。HiMeはmanipulation action success/progressを評価。
- [HELM](2026-2604.18791-helm.md): verifierとrollback recovery。HiMeはsubtask-completion Sentryとplanner memory consistencyが中心。
- FIFO memoryは古い観測が消える。HiMeは追加だけでなく明示的なUpdate/Deleteで矛盾する記憶を訂正。

## 3. 手法

### 3.1 三層制御

1. **Executor**: DROID事前学習のπ0.5を実機demonstrationでfine-tune。2 Hzで10-action chunkを生成し、下位制御は10 Hz。1 chunkから5 actionsをopen-loop実行。
2. **Sentry**: Qwen3-VL-8B。最近8フレームをworking memoryとして監視し、一定step間隔でsubtask完了を判定。完了イベント時にPlannerを呼ぶ。False Negative対策として固定間隔のfallbackあり。
3. **Planner**: GPT-4o（主実験）、Qwen3-VL-30B（追加実験）。semantic DB検索でepisodic memoryを参照し、subgoal stackと記憶を更新。

### 3.2 記憶表現と更新

Transient memoryは現在の観測、Working memoryは短い観測列、Episodic memoryは(a)画像・caption・物体状態・ユーザー嗜好のcontextual storeと(b)subgoal/statusを持つprocedural store。Sentryのイベントに応じPlannerがAdd（新規）、Update（古い記憶の修正）、Delete（不要・矛盾する記憶の削除）を行う。Text embeddingは`text-embedding-3`を用いる。固定サイズmemoryではなく、無制限設定ではepisodeに応じentry数が増える。

### 3.3 KVとの違い

Transformerのattention KVを保存・再利用するのではなく、VLM Plannerの**呼出頻度**を減らす。Planner呼出回数が減ることは計算節約に寄与するが、action inferenceのprefill latencyが減った証拠ではない。

## 4. Experiment Setup

- WidowX-250s、第三者視点＋手首カメラ、実機3タスク：Object Search（6 subtasks、約1450 actions）、Counting（7、約1200）、Rearrangement（6、約1035）。各方式20 trials。
- 比較: Transient memory（周期Planner）、Transient + Sentry、Flat Memory（直近8 + FIFO）、HiMe without Sentry、HiMe、Human high-level oracle。ExecutorとPlanner backboneを揃えてmemory/scheduleを比較。
- **Training**: Executorのみ60実機demonstrations（通常50＋corner case10）、AdamW、30k steps。Planner/Sentryはzero/few-shot利用。学習不要なシステム全体という意味ではない。
- **Deployment**: Sentry Qwen3-VL-8BはH100 80GB×1、local Planner Qwen3-VL-30BはH100 80GB×2（vLLM）。主Planner GPT-4oはAPI。制御loop 10 Hz。
- 指標: Task Progress（subtask完了率）、Memory Hit、Planner API calls/subtask。論文中の90%をすべてのepisodeの**完全成功率**と同一視しない。

## 5. Main Results

- 著者は3タスク平均の**Task Progress約90%**を報告。Flat Memory約65%、Transient系は低い。図ベースの結果は厳密な同一指標の表と区別する。
- Table 2:

| Task | HiMe progress | Flat progress | HiMe Planner calls/subtask | Flat calls | HiMe memory hit | Flat memory hit |
|---|---:|---:|---:|---:|---:|---:|
| Object Search | 92% | 64% | 1.8 | 5.4 | 94% | 68% |
| Counting | 92% | 58% | 2.6 | 4.8 | 98% | 61% |
| Rearrangement | 87% | 73% | 1.4 | 6.2 | 92% | 76% |

- Planner call P50（Appendix Table 11、**Planner呼出のend-to-end latency**）: GPT-4o API 38.59秒、Qwen3-VL-30B local 6.83秒、Qwen3-VL-8B local 6.10秒。**異なるモデルとdeploymentの比較**でありHiMe導入前後の同条件latency改善ではない。
- Planner API call削減はcontrol loopの低遅延化に重要だが、Sentryの推論コスト、GPU占有、通信遅延、policy throughputの総合比較は限定的。

## 6. 主要ablation

### 6.1 記憶モダリティ

画像のみは空間・視覚認識で有利、テキストのみはCounting等の意味・論理で有利。Countingではtext-only 91%対image-only 78%。interleaved画像＋テキストが3タスク平均90%で最良。captionのみでは後から画像詳細を復元できない。

### 6.2 Memory management

- FIFO 8 entries: 平均progress 68%。Append-only（No Management）86%。Active Add/Update/Delete 90%。
- **同容量比較**（Appendix Table 9、Rearrangement）：Unlimited Active 87%、Limited Active 8 entries 80%、FIFO 8 entries 64%。無制限とFIFOだけの比較に存在する容量交絡を、同budget比較で部分的に解消。
- Sentryのrecent window 1→8で完了検出Precision約76→82%、Recall約22→35%。Recallが低く見逃しやすいためfallbackが必要。

### 6.3 長期スケーラビリティ

Object Searchのround数1/2/3で、memory size 5.5/9.9/14.0、progress 92.5/76.3/66.7%。**履歴が長くなると性能は下がる**。memory entry数も増加し、長期で完全に一定メモリを保証する手法ではない。

## 7. Limitations

1. **タスク範囲**: 実機の3種類のtabletop操作に限定。LIBERO等のmatched標準simulation benchmarkはなく、一般化には注意。
2. **比較条件**: 無制限ActiveとFIFOを比較する際の容量差。Appendixの同8-entry実験は改善を示すが、Rearrangementのみ。
3. **長期保持**: round数増加でprogress 92.5→66.7%へ低下。永続的な記憶性能は未証明。
4. **速度**: Planner P50は数秒～数十秒。event-driven制御がその待ち時間を隠すが、すべてのsubtask遷移で即応できる保証はない。
5. **GPU/学習**: Executorの実機fine-tuningが必要。Sentry/Plannerは強力な既存VLMとH100を使用。GPU peak、total energy、throughputの統一比較はない。
6. **KV cache**: 直接のKV eviction/reuse/compressionやprefill削減を実装しない。
