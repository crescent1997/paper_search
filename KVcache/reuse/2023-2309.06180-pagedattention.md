# Efficient Memory Management for Large Language Model Serving with PagedAttention

> **核心：KVを減らすのではなく、未使用領域を予約せず、必要なtoken分だけ割り当て、同一prefixに対するKVの物理コピーを共有する。** 後続のprefix caching・radix tree・distributed KV cache・paged sparse attentionの前提となるserving基盤。

## 概要と問題設定

LLM servingではdecode中に各requestのKV cacheが1 tokenずつ増加する一方、生成長と終了時刻は事前に不明である。従来の連続tensor方式では最大長分のGPU memoryを予約するため、実際には使われないreserved領域、内部fragmentation、外部fragmentationが発生する。論文のFig. 2では、従来方式で実tokenのKVが占める割合は20.4–38.2%にとどまる。

KV cacheの理論上の大きさは、通常のMHAならおおむね

$$M_{KV}=2\,B\,T\,L\,H_{kv}\,d_h\,s$$

（batch size $B$、token数 $T$、layer数 $L$、KV head数 $H_{kv}$、head dimension $d_h$、要素byte数 $s$）で増える。PagedAttentionは**この式のKV要素数を減らす技術ではない**。実際に確保したメモリが、現在必要なKV量に近くなるようにする。

またparallel samplingやbeam searchでは、複数の生成系列が同一promptや共通の途中prefixを持つ。連続tensorを系列ごとに複製すると、内容が同じKVを何度も保存する。PagedAttentionはblock単位の共有を可能にする。

## 手法

### 1. Logical KV blockとphysical KV block

1系列のKVを固定長$B_{blk}$ tokenの**logical block**へ分割し、各logical blockをGPU上の任意の**physical block**へ配置する。論理順序と物理アドレスの対応はblock tableが保持する。

```text
Request A logical: [block 0] [block 1] [block 2]
                         |         |         |
GPU physical:       [#7]       [#1]       [#3]   （非連続でよい）
```

attention kernelはblock tableを参照してK/Vを順に読み、各blockに対する部分attentionを集約する。従来の連続アドレス前提のkernelをそのまま使うのではなく、block-table-aware kernelが必要になる。

- 新規request時に最大生成長分を一括確保せず、blockが埋まるたびに次のphysical blockを割り当てる。
- 固定サイズの物理blockをpool管理するため、異なる長さの連続領域を探す外部fragmentationを避けられる。
- 最終blockに限って最大$B_{blk}-1$ token相当の未使用領域が残る。blockを小さくすれば無駄は減るが、tableやkernelの管理負担が増す。

### 2. Reference countingとcopy-on-write (CoW)

複数系列のlogical blockが同じphysical blockを指すことを許す。共有blockにはreference countを持たせ、すべての参照がなくなるまで解放しない。共有中のblockへ新tokenを書き込む必要があるときだけ、**copy-on-write**でprivate blockへ分岐する。

- **Parallel sampling**：prompt KVは各sampling系列に複製せず共有し、生成後のsuffixだけ個別に保持する。
- **Beam search**：共通祖先のKVを共有し、beamの分岐に応じてCoWを適用する。探索木の共有状態が大きいほど効く。
- **Cross-request prefix**：同じprefixのKVを共有する仕組みも示す。ただし2023年論文の機構を、後年のvLLM Automatic Prefix Cachingが既に実装されていたものとして扱わない。自動発見・管理は後続研究の主要論点である。

### 3. SchedulerとGPU memory不足時の回復

vLLMはiteration-level schedulingとblock managerを統合する。GPU block不足時はrequestをpreemptし、KVをCPUへswapするか、解放後に**promptを再prefillして復元**する方式を選べる。これはCacheBlend/ProphetKVの「reuseによる品質劣化を修復するselective recomputation」と異なり、**memory圧迫への対処として既存状態を復元する計算**である。

kernel側ではblock書込みとreshape、block readとattention、CoWに必要なblock copyをそれぞれfusionして、細かいCUDA起動や非連続memoryアクセスの負担を減らす。

## Experiment Setup

- **Models**：OPT-13B / 66B / 175B、LLaMA-13B。NVIDIA A100搭載Google Cloud A2で1–8 GPUを利用。
- **Workloads**：ShareGPT会話とAlpaca instructionの入出力token長分布からPoisson到着のtraceを合成。加えてparallel sampling、beam search、共通prefix翻訳、chatbotを評価。
- **Baselines**：FasterTransformer、Orcaを再実装したOracle / Pow2 / Max予約方式。**Orca (Oracle) は実際には未知の出力長を事前に知る非実現的な上界**。
- **Metric**：end-to-end latency / output token（normalized latency）、支えられるrequest到着率、GPU KV使用率、batch size。通常の単発kernel高速化とは区別する。

## Main Results

| 評価軸 | 論文での主な結果 | 解釈 |
|---|---|---|
| 全体serving | 従来システム比おおむね**2–4× throughput** | fragmentation削減によるbatch拡大が主因。すべてのモデル・負荷で一律ではない |
| ShareGPT trace | Orca (Oracle)比**1.7–2.7×**、Orca (Max)比**2.7–8×**高い持続request rate | 出力長が不均一・長い場合ほど優位 |
| 同時batch数（OPT-13B） | ShareGPT: Orca Oracle 13.62 → vLLM 30.42、Alpaca: 72.75 → 132.44 | 余分な予約を排し同時実行数を増やす |
| Parallel sampling | Alpacaで**6.1–9.8%**、ShareGPTで**16.2–30.5%**のKV memory節約 | 共有prompt部分が主な節約対象 |
| Beam search | Alpacaで**37.6–55.2%**、ShareGPTで**44.3–66.3%**のKV memory節約 | 共有祖先が長いため節約が大きい |
| Cross-request共通prefix | 1-shot共通prefixで**1.67×**、5-shotで**3.58×** throughput（対Orca Oracle） | prefix長と再利用可能性に強く依存 |

これらは**serving systemの比較値**であり、KVを近似してaccuracyを犠牲にする圧縮方式ではない。原理的には元のfull KVをそのまま読み出すため、model outputの意味的品質を変える設計ではない。

## 主要Ablationとtrade-off

### Block size（Fig. 18）

小さすぎるblockはGPUの並列性とmemory coalescingを損ね、大きすぎるblockは内部fragmentationを増やし、共有できるprefixの粒度も粗くする。ShareGPTでは16–128 tokenが比較的良好、短文中心のAlpacaでは16–32 tokenが有利。**原論文の実装デフォルトは16 token**。

### Kernel overhead（Fig. 18a）

block table参照、分岐、可変長処理により、単体attention kernelはFasterTransformerの高度最適化kernelより**20–26%遅い**。それでもGPU memoryを効率化してbatch数を増やすため、end-to-end servingでは勝つ。したがって「PagedAttentionのkernel自体が常に速い」という理解は誤り。

### Swap vs recomputation（Fig. 19）

blockが小さいとCPU–GPU間で小規模transferが多発しswap効率が悪化するため、再prefillが有利になる。blockが大きいとswapが相対的に有利。16–64 token程度ではend-to-end差が小さい。この比較は**精度修復ではなくメモリ不足時の状態回復**である。

## Limitations

1. **KVの理論容量自体は削減しない**。同じtokenをすべて保存するため、長文脈1requestのKV総量はそのまま。量子化・token eviction・layer sharingとは独立。
2. **Block table / non-contiguous layoutのオーバーヘッド**。専用kernel、CPU metadata管理、indirection、memory localityへの配慮が必要。後続のvAttentionはこの設計上のコストを主題とする。
3. **共有は同一causal prefixが前提**。同じdocumentが途中で出現しても、前文脈が違えばKVは一致しない。semantic similarityによる近似共有は扱わない。
4. **実験の世代依存性**。OPT/LLaMAとA100、当時のOrca/FasterTransformer実装での評価。現代のvLLM v1・FlashInfer等への性能倍率をそのまま外挿できない。
5. **負荷条件依存**。短い系列やcompute-bound条件では、memory効率化がthroughputへ直結しない場合がある。

## Taxonomy・技術的系譜

| 軸 | PagedAttention |
|---|---|
| Category | `reuse`（exact prefix/block sharing + memory manager） |
| Reuse単位 | Request内の複数sequence、および同一prefixを持つrequest間の**KV block** |
| Relevance signal | **Token prefixの完全一致**。semantic/query attentionは使わない |
| Repair / fusion | **不要**（共有するKVは同一causal historyに由来） |
| Model modification / fine-tuning | 不要。ただし**attention kernel / serving runtimeの改修は必要** |
| Full-prefill approximation vs task utility | 近似ではなく**exact state reuse**とmemory管理。task utilityの直接最適化ではない |
| TTFT / TPOT | 直接の主眼はthroughput・batch capacity。prefix reuse可能ならprefill省略にもつながる |

**重要な系譜**：PagedAttentionは「共有できるKVをどこに格納するか」を解決する。後続のChunkAttentionは「共有prefixをどう自動発見し、共有KVへのattentionをどう速くするか」、[Prompt Cache](2023-2311.04934-prompt-cache.md)・[CacheBlend](2024-2405.16444-cacheblend.md)・[Block-Attention](2024-2409.15355-block-attention.md)・[KVShare](2025-2503.16525-kvshare.md)は「同一prefixでない文書・意味的類似区間でもKVを再利用できるか」を問う。[Preble](2024-2407.00023-preble.md)・[Mooncake](2024-2407.00079-mooncake.md)は共有KVの配置やroutingをcluster規模で扱う。

## 関連研究との差分

- **[Prompt Cache](2023-2311.04934-prompt-cache.md)**：schema/モジュール単位の事前KVを使う。PagedAttentionはtoken blockの**物理memory共有**が中心で、任意位置での正確なKV再利用を保証しない。
- **[CacheBlend](2024-2405.16444-cacheblend.md)**：異なるcontextから取得したKVを結合するとattention dependencyがずれるため、selective recomputationで修復する。PagedAttentionはexact prefix共有なのでrepair不要。
- **[KVShare](2025-2503.16525-kvshare.md)**：semantic similarityを利用したsharingとdifferential editing。PagedAttentionにはsemantic hit-rate向上の仕組みはない。
- **[Preble](2024-2407.00023-preble.md)**：prefix再利用とGPU間の負荷分散を同時に最適化するscheduler。PagedAttentionは1 serving engine内のblock配置管理を主眼とする。
- **[Mooncake](2024-2407.00079-mooncake.md)**：KVをCPU/SSD/RDMAなどの分散tierへ置き、cache-aware routingする。PagedAttentionはGPU側block memory管理の基礎。

## まとめ

PagedAttentionの最も重要な貢献は、KV cacheを「requestごとに最大長を予約する連続tensor」から「論理順序と物理配置を分離した動的block群」へ変えたこと。これによりfragmentationを抑え、CoWによる共有を可能にした。**reuse研究では、exact prefix sharingの基準点**として置くべき論文である。
