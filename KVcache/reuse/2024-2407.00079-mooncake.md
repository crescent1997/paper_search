# Mooncake — KVCache-centric Disaggregated Serving

> **要点**：KV cacheの値を近似・量子化するのではなく、**同一prefixのKVをクラスタ全体の共有資源として扱う**。再計算に要するGPU時間と、DRAM/ネットワークからのKV転送時間を比較し、TTFT/TBTのSLOを守りながらgoodputを最大化する。FAST 2025 Best Paperの正式版を基準にする。

## 1. 概要・問題設定

Long-context LLM servingには性質の異なる二つの段階がある。Prefillは長いpromptを処理する計算集約段階、decodeは毎token過去KVを読み出すメモリ帯域集約段階である。同一GPUで両者を混在させると、長いprefillがdecodeのtime-between-tokens (TBT) を乱す。一方、prefillとdecodeを単純に分離するとKV cacheをGPU間で移すコストが発生する。

Mooncakeはさらに一歩進み、GPU HBM以外のCPU DRAM、SSD、NIC/RDMAを組み合わせた**disaggregated KVCache pool**を中心にservingを設計する。前のリクエストで生成したKVを後続の同一prefixリクエストへ共有することでprefill計算を減らす。cacheの所在・転送・prefillノード・decodeノードをまとめて選ぶのがConductorである。

分類は **`reuse` → exact-prefix reuse / cluster-wide KV caching / disaggregated serving**。KV cacheのbit幅・token数を減らす`compress`でも、decode attentionで参照するtokenを減らす`access`でもない。複数の独立文書KVを任意順に連結するsemantic/modular reuseも直接の対象ではない。

## 2. 既存手法の問題と中心仮説

- **HBM/ローカルDRAMだけのprefix cache**：容量が小さく、別ノードに置かれた同一prefixのKVを使えない。キャッシュがホットスポット化すると同じprefixが複数ノードで重複計算される。
- **無条件のremote reuse**：ネットワークからKVを取るよりGPUでprefillし直す方が速い場合がある。TTFTだけでなくTBT SLOと帯域混雑を同時に考慮すべき。
- **prefill/decode同居**：大きいprefill batchがdecodeを中断し、特に長文でtail TBTが悪化する。
- **overload**：全requestを受け付けてからdecode slot不足を発見すると、すでに使ったprefill計算が無駄になる。SLOを満たせないrequestは早期に拒否した方がeffective throughputが上がる。

核心は「**more storage for less computation**」である。大規模モデルではprefix KVを移すバイト数より、同じprefixを再計算するFLOPsの方が高価になりやすい。したがって十分なRDMA帯域があれば分散KV再利用は有利になる。

## 3. 手法

### 3.1 Mooncake Store：content-addressedな分散KV

KVはpaged blocksで管理し、各blockに自身の内容と先行prefixに依存するhash keyを付与する。これにより**同じtoken列かつ同じ先行context**に対応するKVを同一視できる。FAST版ではモデルサイズと転送粒度に応じて16〜512 tokens程度のblockを想定する。LRUでevictionし、利用中のblockは保護する。ホットなblockは複数ノードにreplicaを配置し、単一転送元へのアクセス集中を回避する。

Storeは`put`/`get`/`change_replica`などのobject APIと、memory registration・batch transfer・completion pollingの転送APIを提供する。Transfer EngineはGPUDirect RDMA、複数NIC、topology-aware path selection、endpoint pooling等を用い、GPU/CPU間およびノード間でKVを高速転送する。**ここでの「共有」はexact prefix一致に基づく**。類義表現をsemantic similarityでマッチさせるKVShareとは異なる。

### 3.2 Conductor：prefill/decodeを同時に決定

リクエストのtoken列からprefix hashを求め、候補prefillノードごとに(1)利用可能なprefix長、(2)転送時間、(3)prefill queueと計算時間、(4)DRAM容量を見積もる。同時にdecodeノードのVRAM容量・batch負荷・TBT SLOを確認する。最大cache hitのノードを無条件に選ばず、**推定TTFTを最小化しつつSLOを満たす組**を選ぶ。

Hot prefixの需要が偏ると、他ノードへのKV migration/replicationを行う。これは単なるLRU cacheではなく、cacheの配置をスケジューリング変数として扱う点が特徴。過負荷時には推定生成長・将来のdecode負荷を用いてearly rejectionを行い、処理途中の無駄を減らす。

### 3.3 リクエストの4段階とoverlap

1. **KV reuse**：Conductorが指定したprefix blockをStoreからprefill GPUへロードする。
2. **Incremental prefill**：未キャッシュsuffixを計算。長文はchunked pipeline parallelism (CPP)で分割し、必要に応じて複数prefillノードへ割り当てる。
3. **KV transfer**：生成されたKVを**layer-wise**にdecodeノードへstreamする。prefill計算と非同期転送を重ねる。
4. **Decoding**：decodeノードでKVをロードしてcontinuous batchingに参加する。TBT SLOを満たすようbatchを管理する。

この設計では単純な `prefill完了 → 全KV転送 → decode開始` よりも転送待ちを隠せる。KV cacheの生成表現は通常のTransformerと同じで、モデル重みのfine-tuningは不要。

### 3.4 転送するか再計算するかのbreak-even

FAST論文の§2.2はprefill FLOPsをモデル幅$d$、層数$l$、prefix長$p$で近似する。

$$\mathrm{FLOPs}(n)\simeq l(an^2d+bnd^2)$$

Prefix再利用で節約する計算と、転送するKV量を比較すると、利用可能な帯域$B$とGPU計算性能$G$にbreak-even条件が得られる。論文のLLaMA3-70B・8×A800・prefix 8192の試算では最低約6 GB/s、8×H800では約19 GB/sの帯域が必要とされる（overlapの非理想性により実際はより大きい）。**大きなモデルほどreuseが有利**という定量的な動機付けである。これはCacheGenの「転送byteを圧縮する」方向と相補的。

## 4. Experiment Setup

- **評価版**：FAST 2025正式論文（9著者）。arXiv技術報告の古い結果と混同しない。
- **モデル**：機密保護のためLLaMA3-70Bと同構造のdummy modelでrequest traceをreplay。生成内容の品質ではなくservingの計算・転送・SLOを評価する。
- **ワークロード**：Kimi由来のconversation、tool&agent trace、synthetic。FAST版Table 2の平均input/outputは順に`12035/343`、`8596/182`、`15325/149` tokens。prefix cache ratioは`40%/59%/66%`、request数は`12031/23608/3993`。
- **ベースライン**：vLLM、vLLM prefix caching、vLLM chunked prefill等。比較ではGPU資源数を揃え、TTFT/TBTのSLOを守れる**最大request capacity**を測る。
- **分解評価**：local/global Store、cache-aware scheduling、replica動作、TCP/GlooとのRDMA transfer比較、帯域制限時のTTFT、E2E latency breakdown。

## 5. Main Results

**(a) SLO下の有効request capacity**：FAST版のconversation traceでMooncakeは比較ベースラインに対し**59〜498%増加**。値はTBT SLOの厳しさと比較対象によって変わるため、普遍的な5.98倍高速化ではない。論文は実運用において旧システムよりA800クラスタで**115%**、H800で**107%**多くのrequestを扱えると報告する。これらは生のtoken/sではなくSLO達成条件付きのcapacity。

**(b) Global cacheの効果**：10 prefillノードでlocal DRAM cacheと比較すると、global cacheのhit rateは最大**2.36倍**（+136%）、平均prefill GPU時間は最大**48%減少**。各ノード3M token相当のlocal cacheを持つ条件で、複数ノードのcapacityを共有する効果を確認する。

**(c) KV転送性能**：40 GB（LLaMA3-70Bの128K KV相当）転送で4×200Gbps NIC構成が**87 GB/s**、8×400Gbps構成が**190 GB/s**。TCPに対し約**2.4倍/4.6倍**の帯域改善。これは**Transfer Engine単体**の性能であり、生成全体の速度倍率ではない。

**(d) ネットワーク感度**：synthetic workloadでは帯域が約100Gbps以上のとき平均TTFTが2秒未満となる条件を報告。一方、100Gbps未満では転送混雑によりTTFTが悪化。RDMAや十分な帯域がない環境では同等の効果を保証できない。

## 6. 主要ablationと読み方

- **Local vs global**：総GPU数だけでなく、cacheがノードをまたいで参照できること自体の効果を分離。local-onlyでは人気prefixが別ノードに存在しても再利用できない。
- **Replication/hotspot**：conversationとtool&agent traceでは上位人気blockのreplicaが増え、remote fetchの集中を緩和。syntheticでは人気が分散して効果が小さい。
- **Scheduler**：random、単純load balancing、local cache-aware、global KVCache-centric schedulingを比較。cache hit率のみでなく転送時間とqueueを見込むことが重要。
- **Transfer bandwidth**：高速NICの存在を前提とする結果であり、低帯域ではreuseが再計算より遅くなり得る。
- **Prefix hit 0% vs 95%**：128Kで高いhit率のときprefill時間が約92%減る条件を報告。転送・ロードの一部は計算とoverlapするが、ゼロにはならない。

## 7. Limitations / 再現上の注意

1. 正確な**prefix一致**を前提とする。途中に異なる文書を挿入したり、順序を変えたりしたKVの整合性を保証しない。RoPE位置修復やattention-state repairを提供しない。
2. 大規模なDRAM/SSDプール、高速NIC、global scheduler、cache metadata管理が必要。単一GPUでは構成の利益が薄い。
3. trace replayは実際のuser contentを含まないdummy modelで実施。回答accuracyの評価ではなくシステム指標の評価である。
4. 高負荷時のearly rejectionはgoodput向上に寄与するが、acceptance policyとfairnessのトレードオフを伴う。
5. arXiv技術報告（7著者、最大525%、実運用75%増）とFAST正式版（9著者、59〜498%、115%/107%増）の数値は**別版**。本ファイルではFAST正式版の数値を優先する。

## 8. Taxonomy・関連研究との差分

| 研究 | 再利用単位 | 中心の最適化 | KVの品質修復 |
|---|---|---|---|
| [Prompt Cache](2023-2311.04934-prompt-cache.md) | 再利用可能prompt module | modular prompt caching | 主題ではない |
| [CacheBlend](2024-2405.16444-cacheblend.md) | document/chunk/token | 選択的再計算でcross-attentionを修復 | **あり** |
| [KVShare](2025-2503.16525-kvshare.md) | semantic similarityで対応付けた範囲 | semantic sharingと差分編集 | **あり** |
| [LMCache](2025-2510.09665-lmcache.md) | chunk/block、storage tier | KV offload/load・connector・reuse基盤 | 別途blender等 |
| **Mooncake** | exact-prefix block / request | **クラスタ全体のcache配置・転送・SLO scheduling** | **なし** |
| [CacheGen](../compress/2023-2310.07240-cachegen.md) | 外部保存KVのstream | entropy codingと帯域適応による転送byte削減 | 主題ではない |

**技術的な位置付け**：Mooncakeは`どのKVを再利用するか`をsemanticに判断するアルゴリズムより、**再利用可能なKVをクラスタ上のどこに保持し、どこでprefill/decodeするか**を最適化する基盤。KV修復型のCacheBlend/ProphetKVと組み合わせる場合、修復の演算コストと転送コストをConductorの判断へ組み込む必要がある。
