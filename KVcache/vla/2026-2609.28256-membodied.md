# MemBodied — Recurrent Associative Memory for VLAs

## 1. 概要

過去の観測が現在の画像から消えた後でも、元の物体位置や既に試した操作を覚えておく必要がある。履歴frameをすべてprefixへ追加するVLAは、エピソードが伸びるほどcontext長・prefill・メモリが増える。MemBodiedは、**policy call間で維持される固定サイズの連想記憶**を導入する。

記憶は2つの補完的な経路から成る：(1) action expertの各layerが持つ**associative matrix**（gated delta ruleで行動と観測結果を逐次更新）、(2) 最初の観測から抽出した**episode anchor**（初期sceneを忘れないための固定視覚参照）。毎回の推論では現在の状態から記憶を読み、専用memory tokenを通じてaction self-attentionに条件付けする。action実行後の観測を見てからmemoryへ書くため、未来観測を過去actionの生成に漏らさない。

**KV cache研究との境界**：associative matrixは`key -> value`の関係を保持するが、Transformer attentionの過去token K/Vを保持するKV cacheではない。ここでの改善は**履歴の固定容量化と読出し方式**であり、precomputed visual KVのreuseやlayer KV evictionではない。

## 2. 問題設定・先行研究との差

- 部分観測タスクでは、現在観測`I_t`とrobot state`s_t`だけでは行動が一意に決まらない。例：4つのpadのどこにblockがあったか、電池のどの向きを既に試したか。
- FrameStackやvideo-history compressionは履歴をcontext tokenへ符号化する。一定windowならコストは上限付きだが、長いイベント間隔で証拠が落ちる。
- Recurrent token方式は一定サイズのlatentを持つが、情報のread/writeを明示的に分けていないものがある。MemoryVLAはdual-stream memory bankへのattention retrieval、MEMは短期video+長期text memory。
- MemBodiedは**actionとその結果の観測**を一つのinteraction eventとして書き込み、状態行列をgated deltaで更新する。さらに初期sceneの不可逆な上書きをanchorで補う。
- 元の`π0`、`π0.5`をbackboneにして、history-dependentなRMBenchと、一般的なLIBEROの両方で検証。

## 3. 手法

### 3.1 Episode state / fixed capacity

```text
E_t = (M_t, A)
M_t = { S_t^(l) }_(l=1..L)  # layer-wise associative matrices
A = pooled visual tokens from first observation (fixed during episode)
```

各action layerにrank`r=128`の行列を保持。episode長`T`に対して行列数・サイズは一定で、毎回新しい観測tokenをappendしない。episode開始時にreset。**一定サイズ**は「情報損失なし」を意味しない。古いassociationは更新で上書きされ得る。

### 3.2 Read / memory-token injection

現在のstate tokenのlayer入力`h_in^(l)`からquery`q_t^(l)`を作り、`S_{t-1}^(l)`を検索してreadout`r_t^(l)`を得る。readoutを線形変換し、`α_mem/r`でスケール（default`α_mem=256, r=128`なので係数2）。gateをかけて**そのpolicy callにのみ存在するmemory token**へ加え、action suffixのself-attentionで参照させる。次callに持ち越されるのはmemory token自体でなく行列`S_t`。

比較実装：Attention Steering（Q/attention outputを補正）、Hierarchical Memory（slow LSTM-like stateを追加）、Memory Token（context tokenとして入力）。最終方式はMemory Token。

### 3.3 Delayed write / gated delta rule

action chunk`a_t`を生成・実行後、`I_{t+1}`から次観測のcamera別visual tokenをpoolし、robot stateに基づくattentionで特徴を抽出。実行したactionのsummaryと結合して`v_t^(l)`を作る。post-layer hidden stateからwrite keyとgateを予測し、gated delta ruleで`S_t^(l)`を更新する。

概念的には

```text
S_t = retention_gate * S_(t-1)
      + write_gate * (new_value - old_readout_at_write_key) ⊗ write_key
```

（正確な行列配置・正規化は本文3.2節の定義に従う）。差分補正により同じkeyへの古いvalueを単純加算し続けない。**因果順序はread → action → observe outcome → write**。未来観測を当該actionの生成に使わない。

### 3.4 Initial-scene anchor

初回観測の各cameraの16×16 patch gridを4×4へaverage-poolし、camera間でconcatした固定anchor`A`を保持。現在のrobot state/visual特徴からrank`r_A=64`のcross-attentionで必要な初期位置情報を読み、action embeddingへ融合。prefixへ元画像の全tokenを追加しない。recurrent stateが長期更新で初期配置を忘れる弱点を補うが、タスクによっては過去の初期状態が邪魔になる。

### 3.5 学習と推論実装

複数のpolicy callに相当する連続観測・action対をsequenceで学習。過去のmemory writeへ後続action lossの勾配を伝播し、**memory専用の教師ラベルなし**でaction objectiveからread/writeを学習する。ただし**追加学習は必要**。vision encodingはbatch/sequence方向で並列化、memory更新は時間方向で逐次伝播。

推論は50-step action horizon、10 flow-matching denoising steps、bf16。実装は前callのhidden/actionを保持し、次観測時にdelayed writeする。LIBEROの5-step replanningでは50-step更新間隔を保つため10個のrecurrent slotをround-robin運用する。したがってLIBEROのmemoryの時間意味はRMBenchの50-step呼び出しと完全には同一でない。

## 4. Experiment Setup

| 項目 | 内容 |
|---|---|
| RMBench | 5 memory-dependent task。M(1): Put Back Block / Rearrange Blocks / Swap Blocks、M(n): Battery Try / Block Ranking。各50 rollout |
| LIBERO | Spatial/Object/Goal/Longの4 suite、各10 task×50 rollout。memoryはepisode開始時にreset |
| Real robot | AgileX PiPER双腕、上部1 + wrist2 camera。3 task、各20 rollout、完全達成のみ成功 |
| Main backbone | π0。π0.5にも転移検証 |
| Training | RMBenchでLoRA rank 16（PaliGemma）/32（action expert）、10,000 step、batch 8、sequence長8/14/18等。LIBEROはfull fine-tuning 30k step、batch 32 |
| Baselines | π0 stateless、4-frame stack、vanilla recurrent/Delta-Mem、μVLA、NativeMEM（local reimplementation）、π0.5 published baseline、各memory architecture variant |
| Profiling | A100 80GB、bf16、4 RMBench taskで各50 episode、warm-up除外。NativeMEMのvideo history encoding時間を含むmodel-side cycle latency |

**再現上の留意**：公式GitHub READMEと論文AppendixでSwap Blocksのsequence length記載に差がある（論文ではM(1) 3タスクが8、GitHubのsetup説明ではSwap Blocksが14）。実際のconfigを優先して確認する必要がある。NativeMEMの比較は公開結果そのままでなく、著者らが同環境に移植した実装。NativeMEMは50k tokenizer training + 20k policy trainingで、MemBodiedの10k trainingと計算budgetが揃っていないため、結果の差をアーキテクチャ単独の因果効果と断定しない。

## 5. Main Results

### 5.1 RMBench（5 taskのsuccess rate平均、Table 1）

| Model | Put Back | Rearrange | Swap | Battery | Ranking | Mean |
|---|---:|---:|---:|---:|---:|---:|
| π0 Stateless | 6 | 2 | 8 | 16 | 0 | **6.4** |
| π0 FrameStack | 14 | 30 | 0 | 4 | 26 | **14.8** |
| Vanilla Recurrent | 18 | 22 | 14 | 22 | 8 | **16.8** |
| MemBodied w/o anchor | 34 | 76 | 16 | 30 | 32 | **37.6** |
| **MemBodied** | **40** | **92** | **56** | **40** | **22** | **50.0** |

Stateless比**+43.6pt（7.81×）**、Vanilla Recurrent比**+33.2pt（2.98×）**。別backboneのπ0.5は12.4→48.0%（3.87×）。NativeMEMのlocal比較では**38.4%**、NativeMEM+MemBodiedは45.2%、単独MemBodiedは50.0%。ただしNativeMEMの方がPut BackとSwapで優れるケースもあり、全タスクで一様に優位ではない。

### 5.2 実機とLIBERO

実機3 taskの平均完全成功率：**3.33→26.67%**（合計60 rolloutで2→16成功）。成功率8×だが、絶対値はまだ低い。LIBEROはSpatial 96.2 / Object 97.8 / Goal 95.8 / Long **90.6**、4-suite平均**95.1%**。π0 baselineはLong **85.2**、平均94.2%。Longで+5.4pt、Spatial/Objectではわずかな低下がある。

### 5.3 推論効率（Appendix B.7）

**NVIDIA A100 80GB、bf16、model-sideのみ**。4タスク計200 episode/policy、warm-up除外。NativeMEM 2,548 cycle、MemBodied 2,563 cycle。

| 指標 | NativeMEM | MemBodied | 差 |
|---|---:|---:|---|
| Latency / policy cycle | **1593.7 ms** | **129.2 ms** | **−91.9%** |
| Peak GPU memory | **20.57 GiB** | **18.61 GiB** | **−9.5%** |
| 追加parameter | **415M** | **40M** | 約10.4×少ない |

NativeMEM側はvideo history encoding、増加するcontext、action生成を含む。MemBodied側はvision encoding、associative read/write、50-step action生成を含む。**両者は履歴処理の計算量と学習budgetが異なる**ため、129.2msは一般的なπ0 stateless baseline比のspeedupではない。GPU memoryはJAX allocator peak bytes in use。実機のphysical control frequency、network/ROS overhead、数時間以上の連続稼働におけるlatency driftは未報告。

## 6. 主要Ablation / 誤差分析

| Ablation | Mean success (%) | 読み取り |
|---|---:|---|
| Attention steering (AS) | 20.8 | Q/output補正だけでは弱い |
| Hierarchical memory (H) | 23.2 | slow state追加でも改善限定 |
| Memory-token / no anchor | 37.6 | context token readoutが優位 |
| **Memory-token + anchor** | **50.0** | 初期scene参照が重要 |

AnchorありでSwap Blocksは16→56と大きく改善する一方、Block Rankingは**32→22**に低下。初期状態が必ず有益ではないことを示す。Write-valueの3-task平均は**vision only 42.7 / action only 34.7 / both 46.7**。actionと結果の観測を同時に記録する設計が最も良い。

50 seed-matched rolloutの失敗分析では、Put Back Blockの「誤ったpadに戻す」件数がstateless **37/50**からMemBodied **13/50**へ減少。現在画像だけでは判別不能な時点での誤りが減る一方、motor executionや長期追跡の失敗は残る。

## 7. Limitations / 批判的評価

1. **固定容量 ≠ 永続的な正確記憶**。行列はエピソード長に対してO(1)だが、繰り返しのdelta更新で初期情報が上書きされ得る。anchorも初期sceneだけであり、中盤の重要eventを無損失で保持しない。
2. **比較baselineの公平性**。NativeMEMのtokenizer training 50k + policy 20kとMemBodied 10kはtraining budgetが異なる。論文は明記しているが、11.6pt差や91.9% latency差を純粋な記憶機構だけの効果とみなせない。
3. **タスク数・実機の試行数**。RMBenchは5 task×50、実機は3 task×20で、実機26.67%は完全成功の絶対水準としては限定的。長期の数十分〜数時間にわたる頑健性は未検証。
4. **Sequence trainingコスト**。推論はO(1)状態でも、学習では長いsequenceに勾配を流す必要がある。training-time VRAM/throughputは別問題。
5. **Action-horizonの因果性**。遅延書込はfuture leakageを防ぐが、LIBEROの5-step replanningで50-step predicted chunkをsummaryするslot方式は実際に実行したactionと完全一致しない場合がある。
6. **KV cacheとの区別**。action expert内の過去K/Vの再利用・evictionではない。recurrent matrixはfast-weight associative memoryで、attention cacheの保存形式をそのまま代替するものではない。
7. **再現性**。コードは公開済みだがデータ・trained checkpointの一部は同梱されず、論文とREADMEのsequence設定差の確認が必要。
