# IHEval: Evaluating Language Models on Following the Instruction Hierarchy

> Instruction hierarchyをsecurity attack専用の評価から一般的なinstruction-following問題へ広げ、system > user > conversation history > tool outputという4段階のpriorityについて、Reference / Aligned / Conflict条件を比較する。3,538 examples・9 tasksを通じ、強いLLMでもconflict時にはpriorityではなく低権限instructionの表面的な強さに引っ張られることを示す。

## 概要

[The Instruction Hierarchy](../Defense/2024-2404.13208-instruction-hierarchy.md) はprivileged instructionを優先するtraining方法を示したが、主に安全性関連taskとGPT系列を対象としていた。IHEvalはこれをmodel-agnosticなbenchmarkへ一般化し、「LLMはroleごとのpriorityを本当に理解しているか」を体系的に測る。

benchmarkは **3,538 examples / 9 tasks** からなり、system message、user message、conversation history、tool outputという複数のinstruction sourceを扱う。

## 問題設定

priorityは高い順に概ね

```text
System message
   > User message
      > Conversation history
         > Tool output
```

と定義される。

重要なのは、低priority inputを常に無視すればよいわけではないことである。競合しない場合には低priority instructionも正しく実行し、競合した場合だけhigher-priority constraintを守る必要がある。

このためIHEvalは各taskを次の条件に分ける。

- **Reference**: hierarchy conflictのない通常task。
- **Aligned**: 複数priorityのinstructionが同じ方向を指す。
- **Conflict**: lower-priority instructionがhigher-priority instructionと矛盾する。

理想的なモデルではReference / Aligned / Conflictのperformance gapが小さい。

## 先行研究からの改善点

Instruction Hierarchy論文の評価はprompt injection、system prompt extraction、jailbreak等のsecurity-oriented scenariosが中心だった。IHEvalはこれを一般的なtask completionへ拡張し、特定のrefusal policyを持つかではなく、**instruction source間のorderingそのものを理解しているか**を測る。

またtool outputまで明示的に含めることで、agent / tool-use時のindirect prompt injectionに近い構造も評価対象となる。

## Benchmark Construction

9 tasksは異なるinstruction sourceの組合せと競合形式をカバーする。各exampleではhigher-priority instructionが期待されるbehaviorを規定し、lower-priority fieldにはalignedまたはconflicting instructionを置く。

単純な「悪意ある文字列を拒否できるか」ではなく、同一taskについてpriority relationshipだけを変えて比較できるよう設計されている。このpaired structureにより、通常のinstruction-following能力不足とhierarchy failureをある程度分離できる。

またconversation historyやtool outputにinstructionを埋め込むことで、user promptだけをattack surfaceとするbenchmarkより現実的なmulti-source settingを作る。

## Experiment Setup

proprietary / open-sourceの複数LLMを評価する。主要metricは各taskのaccuracy / task-specific scoreと、ReferenceからConflictへ移った際のperformance degradationである。

さらにinstruction wordingのstrictness等を変え、モデルがrole priorityを利用しているのか、それとも「強い命令口調」「直近のinstruction」といったsurface cueに依存しているのかを診断する。

## Main Results

全モデルでConflict条件になるとReferenceから大幅なperformance dropが発生する。

代表例として **GPT-4oはReference 91.9に対してConflict 70.0** まで低下する。高性能modelでも約22ポイントのgapが残り、通常task能力が高いこととinstruction hierarchy遵守は同義ではない。

open-source modelではさらに顕著で、論文時点の最も競争力のあるopen modelでもconflict resolution accuracyは **48%** にとどまる。Llama-3.1-70Bの代表的Conflict scoreは **14.0** と低く、role-aware chat templateを持つだけではpriority behaviorが自動的に獲得されないことを示す。

## Instruction Strictness Analysis

興味深い診断結果として、lower-priority instructionをより断定的・強制的な文体にすると、モデルがそちらへ従いやすくなる。

これはモデルが

```text
source privilege > content strength
```

という抽象規則を安定して適用しているのではなく、training中に学んだinstruction salienceやwording cuesとpriority cueを競合させている可能性を示す。

したがってsystem/user delimiterを認識できることと、**権限という抽象概念を理解していることは別問題**である。

## Tool Output / Indirect Instruction

tool outputは通常dataとして利用すべきだが、その中に自然言語instructionが含まれるとモデルは命令として解釈しうる。IHEvalはこの低priority sourceを明示的に評価することで、web browsing、RAG、plugin、agent tool useで問題となるindirect prompt injectionとinstruction hierarchyを接続する。

ただしbenchmarkの主眼は特定RAG implementationではなく、モデル自身がsource priorityを識別できるかにあるため、LLM-model-security側のbenchmarkとして位置づけられる。

## Limitations

priority orderingはあらかじめsystem > user > history > toolと固定されている。実際のagent systemでは同じtoolでもauthorityが異なる、複数developer / sub-agentが存在する、organization policyがsystem messageより上位にある等、よりfine-grainedな権限構造がありうる。

またtask数・role種類が有限であり、benchmark上の高得点が未知のrole labelsや任意tier数へ一般化するとは限らない。この点は後続のMany-Tier Instruction Hierarchyが直接扱う。

## LLM Model Security Taxonomyでの位置づけ

```text
Defense primitive
  Instruction Hierarchy training
          ↓
General evaluation
  IHEval  ← 本論文
  fixed roles / 4-level priority
          ↓
Scalability evaluation
  ManyIH-Bench
  arbitrary / up to 12 tiers
```

IHEvalは「prompt injectionに強いか」だけでなく、より根本的な **priority-following capability** を独立した能力として測定可能にした点が重要である。

## 実装・研究上の示唆

モデル評価ではsystem prompt jailbreak benchmarkだけでは不十分であり、benignなinstruction conflict、tool-returned instruction、conversation history conflictも含める必要がある。

またhierarchy-aware trainingを導入する場合、attack-specific ASRだけでなく、IHEvalのReference / Aligned / Conflict gapを測ることで、over-refusalやlower-priority instructionの過剰無視を検出しやすい。
