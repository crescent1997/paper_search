# Pointing the Way, Hiding the Destination: Practical Private Dense Retrieval at Scale

> **位置づけ**: RAG knowledge-base stealingを直接実行するAttackではなく、providerのprivate corpusを検索する際に「ユーザのquery」と「providerの文書」の双方を保護するDefense/secure protocol。文書の直接取得は各roundでk件に制限する一方、K件のscoreと繰り返しqueryによる情報蓄積は明示的な残余リスクである。

## 概要

外部の認可ユーザがproviderの非公開corpusをdense retrievalで検索すると、少なくとも2種類の秘密が衝突する。(i) providerはユーザの検索queryや関心対象を知るべきではない。(ii) ユーザは料金・権限で許された検索結果以外の文書を取得してはならない。通常のembedding APIにquery vectorを送るだけではembedding inversionやproperty inferenceが成立し得る。逆に、全corpusを暗号化したまま厳密に検索すると計算量が巨大になる。

提案の核は **「粗い候補発見のみprivacy-calibratedなbinary codeで行い、厳密な意味類似度の計算は候補K件に限定する」** という2-stage設計である。ユーザはLoRA適応したhash encoderの出力をvMF分布でrandomizeして公開し、providerはHamming searchでK件を選ぶ。元のpretrained encoderによるquery embeddingはBFVで暗号化して送られ、providerはK件との整数内積だけを準同型計算する。ユーザはK件のscoreを復号してtop-kを選び、選択したk件だけをOTで取得する。**Kは暗号化scoreを計算する候補数、kはplaintext payloadの取得上限**であり、両者を混同しないことが重要。

## 問題設定 / Threat Model

- **Corpus Owner（server）**: private documents、全文書のembedding、binary hash index、AEADで暗号化したpayloadを保持する。**honest-but-curious**で、protocolには従うがqueryやユーザの選択結果を推測しようとする。
- **User（client）**: 認可された検索ユーザ。query、encoder、BFV secret keyを持つ。payload取得については**malicious receiver**を想定し、OTで1roundあたりk件までに制限する。ただしBFV scoringの証明は、正しい形式でqueryを暗号化する**conforming user**が前提。
- **Serverが観測**: randomized hash code、候補集合C_K、暗号化query、protocol transcript、ユーザID/時刻/通信長/K/k。plaintext query、K件の復号score、選択したk件の位置は観測しない。
- **Userが観測**: K件の正確な整数類似度score、K件の暗号化payloadと長さ、最大k件のpayload鍵・本文。score oracle自体は文書内容の推定に利用され得る。
- **対象外/追加前提**: endpoint侵害、サイドチャネル、Sybilでquotaを回避するケース、任意の不正形式BFV ciphertextに対する全面的な安全性は保証されない。認証とround間のrate/score-exposure制限が必要。

RAG-Thief、[IKEA](../Attack/2025-2505.15420-silent-leaks-ikea.md)、[RAGCrawler](../Attack/2026-2601.15678-connect-the-dots.md)のように、正常なqueryを反復してcorpusを再構成する脅威と比較すると、本研究は**1roundの未許可payload取得上限**を暗号プロトコルで強制する点が異なる。**全roundでのcorpus coverageを上限付けるわけではない**。

## 先行研究からの改善点

| 系統 | 課題 | 本論文の改善 / 代償 |
|---|---|---|
| Full-corpus MPC/HE（P²RAG等） | N全件の暗号計算で重い | K≪Nに暗号計算を限定。粗いcandidate patternをmetric-DPで公開する設計上のtrade-offを受容 |
| Cluster/PIR（PANTHER等） | 多数のprobeと高次元表現でメモリ・通信が増大 | 256/512bit hash indexで粗探索し、候補だけBFV計算 |
| RemoteRAG | candidate/score disclosureの境界やutility–privacyのtrade-off | learned binary filter + randomized coarse code + exact rerank + key-only OTを統合 |
| [Pisces](2026-pisces-private-rag.md) | SimHash/暗号処理の構成が異なる | 学習型filterで高い候補recallを確保し、厳密な内積をK件に集中 |
| 単純なhash/randomized response | Hamming rankingが崩れてrelevant docsを失う | 連続方向へのvMF randomizationとKの拡大でutilityを回復 |

この論文はDPによる**document-level output privacy**を保証する[DP-RAG](2024-2412.19291-rag-with-differential-privacy.md)や[SparsePay-RAG](2026-2609.27406-sparsepay-rag.md)とは保護対象が異なる。ここでのmetric DPは**ユーザのcoarse query representation**を守るもので、各文書の生成への寄与にDP保証を付けるものではない。

## 手法 / Algorithm

### 1. 学習型binary candidate filter

LoRA適応したencoderとlinear headから、長さLのbinary codeを作る。

$$b(x)=\operatorname{sign}(W\,\operatorname{pool}(E_{\mathrm{LoRA}}(x)))\in\{-1,1\}^{L}.$$

E5-base-v2は256bit/mean pooling、BGE-base-en-v1.5は512bit/[CLS] pooling。MS MARCOのquery-passage supervisionを用い、retrieval loss、continuous-to-Hamming ranking transfer、pretrained geometryへのregularizationを組み合わせる。BM25による候補探索とrerankerを使ってhard negativesを選び、false negativeの混入を抑える。両encoderとも16 epochsで学習する。**hash側のLoRA適応と、Stage 2の元のpretrained dense encoderは別物**であり、hashを学習しても最終scoreの定義を変えない。

### 2. DP coarse code releaseとHamming候補検索

hash headのpre-sign出力zに対して $h=\tanh(\beta z)$、$u=h/\|h\|_2$ を計算する。$Y\sim\mathrm{vMF}(u,\kappa)$ をサンプリングし、$\tilde b=\operatorname{sign}(Y)$ をserverへ送信する。serverは全文書のbinary indexをHamming距離で走査し、候補C_Kを選ぶ。

vMF densityが $p_u(y)\propto\exp(\kappa u^\top y)$ であることから、任意の方向u,u'に対し出力確率比は $\exp(\kappa\|u-u'\|_2)$ 以下。sign変換はpost-processingなので、このboundを維持する。角距離radius $\rho$ 内の方向に対して $\kappa=\varepsilon/(2\sin(\rho/2))$ とすればpure directional metric DPとなる。**これは通常の隣接文書差分DPとは異なる隣接関係**であり、εだけを他のDP-RAGと横並び比較してはいけない。

### 3. 元のdense encoder + BFVによる正確な候補score

Userは元のpretrained encoderから正規化embeddingを作り、int8 symmetric quantization後にBFVで暗号化する。Ownerは候補K件の量子化embeddingをplaintext operandとして保持し、packed BFVで整数dot productを計算する。polynomial degree 8192で複数候補をSIMD処理し、暗号化比較・bootstrappingを省略する。compact layoutでは評価ciphertextの非score slotをクリア/ランダム化し、**K個の規定score以外のembedding情報がciphertextから漏れない**ようにする（正しいquery ciphertextという条件付き）。

### 4. Client-side top-kとactive-secure OT

UserはK件のscoreを復号してtop-k位置をローカルに決める。Ownerは候補K件のAEAD payload ciphertextを送るが、復号鍵は128bitのcontent keyを使った**k回の1-out-of-K OT**で渡す。これによりOwnerは選択位置を知らず、悪意あるreceiverでも1roundに最大k個のcontent keyしか得られない。各文書は4,096-byte単位へpaddingされるが、**padding後の長さ、同じciphertextの再登場、K件のscore**は漏洩対象として明示される。

### 5. オンライン実装の並列化

hash forwardが終わったらOwner側Hamming scanと、User側pretrained forward + BFV encryptionを並列に走らせる。候補確定後はAEAD ciphertext streamingとBFV scoringも重ねる。モデルforwardを2回必要とするが、serial overheadを短縮する構成である。

## 実験設定

- **Training**: MS MARCO。**Zero-shot retrieval**: BEIRのSciDocs（25K）、NQ（約2.7M）、DBpedia-Entity（4.6M）、Climate-FEVER（5.4M）、FEVER（5.4M）。
- **Retriever**: E5-base-v2、BGE-base-en-v1.5。hash候補生成と元encoderによるreranking。比較はdirect sign、LSH、PCA-sign、ITQ、IsoHash、BPR、full-corpus dense。
- **Private retrieval baseline**: P²RAG、RemoteRAG、PANTHER。ネットワーク100Mbps/1Gbps/10Gbps、異なるKを評価。ベースラインごとの信頼モデルやpreprocessingの差に注意。
- **Generator**: Qwen3-32B。NQの500 queries、top-5 passages、128-token生成。EM/F1、retrieval NDCG@10、Recall@K、latency、trafficを測定。
- **Privacy attacks**: ZSInvert型search-based embedding inversion、GEIA型generation-based inversion、topic/sentiment/authorshipのproperty inference。float、no-DP hash、DP codeを比較。

## Main Results

### Retrieval qualityとhash filterの役割

E5のNQでfull-corpus NDCG@10=**0.5854**に対し、K=500で**0.5787**。BGEのNQでは0.5414に対して0.5372。5 corpusの平均E5 Recall@500はlearned filter **0.7170**で、BPR **0.6813**、ITQ **0.6789**を上回る。ここでRecall@Kは関連文書が候補集合に含まれる割合であり、最終NDCGとは別指標。

DP条件を含む3 dataset平均では、plaintext filterのNDCG@10が**0.5363**、pure-vMF（ε=64,K=2000）が**0.5359**でfull-corpus float **0.5394**に近い。randomized response（ε=16,K=3000）は**0.0306**に崩れる一方、continuous noiseではK拡大によってほぼ回復する。なお、pure-vMFとGaussian/RDP-vMFは隣接関係・保証が異なる。

### End-to-end RAG

NQ 2.68M passages、500 queries、Qwen3-32Bではfull-corpus floatが**EM 50.0 / F1 63.09**、pure-vMF（ε=64,K=3000）が**EM 50.0 / F1 62.89**。top-5のanswer-alias Hitは88.4対87.8。RAG品質を維持したままprivate retrievalを実行できるとする主張を支える。

### Latency / throughput

2枚のA100（index用・Qwen3-32B用）を使うNQの128-token生成ではplaintext pipeline約**7.305秒**。K=2000でprivate retrievalの追加コストは**0.728秒（約10%）**、K=3000で**1.098秒（約15%）**。SciDocs/K=500では10Gbpsで**198.9ms**、100Mbpsで**430.9ms**、通信量**2.93MB**。K=3000では通信量13.64MBへ増大する。

同一条件へ寄せた100Mbps比較でSciDocs/Touché/NQ-1Mのprivate retrievalは**0.298/0.160/1.456秒**、P²RAGの2.1/69.2/20.1倍高速と報告。ただしP²RAGは192 hardware threads、trusted-dealer preprocessing除外など比較条件に差があり、一般的な絶対優位と読むべきではない。

### Privacy attack evaluation

E5でsearch-based inversionの成功率（verifier cosine≥0.8）は、float **0.920** → no-DP hash **0.590** → pure-vMF ε=64 **0.325**。generation-based inversionのtoken F1も**0.545 → 0.368 → 0.205**。Property inference macro F1の3属性平均はfloat **0.6911**、no-DP hash **0.6133**、Gaussian ε=8 **0.3875**。embeddingの離散化とrandomizationの両方が効果を持つことを示す。ただしゼロ漏洩ではない。

## Ablation / robustness / 実装上の考察

- **Stage 1の独立評価**: K=200/500の候補recallとStage 2のNDCGを別々に比較。学習hashが他のhashing baselineより高いrecallを持ち、Stage 2で精密に並べ直せる。
- **DP mechanism比較**: randomized responseは高次元bitごとのnoiseでutilityが急落。Gaussian、RDP-vMF、pure-vMFは連続方向をrandomizeしてからsignに落とすため、Kを増やせばretrieval qualityを回復可能。
- **Inversion vs property inference**: 完全な文章復元が失敗してもtopic等のattribute inferenceは残る。両者を別に測定している点は重要。
- **HE leakage accounting**: malicious userへのOT上限と、conforming userへのHE score privacyは異なる保証。悪意あるユーザの任意ciphertextを許す場合、well-formedness proofが追加で必要。
- **Cross-round**: T roundでplaintext payloadは最大Tk件。score oracleを反復すると同じ文書に対する線形観測が蓄積するため、認証・quota・Sybil対策は暗号機構と独立して必須。

## Limitations / 成立条件

1. **Corpus stealingの全面阻止ではない**: ユーザが毎回許されたk件を大量のqueryで集めれば、結果としてcorpusの大部分を回収し得る。OTは各roundの不正な超過取得を防ぐだけ。
2. **Score oracle漏洩**: K個のexact similarity scoreをユーザに公開する。文書本文以外の情報が多roundで推定される可能性があり、paperも明示的に残余リスクとする。
3. **Query privacyの範囲**: coarse codeとcandidate setはOwnerに見える。DP保証はdirectional metric adjacencyに限定され、通信時刻・長さ・IDは固定条件として扱う。
4. **Trust model**: Ownerはhonest-but-curious、UserのBFV ciphertextはwell-formedが前提。強いmalicious serverやendpoint compromiseへのend-to-end保証ではない。
5. **運用**: 2 encoder forwards、hash model配布、HE/OT key管理、quota台帳、文書更新時のindex/AEAD更新が必要。百万文書以上の検索を実験したが、動的indexやproduction adversarial trafficは別途検証が必要。

## RAG data extraction / security taxonomyでの位置づけ

**Defense / Private retrieval infrastructure**。保護境界は「検索サービスが見られるquery」と「検索ユーザが見られる未許可文書」。[RAGFort](2025-2511.10128-ragfort.md)のようにgenerator経由のknowledge-base reconstructionを抑えるDefenseや、[SAGE](2024-2406.14773-sage.md)のようにgeneratorへ渡すcontextをsanitizationするDefenseとは直交する。RAGCrawler/GeoEx型の反復query stealingへの強い保証を主張するには、**cross-round coverageやscore exposureを含むend-to-end評価**が必要。

研究上は、(i) top-K scoreを秘匿するsecure top-k、(ii) queryごとのbudgetではなくuserごとの累積情報利得に基づくquota、(iii) DP coarse retrievalとdocument-level DP generationの組合せ、(iv) indexを安全に更新するprotocol、が発展課題となる。
