# ActionCache — Action-space CacheによるFlow VLA高速化

## 1. 概要
VLAのflow-matching action headは、Gaussian noiseからaction chunkへ到達するために多数のdenoising/flow integration step（NFE）を必要とする。ActionCacheは過去の成功軌道の**中間action**を記憶し、現在の観測・言語・ロボット状態に近いentryを検索してwarm startする。適切なcache hitではNFEを0〜数回まで減らす。既存モデルの重みを変更しない**training-free external cache**。

**注意**：名称にCacheを含むが、保存するのはTransformerのK/V tensorではなく**action-spaceの中間軌道**。長期記憶研究としては「過去の成功経験の再利用」に近く、MemoryVLAのepisodic semantic memoryとは別物である。

## 2. 問題設定・先行研究との差
既存の[VLA-Cache](2025-2502.02175-vla-cache.md)はVLM側のvisual KV再利用、[EfficientVLA](2025-2506.10100-efficientvla.md)はVLM pruningとdenoising中間feature reuseを行う。いずれもaction headの反復回数を必ずしもゼロにしない。隣接actionのwarm-start方式は直近履歴への依存や追加学習を必要とする場合がある。

ActionCacheは**過去episodeや別タスクの類似状況**をindexで検索し、flowの後半の初期値として使う。hit時はfull denoisingを省略し、miss時は通常のGaussian-noiseからの生成へfallbackする。

## 3. 手法
### 3.1 Flow-based action head
通常はcondition `c_t`の下で`A_t^0 ~ N(0,I)`から開始し、

$$A_t^{\tau+\Delta\tau}=A_t^{\tau}+V_\theta(A_t^{\tau},\tau,c_t)\Delta\tau$$

を繰り返す。ActionCacheでは適切な過去の`A_i^τ`を検索し、必要な後半stepだけ実行する。

### 3.2 Multimodal key
VLM output embeddings（GR00Tではrobot-state embeddingsも連結）から長い特徴`h_t`を取り、**固定のsparse ternary random projection**で`k_t=R h_t`へ縮約する。`R`の要素は`{-1,0,1}`、次元`d=500`、非ゼロ密度`p=0.01`。追加学習なし。keyのcosine類似度最大のentryを探し、`s_max >= T_hit`ならhit。`T_hit`未満ならfull inferenceへfallback。

### 3.3 Cacheの書き込み・更新・eviction
cache miss時のfull generationから、hit時の残りNFE数に対応する**中間noisy action**を取り出してpending bufferへ保存する。episodeが成功した場合にのみmain cacheへcommitし、失敗episodeは破棄。容量上限ではLRU/LFU等でeviction。単なるKV reuseと異なり、**success-conditioned write**が長期的なcache品質に関わる。

### 3.4 パラメータ
既定`T_hit=0.85`（π0.5）、`0.65`（GR00T-N1.6）、`d=500`、`p=0.01`、cache capacity 3,000、LRU。大規模比較Table 1ではπ0.5=10,000、GR00T=30,000 entriesを用いており、既定値と異なる。cold startではcacheが空なので効果は小さく、論文は**事前prefill済みのsteady state**を評価する。

## 4. Experiment Setup
- **Models**：π0.5（base NFE=10）、GR00T-N1.6（base NFE=4）。
- **Benchmarks**：VLABench 10 primitive tasks、LIBERO（Appendix）。実機SO-101 6DoFでpick_sausage、pick_and_close（長期複合）、push_button。
- **Baselines**：base full-step、単純なNFE削減、EfficientVLA、Falcon warm-start。VLM側との併用はVLA-Cache。
- **GPU**：VLABench latencyはRTX 5090 32GB。実機ではoverhead＋wrist camera（224×224にresize）。
- **Evaluation**：VLABenchのbase/ActionCacheは4 seeds×200 episodes=800 episodes、他手法は200 episodes。prefillとtestは異なるrandom seed。実機は各50 episodes。
- **Metrics**：task success（SR）、action-head latency、end-to-end latency、cache hit rate、progress score（cross-task時）。GPU memory/control frequencyの比較は十分には報告されていない。
- **追加学習**：ActionCache自体には不要。ただし評価用のGR00Tや実機π0.5 checkpointはタスク向けにfine-tuningされており、「base policyの学習が不要」とは言えない。

## 5. Main Results
### 5.1 VLABench Table 1（action-headのみ、RTX 5090）
| Model | Method | NFE on hit | SR (%) | Action-head latency | Speedup |
|---|---|---:|---:|---:|---:|
| π0.5 | Base | 10 | 38.8±3.0 | 18.8 ms | 1.00× |
| π0.5 | ActionCache | 0 | **40.9±2.8** | **1.8 ms** | **10.44×** |
| GR00T-N1.6 | Base | 4 | 34.0±1.2 | 24.1 ms | 1.00× |
| GR00T-N1.6 | ActionCache | 0 | **30.8±1.8** | **0.6 ms** | **40.17×** |

**10.44× / 40.17×はaction-headの高速化**でありVLM backboneを含むend-to-endの値ではない。GR00TではSRが**-3.2pt**であり、成功率維持と断定すべきでない。比較する旧v1のHTML抽出等では異なるspeedup数値が表示される場合があるため、現行arXiv v2 PDF（2026-08-03）のTable 1を優先した。

### 5.2 実機SO-101（end-to-end）
| Task | Base SR / latency | ActionCache SR / latency | Cache hit rate |
|---|---:|---:|---:|
| pick_sausage | 90% / 103.13 ms | 88% / **81.90 ms** | 41.8% |
| pick_and_close | 88% / 102.24 ms | 90% / **61.56 ms** | 82.8% |
| push_button | 100% / 106.26 ms | 100% / **56.46 ms** | 94.4% |

実機では1.26〜1.88×の**全体**高速化。key projection＋lookupは各0.3ms前後。control frequencyを保証する定量評価ではない。

### 5.3 KV再利用との併用（VLABenchの別3タスク）
| VLA-Cache | ActionCache | SR (%) | End-to-end latency |
|---|---|---:|---:|
| off | off | 40.7 | 97.4 ms |
| on | off | 41.4 | 94.2 ms |
| off | on | **41.2** | **45.9 ms** |
| on | on | **39.1** | **57.0 ms** |

**重要な反例**：VLA-CacheとActionCacheを単純に併用すると、ActionCache単独より遅くなりSRも下がる。著者はVLA-Cacheにより画像tokenの再利用が増え、cache-key類似度分布が歪むため、`T_hit`を厳しくする必要があると説明する。複数のreuse層の相互作用を検証する価値がある。

### 5.4 Cross-task reuse
`select_fruit`だけでcacheを埋め、別タスクの`select_painting`、`select_toy`へ適用。progress scoreは20.0 vs base 21.0、51.7 vs base 50.5。初期フェーズではhit rateが80%を超える。**progress scoreは完全成功率ではない**。

## 6. 主要Ablation
- **key source**：VLM output embeddingsはinput embeddingsより同程度のhit rateで高い成功率（例：HR約83%、SR 37.2 vs 8.1）。action relevanceを反映する特徴が重要。
- **hit threshold / cache capacity**：`T_hit`を上げるとaccepted entryの類似度が高くなり成功率を維持しやすいが、hit rateは下がる。cacheを大きくするとhit率が上がる。50 entries=114KB〜5,000=11.4MBで評価。
- **eviction**：長期的に再利用されるactionがある条件ではLFUがLRUより高いhit率を得る。FIFOはrandom replacementより明確な利益がない。
- **NFE**：類似度が高いhitなら0-step reuseが可能。類似度が低いとrefinement NFEを増やすかmissへfallbackする必要がある。

## 7. Limitations / 批判的評価
1. **事前に成功episodeからcacheを構築したsteady-state評価**。未経験の環境・タスクではmiss率が高くなる。成功episodeのみcommitする仕組みは安全側だが初期学習コストを隠さないよう注意。
2. `T_hit`、`N_hit`、cache容量などのhyperparameter調整が必要。見た目の近さと安全なactionの近さは一致しないことがある。
3. action-head 40.17×はend-to-end 40.17×を意味しない。VLM側が支配的なら効果は限定される。
4. **KV-cacheとの併用で単独より悪化**する具体例があり、cache keyの安定性やaction条件付けの整合性が今後の課題。
5. 実機タスクは3種類であり、長時間の失敗回復・部分観測・環境変化の一般化は十分には示されていない。
