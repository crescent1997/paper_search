# ASIDE: Architectural Separation of Instructions and Data in Language Models

## 概要

ASIDEはprompt injectionの根本原因を、LLMが「実行すべきinstruction」と「処理対象のdata」を同一のtoken embedding spaceで表現していることに求める。

そこでdata tokenだけに固定orthogonal rotationを適用し、instruction tokenとは異なるrepresentation spaceへ写像する。追加trainable parameterは不要であり、既存pretrained modelをarchitecture-levelにinstruction/data-awareへ変換できる。

## 問題設定 / Threat Model

典型的なindirect prompt injectionでは、system/user instructionが「文書を要約せよ」と指示する一方、untrusted document内に「前の指示を無視せよ」といったmalicious instructionが含まれる。

ASIDEはsystem側が各tokenを instruction / data としてラベルできる状況を前提とする。

attackerはdata領域を制御できるが、functional-role labelそのものを変更できない。

## Method

通常のembeddingを E(x) とする。

instruction tokenはそのまま E(x) を使用し、data tokenには固定orthogonal matrix R を適用する。

data embedding = R E(x)

Rはorthogonalなので元embedding空間の幾何構造を大きく壊さず、instruction/data間には明確なrepresentation shiftを作る。

実装ではembedding dimensionを2次元pairに分け、各pairへ90度のisoclinic rotationを適用する。

(x1, x2, x3, x4, ...) -> (-x2, x1, -x4, x3, ...)

rotation自体はparameter-freeである。

## なぜRotationか

単に別embedding tableをrandom initializationするとpretrained lexical knowledgeを失う。

ASIDEは元embeddingをorthogonal transformするため、data token同士のdistance / geometryを保持しながらinstruction representationから分離できる。

したがってpretrainingをやり直す必要がない。

## Training

ASIDE化したmodelを通常のinstruction-tuningでfine-tuneする。

重要なのは、prompt injection専用adversarial safety trainingを必須としない点である。

architecture側にfunctional-role separationというinductive biasを導入するだけでもrobustnessが改善する。

## Instruction-Data Separation

論文ではSEP scoreを用いてinstruction/data representationの分離を評価する。

ASIDEはbaseline modelやISEより強いseparationを形成し、その差がdeep layerでも維持されることをrepresentation analysisで確認する。

## Experiment Setup

複数model familyで評価し、主に以下を確認する。

- instruction-data separation
- benign instruction-following utility
- prompt injection robustness
- internal representation

prompt injection benchmarkにはBIPIAやStruQ系settingを含む。

## Main Results

代表例ではLlama-3.1-8BのBIPIA-text ASRが13.6%から4.1%、BIPIA-codeが22.8%から9.2%へ低下する。

Qwen3-8BのStruQ-IDでは47.0%から8.1%、Mistral-7BのStruQ-IDでは33.4%から9.6%へ低下する。

SEP scoreもmodelによって大きく改善しつつ、general utilityは概ね維持される。

## Generalization

専用attack trainingを行わずに複数prompt-injection benchmarkで改善する点から、特定attack stringのmemorizationではなくinstruction/data representation separation自体がrobustnessへ寄与すると考えられる。

## ISEとの関係

[Instructional Segment Embedding](2024-2410.09102-instructional-segment-embedding.md)はtoken sourceごとのlearnable additive embeddingを元token embeddingへ加える。

ISE:
E'(x) = E(x) + S(role)

ASIDE:
E'(x) = E(x) for instruction
E'(x) = R E(x) for data

ISEがprivilege/sourceをadditive offsetで表すのに対し、ASIDEはfunctional roleごとにembedding geometryを明示的に分ける。

## AIRとの関係

Augmented Intermediate Representations (AIR; arXiv:2505.18907)はISE型のIH signalがdeep layerで弱くなる問題に対し、各decoder layerへlayer-specific privilege embeddingを再注入する。

ASIDEは別方向で、input embedding時点からinstruction/dataをorthogonal transformationで分離する。

AIRは現時点でrepository選定基準を満たす正式venue/citationを再確認できていないため、関連研究としてのみ記載する。

## StruQ / SecAlignとの関係

[StruQ](2024-2402.06363-struq.md)と[SecAlign](2024-2410.05451-secalign.md)はtrusted instructionとuntrusted dataをstructured formatとtraining objectiveで区別する。

ASIDEはその区別をtoken embedding computationそのものへ組み込む。

StruQ/SecAlignがbehavioral separation、ASIDEがarchitectural separationという違いがある。

## Instruction Hierarchyとの関係

[The Instruction Hierarchy](2024-2404.13208-instruction-hierarchy.md)はsystem > user > tool / external data等のpriority relationをbehaviorとして学習する。

ASIDEは任意many-tier hierarchyを直接表現するのではなく、まず instruction vs data という最も基本的なprivilege boundaryをarchitecture-levelに分離する。

したがってfull Instruction Hierarchyの代替というより、その基盤となるprovenance signalの強化と位置づけられる。

## ChatInjectとの関係

[ChatInject](../Attack/2025-2509.22830-chatinject.md)はuntrusted tool data内にsystem/user/assistant chat-templateを偽造し、textual role cueからpriority spoofingを狙う。

ASIDEではdata tokenは外部functional-role labelに基づいてrotated embeddingとして処理されるため、data中にsystem-like文字列が存在してもembedding-levelではdataとして識別できる。

この意味でChatInject型role spoofingと原理的に相性のよいDefenseである。

ただし論文がChatInjectへのadaptive evaluationを実施したわけではないため、実際のrobustnessは別途検証が必要である。

## CaMeLとの関係

[CaMeL](2025-2503.18813-defeating-prompt-injections-by-design-camel.md)はcapability/provenanceをsystem architectureで分離する。

ASIDEはmodel内部representationへprovenance-like functional roleを伝える。

CaMeLがexecution authorityを外部systemで制御するのに対し、ASIDEはLLM自身がdataをinstructionとして誤解しにくくする。

## FocalLoRA / V-Steerとの関係

[FocalLoRA](2025-2502.05416-focallora.md)はconflict-sensitive attention headsを選びQ/KをLoRA trainingする。

[V-Steer](2026-2607.26228-v-steer.md)はinference時にpriority imbalanceを示すheadを検出しcached Vを編集する。

ASIDEはattention headを直接操作せず、attentionへ入る前のembedding representation自体を分離する。

architecture-level Defenseの系譜として、ISE / ASIDE → FocalLoRA / V-Steerという比較ができる。

## White-box / Black-box Attackとの関係

ASIDEは特定attack optimizerを検出するDefenseではない。

data tokenがどのような文字列であってもfunctional role labelがdataならrotated embeddingを使うため、black-box semantic injectionへのstructural robustnessを狙う。

一方、ASIDE architectureを知るwhite-box attackerがrotated representationを前提にGCG等でadaptive optimizationするworst-case robustnessは重要な追加評価となる。

## Limitations

- instruction/data functional-role labelをsystem側が正しく与える必要がある。
- data内部の一部をlegitimate instructionとして実行したいケースは単純なbinary labelingでは扱いにくい。
- arbitrary system/developer/user/tool many-tier hierarchyを直接表現しない。
- adaptive white-box attackへのformal guaranteeはない。
- model architecture / tokenizer pipelineにembedding transformationを組み込む必要がある。
- external tool authorizationやcapability enforcementは別途必要。
- instruction/data境界自体が曖昧なapplicationではpreprocessing policyが必要になる。

## LLM Model Security Taxonomyでの位置づけ

Behavioral separation:
StruQ / SecAlign / Instruction Hierarchy

Source-aware additive representation:
ISE

Geometric architectural separation:
ASIDE

Attention-head intervention:
FocalLoRA / V-Steer

System-level capability separation:
CaMeL

ASIDEはinstruction/data separationをtraining conventionではなくmodel architectureのinductive biasへ変換するDefenseである。

## 実装・研究上の示唆

実装上はtokenごとにfunctional-role maskを持ち、embedding lookup後にdata位置だけ固定rotationを適用すればよい。

重要な研究課題は、ASIDEをmany-tier privilegeへ拡張することである。例えばsystem / developer / user / tool / external dataごとに互いに分離したorthogonal transformationを割り当てられるか、またRoPE・KV cache・GQA等と組み合わせた際にrepresentation separationがどこまで維持されるかが興味深い。

ChatInjectやGCGをASIDE-awareに最適化したadaptive attackも、architecture-level privilege signalが本当にspoof-resistantかを測るうえで重要になる。
