# FASTER — Rethinking Real-Time Flow VLAs

## 1. 概要

VLAの推論を高速化する際、action chunk全体の生成時間だけでなく、**最初のactionを何msでロボットへ渡せるか**（Time to First Action, TTFA）が実時間制御に直結する。FASTERは、flow matchingのdenoisingをaction indexごとに非一様に進め、先頭actionだけを1 sampling stepで確定させるHorizon-Aware Schedule（HAS）を提案する。確定actionをstreamingで逐次送信し、ロボットが実行中に残りactionを精緻化する。

**分類上の注意:** 本研究はTransformerのKV tensorのreuse/eviction/compressionを行わない。対象は**action expertのflow samplingとclient-server scheduling**であり、VLA推論効率化の隣接研究として `KVcache/vla/` に分類する。

## 2. 問題設定と先行研究との差

- 同期型action chunk生成では全denoisingを終えるまでロボットが待つ。非同期型は停止を減らすが、古い観測に基づくactionを実行するズレが残る。
- 既存のReal-Time Chunking（RTC）系はchunkの滑らかな接続を重視し、外界の急変から**次の反応**までの時間を直接最適化していない。
- 先頭actionは現在の観測・proprioceptionで制約されるため、遠い未来actionより短いflow積分で推定しやすいというpilot studyに着目する。
- [BlockVLA](2026-2605.13382-blockvla.md)はblock diffusionのprefix KVをreuseする。FASTERはflow samplingの途中でactionを確定・streamingするため、キャッシュとは独立の設計である。
- [VLA-Cache](2025-2502.02175-vla-cache.md)は連続frameのvisual KV再利用、[LAC](2026-2602.00686-adaptive-visual-token-caching.md)は学習型のcross-frame reuseであり、主にVLM側計算を減らす。FASTERはaction expertの**最初の出力遅延**を短縮する。

## 3. Method

### 3.1 Reaction latencyの定式化

制御周波数 `f`、制御周期 `Δt_ctrl=1/f`、推論遅延 `Δt_infer`、実行するaction数 `s` とし、`Δt_exec=s Δt_ctrl`。突発イベントが推論周期のどこで発生するか一様と仮定すると、反応時間は以下の一様分布になる（論文Table 1）。

- 同期: `U(Δt_infer, 2Δt_infer + Δt_exec)`、期待値 `1.5Δt_infer + 0.5Δt_exec`
- 非同期: `U(Δt_infer, Δt_infer + Δt_exec)`、期待値 `Δt_infer + 0.5Δt_exec`

したがって非同期化だけでは期待反応時間を `0.5Δt_infer` 減らすにとどまる。さらにTTFAと推論周期を短縮する必要がある。ただし**一様分布はイベント発生時刻についての仮定**であり、実世界の全イベントが厳密に一様という主張ではない。

### 3.2 Flow matchingとHorizon-Aware Schedule

通常のflow VLAでは全action indexに同一のdenoising time `τ` を割り当てる。FASTERはglobal sampling progress `ρ^j` に対し、index `i` ごとにhit time `u_i` とlocal time `τ_i^j` を設定する。

```math
u_i = \left(1-\left(\frac{i}{H-1}\right)^\alpha\right)u_0
```

```math
\tau_i^j=\max\left(0,\frac{\rho^j-u_i}{1-u_i}\right)
```

`u_0=(N-1)/N` とすることで最初のactionは最初のsampling stepで `τ_0=0` に到達する。遠いactionは残りstepで引き続きdenoiseする。これは**10回のAE forwardをすべて省略するのではなく、最初のactionを1回で取り出す**手法である。VLM prefillや通信が残るため、end-to-end TTFAが10倍速になるとは限らない。

### 3.3 Mixed-schedule fine-tuning

既存のflow modelは全action共通のtimeで学習している。HASだけでfine-tuneすると学習時のtime分布が偏り、先頭actionが `τ=0` のground truthに固定されて学習崩壊しやすい。各batchのサンプルで確率 `p` によりHAS、確率 `1-p` により元のconstant scheduleを使用する（標準 `p=0.5`）。RTCのaction-prefix conditioningも組み込む。

**追加学習:** 新しいarchitectureや独立したpretrainingは不要だが、HASを含むfine-tuningが必要。「学習不要のtraining-free runtime optimization」とは区別する。

### 3.4 Streamingとearly stopping

Policy serverは確定したactionを順次送信し、robot clientは受信actionをbufferへ追加して実行する。実行horizonに含まれない遠方actionの生成はearly stopできる。したがって**TTFA短縮**と**不要なsampling反復削減**が別々に寄与する。逐次小packet送信は通信overheadを増やし得るが、先頭actionの実行時間に後続actionの通信を隠す設計である。

## 4. Experiment Setup

- Backbones: flow-based `π0.5`、`X-VLA`。比較: synchronous、naive asynchronous、Training-time RTC、その他非同期法。
- GPU: RTX 4090 / RTX 4060。ロボット制御 `30 Hz`、1 step約33.3ms。
- 実機: AgileX Cobot Magic / Piper 6DoF armによるtable tennis（約14分のteleoperation demonstrationでfine-tuning）、Pick Beverage、dual-arm Fold Towel。
- シミュレーション: LIBERO、CALVIN、Kinetix。長時間動作評価はCALVIN連続サブタスクを使用。
- 指標: TTFA、理論期待reaction latency、必要なminimum execution horizon、実機task completion score、simulation success / Avg. Len。
- GPU peak memory、energy、throughput（actions/s）とVLM prefill単独の削減量は体系的な主結果として報告されていない。

## 5. Main Results

### 5.1 TTFAと期待reaction latency（Table 2）

| Model / GPU | Async TTFA | FASTER TTFA | Async expected reaction | FASTER expected reaction |
|---|---:|---:|---:|---:|
| π0.5 / RTX4090 | 80.0ms | 62.1ms | 130.0ms | 112.1ms |
| π0.5 / RTX4060 | 303.3ms | 238.6ms | 470.0ms | 371.9ms |
| X-VLA / RTX4090 | 113.7ms | 44.8ms | 180.4ms | 78.1ms |
| **X-VLA / RTX4060** | **399.5ms** | **129.2ms** | **599.5ms** | **229.2ms** |

X-VLA/RTX4060でTTFAは **3.09倍**、期待反応時間は **2.62倍**の改善。`π0.5`では改善が相対的に小さい（RTX4060でTTFA 1.27倍）。これはVLM prefill等の固定費用により、AE samplingの短縮がそのまま全体速度に反映されないため。

### 5.2 Streamingの時刻制約（Appendix Table 4）

30Hzでは次のactionが33.3msごとに必要。X-VLA/RTX4060ではstreamed action index 3,4,5の必要時刻133.3,166.7,200.0msに対し、受信時刻129.2,159.0,186.8msで間に合う。一方、全chunk完成を待つ設計なら先頭actionもこの時点では利用できない。

### 5.3 実機とシミュレーション

Table tennisでは同期方式が急速なボールへの反応に失敗し、FASTERが反応性能を改善。Pick Beverage / Fold Towelではcompletion scoreと所要時間を評価し、既存方式と同等または改善傾向。ただし**小規模実機試行と採点式の部分成功スコア**であり、全条件の統計的有意性を保証するものではない。

Kinetixの同一wall-clock budget比較（Appendix Table 11）では、Solve Rate: Naive Async 0.492、Training-time RTC 0.726、VLASH 0.813、FASTER **0.869**。FASTERのみ `d=1`、baselineは `d=4` として同じ実時間予算内で比較しており、純粋なpolicyのモデル能力比較ではない。

## 6. Ablation

### 6.1 HASのα（CALVIN ABC→D, X-VLA, Table 12）

| α | Avg. Len | 5-task success |
|---:|---:|---:|
| 0.4 | 4.071 | 63.5% |
| 0.7 | **4.093** | **64.5%** |
| 1.0 | 3.635 | 51.8% |

α=1では未来actionに割り当てるsamplingが不足し、長期性能が低下。先頭だけ高速化しても遠いactionの品質を守る必要がある。

### 6.2 Mixed-schedule比率p（CALVIN, Table 13）

| p | Avg. Len | 5-task success |
|---:|---:|---:|
| baseline constant | 4.151 | 70.2% |
| 0.3 | 3.756 | 55.2% |
| **0.5** | **4.093** | **64.5%** |
| 0.7 | 3.206 | 40.3% |
| 1.0（mixedなし） | 3.112 | 38.1% |

HASのみで学習する `p=1` は顕著に悪化。**高速反応とlong-horizon accuracyのtradeoffが残る**。baseline constantの方がCALVIN長期成功率では高いことを明示すべきである。

## 7. Limitations

1. **KV cacheそのものの効率化ではない**。連続frameのvisual KV再利用・KV memory削減・prefill削減の効果は未検証。
2. HASを考慮したfine-tuningが必要。追加学習なしのplug-inを意味しない。
3. TTFAの10xはaction expert sampling stepsの圧縮であり、end-to-end latency 10xではない。実測のTTFA改善はモデル/GPUに依存し、最大約3.09x（Table 2）。
4. CALVINの5-task successはbaseline 70.2%に対しFASTER標準設定64.5%で低下。高頻度反応が必要でない環境では利益が小さい場合がある。
5. 通信が不安定なロボットや複数clientを持つserverではstreaming packetの遅延・欠落に対する耐性が未解明。
6. RTX4060/4090の結果を組込みJetsonへそのまま一般化できない。GPU memory・実際のnetwork round trip・safety fallbackの詳細は追加検証が必要。
7. 長期記憶（episodic/semantic）や過去観測検索を提供する方式ではない。

## 8. Taxonomy / 関連研究

- **分類:** `KVcache/vla/` / flow-matching action decoding / TTFA / streaming inference。KV直接最適化 **なし**。
- [BlockVLA](2026-2605.13382-blockvla.md): 同一action要求内の確定block KV再利用。FASTERはflow actionの局所time scheduleを変える。
- [LAC](2026-2602.00686-adaptive-visual-token-caching.md): cross-frame visual KV reuse。FASTERとの組合せは技術的に考えられるが、併用効果は未評価。
- [VLA-Cache](2025-2502.02175-vla-cache.md): training-free frame-level visual KV reuse。
- [MEM](2026-2603.03596-mem.md): 長期記憶の保持・検索。FASTERはaction samplingの即応性を改善するだけで、タスク状態記憶の問題は解かない。
- [Chronos](2026-2606.30318-chronos.md): recurrent stateによる履歴保持と二階action generation。異なるaction generatorであり、実験条件が違うため性能優劣は断定できない。
