# Control Illusion: The Failure of Instruction Hierarchies in Large Language Models

## 概要

本論文は、chat APIで一般的な

```text
system instruction > user instruction
```

というhierarchyが、model behaviorとして本当に安定して実現されているかをcontrolled experimentで検証する。

評価では、内容上は同程度に単純で相互排他的なconstraint pairをsystem/userへ割り当て、roleだけをswapする。これにより通常のtask能力不足を減らし、**priority designationそのものがmodel behaviorを支配しているか**を測る。

6つのLLMを評価した結果、system/user separationだけでは信頼できるinstruction hierarchyが成立せず、model固有のconstraint preferenceやpretraining由来のsocial hierarchy cueが明示role priorityより強く働く場合があることを示す。

## 問題設定

hierarchical controlでは、higher-priority instructionとlower-priority instructionが矛盾した場合、modelは前者を選ぶべきである。

しかし通常のbenchmarkでは、

- system instructionの方が複雑
- user instructionの方が自然
- safety refusalが混ざる
- task難易度が異なる

等のconfoundがある。

本論文は**constraint prioritization**として問題を単純化し、同じconstraint pairについてrole assignmentだけを反転する。

## Evaluation Framework

### Mutually Exclusive Constraints

代表的には、

- uppercase vs lowercase
- English vs French
- long vs short
- keyword include vs exclude

等、同時には満たせないが単独なら容易なconstraint pairを使う。

例:

```text
System: answer in UPPERCASE
User: answer in lowercase
```

と、

```text
System: answer in lowercase
User: answer in UPPERCASE
```

を比較する。

もしmodelがsystem priorityを理解していれば、constraint内容に関係なくsystem側を選ぶはずである。

### Constraint Bias

実際にはmodelが特定constraintを好む。

たとえばあるmodelがuppercaseよりlowercaseを強く好む場合、system/user assignmentをswapしてもlowercaseへ引っ張られる。

この**constraint-specific prior**を測ることで、role hierarchyとcontent preferenceを分離する。

## Experiment Setup

6つのstate-of-the-art LLMを対象に、複数constraint pairで、

- constraint単独時の遵守
- system-user conflict
- role swap
- prompt engineering
- fine-tuning
- social hierarchy framing

を比較する。

単独constraintでは高いinstruction-following能力を持つmodelでも、conflict時にpriority遵守が崩れるかを重点的に見る。

## Main Results

主要な結論は、**system/user separationは安定したpriority enforcementを保証しない**ことである。

simple formatting conflictにもかかわらず、primary / system側constraintへのobedienceはmodelによって大きくばらつき、代表的には **9.6%〜45.8%程度**にとどまるsettingが報告される。

これは「system messageを認識できない」という単純な問題ではない。modelは各instructionを単独では実行できるのに、競合するとroleよりconstraint固有のpreferenceへ引っ張られる。

## Inherent Constraint Bias

role assignmentを反転したpaired evaluationから、modelごとに強いconstraint biasが見つかる。

理想的には、

```text
priority(source) >> preference(content)
```

であるべきだが、実際には、

```text
priority(source) competes with preference(content)
```

となる。

security上は、attackerがmodelの好む表現形式・文体・task framingを選ぶことで、低権限instructionの実効的salienceを上げられる可能性を示す。

## Social Hierarchy Experiment

本論文の特徴的な追加評価が、API roleとは別の**社会的authority cue**である。

例として、

- CEO vs intern
- expert / authoritative source vs non-expert source
- scientific publication vs personal blog
- majority consensus vs minority opinion

のようなframingを用いる。

結果として、authority / expertise / consensus等の社会的hierarchyがsystem/user roleより強くmodel behaviorへ影響する場合がある。

これはpretraining corpusから学習した「誰を信頼すべきか」というlatent priorが、post-trainingで付与されたAPI privilegeと競合している可能性を示す。

## Prompt Engineering

「system instructionを必ず優先せよ」等のexplicit reminderを加えるprompt engineeringも検討される。

一定の改善はあるものの、constraint pairやmodelを跨いで完全に安定したhierarchyにはならない。

したがってnatural-language reminderはsecurity boundaryとして十分ではない。

## Fine-tuning

instruction hierarchyを明示するfine-tuningも改善をもたらすが、unseen constraintや別framingへのgeneralizationには限界が残る。

この結果は、[The Instruction Hierarchy](../Defense/2024-2404.13208-instruction-hierarchy.md)や後続IH trainingの必要性を支持する一方、training distribution外のpriority spoofingを継続的に評価する必要性も示す。

## IHEvalとの違い

[IHEval](2025-2502.08745-iheval.md)はsystem / user / conversation history / tool outputを含む9 tasks・3,538 examplesでReference / Aligned / Conflictを比較するgeneral benchmarkである。

Control Illusionはよりdiagnosticで、

- 相互排他的な単純constraint
- role swap
- constraint bias
- social hierarchy cue

を使い、**なぜpriorityが崩れるか**をcontrolledに分解する。

両者は競合ではなく補完関係にある。

## Many-Tier Instruction Hierarchyとの関係

[Many-Tier Instruction Hierarchy](2026-many-tier-instruction-hierarchy.md)はroleとprivilegeを分離し、最大12 tiersまで拡張する。

Control Illusionが「2-roleのsystem/userですらcontent priorがpriorityを上回る」ことを示すのに対し、ManyIHは「tier数が増えるとpriority reasoning自体がscaleしない」ことを示す。

```text
Control Illusion:
  fixed 2-role hierarchyのbehavioral fragility
        ↓
IHEval:
  multi-source fixed hierarchy
        ↓
ManyIH:
  arbitrary many-tier hierarchy
```

という系譜で整理できる。

## Instruction Hierarchy Defenseへの含意

### The Instruction Hierarchy

[The Instruction Hierarchy](../Defense/2024-2404.13208-instruction-hierarchy.md)のようなtrainingでは、attack-specific exampleだけでなく、content preferenceとsource priorityを意図的に衝突させる必要がある。

### ISE

[Instructional Segment Embedding](../Defense/2024-2410.09102-instructional-segment-embedding.md)のようにsource identityをarchitecture-level embeddingとして与える方法は、natural-language role cueだけに依存しないという意味で本論文のfailure modeに直接対応する。

### SecAlign / Meta SecAlign

[SecAlign](../Defense/2024-2410.05451-secalign.md) / [Meta SecAlign](../Defense/2025-2507.02735-meta-secalign.md)ではsecure response preferenceを学習するが、evaluation時にはattack instructionのsemantic contentやauthority-like wordingを変え、model固有biasを利用するadaptive testが必要になる。

## Prompt Injectionとの関係

本論文は直接prompt injection attackを設計する論文ではない。

しかしprompt injectionは本質的に、

```text
higher-trust application instruction
       vs
lower-trust attacker instruction
```

というpriority conflictである。

system/userという明示roleだけでもpriorityが不安定なら、tool outputやretrieved webpageのようにrole boundaryがさらに弱いsettingではより深刻になりうる。

特に社会的authority cueの結果は、attackerが「管理者」「system notice」「expert」「official policy」等を模倣する**priority spoofing / role confusion**を研究する動機になる。

この点は後続の[Prompt Injection as Role Confusion](../Attack/2026-2603.12277-prompt-injection-role-confusion.md)と強く接続する。

## Limitations

- controlled formatting constraintはreal-world policyより単純。
- 2-role system/user conflictが中心で、developer/tool等の多段hierarchyは限定的。
- constraint biasはmodel/version更新で変化しうる。
- behavioral resultだけではlatent mechanismを一意に特定できない。
- social hierarchy cueの影響はpretraining priorを示唆するが、causal mechanismを完全には証明しない。
- benchmark高scoreがadaptive prompt injectionへのrobustnessを保証するわけではない。

## LLM Model Security Taxonomyでの位置づけ

```text
Instruction-following ability
        ↓
Controlled conflict
  same constraints, swapped roles
        ↓
Priority failure
  role cue < content/social prior
        ↓
Security implication
  priority spoofing / role confusion
```

Instruction Hierarchyをsecurity policyとして前提視せず、**role separationが本当にbehavioral privilege separationになっているか**を測るdiagnostic Benchmark / Analysisとして重要である。

## 実装・研究上の示唆

新しいhierarchy-aware modelを評価する際は、単にsystem instruction遵守率を測るだけでなく、

1. constraint内容をswapする
2. roleだけをswapする
3. wording strengthを変える
4. authority / expertise cueを混ぜる
5. unseen constraintへgeneralizeするか測る

必要がある。

このpaired designにより「systemだから従った」のか「その内容を元々好んでいた」のかを区別しやすい。
