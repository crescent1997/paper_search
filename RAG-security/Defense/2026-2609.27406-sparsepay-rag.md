# Only Pay What You Must Spend: On-Demand Privacy Budget Payment for Differentially Private RAG

> **要点**：private RAGで毎token・全corpusに対してDPを適用すると、private dataが不要な処理にもprivacy budgetを消費する。SparsePay-RAGは**retrieval対象・private generation頻度・token当たりのprivate signal**の3つを減らし、文書単位のDP保証を維持しながら回答の有用性を上げる。これは直接的なextraction attackではなく、private corpusの出力への影響を抑える**Defense**である。

## 概要 / Motivation

Private retrieval corpusを使うRAGは、LLMを再学習せずに企業・医療などの内部知識を利用できる一方、回答から文書本文やmembershipが推測される。RAGのretrieved passagesをgeneratorへそのまま渡すと、文書が1件追加・削除されたときの回答分布が変わるため、個別文書を保護対象とするDifferential Privacy（DP）を検討できる。

従来のDP-RAGは、検索した各文書を別々にLLMへ入力し、next-tokenの出力分布を集約してDP samplingする。しかし**全private corpusを対象に検索し、すべての生成stepでprivate文書にアクセス**すると、繰り返しの問い合わせに対してprivacy budgetが急速に尽きる。DPVoteRAGやDPSparseVoteRAGは出力分布のprivate votingを工夫し、MuRAGはretrieval範囲を狭めるが、private accessを本当に必要とするstepに限定しきれない。

SparsePay-RAGの設計原則は「**公開情報だけでできる処理にはprivacy budgetを払わず、private corpusが追加する情報にだけ払う**」。これを次の3軸に分ける。

1. **Scope**：private retrievalを全corpusでなく、public topicsから導いた関連clusterへ限定する。
2. **Frequency**：公開モデルの知識だけで次tokenを高信頼に出せる場合はprivate文書を読まない。
3. **Per-access cost**：private文書条件付きのlogits全体でなく、公開モデルとの差分だけをDP保護する。

この3軸は独立した小手先の最適化ではなく、privacy accountantにおけるclusterアクセス上限、private step数、delta clipping boundへそれぞれ対応する。

## 問題設定 / Threat Model

### 保護対象とattacker capability

- **Protected asset**：外部から直接読めないprivate retrieval corpusの各document。隣接データセットは**1文書の追加・削除**で異なる。
- **Defender**：private corpusとembedding indexを保持するRAG provider。公開LLMの重み・hidden states・logitsを利用でき、queryとretrievalを処理する。private文書を条件付けしたnext-token分布を計算できる。
- **Attacker**：RAGの外部query/answer interfaceを通じて出力を観測し、候補文書のmembershipを推測しようとする。本文中の実証では、既知の候補文書から自然なyes/no queryを30件生成する**Interrogation Attack**を使う。
- **保証対象**：文書単位のDPにより、1文書の有無が**公開される回答分布**に与える影響を制限する。retriever内部の中間結果や実行時間がすべて公開される状況まで保証するものではない。

DP保証は最悪ケースの出力分布に対するもので、個々のprompt injection、corpus extraction、reconstruction攻撃へのASRを網羅的に評価したものではない。実証されたprivacy attackは主にmembership inferenceである。

### Privacy accounting

通常の$(\epsilon,\delta)$-DPに加え、逐次合成が扱いやすい**zero-Concentrated DP（zCDP）**のbudget $\rho$で解析する。$\rho$-zCDPから$(\epsilon,\delta)$-DPへの変換は

$$\epsilon = \rho + 2\sqrt{\rho\log(1/\delta)}.$$

Private corpusをdisjoint clustersに分けることで**parallel composition**を利用し、同一cluster内の反復accessには**sequential composition**を適用する。

## Method / Algorithm

### 全体フロー

```text
[Offline]
 Public domain description → public LLMでtopic descriptionsを生成
                                  ↓
 Private document embeddings → 各topicへdisjoint assignment
                                  ↓
                  Cluster sizesにGaussian noiseを加えて公開

[Online query]
 Query → public topicsでrouting → 対象clusterのみにprivate retrieval
                                   ↓
                  Public LLMで次token候補とcross-layer軌跡を計算
                                   ↓
                     confidence > threshold ?
                        /                 \
                    Yes                   No
                    ↓                     ↓
               Public token      文書別private logitsを計算
                                          ↓
                                   Private − Public delta
                                          ↓
                                  Clip → Average → DP sampling
                                          ↓
                                   zCDP budgetを更新
```

### 1. Public Topic-Guided Clustering：private retrieval scopeを縮小

Offlineでpublic LLM（実験ではGPT-4）へ**private文書を渡さず**、domain descriptionから$m$個のtopic description $t_1,\ldots,t_m$を生成する。private文書$d_i$と各topicをローカルencoder $E$でembedding化し、最大cosine similarityのtopicに各文書を割り当てる。

$$C_j=\{d_i: j=\arg\max_k\operatorname{sim}(E(d_i),E(t_k))\}.$$

各documentは1 clusterだけに属するため、cluster同士はdisjoint。cluster size $c_j$の公開値には$\tilde c_j=\max(c_j+\mathcal N(0,\sigma^2),0)$を用い、**private corpusから外部へ出るoffline統計**の漏洩を抑える。

Query時はまず**public topicとの類似度**でtopicを順位付けし、公開されたnoisy sizeを足し合わせて、候補集合が$N_{coarse}$に達するまでclusterを選ぶ。その中でDPRによるtop-$K$ private retrievalを行う。Global retrievalを毎回行うよりprivate文書への接触範囲が小さくなる。

さらに各clusterのアクセス回数に**$N_{max}$**という上限を設け、超過clusterをskipする。これは単なるrate limitではなく、最悪ケースのprivacy accountingを有限に保つ条件である。Cluster assignmentの偏りやpublic topicsの質が悪いと、必要なprivate evidenceを取りこぼす可能性がある。

### 2. Isotonic Cross-Layer Trajectory Fitting：private generationの頻度を縮小

Public LLMだけで次tokenを推測し、private retrievalが本当に必要なstepを判定する。単純な最終layer softmax confidenceだけでなく、**logit lens**で中間layerから各tokenの確率を推定し、後半layerにおける確率軌跡を観察する。

まず最終layerの最大確率に対する割合$\alpha$でhigh-probability candidate集合$V_{head}$を作る。各候補token $x$についてlayer $l_s,\ldots,L$の確率$\{p^{(l)}(x)\}$を計算する。確信度が高いtokenは深いlayerに向けて確率が上昇・安定する、という仮説に基づき、**単調非減少のisotonic regression**をPAV algorithmでfitする。

$$\hat\mu(x)=\arg\min_{\mu_{l_s}\le\cdots\le\mu_L}\sum_{l=l_s}^L(p^{(l)}(x)-\mu_l)^2.$$

Fit後の最終値から残差RMSEを引き、

$$S(x)=\hat\mu_L(x)-\sqrt{\frac1{L_w}\sum_{l=l_s}^L(p^{(l)}(x)-\hat\mu_l(x))^2}$$

をconfidence scoreとする。$x^*=\arg\max_{x\in V_{head}}S(x)$が$\theta_{reject}$を超えれば**public tokenをそのまま出力**し、private文書へアクセスしない。閾値以下ならprivate generationをtriggerする。

このtriggerはpublic modelのhidden statesしか使わないため、著者らのprivacy accountingでは**追加privacy costが0**。ただし、parametric knowledgeが不正確なまま高confidenceになる場合にはretrievalをskipしてhallucinationを増やし得る。Calibrationの質が重要である。

### 3. DP Contrastive Decoding：private signalの保護対象を縮小

Private generationをtriggerしたときだけ、retrieved top-$K$文書を**文書別prompt**へ入力し、private logits $\ell^{(i)}_{priv}$を計算する。Public modelの同じ生成位置のlogits $\ell_{pub}$は既にある。

各文書のprivate incrementをlog-probability差分として定義する。

$$\ell_\Delta^{(i)}=\log\operatorname{softmax}(\ell^{(i)}_{priv})-\log\operatorname{softmax}(\ell_{pub}).$$

このdeltaをelement-wiseに$[-C,C]$へclipし、$K$文書で平均したものをpublic log-probabilityへ戻す。

$$u=\log p_{pub}+\frac1K\sum_{i=1}^K\operatorname{clip}_C(\ell_\Delta^{(i)}).$$

最後に$V_{head}$内で$y_t\sim\operatorname{softmax}(u/\tau)$とsamplingする。これはutility $u$の**exponential mechanism**としてprivacy解析できる。Privacy budgetを超えた場合にはprivate samplingを続けず、public candidateへfallbackする。

Public logits全体には既知の一般知識も含まれる。これまでの方式はその分までnoiseを掛けていたが、SparsePay-RAGは**private corpusが付加したdelta**だけをclip・集約するため、privacy noiseの効用損失を抑えるという設計である。

### 4. 形式的privacy guaranteeと成立条件

Gaussian noiseを用いたcluster-size releaseは、感度$\Delta_2=1$の下で$\rho_{cls}=1/(2\sigma^2)$を消費。DP contrastive decodingはutility感度$\Delta_u=2C/K$として、private token当たり

$$\rho_{token}=\frac{2C^2}{K^2\tau^2}$$

のzCDP costとなる。Cluster access上限$N_{max}$、query当たりprivate step上限$T_{priv}$を使うと、本文Section 4のworst-case boundは

$$\boxed{\rho_{total}=\frac1{2\sigma^2}+N_{max}T_{priv}\frac{2C^2}{K^2\tau^2}}.$$

$N_{max}$はscope、$T_{priv}$はfrequency、$C$はper-access costに対応する。**Clusterがdisjointであること、公開モデルのみでtriggerを決めること、access capとsamplingの条件を守ること**が保証の前提。任意のretrieval policyや無制限queryにそのまま適用できる式ではない。

## 先行研究からの改善点

| 先行方式 | 基本方針 | SparsePay-RAGとの差分・残る制約 |
|---|---|---|
| [RAG with Differential Privacy](2024-2412.19291-rag-with-differential-privacy.md) | DP retrievalと文書別next-token分布の集約 | 全stepでprivate logitsを扱う負担に対し、public triggerとdeltaのみのDPで費用を減らす。 |
| DPVoteRAG | 各tokenでDP voting | strict budget下ではquery単位で出力が途中停止する場合がある。public fallbackを備えたSparsePayは重要stepへbudgetを集中。 |
| DPSparseVoteRAG | Private token生成を疎にする | Voting自体がbudgetを消費するのに対し、public-only triggerは追加budget不要。 |
| MuRAG | Retrieval対象を絞ってDP costを削減 | Retrieval scopeだけでなくprivate generation頻度とprivate deltaまで削減。 |
| [DP-SynRAG](2025-2510.06719-dp-synrag.md) | 一度DP synthetic corpusを作って再利用 | Offline DPの再利用可能性に強み。一方SparsePayは更新可能な元private corpusをquery時に使い、budgetを都度会計。**直接の実験baselineではない**。 |

[PRAG](2026-2604.26525-prag.md)はcloudからのretrieval内容・query秘匿が主対象であり、**authorized RAG利用者への出力漏洩を抑えるSparsePay-RAGとはattacker capabilityが異なる**。同じ「privacy-preserving RAG」でも保護境界を混同しない。

## Experiment Setup

### Datasets / Retriever / Generator

- **NQ / TriviaQA**：外部corpusはWikipedia約**2,100万passages**。それぞれ100 queriesをmain evaluationに使用。Metricは**Match Accuracy**（acceptable answerのいずれかを含むか）。
- **ChatDoctor**：HealthCareMagic / icliniq / GenMedGPT由来の約**115,000 patient-doctor dialogues**をprivate corpusとし、100 patient queriesで評価。Metricは**BERTScore F1**。
- **Retriever**：**DPR**を使い、topicとprivate documentのembeddingには`all-MiniLM-L6-v2`。Public topic生成にはGPT-4を使用。Wikipediaは10,000 topics、ChatDoctorは1,000 topics。
- **Generators**：OPT-1.3B、Pythia-1.4B、Mistral-7B、Llama-3.1-8B。異なるsizeの公開モデルで再現性を評価。
- **Privacy parameters**：$\epsilon\in\{1,5,10,100\}$、$\delta=1/(|D|\log|D|)$。Offline noisy cluster-size releaseとonline DP generationのbudget比率は**1:4**。$N_{max}=5$、$K\in\{50,30,15,10\}$、per-token budgetは$\{0.1,0.2,0.5,1.0\}$から設定。Triggerでは$\alpha=0.2$、$l_s=L/2$、$\theta_{reject}$をモデル別EERで校正。
- **Baselines**：Non-RAG、Non-Private RAG、DPVoteRAG、DPSparseVoteRAG、MuRAG。さらにAppendix D.4で、baselineがbudget不足で停止した場合にpublic generationへfallbackする公正性比較も追加。

## Main Results

### 1. 厳しいprivacy budgetでも回答を完了できる（Table 1）

| Dataset / Model | $\epsilon$ | MuRAG | **SparsePay-RAG** | Metric |
|---|---:|---:|---:|---|
| NQ / OPT-1.3B | 1 | 0.17 | **0.40** | Match Accuracy |
| NQ / OPT-1.3B | 10 | 0.39 | **0.51** | Match Accuracy |
| NQ / Llama-3.1-8B | 1 | 0.63 | **0.83** | Match Accuracy |
| TriviaQA / OPT-1.3B | 1 | 0.51 | **0.53** | Match Accuracy |
| TriviaQA / Pythia-1.4B | 10 | 0.53 | **0.58** | Match Accuracy |
| ChatDoctor / Pythia-1.4B | 1 | 0.60 | **0.76** | BERTScore F1 |
| ChatDoctor / OPT-1.3B | 10 | 0.68 | **0.72** | BERTScore F1 |

NQ / OPT-1.3B / $\epsilon=1$では**0.17→0.40（+0.23）**と大幅に改善。MuRAGも局所retrievalでbudgetを節約するが、SparsePayは生成stepとprivate deltaまで節約するため、tight budgetで差が出る。TriviaQAや強いgeneratorでは差が小さい条件もあるので、全条件で一様な大幅改善と誇張しない。

DPVoteRAGとDPSparseVoteRAGの表中「−」は、**全100 queriesを評価できなかったことではなく、各queryに割り当てられたbudgetを生成途中で使い切り、有効な回答を完了できなかったこと**を表す。比較の公平性に関わる重要な注記である。

### 2. Fallbackをbaselineへ追加しても改善は残る（Appendix D.4）

OPT-1.3B、$\epsilon=10$で、DPVoteRAG / DPSparseVoteRAGのbudget不足後をpublic generationで補完した結果：

| Dataset | DPVoteRAG + fallback | DPSparseVoteRAG + fallback | **SparsePay-RAG** |
|---|---:|---:|---:|
| NQ | 0.33 | 0.37 | **0.51** |
| TriviaQA | 0.50 | 0.53 | **0.61** |
| ChatDoctor | 0.31 | 0.36 | **0.72** |

Baselineを強化しても、budgetが尽きた後に必要なprivate signalを取り戻せない。SparsePayは「最後にfallbackする」のではなく、**前半からprivate budgetを必要なstepへ残す**点に価値がある。

### 3. Ablation（Table 2）

OPT-1.3Bの$\epsilon=1$で、topic-guided clustering（TGC）、adaptive triggering（AT）、contrastive decoding（CD）を1つずつ除去する。

| Dataset | Full | −TGC | −AT | −CD |
|---|---:|---:|---:|---:|
| NQ | **0.40** | 0.31 | 0.32 | 0.36 |
| TriviaQA | **0.53** | 0.50 | 0.51 | 0.50 |
| ChatDoctor | **0.68** | 0.38 | 0.44 | 0.53 |

特にChatDoctorではTGC除去で**−0.30**、AT除去で**−0.24**、CD除去で**−0.15**。Retrievalを限定するだけでは不十分で、private generationの呼び出し回数とlogit保護対象も独立に効く。

### 4. Membership Inference Defense（Section 5.4）

ChatDoctor / Llama-3.1-8Bに対して、[Riddle Me This!](../Attack/2025-2502.00306-riddle-me-this.md)の**Interrogation Attack（IA）**を適用。候補文書ごとにGPT-4が**30件のyes/no questions**を生成し、正答率をmembership scoreとしてAUCを評価する。

- **Non-Private RAG：AUC 0.717**
- **SparsePay-RAG（$\epsilon=1$）：AUC 0.503**

この条件ではmembership inferenceの識別力がほぼrandom guessingまで低下した。ただし、[MBA](../Attack/2024-2410.20142-mask-based-membership-inference-mba.md)、[MEntA](../Attack/2026-2605.24312-menta-five-queries-entailment.md)、RAG-Thief/GeoEx等の**異なるattack classで同様の低AUC・低extraction rateを直接実証したわけではない**。

### 5. Budget配分・query規模・実行コスト（Appendix C / D）

- **Offline:online budget比率**：OPT-1.3B、$\epsilon=1$で**1:4**がNQ 0.40 / TriviaQA 0.53 / ChatDoctor 0.68と最良。4:1にすると0.31 / 0.41 / 0.32へ低下。Offlineへ過剰配分するとprivate generationでdeltaが過度にclipされ、onlineへ過剰配分するとcluster-size noiseでroutingが悪化する。
- **1,000-query追加評価**：OPT-1.3B、$\epsilon=100$でMuRAG→SparsePayはNQ **0.42→0.52**、TriviaQA **0.51→0.59**、ChatDoctor **0.67→0.74**。Mainの100-query比較だけに依存しない傾向を確認。
- **有意差**：$\epsilon=5$でMuRAGとのutility差は全dataset / model条件で$t$-test **$p<0.05$**と報告。
- **Offline**：Wikipedia向け10,000 topics生成は約3時間・約$15、ChatDoctor向け1,000 topicsは約20分・約$3。ChatDoctor約115K embeddingsのローカル生成は約1.5分。
- **Retrieval latency**：Wikipedia約21M passagesではglobal 7.0s/query→localized 3.5s/query。一方、ChatDoctorでは0.3→0.5s/queryとrouting overheadが増える。
- **Generation latency**：単一A100 80GBでNQはOPT-1.3B約5s、Llama-3.1-8B約10s/query。ChatDoctorはそれぞれ約7s、14s/query。**privacy budgetの節約とwall-clockの高速化は同義ではない**。

## Limitations / 成立条件

1. **Document-level DPと出力side channelの違い**：保証は公開されるtextual output分布に対するもの。推論時間やcluster skipによるlatency変化からの情報推測は保護範囲外と著者らも明記する。
2. **Fixed per-query allocation**：簡単な質問ではprivate generationが少なく、割り当てたbudgetを使い残す。真の消費に合わせたquery-adaptive budget allocationは未実装。
3. **Disjoint topic assignmentが必要**：Clusterが重複するとparallel compositionの根拠が変わる。Topic generationやroutingがdomainに合わなければ回答品質が低下する。
4. **Public modelのconfidence calibration**：Logit-lens軌跡が単調でも正しいとは限らない。高confidenceの誤答をprivate retrievalなしで確定させる可能性がある。
5. **Private logitsの計算コスト**：Triggerされたstepでは$K$文書別promptからdistributionを計算する。GPU memory、KV cacheの多重管理、batch schedulingの負担がある。Latencyは小さくない。
6. **Empirical attack coverage**：直接のprivacy attack評価はChatDoctorのIA（30 queries）に限定。Corpus stealing、prompt injection exfiltration、adaptive MIA、retrieverを直接観測できる設定での耐性は未評価。
7. **Privacy budgetの解釈**：$\epsilon=100$は厳しいprivacy設定とはいえない。高utilityの数値だけで強いprivacyを主張せず、$\epsilon=1,5$の結果と区別する。
8. **Evaluation sample size**：Mainはdataset当たり100 queries。1,000-queryの追加評価はOPT-1.3B、$\epsilon=100$に限られ、全model・tight budgetでのlarge-scale評価ではない。
9. **Corpus privacyとquery privacyは別**：利用者のquery自体をcloud providerから秘匿するcryptographic retrievalとは異なる。Privacy unit、attacker access、side channelの前提を確認する必要がある。

## RAG Data Extraction / Security Taxonomyでの位置づけ

| Security risk | SparsePay-RAGとの関係 |
|---|---|
| Knowledge-base / private corpus extraction | **防御目的の中心**。document-level DPで各文書が回答分布へ与える影響を制限する。ただしwhole-corpus extraction ASRの実験はない。 |
| Membership inference | **直接評価あり**。Interrogation AttackでAUC 0.717→0.503。 |
| PII / retrieved document leakage | 出力分布をDP化することで間接的に抑制する。PII chunk recovery rate等は未報告。 |
| Prompt injection exfiltration | 個別のinjection guardではない。攻撃成功率の網羅的評価はない。 |
| Poisoned retrieval / answer manipulation | 主対象外。Malicious corpus entryへのrobustnessを保証するわけではない。 |
| Cloud-side encrypted retrieval | 主対象外。Providerにprivate corpusやqueryを見せない暗号学的保証ではない。 |

## 実装・研究上の重要な示唆

- **KV cache reuse / batching**：Private stepでは同じ生成prefixに対し$K$文書別のforwardが必要。Public prefixのKV reuse、document-conditioned KVのbatch管理、private step間のcache保持が高速化候補。ただし**論文で実証された最適化ではない**。異なるdocument contextのKVを無条件に混ぜることはできない。
- **Logit lensの追加処理**：中間layerのhidden stateを使うconfidence estimatorが必要で、標準的な高速decode servingで中間layer logitsを逐次取得するcostを測る価値がある。
- **Privacy accountingをserving schedulerに組み込む**：Per-cluster $N_{max}$、query別$T_{priv}$、累積$\rho$、public fallbackをrequest横断で整合的に管理する必要がある。並列requestではcluster access countの競合に注意する。
- **Attack-oriented evaluation**：MIA AUCだけでなく、[LeakDojo](../Benchmark/2026-2605.05818-leakdojo.md)のchunk coverage/漏洩率、[Connect the Dots](../Attack/2026-2601.15678-connect-the-dots.md)のquery efficiencyなど、直接的なcorpus extraction指標を追加すると実運用上の防御能力を比較しやすい。
- **Differential Privacyの適用境界**：Private documentの単位と個人単位が一致するかを確認する。1人が複数文書を持つ医療RAGではdocument-level保証をperson-level保証として解釈しない。
