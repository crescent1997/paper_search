# Beyond Oracle: Verifier-Supervision for Instruction Hierarchy in Reasoning and Instruction-Tuned LLMs

## 概要

Beyond OracleはInstruction Hierarchy (IH) alignmentを、強いLLMが生成したoracle responseを模倣する問題ではなく、**outputがhigher-priority directiveを満たしたかをprogrammatically verifyできるRL / fine-tuning問題**として再定式化する。

各training instanceは、

- compliance directive
- conflicting directive
- executable verifier

から構成される。

verifierがoutputのhierarchy complianceをdeterministicに判定できるため、GPT-4o等によるreference responseやreasoning traceを必要としない。

## 問題設定

system instructionとuser instructionなど、異なるpriorityのdirectiveがconflictする場合を考える。

higher-priority directiveを i+、conflicting lower-priority directiveを i-、model outputを O とする。

training objectiveは単にoracle answer O*をimitateすることではなく、

```text
f_i+(O) = 1
```

となるoutputを生成することである。

f_i+はhigher-priority directiveへのcomplianceをprogrammatically判定するexecutable verifierである。

## 既存手法の問題

従来のIH trainingでは強いteacher modelからoracle completionを生成し、それをSFT / preference optimizationする場合が多い。

reasoning modelではこれに2つの問題がある。

1. final answerだけではintermediate reasoningをsuperviseできない。
2. teacher / reward modelによるjudgmentはcostlyかつnon-deterministicである。

CoT付きoracleを大量生成する方法もあるが、teacher reasoningのqualityやstyleへstudentが依存する。

Beyond Oracleは「正しいreasoning traceを教える」のではなく、「最終outputがconstraintを満たしたかを実行可能なprogramで検証する」。

## Training Instance

概念的には、

```text
x = {
  scaffold,
  compliance directive i+,
  conflicting directive i-,
  verifier f_i+
}
```

を生成する。

modelにはconflicting instructionsを含むpromptを与え、output Oを生成させる。

rewardは、

```text
r(O) = f_i+(O)
```

のbinary signalとして得られる。

## Synthetic Data Generation

Persona-Hubから多様なpersona / contextをsampleし、LLMを使ってtask scaffoldとconflicting directivesを生成する。

generationではQwen-2.5-72BやGrok-3-mini等を利用する。

重要なのはpromptだけでなく、そのdirectiveを検証するPython verifierも同時に生成することである。

## Unit-Test-based Validation

LLM-generated verifierは誤っている可能性がある。

そこでGPT-4o-mini等を用いてpositive / negative unit testsを生成する。

### Positive tests

directiveを満たすoutputを作り、

```text
verifier(output) == True
```

であるべきとする。

### Negative tests

directiveを破るoutputを作り、

```text
verifier(output) == False
```

であるべきとする。

verifierがunit testsに失敗した場合はrepair loopへ送る。

## LLM-assisted Repair

failed verifier / instanceをLLMへ戻し、failure reasonとunit testを使って修正する。

最大R回repairし、それでもvalidationを通らないinstanceは除外する。

このpipelineによりinitially generated 99,361候補から22,922 high-quality verifier-supervised examplesを残す。

## Cleaning Reliability

unit test自体も完全ではないため、paperではvalidation pipelineのfalse retention / false rejectionを確率的に分析する。

複数positive / negative testを組み合わせることでinvalid verifierがclean setへ残る確率を下げる。

単なるLLM-as-a-judge filteringではなく、executable checkを中心にdata qualityを担保する点が重要である。

## Instruction-Tuned Model

通常のinstruction-tuned modelではverified examplesを使ってSFTする。

oracle answerをteacherから生成するのではなく、verifierを満たすtraining target / generated responseを利用してhierarchy behaviorを学習する。

## Reasoning Model / GRPO

reasoning modelではprogrammatic verifierをrewardとしてGRPOを適用する。

```text
prompt with conflict
      ↓
multiple reasoning rollouts
      ↓
executable verifier
      ↓
binary reward
      ↓
GRPO
```

CoT supervisionなしにmodel自身のreasoning trajectoryを探索させられる。

これはverifiable rewardを使うreasoning RLをInstruction Hierarchyへ適用した構成である。

## Experiment Setup

instruction-tuned modelとreasoning modelの双方を評価する。

主な評価には、

- IHEval
- StrongREJECT
- safety / jailbreak-related benchmarks
- MMLU
- MATH-500

等を用いる。

hierarchy complianceだけでなくgeneral capability degradationも確認する。

## Main Results: Reasoning Models

DeepSeek-R1-Distill-Llama-8BではIHEval Safety Conflictが16.7から36.5へ改善する。

DeepSeek-R1-Distill-Qwen-7BではStrongREJECTが77.4から82.2へ改善する。

security-specific benchmarkだけを直接superviseしなくてもsafety robustnessへgeneralizeする。

## Main Results: Instruction-Tuned Models

Llama-3.1-8B-InstructではIHEval Conflictが、

```text
Rule:   17.8 -> 54.9
Task:    9.8 -> 59.4
Safety: 15.2 -> 60.6
```

へ改善する。

単一ruleだけではなくtask / safety conflictへ広く効果がある。

## General Capability

MMLU / MATH-500等では大きな能力退行を示さず、hierarchy compliance improvementを単純なover-refusalやgeneral degradationだけで得ていないことを確認する。

## Safety Generalization

training dataは特定jailbreak benchmarkのattack stringを直接memorizeさせるものではない。

それでもadversarial safety benchmarkで改善することから、higher-priority constraintを維持するbehavior自体がsafetyへtransferすることを示す。

## The Instruction Hierarchyとの関係

[The Instruction Hierarchy](2024-2404.13208-instruction-hierarchy.md)はsynthetic hierarchy dataを使ってprivileged instructionを優先するbehaviorを学習する代表的研究である。

Beyond Oracleはそのtraining signalを、

```text
oracle response
    ↓
programmatic verifier
```

へ変更する。

特にreasoning modelではoracle CoTを用意しなくてもRL可能になる点が大きい。

## Instructional Segment Embeddingとの関係

[Instructional Segment Embedding](2024-2410.09102-instructional-segment-embedding.md)はsource / privilegeをembeddingとしてarchitectureへ明示する。

Beyond Oracleはarchitectureを変えず、training signalのverifiabilityを改善する。

両者は併用可能である。

## Reasoning Up the Instruction Ladderとの関係

[Reasoning Up the Instruction Ladder](2025-2511.04694-reasoning-up-instruction-ladder.md)もInstruction Hierarchyをexplicit reasoning / RL problemとして扱う。

Beyond Oracleはより早い段階で、programmatic verifierを使うことでreasoning traceのoracle supervisionなしにhierarchy RLを可能にした技術的先行研究として位置づけられる。

## IH-Challengeとの関係

[IH-Challenge](2026-2603.10521-ih-challenge.md)はshortcut-resistantでprogrammatically gradeableなRL environmentを構築し、online adversarial generationも組み合わせる。

系譜としては、

```text
Instruction Hierarchy
  synthetic hierarchy training
       ↓
Beyond Oracle
  executable verifier supervision
       ↓
IH-Challenge
  harder gradeable RL environment
  + online adversarial generation
```

と整理できる。

## Prompt Injectionとの関係

本手法は特定prompt-injection detectorではない。

lower-priority instructionとhigher-priority constraintのconflictを正しく解決する能力を学習するため、prompt injection / jailbreakへのrobustnessがdownstreamに改善する。

ただし[The Attacker Moves Second](../Attack/2025-2510.09023-attacker-moves-second.md)や[PISmith](../Attack/2026-2603.13026-pismith.md)のようなDefense-aware adaptive attackを直接training objectiveへ組み込むものではない。

## Limitations

- verifierを書けるtaskへtraining signalが偏る。
- semantic / open-ended complianceはprogrammatic verificationが難しい。
- generated verifierのcorrectnessはunit-test qualityに依存する。
- binary verifierはpartial complianceの細かいcredit assignmentを失う。
- synthetic conflict distributionがreal-world prompt injectionを完全には代表しない。
- adaptive attackerへのformal guaranteeはない。
- system / user以外のmany-tier privilegeを網羅的に扱うわけではない。

## LLM Model Security Taxonomyでの位置づけ

```text
Behavioral hierarchy training
  Instruction Hierarchy
       ↓
Verifier-supervised hierarchy
  Beyond Oracle
       ↓
Reasoning / RL hierarchy
  Reasoning Up
  IH-Challenge
  HIPO
```

Instruction Hierarchyを**verifiable RL problem**へ変換したDefenseとして重要である。

## 実装・研究上の示唆

Instruction Hierarchy RLでは高価なLLM judgeを毎rolloutで呼ぶより、task-specific executable verifierを生成・検証して再利用する方がscalableである。

研究上は、

1. verifier生成
2. positive/negative unit tests
3. repair loop
4. GRPO reward
5. unseen safety benchmarkへのtransfer

を分離して評価することが重要である。
