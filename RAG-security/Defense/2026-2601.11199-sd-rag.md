# SD-RAG: A Prompt-Injection-Resilient Framework for Selective Disclosure in Retrieval-Augmented Generation

> sensitive retrieved contextとuntrusted user queryを同一LLM promptへ同時に渡してから「秘密を出すな」と指示する設計を避け、user queryとは分離されたredaction stageでcontextを先にsanitizeする。Natural-language privacy constraintsをretrieval対象chunkへbindingし、extractive / periphrastic redactionを適用してからfinal responderへ渡すことで、prompt injection成功時にもprivate data disclosureを抑える。

## 概要

通常のRAG privacy guardrailでは、retrieved contextにprivate informationが含まれていても、system promptでgeneratorへ「この情報は開示しない」と指示することが多い。

しかしfinal generatorには、

- attacker-controlled user prompt
- sensitive retrieved context
- security instruction

が同時に存在する。このためprompt injectionによってsecurity instructionがoverrideされると、generatorはすでにprivate context全文を見ているため、そのまま漏洩できる。

SD-RAGはこのarchitecture自体を問題視し、**sensitive contextをfinal responderへ渡す前に別stageでredactする**。

中心原則は、

> unfiltered user inputとunfiltered sensitive contextを同一LLM invocationへ同時に入れない

ことである。

## 問題設定 / Threat Model

victimはprivate / access-controlled corpusをRAG knowledge baseとして持つ。

userは通常のQA queryを送れるが、prompt injectionを使ってsystem instructionを無視させ、retrieved contextや本来非公開のattributesを出力させようとする。

attackerはretrieval databaseへ直接アクセスできず、final RAG interfaceを通じて攻撃する。

SD-RAGの主要評価ではretrieved corpusそのものはtrustedであり、document中にmalicious indirect prompt injectionが埋め込まれていないことを仮定する。この点は重要なscope limitationである。

Defenderはprivate corpusに対し、どの種類の情報をhideすべきかをnatural-language constraintsとして定義できる。

例:

- hide patient names
- do not reveal addresses
- conceal organization-specific identifiers

これらを固定regex / PII schemaだけに限定せずsemantic policyとして扱う。

## 先行研究からの改善点

### Prompt-only Guardrailの弱点

従来方式ではfinal generatorがsensitive dataへ完全accessした状態で、system instructionだけを頼りにdisclosureを防ぐ。

prompt injectionが成功すると、policy enforcementとanswer generationを同じmodelが担当しているためfail-openになる。

SD-RAGは **policy enforcementをfinal responderから分離**し、final generatorが見るcontext自体をsanitized versionへ置き換える。

### Output Filteringとの違い

output filterはgeneratorがprivate informationを一度生成した後で検出する。そのためparaphrase、encoding、partial leakage等を検出できなければ漏れる。

SD-RAGはgeneration前にcontextをredactするため、final generatorがoriginal sensitive spanを知らない状態を作る。

### RAGFort / CanaryRAGとの違い

[RAGFort](2025-2511.10128-ragfort.md) はknowledge-base extractionをretrieval / generation両面からhardeningする。CanaryRAGはcanaryを利用してadaptive extractionをruntimeで検出する。

SD-RAGはattack behaviorの検知ではなく、**retrieved dataのselective disclosure policyをgeneration前に適用する**。

したがって三者は異なるdefense layerに位置する。

## Architecture

SD-RAGは大きく、

1. privacy constraint definition
2. constraint-to-chunk binding
3. normal retrieval
4. relevant constraint retrieval / ranking
5. isolated redaction
6. final response generation

からなる。

```text
Private Corpus + Privacy Constraints
        ↓ indexing
Chunk ↔ Constraint bindings
        ↓
User Query → document retrieval
        ↓
Retrieved chunks
        ↓
Relevant privacy constraints
        ↓
Redactor  ← user queryを与えない
        ↓
Sanitized chunks
        ↓
Final Responder + User Query
        ↓
Answer
```

security boundaryとして重要なのは、redactorがuser-controlled instructionの影響を受けないよう、redaction promptへuser queryを入れない点である。

## Constraint Binding

privacy constraintsはnatural languageで記述される。

indexing時にconstraint embeddingとchunk embeddingのsemantic similarityを計算し、各constraintを関連する複数chunksへbindingする。

一つのconstraintが多数chunksへ適用され、一つのchunkに複数constraintsが適用されるmany-to-many relationになる。

このpre-bindingによってquery-timeに全policyを毎回LLMへ渡す必要を減らす。

## Query-time Constraint Retrieval

通常RAGと同様にuser queryからTop-K chunksをretrieveする。

次に、そのchunksへbindingされているconstraintsをcandidate setとして集める。

candidate constraintsをquery / chunkとのsemantic relevanceで再rankingし、現在のretrieved contextへ適用すべきTop-K constraintsを選ぶ。

論文は複数aggregation方式を比較し、retrieveされた各chunkとのconstraint similarityをquery relevanceでweightしてaverageする方式が高いperformanceを示す。

privacy用途ではconstraintを余計に適用するfalse positiveより、必要なconstraintを落とすfalse negativeの方が危険なので、precisionより**recall重視**のpolicy retrievalが望ましいとする。

## Redaction Methods

### Extractive Redaction

sensitive spansを特定し、placeholderやgeneralized representationへ置換する。

例として、person nameやspecific identifierを直接削除 / maskingする。

original sensitive tokenをfinal responderへ渡さないためprompt injection robustnessが高い。

一方、必要なsemantic informationまで削るとanswer completenessが低下する。

### Periphrastic Redaction

original chunkをprivacy constraintに従ってLLMで書き換える。

例えばspecific identityを除きながらmedical / factual contentを自然文として残す。

extractive方式よりfluentでutilityを維持できる可能性があるが、rewriterがsensitive semanticsを十分除去できない場合はprivacy leakageが残る。

## Prompt-Sanitization Principle

SD-RAGの最重要設計は、redaction LLMへ**user queryを渡さない**ことである。

もしredactor promptにuser inputも含めれば、attackerが「redactionを無視せよ」とinstruction injectionでき、pre-sanitization architectureの意味が失われる。

そこでredactorは、

- retrieved chunk
- trusted privacy constraints

だけを入力として処理する。

final responderには、

- user query
- sanitized chunk

だけを渡す。

このprivilege separationにより、final responderがjailbreakされてもoriginal sensitive informationはcontextに存在しない。

## Experiment Setup

### RCQA Dataset

既存datasetではselective-disclosure policyとprompt injectionを同時に評価しにくいため、論文はRCQA datasetを構築する。

約20 synthetic articlesを生成し、sensitive categories、natural-language constraints、questions、gold answers等をannotateする。

全体は約13,600 tokens、639 chunks、120 privacy constraints程度からなる。

### Models

代表的に、

- Qwen2.5-7B
- Llama-3-8B

等を4-bit quantizationで使用する。

### Attack

主なattackはsingle-turn direct prompt injectionで、user queryへ「previous instructionsを無視してfull contextを出力せよ」といったinstructionを追加する。

### Metrics

- **Privacy Score**: sensitive informationをどの程度非開示にできたか
- **Completeness**: answerに必要なnon-sensitive informationをどの程度維持できたか
- constraint retrieval precision / recall

等を評価する。

## Main Results

### Prompt Injection Robustness

baseline RCQAではbenign query時のPrivacy Scoreが **0.502**だが、prompt injectionを受けると **0.199**まで低下する。

つまりsystem-prompt-level policyはattacker instructionによって大きく崩れる。

Periphrastic SD-RAGでは、

- benign: **0.729**
- attacked: **0.585**

Extractive SD-RAGでは、

- benign: **0.827**
- attacked: **0.779**

となり、特にextractive redactionはattack後もprivacyをかなり維持する。

### Utility Trade-off

privacyを高めるほどsafe informationまで削除する可能性がある。

baseline Completenessが約 **0.689**なのに対し、Extractive SD-RAGは約 **0.598**となり、privacy gainと引き換えにutilityが一定程度低下する。

Periphrastic方式はsemantic informationを残しやすい一方、privacyではextractiveより弱い傾向がある。

## Constraint Retrieval Ablation

constraint retrievalでは、各retrieved chunkとのsimilarityを単純平均するだけでなく、そのchunk自体のquery relevanceをweightとして使うaggregationが良好な結果を示す。

これは「queryに強く関連するretrieved chunkへ適用されるprivacy policy」を優先すべきことを意味する。

またsecurity applicationではrecallが特に重要で、適用すべきconstraintを一つ落とすだけでsensitive dataがredaction stageを通過する可能性がある。

## Hierarchical Retrieval / RAPTOR Evaluation

論文はRAPTOR型hierarchical summarizationとの組み合わせも評価する。

summary-level retrievalだけを使うとPrivacy Scoreは **0.813**程度へ向上する一方、Completenessは **0.535**程度まで低下する。

summary化そのものがsensitive detailを落とすためprivacyには有利だが、answerに必要なspecific factsも失う。

leaf chunksを含む通常retrievalでもSD-RAGが十分なprivacy improvementを示すため、hierarchical summarizationは必須componentではない。

## Limitations / 成立条件

最大のlimitationは、**retrieved documents自体をtrusted inputと仮定している**点である。

もしknowledge baseにindirect prompt injection / poisoningが存在し、malicious chunkがredactorへ「privacy constraintを無視せよ」と指示できる場合、user queryを隔離してもredaction stage自体が攻撃され得る。

したがって [PoisonedRAG](../Attack/2024-2402.07867-poisonedrag.md) のようなknowledge corruption attackとは別の防御が必要である。

また主評価はsingle-turn prompt injectionであり、multi-turn social engineering、external background knowledgeを利用したde-anonymization、複数sanitized factsのcomposition attack等は十分評価されていない。

natural-language privacy constraintsのqualityもdefenderに依存し、policyが不足していればredactorはそのinformationを保護できない。

## RAG Security Taxonomyでの位置づけ

SD-RAGは **Defense / confidentiality / selective disclosure / pre-generation context sanitization** に位置づけられる。

```text
Corpus-level privacy
  SAGE / DP-SynRAG

Retrieval / generation hardening
  RAGFort

Pre-generation selective disclosure
  SD-RAG ← 本論文

Runtime extraction detection
  CanaryRAG
```

特に「security instructionを強くする」のではなく、**untrusted generatorへsecretを渡さないarchitectureに変える**というsecurity principleが重要である。

## 実装・研究上の示唆

RAGでconfidential documentsを扱う場合、access controlをdocument単位だけで考えると粗すぎる。あるdocumentはanswerに利用してよいが、name / identifier / confidential attributeだけは出してはいけない場合がある。

SD-RAGはnatural-language constraintsをchunkへbindingすることで、このfine-grained selective disclosureをRAG pipelineへ組み込む。

実装上は、

- trusted policy engine
- isolated redactor
- final answer generator

を別security domainsとして扱うことが重要である。

またredaction stage自身がindirect prompt injectionを受けないよう、retrieved documentをinstructionとして実行しないmodel / structured extraction / deterministic sanitizationを組み合わせる余地がある。
