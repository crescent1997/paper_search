# OxyGen — Unified KV Cache Management for VLA Multi-Task Inference

## 1. 概要と研究上の位置付け

VLAが同じカメラ観測から**robot action、言語説明、長期記憶のためのテキスト生成**などを並列実行するとき、従来の独立したexpert実行はVLM prefillを重複計算し、長いlanguage decodeがaction更新を妨げる。OxyGenはMoT（Mixture-of-Transformers）VLAの共通prefix KVを一級の共有資源として管理し、(1)同一フレーム内のcross-task KV sharingと(2)フレームを跨いだlanguage decodeのcontinuous batchingを組み合わせるシステム研究。**異なる視覚フレーム間のtoken KVを近似再利用するVLA-Cacheとは異なる**。

## 2. 問題設定・先行研究との差

MoT VLAはVLM backboneのprefill結果を複数expertが利用できるが、一般的な実装ではaction pathとlanguage pathが独立してprefillする。action生成は制御周期ごとに厳しいdeadlineを持ち、languageは複数周期を跨いでもよい。通常のLLM continuous batchingはこうした制御周期を考慮しない。

本論文は「制御周期のdeadlineを守りながら、同じ観測のprefillを共有し、未完了language requestを次周期に継続する」というスケジューリング問題をKV managerで解く。LMCache/KVShareのcross-request KV管理に近いシステム視点を、MoT VLAのaction+language同時生成に拡張する。

## 3. 手法

### 3.1 共有prefixとexpert別生成状態

時刻`t`の観測 `o_t` をVLMで1回prefillして、全layerの `K_t={(K_t,l,V_t,l)}` を生成する。action expertはこのprefixを読みながらS回のflow/diffusion denoisingでH個のactionを生成。language expertは同じprefixから自己回帰でN tokenを生成する。**両者はprefillを共有するが、生成側の状態・追加KVは独立**。

### 3.2 Cross-frame continuous batching

言語requestごとに `(prefix_and_generated_KV, decoded_tokens, finished_flag)` のresumable stateを保持し、IDを発行する。各制御フレームで次の処理を行う。

1. 新観測を1回prefillし、action chunkを生成。
2. 新しいlanguage requestを既存の未完了request集合へ追加。
3. requestごとのKV・位置・maskを保ったままbatchを構築し、**各requestをk token分だけ**decode。
4. 完了requestはevict、未完了requestは更新して次フレームへ持ち越す。

1フレームあたり1request、長さN、各フレームでk token/requestを処理する定常状態では、active batch sizeは概ね `B=N/k`。frame latencyをTとするとaction frequencyは `H/T`、language throughputは `Bk/T`。小さなkはbatching効率を上げる一方、**個別requestの完了までのwall-clock latencyが伸びる**。

### 3.3 実装上の重要点

`Store/Retrieve/Update/Remove` と `Batch/UnBatch` をKV managerのAPIとし、requestごとにtoken positionとattention maskを保持する。π0.5のopenpiをJAX/PyTorchで拡張。共通backboneを使うexpertが増えるほどprefill共有の利益が増える。別backbone間の異種KV変換までは扱わない。

## 4. Experiment Setup

- **Hardware**：NVIDIA GeForce RTX 4090、Jetson AGX Thor、Thor搭載humanoid実機。
- **Model**：π0.5（LIBERO/ALOHA/DROID相当の観測・制御設定）。追加検証にXiaomi-Robotics-0、StarVLA（Qwen3-VL/PI_v3、GR00T、OFT expert）、Qwen3.5 0.8B〜9B。
- **Baseline**：openpiベースのsequential isolated execution（action/languageが個別prefill）、GPU MPSを用いたparallel isolated execution。cross-task sharingのみ、sharing+batchingをablation。
- **Workload**：language token数 `N∈{5,10,15,20,30}`、フレーム内budget `k∈{1,5,10}`、action denoising steps S、到着間隔・長さ分布。π0.5の既定H=10、S=10。
- **指標**：action frequency（`H/T`、action生成速度でありreplanning rateは`1/T`）、aggregate language throughput、frame latency、request completion time、peak GPU memory、power/energy、LIBERO成功率。

## 5. Main Results

### 5.1 性能とlatency

- RTX 4090上、π0.5で**最大3.7倍**のaction frequency/aggregate language throughput改善。条件によって200 tokens/s超と70Hzを同時達成。
- `N=5`の短い言語出力では、KV sharingのみでframe latency **200.3→145.1ms（約1.4倍）**。
- `N=30,k=5`では、sharingのみ469.3msに対し、sharing+batching **175.8ms（追加で約2.7倍）**。action frequencyは21.3→56.9Hz。
- 異なるbackboneの`N=30,k=5`：Xiaomi-Robotics-0 **3.23倍**、StarVLA Qwen3VL-PI_v3 **3.60倍**。3/4 expert構成は3.53/3.69倍。
- Jetson AGX Thor搭載humanoid：action+languageの推論経路合計 **1030→393ms**。action path 207.5→198.0ms、language path 822.3→195.4ms。物理action実行333ms中にlanguage処理の一部を隠蔽できると報告。これは物理動作全体の速度が2.6倍になることを意味しない。

### 5.2 Action quality（LIBERO）

| 指標 | openpi公表値 | OxyGen（10 seed） |
|---|---:|---:|
| Spatial | 98.80% | 98.42% [98.12,98.72] |
| Object | 98.20% | 98.52% [97.95,99.09] |
| Goal | 98.00% | 97.24% [96.66,97.82] |
| LIBERO-10 | 92.40% | 92.86% [92.40,93.32] |
| **Overall** | **96.85%** | **96.76% [96.55,96.97]** |

OxyGenは計20,000 rollout、10 seedの95% CI。openpiは論文公表のpoint estimateであり、**同じseedのpaired検定ではない**。「品質劣化がない」はほぼ同等という意味にとどめる。

### 5.3 GPU memory / energy（RTX 4090）

| 条件 | Peak memory | 平均power | Energy/request |
|---|---:|---:|---:|
| Sequential baseline | 6.43GiB | 293.5W | 117.4J |
| MPS parallel | 12.49GiB | 324.4W | 120.9J |
| KV sharingのみ | 6.43GiB | 287.9W | 97.7J |
| OxyGen, batch 2 | 7.35GiB | 173.3W | 39.1J |
| OxyGen, batch 4 | 7.41GiB | 154.4W | 25.8J |

batch 4ではmemoryが約15%増えるがenergy/requestは78%減。**キャッシュ共有＝メモリ容量削減とは限らない**。並行language requestの生成状態を保持する分の追加メモリが必要。

## 6. 主要ablation / システム分析

- **sharingとbatchingを分離**：短い出力ではprefill共有の利益が支配的。長い出力ではbatchingの利益が大きい。`N=30,k=5`のsharing-only 469.3ms→両方175.8ms。
- **prefillの内訳**：1回のprefill約44.0ms、action denoising約20.4ms（π0.5 LIBERO, S=10）。prefill共有だけでも、`N=1`でE2E 36.4%減、`N=5`で25.9%減。
- **batchingの管理コスト**：active batch 6でframe latency比JAX 3.4%、PyTorch 1.2%。batch 30ではJAX 17.5%、PyTorch 6.6%。cacheのstack/splitが支配的で、固定slot化が改善余地。
- **expert数**：2→3→4 expertでprefill共有の利益が増加。長いlanguage出力と小さなkほどbatching効果が増す。
- **language request latency**：小さいkでは1requestが複数フレームに跨るため、throughputと個別完了時間のtradeoffを区別する必要がある。

## 7. Limitations / 批判的評価

1. **同一フレームのcross-task prefill共有**であり、連続視覚フレームの類似性を利用したcross-frame visual KV reuseではない。過去観測の意味記憶そのものを管理するMemoryVLA/MEMとも異なる。
2. 現行実装はaction＋language中心。video等の出力expert、非同期制御、学習中のmemory constructionまで含む完全な同時実行は未検証。
3. `k`は固定で、個別language responseの遅延を増やす。負荷変動・deadline違反へのadaptive schedulingは課題。
4. batchサイズが大きいとKV管理overheadとGPU memoryが増える。JAX実装では特にcache stack/splitが支配的。
5. throughput/Hzは生成済みaction数をframe latencyで割った値であり、ロボットの実際の**replanning frequencyや制御安定性と同義ではない**。
6. NeurIPS 2026と記載されているが、再現実験やコード動作確認は今回行っていない。公開repoを用いた同条件追試が望ましい。

## 8. Taxonomy / 関連研究

- **分類**：`KVcache/vla/`。**Cross-task KV sharing / cross-frame language continuous batching**。LLM servingの`reuse`/`access`に近いが、VLA固有のaction deadlineが主題のためVLAへ分類。
- **[Reflex](2026-2607.14695-reflex.md)**：action生成と非同期実行、flow-matching時のKV配置を最適化。OxyGenはactionとlanguageの並行処理を対象。
- **[MEM](2026-2603.03596-mem.md)**：長期記憶の内容・表現を設計。OxyGenのAppendix Eはtextual-memory生成を同時処理するが、記憶内容の品質は主題でない。
- **[TempoFit](2026-2603.07647-tempofit.md)**：過去観測のK/Vを検索・融合して長期操作に活用。OxyGenは同じ観測のprefillを複数expertへ共有。
- **[VLA-Cache](2025-2502.02175-vla-cache.md)**：連続フレームのvisual KV再計算を削減。OxyGenの共有軸はexpert間。
