# Mitigating the Privacy Issues in Retrieval-Augmented Generation (RAG) via Pure Synthetic Data

> private dataをそのままRAG retrieval databaseへ保存する代わりに、必要なtask informationだけを保持したsynthetic corpusへ置換する **SAGE** を提案する。Attribute-based Data Generationでutilityを保ち、Agent-based Private Data Refinementで残存privacy informationを反復的に除去することで、RAGのtargeted / untargeted extraction riskを大幅に下げる。

## 概要

RAGではLLM parameterへprivate dataを直接学習させなくても、retrieval databaseにprivate recordsを保存している限り、retrieved contextを経由してsensitive informationがresponseへ漏れる可能性がある。[The Good and The Bad](../Attack/2024-2402.16893-the-good-and-the-bad.md) が示したように、attackerはblack-box queryだけでtargeted / untargeted data extractionを行える。

SAGEはこの問題をgeneration-time filteringではなく **retrieval data layerそのものの置換** で解決する。original private corpusを直接indexせず、LLMを用いてprivacy-preserving synthetic corpusをoffline生成し、そのsynthetic corpusだけを通常RAGでretrieveする。

単純なparaphraseではprivate factがそのまま残り、privacy-preserving synthetic generationで情報を落としすぎるとRAG utilityが低下する。そこでSAGEは2-stage pipelineを用い、Stage-1でtask-relevant informationを構造的に抽出・再生成し、Stage-2でoriginal / synthetic pairを比較するprivacy agentによって残存sensitive informationを反復的に除去する。

## 問題設定 / Threat Model

victim RAGはprivate corpus $D$ をretrieval databaseとして保持し、user queryに対して関連documentsをretrieveしてLLMへcontextとして渡す。

attackerは通常userと同じblack-box query accessを持ち、retrieval databaseそのものやretrieval score、内部prompt、model parameterにはアクセスしない。一方、queryを工夫することでretrieved private contentをresponseへ露出させることを狙う。

論文では主に2種類のprivacy attackを評価する。

- **Targeted attack**: 特定person / record / sensitive attributeを狙ってqueryする。
- **Untargeted attack**: 特定targetを事前に限定せず、retrieval contextからprivate informationを広く引き出す。

SAGEのdefender capabilityは、RAG deployment前にprivate corpusへoffline preprocessingを行えること、synthetic data generation用LLMを利用できることである。online queryごとのprivacy budgetやgenerator modificationは要求しない。

## 先行研究からの改善点

### Direct Private Corpus Retrievalの問題

[The Good and The Bad](../Attack/2024-2402.16893-the-good-and-the-bad.md) のようなattackでは、retrieverがprivate recordをgenerator contextへ入れた時点でLLM instruction-followingを通じて漏洩する。output filterだけではparaphraseされたsensitive informationを完全には止めにくい。

SAGEはそもそもonline retrieval databaseからoriginal private recordを除くことでattack surfaceを縮小する。

### 単純Synthetic Generationの問題

original documentを単にparaphraseすると、email、phone number、specific medical factsなどprivacy-sensitive attributesがそのまま残る。一方、privacyを優先して情報を大量に削除するとdownstream QAに必要なfactsも失われる。

SAGEは **utility preservationとprivacy refinementを別stageに分離**することでこのtrade-offを扱う。

### DP-SynRAGとの位置づけ

後続の [DP-SynRAG](2025-2510.06719-dp-synrag.md) もprivate corpusをsynthetic corpusへ置換するdata-layer defenseであり、技術的にはSAGEの方向性をformal privacyへ発展させたものと整理できる。

SAGEはLLM-based privacy agentによるempirical sanitizationであり、Differential Privacyのようなformal guaranteeを持たない。一方DP-SynRAGはsynthetic corpus generationへDP mechanismを導入し、privacy budgetを明示する。この違いは両論文を比較する上で重要である。

## Method / Algorithm

SAGEは **Stage-1: Attribute-based Data Generation** と **Stage-2: Agent-based Private Data Refinement** の2段階からなる。

### Stage-1: Attribute-based Data Generation

まずdataset / domainの少数sampleをLLMへ与え、downstream taskに重要なattributeを抽出する。

例えばhealthcare recordであれば症状、診断、治療等、task answerに必要なsemantic fieldsを抽象化する。各original sampleについて、抽出されたattributeごとにkey informationをLLMに抽出させる。

概念的にはoriginal document $x$ をそのままparaphraseするのではなく、

$$
x \rightarrow \{(a_1,k_1), (a_2,k_2),\ldots,(a_m,k_m)\}
$$

というattribute / key-information representationへ変換する。

その後、このstructured representationのみをconditionとして別のLLMにsynthetic document $\tilde{x}$ を生成させる。

この処理には2つの意味がある。

1. downstream QAに必要なinformationをattribute単位で明示的に保持する。
2. original wordingやtaskに不要なprivate detailsをgeneration processから切り離す。

ZeroGenやgeneric paraphraseと異なり、単に「似たdocument」を作るのではなく、RAG utilityに必要なinformation contentを明示的に制御する点がStage-1の中心である。

### Stage-1だけではPrivacyが不十分

attribute extraction時にspecific identifierやsensitive relationがkey informationとして残れば、それを使ってsynthetic documentを生成してもprivacy leakageは残る。

例えばperson name、email address、phone number、patient-specific combination等は、文章表現を変えてもprivate informationとして再現され得る。

そこでStage-2を導入する。

### Stage-2: Agent-based Private Data Refinement

Stage-2では **Privacy Agent** と **Rewriting Agent** を用いる。

Privacy Agentにはoriginal sampleとcurrent synthetic sampleを与え、synthetic textにoriginal private informationがどの程度残っているかを検査させる。問題があれば、どの部分を修正すべきかprivacy feedbackを生成する。

Rewriting Agentはそのfeedbackを受け、task-relevant semantic contentをできるだけ保持しながらsynthetic documentを書き直す。

このprocessを、Privacy Agentが追加privacy issueを検出しなくなるまでiterativeに繰り返す。

```text
Original Data
    ↓
Attribute / Key Information Extraction
    ↓
Synthetic Generation
    ↓
Privacy Agent ── issue detected ──→ Rewriting Agent
    ↑                                  │
    └──────── refined synthetic ───────┘
    ↓ safe
Synthetic Retrieval Corpus
```

実験ではrefinementは無制限に続くわけではなく、平均して数round、概ね3 round前後で収束する。

## Experiment Setup

### Dataset

privacy evaluationの中心は、

- **HealthCareMagic**
- **Wiki-PII**

である。

さらにgeneral RAG / open-domain QA utilityを確認するため、

- Natural Questions (NQ)
- TriviaQA
- WebQuestions
- CuratedTREC

等も評価する。

### Baseline

主な比較対象は、

- Original private corpus
- simple paraphrasing
- ZeroGen
- AttrPrompt
- SAGE Stage-1 only
- SAGE Stage-1 + Stage-2

である。

これにより「synthetic dataにしただけ」の効果と、attribute-based generation、privacy refinementそれぞれの寄与を分離する。

### Models

default configurationではStage-1 generationにGPT-3.5系、Stage-2のagent-based refinementにGPT-4系を利用する。RAG answer generationについても複数settingでutility / privacyを評価する。

### Metrics

utility側ではROUGE、BLEU、QA performance等を測定する。

privacy側ではtargeted / untargeted extraction queryを送り、target private informationがresponseへ含まれた件数や、repeat promptによってprivate contextが再現された件数を測る。

## Main Results

### Utility Preservation

HealthCareMagicではOriginal corpusのROUGE-L **0.0789** に対しSAGE Stage-2は **0.0943**、BLEU-1もOriginal **0.0846** に対してStage-2 **0.113** と、privacy-preserving synthetic corpusでもutilityが低下せず、むしろ改善するsettingがある。

これはsynthetic generationが単なるinformation deletionではなく、task-relevant factsをattribute単位で整理するため、retrieval contextのnoiseが減る可能性を示す。

Wiki-PIIやODQA settingでも、SAGEはoriginal retrieval corpusに近いdownstream performanceを維持する。

### Targeted Privacy Attack

250 targeted promptsを用いたevaluationでは、Original corpusはsettingによって **25～167件**のtarget-information leakageを生じ、repeat-prompt extractionでも **12～132件**のleakageが観測される。

Stage-1だけでもOriginalより大きく改善するが、sensitive attributesが残るsettingでは依然として漏洩する。

Stage-2まで適用すると、評価した8条件中7条件でtargeted leakageを **0件**まで抑える。残る1条件でもrepeat-prompt leakageは **7件**に低下する。

したがってprivacy agentによるiterative comparison / rewritingが単なるattribute-based synthesis以上の効果を持つ。

### Untargeted Privacy Attack

untargeted extractionではStage-2 SAGEは評価した条件で **0件**のprivate-information leakageを達成する。

特定targetを狙わないgeneric extraction commandに対して、original private recordsがretrieval corpusに存在しないことが大きく効いている。

## Retrieval Top-k Robustness

retrieval top-kを増やすとgeneratorへ渡されるcontext量が増えるため、Original corpusやStage-1ではprivacy leakageが増える場合がある。

Stage-2はtop-k増加後も低いleakageを維持し、privacy refinementが単一retrieval configurationだけにoverfitしたものではないことを示す。

ただしこれはformal guaranteeではなく、評価したattack / domain内でのempirical robustnessである。

## Ablation / Component Analysis

Stage-1とStage-2の比較から、2つのcomponentは異なる役割を持つことが分かる。

**Stage-1** はtask-relevant attributeを明示的に保持することでsynthetic corpusのutilityを確保し、original wordingや不要detailsを減らす。

**Stage-2** はStage-1で残ったspecific private informationをoriginal-synthetic comparisonを通じて検出・修正し、privacy leakageを大幅に下げる。

generic synthetic generationだけではutility/privacy trade-offの両立が難しく、このrole separationがSAGEの主要設計である。

## Limitations / 成立条件

最大のlimitationは **formal privacy guaranteeがない**ことである。Privacy AgentはLLMによるsemantic judgementであり、見逃したprivate informationはsynthetic corpusに残り得る。

またPrivacy Agentがoriginal dataへアクセスする必要があるため、offline synthesis environment自体はtrustedでなければならない。

評価domainはhealthcare / PIIを中心としており、企業内部文書、code、legal data等へ同じprivacy-utility trade-offが一般化する保証はない。

さらにagent-based iterative refinementにはstrong LLM APIの利用costがかかる。ただしこれはoffline preprocessingなので、queryごとにcostを払うonline defenseとは性質が異なる。

membership inference、single-fact inference、side-channel leakage等を包括的に防ぐ方式でもなく、主張の中心はretrieval contextを利用したcontent extraction riskの低減である。

## RAG Security Taxonomyでの位置づけ

SAGEは **Defense / confidentiality / data-layer sanitization / synthetic retrieval corpus** に位置づけられる。

RAG extraction defenseを大きく分けると、

```text
Original private corpus
    │
    ├─ Runtime hardening → RAGFort
    ├─ Runtime detection → CanaryRAG
    └─ Corpus replacement
          ├─ SAGE: LLM-agent empirical privacy refinement
          └─ DP-SynRAG: Differential Privacy付きsynthetic generation
```

となる。

SAGEの重要な位置づけは、RAG runtimeでattackを検知・filterするのではなく、**retrieverがoriginal private recordへ到達できない状態をdeployment前に作る**ことである。

## 実装・研究上の示唆

private corpusをRAGで利用する場合、単純PII maskingだけでなく「downstream taskに本当に必要なinformationは何か」をattribute levelで抽出し、そのinformationから新しいretrieval corpusを構築する設計は有力である。

一方、LLM agentが「安全」と判定したことをprivacy guaranteeとみなすのは危険である。そのため実運用では、

- deterministic PII / secret scanner
- human / policy-based review
- DP synthetic generation
- runtime extraction detection

等とのdefense-in-depthが望ましい。

特に [DP-SynRAG](2025-2510.06719-dp-synrag.md) との比較は、**empirical LLM sanitizationとformal DP guaranteeのutility / cost / privacy差**を検討する上で重要である。
