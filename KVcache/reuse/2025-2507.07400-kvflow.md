# KVFlow — Workflow-aware prefix cache management

## 概要 / 問題設定

LLM agentを複数段に接続するworkflowでは、各agentが長い固定system prompt・role・few-shot例を繰り返し使用する。既存のprefix cacheは**一致する先頭token列**のKVを再利用できるが、GPU容量不足時のLRU evictionは「最近使ったか」を見るため、**次のstepで再び使うagentのKVを捨てる**ことがある。CPU HiCacheがあっても、必要になってから転送するreactive loadはlatencyを生む。

KVFlowはモデルのattention精度を修復する手法ではなく、**workflowの制御構造をserving engineに渡してcacheの残し方・転送時刻を改善**する。保存KVのtoken数やKV表現自体を圧縮しないため`reuse`（prefix sharing/cache-aware scheduling）に分類する。

## 手法

### 1. Agent Step Graphとsteps-to-execution

Agent呼び出しをnode、依存関係をedgeとするAgent Step Graphを作り、各agentが**最短で何step後に起動可能か**を求める。依存がANDなら `max(E1,E2)+1`、ORなら `min(E1,E2)+1` と集約する（本文Fig. 3）。これは実行順序を完全に予知するものではなく、workflow構造から求める**earliest possible**な近似である。

### 2. Radix-tree KV nodeごとのeviction priority

SGLang型のprefix radix treeでは、異なるagentの固定promptが共通prefixを共有する。KVFlowはagent単位でcacheを丸ごと削除するのではなく、**各agentの固定prompt末尾nodeにstep距離を付け、親へminで伝播**する。これにより、複数agentが共有する上流nodeは「最も早く再利用される子」に合わせて保護される。

- 動的suffixは再利用見込みが低いので**最優先でevict**。
- 固定prompt nodeはsteps-to-executionが大きいほどevictしやすくする。
- 複数workflowが同じnodeを使う場合も、保護側の最小値を採用。

LRUと異なり、最近使われていなくても次stepで必要になるprefixを残す。

### 3. Overlapped KV prefetchingとstatus-aware scheduling

GPU上にない固定prompt KVはCPU DRAMに置き、**現在のagentがdecode中に次agentのKVをCPU→GPUで非同期prefetch**する。分岐がある場合は、予算内で次に実行し得るagentを複数prefetchする。転送が未完了のagentは待たせ、GPUで実行可能な別workflow/agentを先に処理する**status-aware scheduling**で転送stallを隠す。

### 4. Integration

SGLang frontendの `sgl.function` をagentに対応させ、HTTP requestへclient ID、agent ID、Step Graph/step距離を付与する。固定prompt末尾は明示APIまたは過去のprefix hit履歴から推定。backendはradix tree eviction優先度を更新し、容量を見ながらprefetchを発火する。**モデルの重み・token列・attention計算・fine-tuningは変更しない**。

## Experiment Setup

- **Baselines:** SGLang（GPU radix cache / LRU）とSGLang + HiCache（CPU階層cache、reactive load）。
- **Single workflow:** 10-agent逐次workflow、固定/動的/output token数を制御したsynthetic prompt、cache warmup後10回実行の平均、batch=1。
- **Hardware/models:** Llama-3.1-8B on A10G 24GB / PCIe Gen1 2GB/s、Qwen2.5-32B on H100 80GB / PCIe Gen5 64GB/s。temperature=0 / greedy。
- **Concurrency:** H100上の複数独立workflow、dynamic/output各256 tokens。PEERを用いたFinancial QA workflowのsimulationも評価。
- **Metrics:** end-to-end workflow latency / speedup。accuracyはKV値を変えない設計のため主たる評価対象外。

## Main Results

| 設定・比較対象 | 報告された改善 |
|---|---|
| 10-agent、A10G、固定8192 / dynamic32 / output32、対HiCache | **1.83×** |
| 同条件、対GPU-only SGLang | **2.91×** |
| H100上の高並列workflow、対GPU-only SGLang | 最大 **1.25×** |
| 同高並列、対HiCache | 最大 **2.19×** |
| PEER-style realistic simulation、対SGLang / HiCache | 最大 **1.12× / 1.08×** |

論文abstractの「最大2.19×」は**高並列時のHiCache比**であり、あらゆるagent workflowで2倍速くなるわけではない。固定promptが長くGPU容量を圧迫するほど有効で、decodeが長くなるほどprefill/cache loadが全体時間に占める比率が小さくなり改善率は下がる。実際、固定4096では平均1.28×、8192では平均1.48×と記述される。

## 主要ablation / 効く条件

論文は「eviction-only」「prefetch-only」の詳細な数表を独立して網羅する構成ではなく、baseline・prompt長・concurrencyの変化から寄与を検証する。

- **固定prompt長:** 4096→8192で利益増。prefix cache missが高価なほど未来使用情報が効く。
- **出力長:** 長いdecodeでは改善率低下。prefetchはdecodeそのものを速くしない。
- **CPU階層cache:** HiCacheは一般にGPU-onlyより良いが、高並列1024 fixed/64 workflowsではGPU-onlyの0.57×まで低下した例があり、reactive transferとschedulingの干渉が顕在化する。
- **現実的prompt:** PEERでは固定promptが数十〜数百tokenのため、合成長promptでの最大値より利益は小さい。

## Limitations

1. **Workflow graphの取得・維持が前提**。完全に予測不能な自律agent、動的なtool呼び出し、変化の大きいpromptではstep距離の精度が下がる。
2. 実験はGPU memoryにactive requestだけで埋まり切らず、prefix cacheを維持できる並列度に限定。極端な過負荷には未対応。
3. Prefix一致と同一modelの再利用が前提。非prefix document再利用や異model KVの互換性は解決しない。
4. PCIe帯域、GPUメモリ、agent output長に依存。先読みが外れた場合は不要転送・cache汚染が起こり得る。
5. GPU KVのfragmentation問題自体は解決しないと本文で明記。コード公開URLは今回の一次資料では特定できなかった。

## Taxonomy / 関連研究との差分

- **Category:** `reuse` / exact prefix / workflow-aware eviction / hierarchical CPU-GPU prefetch / agent-level scheduling。Reuse granularityは**radix-tree KV node**、signalは**未来の実行step距離**、repair/recomputationはなし。
- [PagedAttention](2023-2309.06180-pagedattention.md)：物理page管理・共有prefixの基盤。KVFlowは共有されたcacheの**将来需要に応じた優先順位**を追加。
- SGLang / RadixAttention（[論文](https://arxiv.org/abs/2312.07104)）：radix treeを利用したprefix reuse。KVFlowは**LRUの代わりにworkflow-aware eviction**と非同期prefetchを導入。
- [Preble](2024-2407.00023-preble.md)：複数GPUへのrequest placementとcache localityを最適化。KVFlowは**同一serving engine内のagent順序予測**に重点。
- [Mooncake](2024-2407.00079-mooncake.md)：分散KV cache・prefill/decode分離。KVFlowは**agent workflow graph**を直接cache policyへ反映する。
- [CacheBlend](2024-2405.16444-cacheblend.md)：非prefixなdocument KVをselective recomputationで品質修復。KVFlowは**完全一致prefix**を対象とし、精度修復は不要。
