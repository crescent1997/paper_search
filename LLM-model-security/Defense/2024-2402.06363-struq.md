# StruQ: Defending Against Prompt Injection with Structured Queries

## 概要

StruQは、LLM-integrated applicationへのprompt injectionを、trustedな**prompt/instruction**とuntrustedな**data**が同じ自然言語token列に混在することから生じる権限分離問題として扱う。中心的な発想は、両者を明示的な2-channel structured queryとして分離し、モデルにも「prompt部分のinstructionだけを実行し、data部分は処理対象として読むが命令としては従わない」性質をfine-tuningで学習させることである。

この意味でStruQは、後続の[The Instruction Hierarchy](2024-2404.13208-instruction-hierarchy.md)がsystem / user / tool / third-partyへ一般化する前段階に位置する、**2-level privilege separation**の代表的研究とみなせる。

## 問題設定 / Threat Model

LLM applicationへの入力を、開発者またはユーザーが意図したtrusted instruction `P` と、web page・retrieval result・document・API response等から得たuntrusted data `D` に分ける。

通常のLLMでは両者が単一token sequenceへ連結されるため、攻撃者は`D`の中へ「以前の命令を無視して…」のようなinstructionを埋め込み、モデルに`P`ではなくattack instructionを実行させられる。

StruQのsecurity objectiveは、`D`の内容をtask遂行に利用しながら、`D`中のinstruction-like textには従わないことである。untrusted dataを単純に削除・無視するdefenseではない点が重要である。

## 先行研究からの改善点

prompt engineeringによる「以下はdataなので命令に従うな」といったreminderやsandwichingは、instructionとdataの境界自体を自然言語で表現するため、攻撃者が類似の文字列を注入して境界をspoofできる。

StruQはこの問題を、(1) application側のsecure front-endで構造を強制し、(2) model側をその構造に合わせて再学習することで解決する。単なるinput sanitizationではなく、**interfaceとmodel trainingをセットで設計する**点が主要な差分である。

## Method / Algorithm

### 1. Structured Query

入力を概念的に

```text
[INSTRUCTION]
trusted prompt P
[DATA]
untrusted data D
[RESPONSE]
```

のような構造へ変換する。実装ではreserved delimiterを利用し、prompt領域とdata領域を明確に区別する。

### 2. Secure Front-End

攻撃者がdata内にdelimiterを直接書き込んでprompt領域へ脱出するdelimiter injectionを防ぐため、front-endがreserved token / delimiterを処理する。したがってsecurity propertyはfine-tuned model単体ではなく、front-endとの組合せで成立する。

### 3. Structured Instruction Tuning

通常のinstruction tuning sampleをstructured formatへ変換するだけでは、モデルはdata側のinstructionを無視することを学習していない。そこでtraining dataの一部に意図的なprompt injectionを挿入する。

52K規模のinstruction-tuning dataを用い、半分をcleanなまま保持しつつ、input/dataを持つsampleの一部へ別sample由来のinstructionを挿入する。training attackとして主にNaiveとCompletion型を利用し、target responseは元のtrusted instructionへの正しい回答のままとする。

つまりSFT objectiveは

```text
(P, D + injected instruction) -> answer to P
```

を学習することであり、data内の命令をnegative channelとして明示的に扱う。

## Experiment Setup

Llama系・Mistral系モデルを中心に、通常utilityとprompt-injection robustnessを評価する。attackにはtrainingで見たNaive / Completionだけでなく、Ignore attack、より自然なcompletion attacks、optimization-basedなGCG等を含める。

utilityについてはAlpacaEval等を用い、security向上のために通常instruction-following能力が大きく低下していないかを確認する。

## Main Results

manual / template-based prompt injectionに対してStruQは非常に高いrobustnessを示し、多くの設定でattack success rateをほぼ0–2%程度まで低下させる。単純なprompt-level defenseより、trainingによってprompt/data separationを内部化させることが大きく効いている。

一方、adaptive optimization attackに対しては完全ではない。代表的結果ではTAP型attackのASRを約97%から9%へ大幅に低下させる一方、GCGでは約97%から58%までの低下にとどまる設定がある。これはstructured trainingで未知attackへのgeneralizationは得られるものの、モデル内部のtoken-level optimizationで境界を突破する余地が残ることを示す。

## Generalization / Robustness

trainingで使用するinjectionは比較的単純だが、未学習のprompt-injection templatesにもgeneralizeする。これは特定文字列をmemorizeしてfilteringしているだけではなく、「data channelのinstructionは実行対象ではない」というbehaviorを一定程度学習していることを示唆する。

ただしwhite-box / optimization-based attackへの残存ASRは、SFTでpositive targetのみを学習する方式の限界でもある。この点を直接改善するのが後続の[SecAlign](2024-2410.05451-secalign.md)である。

## Limitations

第一に、StruQは基本的にpromptとdataという2-level hierarchyであり、system / developer / user / toolなど多数の権限階層を一般的に表現するものではない。この一般化は[The Instruction Hierarchy](2024-2404.13208-instruction-hierarchy.md)へつながる。

第二にsecure front-endを迂回してraw textを直接modelへ与えるとsecurity assumptionが崩れる。model checkpointだけを導入すればよいdefenseではない。

第三にoptimization-based adaptive attackへのrobustnessは不完全であり、単純なSFTでは「正しいresponseを増やす」ことと「攻撃者responseを明示的に下げる」ことが同一ではない。

## LLM Model Security Taxonomyでの位置づけ

```text
Prompt/data privilege separation
    StruQ
      | 2-level structured interface + SFT
      +--> Instruction Hierarchy
      |      multi-level authority hierarchy
      +--> SecAlign
             preference optimization against insecure output
```

RAG固有のdefenseではなく、external dataを持つ任意のLLM applicationに対するmodel/interface-level privilege separationとして位置づけられる。

## 実装・研究上の示唆

重要な示唆は、instruction hierarchyをmodel promptだけで表現するのではなく、**入力interface上でもtrusted instructionとuntrusted contentを型として分離する**ことである。

一方、後続研究を含めて考えると、構造化interface、hierarchy-aware model training、preference optimizationは競合する代替案ではなく、複数layerで組み合わせられる可能性が高い。
