# SnapKV: LLM Knows What You are Looking for Before Generation

> generation開始前のprompt末尾にある短いobservation windowを見るだけで、各attention headが将来どのprompt位置を参照するかをかなり予測できる、という観察をKV evictionへ利用する。

## 概要

long-context LLMではprefill終了時点で入力全tokenのKVを保持する。

例えば16K inputなら、decodeの各stepで16K token分のK/Vを参照する。これはKV memoryを増やすだけでなく、decode attentionのmemory trafficと計算長も増やす。

KIVIのようなquantizationは1 token当たりのbytesを減らすがtoken数自体は減らさない。SnapKVは別の方向から、generation中に実際に強く参照されるprompt tokenは全体の一部に限られると考える。

著者らはattention mapを分析し、各headがgeneration中に参照するprompt位置には比較的安定したpatternがあり、そのpatternがprompt最後の短いwindowから過去を見るattentionにも既に現れていることを示す。

このためgeneration開始前に重要KVを選び、それ以外を捨てられる。

## Key Observation: Prompt末尾からfuture attentionを予測できる

あるattention headについて、generation tokenからpromptへのattention分布を見ると、prompt末尾のtokenが過去promptへ向けるattentionと高い類似性を持つ。

つまりLLMはanswer生成を始める前から、このpromptではどの領域が重要かをある程度attention patternとして表現している。

SnapKVはこの性質を使い、generation途中のstatisticsを待たずにprefill終了直後にcache compressionを行う。

## Observation Window

promptの最後の短い領域をobservation windowとする。

各attention headについて、observation window内tokenから過去prompt tokenへのattention scoreを集計し、prompt positionごとのimportance scoreを作る。

概念的には、

importance(i, h) = observation window内のquery tokenからprompt位置iへのattentionの集約

と考えればよい。

重要なのは、globalな1本のscoreではなくheadごとに別々のscoreを持つこと。

## Head-wise Selection

attention headごとに役割が異なるため、重要tokenも異なる。

あるheadはentity tokenを追い、別headはdelimiterやlocal syntax、別headはdistant evidenceを見る可能性がある。

そこでSnapKVはhead hごとにtop important positionsを選択する。

全head共通のtop-kではなくhead-wise selectionにすることで、同じKV budgetでも多様な情報を残せる。

## Clustering / Pooling

attention importanceは単一tokenだけにsharpに集中するとは限らない。

重要なsentenceやentity spanの近傍にscoreが分散することがある。単純なtop-k selectionだけでは、1つの重要spanから一部tokenしか残らずcontextが欠ける。

そこでSnapKVはimportance scoreへpoolingを適用し、attention peak周辺のtokenをclusterとして扱いやすくする。

この処理により、重要regionのlocal contextをまとめて残せる。

## 全体pipeline

処理は次のように整理できる。

1. full promptを通常どおりprefill
2. prompt末尾をobservation windowとして使う
3. 各headでprompt token importanceを計算
4. poolingで近接importanceをまとめる
5. head-wiseにimportant positionsを選択
6. 選ばれなかったKVを削除
7. generationではcompressed KVだけを参照

外部selector modelや追加fine-tuningは不要。

## なぜRecent Windowだけでは足りないか

StreamingLLM等の方式では、attention sink tokenとrecent tokensを固定的に残す。

これはstreaming用途では有効だが、long-document QAではanswer evidenceがprompt前半や中央にあることが多い。

固定recent windowではそうしたdistant evidenceを失う。

SnapKVはprompt-specific attentionからsemantic importanceを推定するため、遠距離のimportant tokenを残せる。

## Experiment Setup

NeurIPS論文では16種類のlong-sequence datasetを使い、long-document QA、multi-document QA、summarization、few-shot、synthetic retrieval、Needle-in-a-Haystack等を評価する。

複数LLMでfull KV cacheや既存KV eviction / streaming方式と比較する。

system評価ではA100 80GBを用い、GPU memory、generation latency、最大context lengthを測定する。

## Main Results: Task Accuracy

強いcache compressionを行っても、多数のlong-context benchmarkでfull-cache baselineに近い性能を維持する。

特にdistant evidence retrievalが必要なtaskでは、recent-window型より有利。

これはobservation windowから得たattention importanceがfuture generation時の参照先をよく予測しているため。

## Main Results: Memory

16K inputでbaselineに対して約8.2×のmemory efficiency improvementを報告する。

SnapKVはbit widthではなくcache token数を減らすため、memoryだけでなくその後のattention lengthも短くなる。

## Main Results: Generation Speed

16K inputで約3.6×のgeneration speedupを報告する。

prefill自体はfull promptを処理するが、その後のdecodeでは短いcompressed cacheのみを読むため、生成token数が多いほどbenefitが蓄積する。

## 380K Context

HuggingFace実装へ小変更を加えることで、単一A100 80GB上で最大約380K context tokenを処理できると報告する。

full KV cacheでは困難なcontext lengthであり、token evictionによるcapacity benefitを示す結果。

Needle-in-a-Haystackでもaccuracy dropは小さい。

## Needle-in-a-Haystackが意味するもの

Needle testでは非常に長いcontextの中に1つだけanswer evidenceを埋め込む。

SnapKVがこれを維持できるのは、observation windowがneedle位置へattentionしていれば、そのKVが重要tokenとして残るため。

一方でobservation phaseでimportanceが低く評価された情報は捨てられるため、あらゆるfuture generationに対してlosslessなcompressionではない。

## Compression RatioのTrade-off

cache budgetを小さくするほどmemoryとdecode speedは改善するが、重要tokenを取りこぼすriskが高まる。

multi-hop reasoning、broad summarization、複数documentを広く参照するtaskでは、必要なcache budgetが増える可能性がある。

SnapKVのhead-wise selectionは、同じbudgetを全head共通に割り当てるより効率的に使う設計。

## KIVIとの違い

[KIVI](2024-2402.02750-kivi.md)は全tokenを残し、各KV elementのbit数を減らす。

SnapKVはprecisionは維持しつつtoken数を減らす。

KIVIはquantization error、SnapKVはeviction errorという異なるinformation lossを持つ。

原理上は併用可能で、SnapKVで残したtokenをKIVIで2-bit化する二段圧縮も考えられる。

## Heavy-Hitter系との違い

generation中のattention historyを追いながらheavy hitterを残す方式と比べ、SnapKVはgeneration前にcompressionを完了できる。

そのためdecode loop内で継続的にimportanceを更新するoverheadが小さい。

一方、generation途中でfocusが大きく変わっても、一度捨てたtokenは復元できない。

## CacheBlendとの共通点と違い

[CacheBlend](../reuse/2024-2405.16444-cacheblend.md)も一部tokenを重要とみなして処理するが、目的が異なる。

SnapKVは「どのKVを保持するか」を選ぶ。

CacheBlendは「どのcached KVをfull-contextで再計算するか」を選ぶ。

SnapKVはunselected KVを削除し、CacheBlendはstale KVを修復する。

## Limitations

- observation-window attentionがfuture generation attentionを予測できることに依存する。
- evictionは不可逆で、捨てたtokenを後から必要としても戻せない。
- full prompt prefillは必要なので、TTFTを直接削る手法ではない。
- broad coverageやmulti-hop taskではaggressive compressionで性能が落ちる可能性がある。
- selection overhead自体も極端なlong contextでは無視できない可能性がある。

## KV-cache taxonomyでの位置づけ

SnapKVはcompressカテゴリのtoken-level compression / eviction。

KIVIのbit-level compressionとは別軸。

同じcompressでも「1 tokenを小さくする」のか「tokenを減らす」のかで設計思想が異なる。

## 実装・研究上の示唆

SnapKVの重要な観察は、long-context attentionがhead-wiseにかなりsparseで、そのsparsityがgeneration前から予測可能という点。

KV cacheを均一な過去memoryとして扱うのではなく、head-specific working setとして扱えば大幅に削減できる。

今後の拡張としては、SnapKV + quantization、generation途中でのre-selection、必要tokenの再hydrateなどが自然。

## まとめ

SnapKVは、

1. prompt末尾にobservation windowを設定
2. headごとに過去promptへのattentionを集計
3. poolingでimportant regionをcluster化
4. head-wiseに重要KVだけを選択
5. 残りKVを削除
6. compressed cacheでgeneration

を行う。

16K contextで8.2×のmemory efficiency、3.6×のgeneration speedupを報告し、16 long-context datasetでbaselineに近い性能を維持する。さらに単一A100 80GBで約380K contextを処理できることを示し、KV token evictionの実用性を示した。
