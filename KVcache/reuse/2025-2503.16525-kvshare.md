# KVShare: An LLM Service System with Efficient and Effective Multi-Tenant KV Cache Reuse

> **版に注意**：arXiv v1は Semantic-Aware Key-Value Cache Sharing for Efficient Large Language Model Inference で、semantic similarity / semantic alignment / differential editingが中心だった。現在のv2はタイトル・著者・手法が大幅に変更され、cross-request cache reuse + Dual-Stage High Deviation (DHD) + cache-aware scheduling が中心。本要約は現行v2を主対象とし、v1との差も記録する。

## 概要

長context LLMではprefillがTTFTの主要bottleneckになる。prefix cachingは完全一致prefixなら有効だが、multi-tenant workloadでは再利用可能なtext fragmentがrequest内の任意位置に現れたり長さが異なったりするため、固定chunk・prefix一致だけではreuse opportunityを十分に拾えない。

一方、document/chunkを独立に計算したKVを別contextへ挿入すると、preceding contextが変わるため本来のfull prefill KVとのずれが生じる。[CacheBlend](2024-2405.16444-cacheblend.md)は一部tokenを再計算してこのずれを修復した。KVShare v2はこれをmulti-tenant serving全体へ拡張し、adaptive-lengthなcross-request reuse、prefillだけでなくdecode中も重要tokenを更新するDHD、cache hit rateを考慮したrequest schedulingを一体化する。

## v1: Semantic-Aware KVShare

初版v1は現在版とかなり異なる。問題意識は、prefix cachingが文字列完全一致しか再利用できず、semantic cachingは似たqueryに以前のresponseを返すためresponse diversityを失うという点にあった。

そこでsemantic similarityからreuse候補を探し、semantic alignmentで対応spanを特定し、differential editingで差分を補正する。responseそのものではなくKVを共有することで、real-world conversation dataset上でcache hit rateを60%以上改善しつつBLEU / Rouge-Lでfull computationと大きな品質差を生じないと報告した。

v1は「semanticに似ている別request間でKV reuse opportunity自体を広げる」という発想であり、現行v2やProphetKVのselective recomputationとは直接の目的が異なる。

## v2の問題設定

v2では、同一または再利用可能なtext fragmentが複数requestに現れるmulti-tenant workloadを想定する。固定長chunkには、chunkを大きくすると一致しにくくhit rateが下がり、小さくするとreuseしやすいが独立計算境界が増えてaccuracyが悪化するtrade-offがある。

さらに同一token fragmentでもprefix/contextが違えばattention outputが変化し、cached KVとfull recomputation KVの間にdeviationが生じる。KVShareは「cache hitを増やすこと」と「reuseによるrepresentation errorを抑えること」を同時に扱う。

## Adaptive-Length KV Reuse

KVShareは固定長chunkだけに依存せず、request間で再利用できるtoken fragmentを柔軟な長さで扱う。prefix全体が一致しなくても既計算部分を利用できる一方、そのfragmentのKVは別context条件で作られているため、そのまま使うだけではfull prefillと一致しない。この修復をDHDが担当する。

## Dual-Stage High Deviation (DHD)

### Prefill-stage selection

すべてを再計算するとreuseの意味がないため、KVShareはfull-context条件との差が大きく、かつattention上重要なtokenを選択して再計算する。

単純なKV deviationだけでは「値は大きく変化したが最終outputにはほとんど影響しないtoken」にbudgetを使う可能性がある。DHDはattention contributionとValue側のdeviationを組み合わせ、outputへの影響が大きいtokenを優先する。直感的には importance ≈ attention × value deviation である。

これはCacheBlendの「cached KVとfull-context KVの差を見て再計算する」という系統を、attention importanceで重み付けしたものと理解できる。

### Decode-stage update

KVShareの特徴はprefill時だけでselectionを固定しない点にある。generationが進むと新しいtokenが追加されattention patternが変わる。prefill時に重要でなかったcached tokenがdecode途中で重要になる可能性があるため、DHDはdecode段階でもattention deviationを観測し、必要なcached representationを追加修復する。

## Cache-Aware Scheduler

multi-tenant servingではcache hit rateが高いrequestと低いrequestを同じbatchへ無差別に入れると、高hit requestも低hit requestの処理時間に引きずられる。

KVShareはrequestをcache hit rateに基づいて優先・groupingし、continuous batchingをcache状態に合わせる。論文ではexecution timeとaverage hit rateの関係を分析し、hit-rate-aware orderingが平均TTFT削減に有効であることを示す。

## Experiment Setup

主なmodelはQwen2.5-7B、Llama-3.1-8B、Yi-1.5-9Bなど。full KV recomputationと既存KV reuse / selective recomputation手法を比較し、accuracy、TTFT、throughput、cache hit rate、recomputation ratio、scheduling effectを評価する。

## Main Results

主要主張は以下。

- full KV recomputation比で最大 **9.39× TTFT短縮**
- throughputを最大約 **1.2×**
- 既存SOTA reuse手法に対してaccuracyを平均 **20.38%改善**

単にcache hitを上げるだけでなく、DHDによるrepairとschedulerまで含めてmulti-tenant servingのend-to-end performanceを狙っている点が重要。

## 主要Ablation / 分析

固定chunk長では、chunk sizeを小さくするとhit rateは上がるがaccuracyが落ちやすく、大きくするとaccuracyは改善するがreuse opportunityが減る。adaptive-length reuseはこのtrade-offを緩和する。

prefill-only selectionではdecode中のattention driftを捉えられず、decode-stage selectionを加えることでgeneration中に新たに重要になったtokenを補正できる。

またhit rateの異なるrequestを無差別にbatchingする場合より、cache stateを考慮したordering/groupingでTTFTが改善する。

## CacheBlendとの差

[CacheBlend](2024-2405.16444-cacheblend.md)は最も直接的なpredecessorの一つ。

| | CacheBlend | KVShare v2 |
|---|---|---|
| 主対象 | RAG document KV fusion | multi-tenant cross-request reuse |
| reuse | cached chunk/document | adaptive-length reusable fragment |
| repair signal | KV deviation中心 | attention-weighted deviation |
| repair phase | 主にprefill | prefill + decode |
| scheduling | 主眼ではない | cache-aware schedulerを統合 |

KVShareはCacheBlend型selective recomputationをserving system全体へ拡張した研究と位置づけられる。

## ProphetKVとの差

[ProphetKV](2026-2602.02579-prophetkv.md)はKVShare v2をbaselineとして直接比較する。最大の違いはselection objective。

KVShareは「どのreused KV stateがattention-weighted deviationを持つか」を重視する。ProphetKVは「このuser queryにどのcontext tokenが重要か」を直接見る。

| | KVShare v2 | ProphetKV |
|---|---|---|
| relevance signal | attention × KV deviation | query→context attention |
| objective | reuse errorの重要部分をrepair | query utilityを保つ |
| decode update | あり | query-driven prefill repair中心 |
| serving scheduler | あり | 主眼ではない |
| granularity | token/fragment | token |

技術系譜は CacheBlendのglobal KV deviation → KVShare v2のattention-weighted deviation + decode repair → ProphetKVのexplicit query-conditioned relevance と見ると分かりやすい。一方v1のsemantic-aware sharingは、semantic similarityでcross-user reuse opportunityを増やす別枝。

## A³との関係

[A³](2025-2511.17560-a3.md)も「再計算tokenとquestion-relevant contextが一致していない」ことを問題視する。KVShareがattention-weighted deviationを使うのに対し、A³はquestionからdocumentへのattentionをより直接的なselection signalとして使う。

A³とProphetKVはKVShare/CacheBlendのstate-repair中心の考え方からquery-aware repairへ進んだ研究として近い。

## Limitations

1. request間にreuse可能なfragmentが少なければbenefitは小さい。
2. DHDのimportance推定とselective recomputation自体にもoverheadがある。
3. decode-stage repairはdynamic attentionを追跡しながらcacheを更新する実装複雑性を増す。
4. v1からv2で手法が大幅変更されており、KVShareをsemantic-aware methodとしてのみ引用すると現行版と食い違う。

## KV-cache taxonomyでの位置づけ

KVShare v2は **cross-request reuse + selective repair + cache-aware serving**。model architecture変更やfine-tuningは不要で、cached KVを直接再利用し重要tokenだけruntimeで修復する。

## まとめ

KVShare v2はmulti-tenant LLM servingにおけるKV reuseを、adaptive reuse + selective repair + decode-time adaptation + schedulingとしてsystem-levelに扱う。

技術的にはCacheBlendのselective recomputationをattention-awareかつdual-stageへ発展させた位置づけが強い。後続のA³ / ProphetKVはさらにselection criterionをquestion/query relevanceへ寄せ、「full-prefill stateをどこまで復元するか」より「このqueryに必要なrepresentationをどこまで復元するか」を重視する。
