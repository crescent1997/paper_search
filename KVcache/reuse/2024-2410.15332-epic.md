# EPIC: Efficient Position-Independent Caching for Serving Large Language Models

> prefixが一致しなくても同じimmutable context chunkを再利用できる **Position-Independent Caching (PIC)** を整理し、既存のCacheBlendより小さいruntime recomputationでqualityを保つLegoLinkを提案する。

## 概要

通常のprefix cachingは、同じtoken列がprompt先頭から一致する場合に非常に有効である。

しかし実際のLLM applicationでは、同じcontext chunkがrequestごとに異なる位置へ置かれる。

たとえば、

```text
Instruction A + Document X + Query A
Instruction B + Document X + Query B
```

ではDocument X自体は同じでもprefixが異なる。

RAG、few-shot examples、shared system context、tool descriptionsなどではこのpatternが頻繁に起こる。

EPICは、こうしたimmutable chunkをprompt位置に依存せずcompile / cacheし、後から別requestへlinkする方式を **Position-Independent Caching (PIC)** として明示的に整理する。

PICは概念的に2 stepからなる。

1. **Compile step**  
   immutable chunkを単独prefillしKV cacheとして保存する。
2. **Link step**  
   request時に複数cached chunkとmutable tokensを組み合わせ、必要な補正だけ行う。

問題は、単独計算したchunk KVをそのまま連結するとfull recomputeとはattention patternが大きく異なることである。

## CacheBlendの限界

[CacheBlend](2024-2405.16444-cacheblend.md)はPICに近い問題をselective recomputationで解く。

defaultでは約 $15\%$ のtokenを動的に選び、各layerでKVを再計算する。

qualityは高いが、EPICは2つのsystem-level問題を指摘する。

### 1. 計算量が依然として大きい

15%に絞っても、どのtokenを更新するかを判断するためにattention computationが必要であり、long promptでは重い。

### 2. Dynamic selection overhead

layerごとにtoken importanceを計算してsubsetを選ぶ処理自体にruntime overheadがある。

論文のprofilingではCacheBlendのselection / recomputation関連overheadがTTFTの約16〜64%を占めるケースがある。

そこでEPICは、

> 本当にdynamicに全tokenを調べる必要があるのか

をattention mapから再検討する。

## Attention Sinkの観察

naive PICでは、各chunkをposition 0から独立にcompileする。

その結果、各chunkの先頭tokenが不自然に大きなattentionを集める。

これは **attention sink** と呼ばれる現象で、chunkごとに先頭tokenが擬似的なanchorになってしまう。

```text
Chunk A: [sink] ......
Chunk B: [sink] ......
Chunk C: [sink] ......
```

full recomputeでは本来1本のsequenceとしてattentionが分散するため、このような「chunkごとに独立したsink」は存在しない。

EPICはCacheBlendで実際に選ばれるtokenを分析し、再計算対象がchunk先頭付近へ強く集中していることを発見する。

つまりdynamic HKVD selectionの多くは、

> independent compilationによって生じたchunk-boundary artifactを直している

と解釈できる。

この観察からLegoLinkが導かれる。

## LegoLink

LegoLinkは、chunk全体からdynamicにtokenを探すのではなく、**各chunk先頭の固定少数tokenだけを再計算**する。

LegoLink-$k$ は各chunkから先頭 $k$ tokenをlink stepで再計算するvariant。

```text
Cached Chunk A: [recompute k][reuse rest]
Cached Chunk B: [recompute k][reuse rest]
Cached Chunk C: [recompute k][reuse rest]
                         ↓
                    Mutable query
```

chunk数を $C$ とすると、recompute対象数はcontext length全体の一定割合ではなく、

$
O(kC)
$

へ抑えられる。

$k$ が小さければlong contextで特に有利になる。

## LegoLink-0

さらにEPICは **LegoLink-0** という興味深いvariantを評価する。

compile時に各immutable chunk先頭へ少数のdummy tokenを追加し、attention sinkをdummy側へ吸収させる。

```text
[dummy][dummy][dummy][dummy] + real chunk
```

prefill後、dummy tokenのKVは捨てる。

これによりreal token先頭がsinkになるのを防ぎ、link stepではtokenを再計算しない。

つまり、

```text
compile時にsink処理
→ runtime recompute = 0
```

という構成。

LegoLink-0でもかなりのqualityが維持されることから、chunk先頭のattention sinkがPIC degradationの主要因であることを裏付ける。

## EPIC System

EPICはalgorithmだけでなくserving systemとして実装される。

主なcomponentは、

- **KVCompile**: immutable chunkをcompileしてcache IDを発行
- **KVCache**: KV vectorsを保存
- **Scheduler**: requestとcache IDsを受け取りprefillをschedule
- **KVLink Prefill**: LegoLinkでcached chunksをlink
- **Decode Stage**: 通常decode

である。

APIはexplicit caching方式を採用し、application側がimmutable contextを事前登録してcache IDを保持する。

request時にはcache IDsとnew mutable tokensを送る。

RAGのようにどのdocumentをreuseするかapplication側で既に分かっている場合、内部hash lookupに頼らず直接cacheを指定できる。

## Experiment Setup

EPICはvLLM / CacheBlend系systemを基盤に実装し、

- 6 tasks
- 3 model architectures
- RAG / QA / summarization等のworkload

で評価する。

主な比較対象は、

- Full Recompute
- Naive PIC
- CacheBlend-$r$
- LegoLink-$k$

である。

metricはtask qualityに加え、TTFT、throughput、GPU memory、long-context scaling。

## Main Results: Quality / TTFT

LegoLink variantsは多くのtaskでCacheBlendより良いquality-TTFT Pareto frontierを形成する。

特に **LegoLink-2** はdefaultのCacheBlend-15と比較して、

- accuracy lossを **0〜7%以内**
- TTFTを最大 **3×改善**

する。

一方、CacheBlend-1 / CacheBlend-5のように単純にrecompute率だけを小さくすると、full recomputeから大きくaccuracyが落ちるcaseがある。

つまり重要なのは、

> 少数tokenを再計算すること

ではなく、

> **chunk先頭tokenを狙って再計算すること**

である。

LegoLinkで $k$ を増やしてもaccuracy gainは次第に小さくなり、少数先頭tokenだけで大部分のartifactを修復できる。

## Multi-request Serving

asynchronous workloadではLegoLink-16とCacheBlend-15を比較する。

EPICは、

- TTFT: 最大 **8× reduction**
- throughput: 最大 **7× increase**

を報告する。

LegoLinkは再計算tokenが少ないためintermediate activationも小さく、同時により多くrequestを走らせられる。

Context Cache Ratioが高いworkloadほどPICによるreuse benefitも大きくなる。

## Long-context Scaling

512-token chunkを固定しtotal context lengthを増やす実験では、

- Full Recompute: quadratic growth
- CacheBlend-15: attention selectionのためquadratic要素が残る
- LegoLink: $O(kN)$

という違いが現れる。

CacheBlend-15は約35K tokens付近でOOMする一方、LegoLink-16は約50K tokensまで動作する例を示す。

これはrecompute token数とintermediate tensorが大きく減るためである。

## CacheBlendとの違い

| | CacheBlend | EPIC / LegoLink |
|---|---|---|
| token selection | dynamic HKVD | chunk先頭固定 |
| recompute amount | contextの約 $15\%$ | chunkごとに $k$ tokens |
| complexity | quadratic要素が残る | $O(kN)$ |
| target artifact | general KV deviation | attention sink中心 |
| runtime overhead | selection costあり | 小さい |

CacheBlendはよりgeneralなcross-chunk mismatchを修復する一方、EPICは実際のerrorがchunk先頭へ集中していることを利用して高速化する。

したがってEPICは単なる実装高速化ではなく、

> PIC errorの主要構造をattention sinkとして再解釈した手法

と見る方が近い。

## Block-Attentionとの違い

[Block-Attention](2024-2409.15355-block-attention.md)はreuse時のcross-document dependencyをmodel training側で変更する。

EPICはpretrained modelを維持し、compile / link algorithmだけでPICを成立させる。

したがって、

- Block-Attention: **reuse-aware fine-tuning**
- EPIC: **inference-time position-independent linking**

という違い。

EPICは追加training不要という利点がある一方、full-attention modelとの内部state差は残る。

## LegoLink-0が示すこと

LegoLink-0の結果はEPICの分析上かなり重要。

runtime recomputeを0へしても、compile時にdummy tokenでattention sinkを吸収するだけでqualityがかなり回復する。

これは、

> PICのaccuracy degradationのかなりの部分は、missing cross-chunk attention全般ではなく、chunk boundaryで生じるsink artifactによる

可能性を示す。

ただしすべてのtaskでfull recomputeへ一致するわけではなく、task-dependentなcross-chunk interactionも残るため、LegoLink-$k$（$k>0$） が必要になる。

## Limitations

1. **Full prefillとの厳密一致ではない**  
   LegoLinkは近似であり、全cross-chunk dependencyを再現するわけではない。

2. **Attention sink仮説への依存**  
   model architectureやtraining recipeによってsink集中が弱い場合、固定先頭token strategyの利点は小さくなる可能性がある。

3. **Explicit cache management**  
   application側でcache IDを管理するintegrationが必要。

4. **Workload依存**  
   cache hit率、request rate、chunk sizeによってthroughput gainは変わる。

5. **Serving policyの影響**  
   asynchronous resultはscheduler / queueing policyにも左右される。

## KV-cache taxonomyでの位置づけ

EPICは **Position-Independent Caching / lightweight link-time repair** に分類できる。

reuse研究の流れとしては、

```text
Prefix caching
    ↓
Non-prefix modular reuse
    ↓
CacheBlend: dynamic repair
    ↓
EPIC: structured lightweight repair
```

という位置。

CacheBlendが「どのtokenが壊れているかを毎回探す」のに対し、EPICは「壊れやすい場所はchunk先頭に偏る」としてstatic ruleへ落とし込む。

## まとめ

EPICは、同じimmutable contextをprompt内の任意位置でreuseするPosition-Independent Cachingをformalizeし、そのruntime costを下げるLegoLinkを提案する。

中心的な観察は、naive PICで生じるerrorが各chunk先頭のattention sinkへ強く集中すること。

| Component | Role |
|---|---|
| KVCompile | immutable chunkをcache化 |
| Attention-sink analysis | degradationの主要原因を特定 |
| LegoLink-$k$ | 各chunk先頭 $k$ tokenだけ再計算 |
| Explicit cache API | application側からcacheを指定 |
| Scheduler / KVCache | multi-request servingを管理 |

LegoLink-2はCacheBlend-15比でaccuracy lossを7%以内に抑えつつTTFTを最大3×改善し、multi-request workloadでは最大8×低いTTFT、7×高いthroughputを報告する。

reuse研究としては、**dynamic selective recomputationをerror structureに基づく固定少数token repairへ簡略化した手法**として重要である。
