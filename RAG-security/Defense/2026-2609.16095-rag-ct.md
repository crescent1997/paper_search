# RAG-CT: Mitigating Privacy Risks on Retrieval-Augmented Generation Systems via Scanning Prompt Distribution

> **読むべきポイント**：RAGの情報漏洩を出力テキストの危険表現から検知するのではなく、**generatorへ渡す前のretrieval-score分布**を監視する。private documentを狙い撃ちするqueryは、top-1が突出してtop-k score分布が集中するという仮説に立つ。軽量だが、benign false-positive rate・通常QA品質・score calibrationの検証が薄い点を明確に区別して読む必要がある。

## 概要

RAGでは、retrieverが非公開Knowledge Baseから得たchunksをgeneratorのcontextへ挿入する。このcontextにメールアドレス、住所、電話番号、個人名、ID等が含まれていれば、攻撃者はAPIからのqueryを工夫して個人情報を出力させられる。prompt-injection型に加えて、RAG-ThiefやPirateのような反復的・適応的queryによる漏洩が問題になる。

RAG-CTは、**PIIを含むretrieved textを直接分類・編集せず、検索結果のscore分布を使ってqueryを判定**する。一般の情報探索queryでは複数の関連chunkが比較的均等に上位へ来るのに対し、特定のprivate recordを抜き出すqueryでは最上位chunkへの類似度が突出する、という経験的観察を利用する。

具体的にはtop-k類似度をsoftmaxで正規化し、(1)正規化entropyと(2)top-1/top-2 marginを合成したanomaly scoreを作る。scoreが閾値以上のqueryはgeneration前に遮断する。retrieverの再学習、generatorのfine-tuning、corpusの全面sanitizationを必要としない。

論文はHealthcareMagic-101とEnron Emailで、TBTG/TGTB、PIDE、RAG-Thief、Pirateの4種を評価する。Healthcareで、RAG-CTはTBTG/PIDEのPII leakage ASRを0へ、RAG-Thiefを0.03–0.05、Pirateを0.05–0.08へ下げた。ただし完全防御ではなく、**ULC（漏洩chunk数）が0ではない条件もある**。また、false-positive rateやbenign utilityの定量比較がないため、実運用での正当queryへの影響は別途検証が必要である。

## 問題設定 / Threat Model

### Victim RAGと保護対象

Victimは、検索対象の非公開corpus $\mathbf K$、retriever $R_D$、generator $\mathcal G$を持つ標準的なRAGである。query $q$に対してtop-$k$ chunks $c_1,\ldots,c_k$を検索し、

$$r=\mathcal G(c_1\oplus\cdots\oplus c_k\oplus q)$$

で応答を返す。保護対象はretrieved chunksのうちPIIを含む内容。実験上のPIIには、氏名、電話番号、メールアドレス、ID番号、SSN、パスポート、免許証、生年月日、自宅・勤務先住所などを含める。

### Attacker capability

- **Black-box API access**：攻撃者は通常のRAG問い合わせinterfaceからqueryを送信し、応答を観測できる。
- **No privileged access**：private corpus、retriever weights、generator weights、internal retrieval scoresへの直接アクセスは持たない。
- **Domain knowledge可**：個人情報のある領域、ターゲットとなるレコードの種類等について事前知識を持ちうる。
- **Repeated/adaptive querying可**：過去の応答を使って次のqueryを選ぶ攻撃も想定する。

目的はquery列 $Q=(q_1,\ldots,q_n)$から、PIIを含むprivate chunksの集合 $\Omega=\bigcup_i C_i$ を復元すること。ここで$C_i$は応答$r_i$から抽出できた機密情報候補である。

### Defender capabilityと前提

Defenderは**retriever内部のtop-k similarity scoresを読める**。これは攻撃者がblack-boxであることと矛盾しないが、RAGサービス側へのmiddleware実装権限が必要である。query単位でanomaly scoreを計算し、閾値を超えたqueryのgenerationを拒否する。

主要な仮定は「targeted extraction queryでは、top-1へのscore集中がbenign queryより強い」こと。必ず成立する性質ではない。特定の正当なFAQ/社員記録を探すqueryもtop-1集中を示しうるし、攻撃者が複数の文書へscoreを分散させるqueryを作れる可能性もある。

## 手法 / Algorithm

### 1. Retrieval-score取得

query embedding $q\in\mathbb R^d$とcorpus record embedding $r_i$からsimilarity

$$s_i=\langle q,r_i\rangle$$

を計算し、降順に並べた上位$k$件 $s_{(1)}\ge\cdots\ge s_{(k)}$を使う。文書本文やLLM生成結果ではなく、retrieverが通常計算するscoreを利用する点が重要。

### 2. Softmaxによる確率化

$$p_i=\frac{\exp(s_{(i)})}{\sum_{j=1}^{k}\exp(s_{(j)})}$$

としてtop-k scoreを確率分布へ変換する。元scoreのscaleが変わると$p_i$の尖り具合も変わるため、retriever間でのcalibrationは自明ではない。

### 3. Entropy：retrieval結果全体の集中度

$$H=-\sum_{i=1}^{k}p_i\log p_i,\qquad \widehat H=\frac{H}{\log k}.$$

$\widehat H$は0–1に正規化され、低いほどtop-kのうち少数のrecordへscoreが集中する。したがってanomalyの指標には$1-\widehat H$を使う。

### 4. Margin：最上位recordの優位性

$$M=s_{(1)}-s_{(2)}$$

を求め、min-max正規化による$\widehat M\in[0,1]$へ変換する。$M$が大きいほど最上位文書が2位から離れており、特定recordの狙い撃ちの可能性が高いと判断する。

**実装上の注意**：min-max normalizationの参照集合・分布変化時の再calibrationについて論文本文の説明は限定的であり、deploymentで再現性を確保するには別途仕様化が必要。

### 5. Anomaly scoreとgeneration前遮断

$$A(q)=\alpha(1-\widehat H)+\beta\widehat M,\qquad \alpha,\beta\ge0.$$

$A(q)\ge\tau$ならmaliciousとしてflagする。本文のablationではdefault threshold $\tau=0.5$。entropyとmarginの単独判定ではなく合成することで、globalなscore集中とtop-1局所優位性を補完的に利用する。

```text
Incoming user query
       ↓
Retriever → top-k chunks + similarity scores
       ↓
Softmax → normalized entropy + top-1/top-2 margin
       ↓
Anomaly score A(q) ≥ threshold?
       ├─ Yes → block / reject query
       └─ No  → retrieved context + query → Generator
```

この位置で遮断することで、generatorがPIIを含むcontextを見てから漏洩するのを防ぐ。generation済みoutputを監視する方式と異なり、追加のLLM呼び出しは必須ではない。

## 先行研究からの改善点 / 技術的系譜

### 防御対象のAttack primitive

- **[The Good and The Bad](../Attack/2024-2402.16893-the-good-and-the-bad.md)**：RAGにおけるprivate retrieval data leakageを体系化。RAG-CTはこの脅威のうちPII extractionを対象とする。
- **[Follow My Instruction and Spill the Beans（PIDE）](../Attack/2024-2402.17840-follow-my-instruction-and-spill-the-beans.md)**：retrieved contextを再出力させるinstruction-following exploit。RAG-CTは出力検査より前のscore偏りを利用する。
- **[RAG-Thief / CopyBreakRAG](../Attack/2024-2411.14110-feedback-guided-extraction-copybreakrag.md)**：複数queryのfeedbackで非公開corpusを抽出するadaptive attack。RAG-CTの評価対象。**攻撃側のquery budget全体を監視する方式ではなく、各queryを独立に判定する**点に注意。
- **Pirates of the RAG（Pirate）**：応答から得たrelevanceを手掛かりにadaptiveにqueryを更新する攻撃。本文の主要評価対象だが、当該repositoryに要約済みファイルを確認できないため相対リンクは付けない。原論文 arXiv:2412.18295。
- **[DGEA / Unleashing Worms and Extracting Data](../Attack/2024-2409.08045-unleashing-worms-extracting-data.md)**：jailbreakと探索を組み合わせるextraction。RAG-CTの背景脅威に該当するが、DGEA専用の評価結果は提示されない。

### 従来Defenseとの違い

| Defense class | 判定・介入場所 | 弱点 | RAG-CTの差分 |
|---|---|---|---|
| Query rewriting / rephrasing | user input text | adaptive queryが言い換えを突破 | queryの表面形でなくretrieval分布を見る |
| Rule-based filter | prompt/contentのkeyword | keyword回避やbenign-looking extractionに弱い | score集中度で判定 |
| Summarization | retrieved content | 要約にもPIIが残り得る・追加生成が必要 | generation前に遮断 |
| Erase-and-check | promptを部分削除して安全性検査 | 反復攻撃・query最適化に弱い | retrieverの実際の応答傾向を利用 |
| [SD-RAG](2026-2601.11199-sd-rag.md) | retrieved contentのselective disclosure | redactionのutilityとの両立が必要 | query-level blockingで、redaction自体は行わない |
| [RAGFort](2025-2511.10128-ragfort.md) | indexとgeneratorの二重防御 | architecture変更・対比学習等の導入が必要 | retriever scoreへの軽量middleware |
| [CanaryRAG](2026-2604.10717-canaryrag.md) | canary / dual-path runtime監視 | 検知のためのcanaryとoracle経路が必要 | top-k scoreのみを使用 |

Mirabel（arXiv:2505.22061）は、本文で「近いqueryによるmembership inference」の先行研究として引用される。RAG-CTはmembership判定そのものを防ぐ保証ではなく、PII-targeted extractionの経験的検知に主眼がある。

## Experiment setup

### Dataset / retriever / generator

| 要素 | 設定 |
|---|---|
| Healthcare | HealthcareMagic-101：患者と医師の対話 |
| Email | Enron Email：電子メール |
| Framework | LangChainベースのRAG |
| Healthcare embedding | all-MiniLM-L6-v2 |
| Email embedding | BGE v1.5-large |
| Retrieval | top-$k=3$ chunksをqueryと連結 |
| Generators | Llama2-7b-chat、Llama2-13b-chat、Qwen2-72B-Instruct、ChatGPT-4 |
| Attacks | TBTG/TGTB（表記揺れあり）、PIDE、RAG-Thief、Pirate |
| Defense baselines | Rephrasing、Summarization、Rule-based、Erase-and-check |
| Main attack budget | 各attackで100 prompts（Table 1, Table 2） |

### Metrics

- **ULC（Unique Leakage Chunks）**：private informationを含む、重複除去済みの漏洩chunk数。
- **PII count**：実際に漏洩した個別PII項目数。
- **ASR**：少なくとも1つのPIIが漏洩したattack queryの割合。

ULC、PII、ASRは同じ指標ではない。例えばULCが正でも、論文のPII定義に該当する情報が抽出されずPII count=0となり得る。

## Main Results

### 防御なしでの漏洩（Table 1）

| Attack | Healthcare ULC | Healthcare PII | Healthcare ASR | Enron ULC | Enron PII | Enron ASR |
|---|---:|---:|---:|---:|---:|---:|
| TGTB | 105 | 78 | 0.75 | 112 | 117 | 1.00 |
| PIDE | 124 | 73 | 0.69 | 133 | 109 | 1.00 |
| RAG-Thief | 156 | 81 | 0.72 | 182 | 156 | 1.00 |
| Pirate | 212 | 97 | 0.93 | 238 | 201 | 1.00 |

HealthcareではPirateのULC/PII/ASRが最大。Enronでは4種類すべてASR=1.00で、保護なしのRAGは個人情報を広く露出する。論文のTable 1はモデル名を「Llama2-8b-chat」と記載するが、実験設定とTable 2は「Llama2-7b-chat」であり**原論文に表記不一致がある**。

### RAG-CT適用後（Healthcare、Table 2）

| Generator | TBTG ASR / PII | PIDE ASR / PII | RAG-Thief ASR / PII | Pirate ASR / PII |
|---|---|---|---|---|
| Llama2-7b-chat | **0.00 / 0** | **0.00 / 0** | **0.03 / 3** | **0.08 / 11** |
| Qwen2-72B | **0.00 / 0** | **0.00 / 0** | **0.05 / 5** | **0.05 / 9** |
| ChatGPT-4 | **0.00 / 0** | **0.00 / 0** | **0.04 / 4** | **0.06 / 6** |

TBTG/PIDEのPII countは0まで低下。一方、adaptiveなRAG-Thief/Pirateでは漏洩が残る。したがって「RAG-CTはPII extractionを完全に防ぐ」ではなく、**既知attack分布で大幅なASR低下を示す**と解釈すべき。

ULCは、Llama2-7b-chatでTBTG=2、PIDE=6、RAG-Thief=22、Pirate=67。PII countが0でもULCが正の条件があり、chunk-levelとitem-levelの指標を区別する必要がある。

| Defense | TBTG ASR | PIDE ASR | RAG-Thief ASR | Pirate ASR |
|---|---:|---:|---:|---:|

## Ablation / Robustness / Additional Experiments

### top-$k$の影響

Fig.5(b)はHealthcare + Pirate + Llama2-7b-chatで$k$を変える。retrieveするchunk数が増えるほど、生成contextに漏洩候補が増えるためASRが上がる。これはRAGのutility改善を狙ったmulti-chunk retrievalがexposure surfaceを増やす可能性を示す。

### Thresholdの影響

Fig.5(c)では低い$\tau$ほど多くのqueryを遮断し、攻撃ASRが下がる。defaultは$\tau=0.5$。**低いthresholdがbenign false positiveをどれだけ増やすかは数値で示されていない**。単にASRを下げるだけでは実運用上の最適値を決められない。

### Entropy-only / Margin-only / Combined

Fig.5(d)では、entropyのみ、marginのみ、両者の合成を比較し、combinedが最も良い防御効果を示す。global concentrationとtop-1 decisivenessを併用する設計を支持する。ただし図から読み取れない具体値を捏造しない。

### Adaptive attackへの一般化の範囲

RAG-Thief/Pirateを評価した点は、固定prompt injectionだけを評価する研究より強い。ただし**RAG-CTの$A(q)$を推定・回避することを直接目的としたarchitecture-aware adaptive attacker**は本文で検証されていない。単にadaptive query generationを行う既存attackへの評価と、detector-aware evasionへの評価は区別する必要がある。

## Limitations / 成立条件

1. **Benign utility / false-positiveが未検証**：正当な「特定の個人・契約・医療記録を調べたい」queryもtop-1に集中しうる。Precision、FPR、TPR@FPR、answer accuracy、refusal rateが必要。
2. **Retriever依存のscore calibration**：softmax entropyはscore scaleに敏感。cosine / inner product / BM25 / hybrid、温度係数、embedding normalization、reranker有無で$A$の分布が変わる。min-max margin normalizationの母集団も明確に固定する必要がある。
3. **$k$依存**：$k=3$で評価しており、$k=1$ではentropyが定義上使えず、$k=2$でも統計量の分解能が小さい。top-k増加は攻撃面を広げる。
4. **攻撃者の回避余地**：単一PII recordを狙うのではなく、複数の類似recordsを同時にヒットさせてentropyを高くするqueryや、multi-query retrievalを使う攻撃が考えられる。これは本論文で実証された攻撃成功ではなく、今後の検証課題。
5. **Threat coverage**：PIIを含むtargeted extractionに焦点を当てる。一般のcopyright corpus reconstruction、implicit knowledge extraction、membership inference、GraphRAG node/edge stealingに対する有効性は未確立。
6. **定量的なsystem costが不足**：score計算自体は軽いが、detectorのcalibration、logging、reranking、分散retrieverにおけるoverheadやlatencyは十分評価されていない。
7. **本文の表記揺れ**：TGTB/TBTG、Llama2-7b/8b-chatの記述が混在。実装再現時は原論文表・コードの整合性を確認する必要がある。

## RAG Security Taxonomyにおける位置づけ

| 軸 | RAG-CT |
|---|---|
| Category | Defense |
| Protected asset | private retrieval corpusに含まれるPII |
| Threat | black-box query-driven PII extraction / retrieved document leakage |
| Intervention | retrieval後・generation前のquery blocking |
| Detection signal | top-k retrieval score entropy + top-1/top-2 margin |
| Training requirement | retriever/generatorの再学習不要 |
| Formal privacy guarantee | なし（経験的防御） |
| Strongest demonstrated evaluation | 既存adaptive attacks RAG-Thief / Pirate |
| Not established | detector-aware adaptive evasion、benign FPR、whole-corpus extraction防御 |

## 実装・研究上の示唆

**実装位置**：retrieverがtop-k chunk IDとscoreを返した直後、generatorへのcontext構築より前に実装できる。vLLMやSGLangなどのgenerator側を変更する必要は原理上ない。複数retrieverやrerankerを使用する場合、どの段階のscoreを監視するかを固定しないと判定が不安定になる。

**再現実験の推奨**：RAG-Thief / RAGCrawler / IKEA / GeoExに対して、(a) extraction coverageとASR、(b) benign query FPR、(c) detector-aware query optimization、(d) query budget・閾値・retriever switchingを同時に評価する。特に[Connect the Dots / RAGCrawler](../Attack/2026-2601.15678-connect-the-dots.md)は、自然なqueryでglobal explorationを行うため、単一recordへのscore集中を前提とするRAG-CTに対する重要な追加baselineとなる。

**技術的な比較対象**：生成後に漏洩兆候を検知してrollbackする[ABack](2025-2508.06087-adaptive-backtracking-aback.md)とは補完的。RAG-CTは生成前のblocking、ABackは生成中のsemantic leakage検知・再生成であり、false positive / utility / costのtrade-offを比較する価値がある。

**研究上の重要点**：高いretrieval confidenceは、本来のRAGでは「検索が成功した」ことを示すが、private data protectionでは「特定recordが狙われている」signalにもなり得る。このdual-use性を明示し、benign high-confidence retrievalを許容しつつtargeted extractionだけを拒否する仕組みが次の課題となる。
