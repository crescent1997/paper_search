# SlotGCG: Exploiting the Positional Vulnerability in LLMs for Jailbreak Attacks

## 概要

SlotGCGは、[GCG](2023-2307.15043-gcg.md)および多くの後続optimization-based jailbreakが暗黙に採用してきた「adversarial tokensはprompt末尾のsuffixへ置く」という仮定を再検討する。

著者らはprompt中の**挿入位置そのもの**によってjailbreak vulnerabilityが大きく変わることを実証し、各candidate positionをslotとして評価するVulnerable Slot Score (VSS)を提案する。

SlotGCGはまずVSSで脆弱なslotを選び、その位置でGCG等のtoken-level optimizationを実行する。position searchはattack-agnosticなfront-endとして設計され、既存optimization attackへ追加できる。

## 問題設定 / Threat Model

基本的にはwhite-box optimization-based jailbreakである。

従来GCGは、

```text
[harmful instruction] [adversarial suffix]
```

という形を固定する。

SlotGCGはこれを、

```text
[slot 0] token...
[slot 1] token...
...
[slot k] token...
```

のように考え、prompt中のどのboundaryへadversarial tokensを挿入するかもattack variableとする。

attackerはmodel behaviorをprobeしてslot vulnerabilityを推定し、その後選択slotでtoken optimizationを実行する。

## 先行研究からの改善点

GCG後続研究の多くは、

- token candidateの選び方
- gradient estimation
- initialization
- attention manipulation
- transfer optimization

を改善してきた。

しかし**adversarial tokensの位置はsuffixに固定**されることが多かった。

SlotGCGは、この固定位置がattack strengthを人工的に制限している可能性を指摘する。

## Positional Vulnerability

実験では同じ種類のadversarial tokensでも、挿入位置によってattack successやoptimization difficultyが大きく変わる。

これはLLMがprompt中のすべてのtoken positionを等価に処理しているわけではなく、attention patternやinstruction structureとの関係で、特定位置のperturbationが出力へ強く影響するためと考えられる。

したがってoptimization variableは、

```text
what tokens?
```

だけでなく、

```text
where to insert them?
```

も含むべきである。

## Method / Algorithm

### 1. Candidate Slots

prompt内のtoken boundariesをcandidate insertion slotsとして列挙する。

### 2. Vulnerable Slot Score (VSS)

各slotへprobeを行い、その位置がjailbreak objectiveへ与える影響をscore化する。

VSSはfull GCG optimizationを各位置で実行するより軽量に、どのslotがattackに有望かを推定するための指標である。

### 3. Slot Selection

VSSの高いslotを選択する。

### 4. Token-level Optimization

選択slotへadversarial tokensを挿入し、GCGなど既存のoptimization-based attackでtoken内容を最適化する。

したがってSlotGCGはGCGを置き換えるというより、

```text
position search
      ↓
existing token optimizer
```

というwrapperとして理解できる。

## Attack-agnostic Design

SlotGCGのposition searchはGCGだけに依存せず、AttnGCG、I-GCG、GCG-Hij等のoptimization-based attackにも組み合わせられる。

これは「slot vulnerability」が特定optimizer固有ではなく、より一般的なattack dimensionであることを検証する設計になっている。

## Experiment Setup

複数LLMと複数optimization-based baselineを用い、

- suffix固定baseline
- SlotGCGによるposition-aware attack
- convergence speed
- Attack Success Rate
- defense適用後のASR

を比較する。

実装はHarmBench evaluation pipelineを基盤とし、GCG familyの複数attackを統一的に評価する。

## Main Results

論文ではSlotGCGがGCG-based attackに対し平均で**約14%高いASR**を達成する。

またoptimization convergenceも速く、位置選択を追加するpreprocessing overheadは**約200 ms**にとどまる。

さらにdefense適用下でもsuffix固定baselineより最大**42%高いASR**を示し、suffix-only evaluationではdefense robustnessを過大評価する可能性を示す。

## GCG / Faster-GCGとの違い

```text
GCG:
  suffix位置固定
  token内容をoptimization

Faster-GCG:
  suffix位置固定
  token candidate探索をefficient化

SlotGCG:
  insertion位置をsearch
        ↓
  選択slotでtoken optimization
```

つまり[Faster-GCG](2024-2410.15362-faster-gcg.md)が**token search efficiency**を改善するのに対し、SlotGCGは**search spaceそのものをposition dimensionへ拡張**する。

## White-box / Black-box条件

token-level optimizerとしてGCG familyを用いる場合、基本的にはgradient accessを必要とするwhite-box attackである。

position selection自体は比較的軽量だが、最終的なadversarial token optimizationのaccess requirementはbackend attackに依存する。

したがってSlotGCG framework自体はattack-agnosticでも、GCG-backed SlotGCGはwhite-boxと考えるのが適切である。

## Transferability

主眼はposition vulnerabilityであり、元GCGのようなuniversal black-box transferが中心テーマではない。

ただしposition searchをtransfer-capableなGCG variantへ組み込めるため、slot selectionとmulti-model suffix optimizationを組み合わせる余地がある。

## Defense Evaluation

SlotGCGの重要なsecurity implicationは、defense側が「adversarial suffixは末尾にある」と仮定していると、位置を変えるだけでrobustnessが崩れる可能性があることである。

perplexity filter、suffix detector、retokenization等のinput defenseだけでなく、model-level defenseでも、評価attackの位置を固定するとattack spaceを過小評価する。

[The Attacker Moves Second](2025-2510.09023-attacker-moves-second.md)の「defenseを知ったattackerはattack strategyを適応させる」という主張と非常に整合的である。

## Instruction Hierarchy / Privilege Separationとの関係

SlotGCG自体はjailbreak attackであり、authority hierarchyを直接攻撃するものではない。

しかしprompt injection settingでは、untrusted content内のどこへadversarial instruction/tokenを配置するかは自然なadaptive dimensionになる。

たとえばtool output全体の末尾だけでなく、

- trusted-looking metadata直後
- quoted text内部
- user contentとの境界付近
- modelが強くattentionする位置

を探索することで、hierarchy-aware modelのfailure modeをより厳しく評価できる可能性がある。

## Limitations

- GCG backendではwhite-box gradient accessが必要。
- position searchを加えてもformal guaranteeはない。
- jailbreakでの位置脆弱性がそのままmulti-role prompt injectionへ一般化するとは限らない。
- chat templateやtokenizationが変わると最適slotも変化し得る。
- attack surface拡大によりevaluation costは増える。

## LLM Model Security Taxonomyでの位置づけ

```text
GCG
  optimize adversarial token content
       ↓
Faster-GCG
  optimize content more efficiently
       ↓
SlotGCG
  optimize WHERE + WHAT
       ↓
adaptive evaluation of model defenses
```

## 実装・研究上の示唆

Defense benchmarkでGCGを使用する場合、suffix固定だけでは十分でない可能性がある。

Instruction Hierarchy / prompt injection defenseでは、attack contentだけでなく**injection position**もadaptive variableとして扱う評価が今後重要になる。

特にtool outputやretrieved documentのように長いuntrusted contextを扱う場合、どの位置のinstructionが最もhigher-priority behaviorへ干渉しやすいかを調べる研究へ自然に発展できる。
