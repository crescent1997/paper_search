# Unleashing Worms and Extracting Data: Escalating the Outcome of Attacks against RAG-based Inference in Scale and Severity Using Jailbreaking

> RAGに対するjailbreakを単なる一回のcontext leakageとして使うのではなく、retrieverをembedding space上で能動的に探索してdatabase全体を高率に抽出するdocument-extraction attackへ拡張する。さらに、retrieved dataへself-replicating adversarial promptを埋め込むことで、RAG-enabled applications間を伝播するwormを構成し、単一applicationへの攻撃をecosystem-scaleへ拡張する。

## 概要

本論文の中心的な問題意識は、従来のRAG privacy attackがmembership inferenceやentity extractionといった限定的な情報漏洩を扱うことが多い一方、generatorをjailbreakできるなら、retrieverがアクセス可能な**documentそのものを系統的に回収できるのではないか**という点にある。

論文は二つのattack classを扱う。

1. **RAG document extraction**: embedding-space explorationとjailbreakを組み合わせてretrieval databaseを広く走査する。
2. **RAG worm**: self-replicating adversarial promptをretrievable contentへ埋め込み、複数RAG applicationsへ攻撃を連鎖伝播させる。

前者はseverityを、後者はscaleを拡大するという整理になっている。

## 問題設定 / Threat Model

### Document Extraction

attackerは通常userとしてtarget RAGへblack-box queryできるが、retrieval databaseそのものには直接アクセスできない。generatorをdirect prompt injection / jailbreakingによって、retrieved contextをresponseへ露出させられることを仮定する。

さらにadaptive extractionでは、target systemが利用しているembedding algorithmを知り、そのembedding modelへqueryできることを前提とする。candidate documentを事前に知るmembership inferenceとは異なり、attackerはdatabase contentsを事前に保持している必要がない。

attackの目的は、単一documentの存在確認ではなく、有限query budgetの中で**distinct documentsをできるだけ多く抽出すること**である。

### RAG Worm

worm settingでは、attackerがRAGへ取り込まれるdocument、例えばemailを送り込める。malicious document中のself-replicating promptがretrieveされると、generatorへ自身の複製とmalicious payloadの実行を指示し、生成されたcontentが別applicationのRAGへ入り込むことで伝播する。

これはPoisonedRAGのように単一knowledge baseへmalicious contentを入れてtarget answerを操作するだけでなく、**retrieval → generation → downstream ingestion** のloopを利用して複数RAG systems間を伝播させる点が異なる。

## 先行研究からの改善点

### Membership / Entity ExtractionからDocument Extractionへ

初期RAG privacy研究では、あるrecordがretrieval corpusに含まれるかを推定するmembership inferenceや、特定entity / attributeを抜き出すextractionが中心だった。

本論文はgenerator jailbreakを用いることで、retrieved contextをほぼ直接取り出せるなら、次の問題は「どうやって未取得documentをretrieveさせ続けるか」であると捉える。

このためattackを **retrieval-space exploration problem** として扱う。

### 後続のAdaptive Extractionとの系譜

この観点は、後続の [Feedback-Guided Extraction / CopyBreakRAG](2024-2411.14110-feedback-guided-extraction-copybreakrag.md) や [Connect the Dots / RAGCrawler](2026-2601.15678-connect-the-dots.md) と技術的に近い。

- 本論文: 抽出済みdocumentsのembeddingから未探索方向を作る。
- CopyBreakRAG: 抽出済みchunksをfeedback memoryとしてexploration / exploitationを制御する。
- RAGCrawler: responseからKnowledge Graphを構築しglobal planningで未探索semantic regionsを選ぶ。

したがって本論文は、単純prompt-based context spillingからadaptive corpus reconstructionへ移る中間的な位置を占める。

また、[Follow My Instruction and Spill the Beans](2024-2402.17840-follow-my-instruction-and-spill-the-beans.md) がinstruction-followingを利用してretrieved contextを直接露出させるのに対し、本論文はその**retrieval coverageをembedding-space optimizationで高める**点が特徴である。

## Method / Algorithm: Document Extraction

論文は3種類のretrieval query generation methodを比較する。

### 1. Random Draw

もっとも単純なbaselineで、random token sequenceを生成してRAGへqueryし、偶然retrieveされたdocumentsをjailbreak promptで露出させる。

retrieval spaceを意図的にcoverageしないため、同じdense regionを何度も引きやすく、distinct document extraction rateは低い。

### 2. English Distribution

自然言語document embeddingの分布を近似するため、Enron emails等からembedding各dimensionのmean / varianceを推定し、そのGaussian distributionからtarget vectorをsampleする。

次にGreedy Embedding Attack (GEA)を用いて、そのtarget embeddingに近いembeddingを持つtoken sequence / suffixを探索する。

概念的には、

```text
sample target embedding z
        ↓
optimize token sequence q so that E(q) ≈ z
        ↓
submit jailbreak + q
        ↓
retrieve documents near z
```

という流れである。

random tokenよりはretrievable natural-language embedding regionへqueryを送りやすいが、実際のtarget corpus coverageをfeedbackとして利用しない。

### 3. Adaptive / Dynamic Greedy Embedding Attack (DGEA)

中心手法では、これまで抽出したdocumentsのembeddingsを利用して次のquery embeddingを決定する。

抽出済みdocument embeddingsのcentroidやoccupied regionsを基準に、そこからcosine similarityが低い方向、すなわち**既知documentsから離れたembedding-space region**へtarget vectorを移動する。

そのtarget vectorに対してGEAでembedding collisionするquery suffixを作り、jailbreak instructionと組み合わせてRAGへ投入する。

このloopを繰り返すことで、すでに回収したdocumentsの近傍を避け、新しいretrieval neighborhoodへ移動し続ける。

```text
Extracted documents D_seen
        ↓ embed
Estimate explored region / centroid
        ↓
Choose target vector far from D_seen
        ↓
GEA: construct query whose embedding ≈ target
        ↓
RAG retrieval
        ↓
Jailbreak generator to reveal context
        ↓
Add new documents to D_seen and repeat
```

重要なのは、jailbreak自体ではなく**retrieverに未知documentを返させるquery synthesis**がattackのscalabilityを決める点である。

## Experiment Setup: Document Extraction

Q&A chatbotを構築し、ChatDoctor等のcorpusをretrieval databaseとして使用する。複数のembedding algorithms / dimensionalities、context sizes、generator enginesを変えてattackを評価する。

主な評価軸は、一定query budget後にdatabase中のdistinct documentsを何%抽出できたかというextraction rateである。

論文は5種類のembedding configurationsを比較し、context sizeやgenerator modelがextraction efficiencyへ与える影響も測定する。

## Main Results: Document Extraction

800 queriesの代表settingでは、Random Draw / English Distributionは20%未満のextractionにとどまる一方、Adaptive methodは **80.6%** を抽出する。

context sizeを増やすと1 queryで露出するdocuments数が増え、Adaptive attackのextraction rateは、

- k=5: **43.4%**
- k=10: **64.5%**
- k=20: **80.6%**

まで上昇する。

embedding modelによる差も大きく、代表例ではMPNet-768で **98.8%**、Nomic-768で **90.9%**、GTE-base-768で **80.6%**。論文全体ではsettingにより **80–99.8%** のdatabase extractionを報告する。

この結果は、privacy riskがgenerator jailbreakの有無だけでなく、embedding geometry、retriever context size、同一query budgetでどれだけdistinct regionsをcoverageできるかに大きく依存することを示す。

## RAG Worm

### Self-Replicating Prompt

第二のattackは、malicious promptをretrievable contentの中へ埋め込むindirect prompt injectionである。

self-replicating promptには概ね、

1. generator safety / system instructionをoverrideするjailbreak
2. 自身のpromptをoutputへ再挿入するreplication instruction
3. confidential data extraction等のpayload

が含まれる。

email assistantを例にすると、感染emailがretrieveされるとassistantがmalicious instructionを実行し、自身のself-replicating contentを別emailとして生成する。それが別user / applicationのRAG corpusへ取り込まれれば次の感染が成立する。

### Experiment

Enron-based email ecosystemを用い、20 users / 20 hops程度の伝播を模擬する。context size、embedding model、generator engine、prompt variantを変え、

- self-replication success
- malicious payload success
- confidential email-address extraction
- hop numberに伴うperformance degradation

を測る。

### Main Results

replication + payload successは代表settingで **11 hop目まで90%以上**を維持し、その後はcontext size等に依存して40–80%程度へ低下する。

一方Claude 3.5 Sonnetを用いたsettingでは20 hopsまでほぼ100%に近いpropagationを維持する。

confidential email-address extractionでは、context 10 emailsでF1 **0.78**、100 emailsでは **0.58**。contextが大きくなると対象informationは増えるものの、hallucinated addressesも増加してprecision / F1が低下する。

## Defense / Guardrail Evaluation

論文は複数のmitigationを整理する。

- access control
- rate limiting
- retrieval similarity threshold
- human-in-the-loop
- output / content size restriction
- automatic content sanitization

ただし、document extractionではrate limitingやquery quotasはattack costを増やすだけで、distributed attackerやlong-running attackを完全には防げない。

retrieval thresholdも、attackerがembedding modelを利用してhigh-similarity queryを生成できる場合は十分でない。

worm側ではretrieved contentをuntrusted inputとして扱い、prompt/data boundaryを強化する必要がある。

## Limitations / 成立条件

最大の前提は **generatorをjailbreakしてretrieved contextを露出させられること**である。強力なoutput mediationやcontext-isolationがある場合、retrieval coverageが高くてもdocument本文を回収できない。

DGEAはtarget embedding algorithmに関するknowledge / query accessを要求し、完全なmodel-agnostic black-box attackではない。

また高いdatabase extraction率は評価corpusのsize / geometry / retriever configurationに依存する。実世界の巨大heterogeneous corpusで同じquery efficiencyが得られるとは限らない。

wormはmalicious contentがRAG indexへ入り、生成outputが別RAGへ再度ingestされるecosystem structureを必要とする。

## RAG Security Taxonomyでの位置づけ

本論文は二つのtaxonomyにまたがる。

```text
Confidentiality / Extraction
  Membership / entity leakage
      ↓
  Prompt-based document exposure
      ↓
  Embedding-guided adaptive document extraction  ← 本論文
      ↓
  Feedback / KG-guided global reconstruction

Integrity / Propagation
  Data poisoning
      ↓
  Indirect prompt injection
      ↓
  Self-replicating RAG worm  ← 本論文
```

特に最初の軸では、RAG extractionを「responseをjailbreakする問題」だけでなく、**retrieval spaceをcoverageする探索問題**として明確に扱った点が重要である。

## 実装・研究上の示唆

RAG confidentiality defenseでは、generator output filterだけでなく、同一clientがembedding spaceを異常に広く探索していないか、distinct retrieved regionsが急増していないかといった**query/retrieval trajectory monitoring**が有効な可能性がある。

この観点は後続のRAGFort / CanaryRAGのようなruntime defenseとも接続しやすい。

またRAG wormは、retrieved documentsをtrusted contextとしてLLM promptへ直結させる設計そのものが危険であることを示す。retrieval resultにはuser inputと同様のtaint / privilege separationを適用すべきである。
