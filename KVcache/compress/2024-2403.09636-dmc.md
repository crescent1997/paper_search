# Dynamic Memory Compression (DMC)

## 概要・問題設定

通常のautoregressive Transformerは各layer/headで各tokenのKey/Valueをそのままappendするため、KV cacheは系列長・batch数に比例して増加する。既存のGQAはhead方向の共有で固定的に容量を減らし、H2O等のevictionは重要でないと推定したtokenを捨てる。一方、**隣接tokenの情報をKV空間でまとめる**なら、捨てずに履歴を短くできる可能性がある。

DMCは学習済みLLMのattentionをほぼ保ったまま、**tokenが来るたびに「新規append」か「末尾KVへのaccumulate（merge）」かを予測**する。headとlayerごとに異なる長さのcacheを作り、promptと生成tokenの両方をonlineで圧縮する。分類上は、architectureを根本から新設する`model`よりも、**保存するKV token数を削減する`compress`**が主目的。

## 既存法との違い

- [GQA](../model/2023-2305.13245-gqa.md)：Query headのグループ化による固定的なKV head数削減。DMCは**各KV headの時間方向**を可変長にするため併用可能。
- [H2O](2023-2306.14048-h2o.md) / [Scissorhands](2023-2305.17118-scissorhands.md)：attention由来の重要度でKVをevict。DMCはtoken境界を学習してKVを**merge**し、情報の一部を保持する。
- [FastGen](2023-2310.01801-fastgen.md)：prefill時にheadごとの保存policyを選択。DMCはheadごとにonlineでappend/mergeを決める**learned policy**。
- [PagedAttention](../reuse/2023-2309.06180-pagedattention.md)：メモリ割当・共有の仕組みであり、KV内容自体を圧縮しない。DMCでは可変長head cacheの物理管理にPagedAttentionを利用する。

## 手法

### 1. Inference時のKV更新

各token `t` のQuery/Keyから2つのscalarを得る（論文§3.1, Algorithm 1）。

- `α_t = round(sigmoid(k_t[0]))`：`1`なら直前cache要素に**accumulate**、`0`なら新規**append**。
- `ω_t = sigmoid(q_t[0])`：新しいKVの重み。最初のQuery/Key次元を制御信号へ転用し、attention計算ではこの次元を0にする。**追加学習パラメータはない**が、元モデルの重みは更新する。

`α_t=1` のとき、末尾のcache entryを累積重み `z` による加重平均で更新する：

`K_last ← (z_old K_last + ω_t k_t)/(z_old+ω_t)`、`V_last`も同様。`α_t=0`なら新しいKV pairをappendして`z=ω_t`へリセットする。これをheadごとに独立に行い、cache長は概念的に `Σ_t(1−α_t)`。**異なるheadの保持位置と長さは揃わない**。

### 2. Retrofittingとtraining–inference一致

離散的なappend/merge判断には直接逆伝播できないため、trainingでは**Gumbel-Sigmoid**で`α`を連続緩和し、部分的にaccumulateした中間KVを計算する。さらに、training中は全中間KVが存在するのにinferenceでは古い中間状態が消えるという不一致があるため、**αに依存するadditive attention mask**で「その時点で参照可能だったKV」のみを再現する（§3.2、Fig. 2–3）。単純な通常causal maskのままではこの意味論を再現できない。

損失は `L = L_LM + L_CR`。`L_CR`は全head/layer/tokenでのappend数が目標compression ratioを超えた分を罰する**one-sided budget penalty**。初期は全appendに近づけ、compression ratioを徐々に1×から引き上げる。最初から強圧縮すると一度失った下流性能を回復しにくい。

### 3. 実装上の要点

- Headごとにcache長が異なるので、単純なdense KV tensorより**page単位の動的割当**が適する。論文はPagedAttention/FlashAttentionベースの実装を評価。
- Trainingの部分accumulationを全系列で逐次計算すると遅い。直近window（実験では`w=12`）で近似し並列化するが、長いmerge区間には追加状態が必要。
- RoPEやattentionの完全な数学的同値性を維持する「lossless KV reuse」ではない。圧縮に適応した**モデル重みの継続学習が必須**。

## Experiment Setup

- Backbone：Llama 2 **7B / 13B / 70B**。7B/13BはMHA、70BはもともとGQAを使用。
- Baseline：original、GQAへのuptraining、H2O、TOVA。
- 評価：MMLU（5-shot）、PIQA/BoolQ/ARC/HellaSwag/WinoGrande等のcommon-sense QA（0-shot平均）、HumanEval（pass@1）。
- Retrofitting：7B/13Bの目標2×/4×/6×/8×に対して論文記載の継続学習量は**24B/72B/120B/168B tokens**。最後にcompression ratio固定の追加学習。7B/13B/70Bで概ね8k/16k/28k H100 GPU-hoursと報告（§4）。
- Throughput：A100/H100、4K token sequenceの最後の1K token生成、利用可能最大batchを変えて測定（Fig. 5）。**TTFTを主指標とする論文ではない**。

## Main Results

1. **精度**：4× compressionでLlama 2 7BのMMLUはfull比 **−0.7 point**、13Bは **−0.3 point**。8×では7Bで **−2.8 point**、13Bで **−2.4 point**（§5.1）。H2O/TOVAは高圧縮率、とくにHumanEvalで大きく悪化する。
2. **Throughput**：arXiv v2 Fig. 5ではH100で2×圧縮→最大**2.0×**、4×→**3.9×**、6×→**5.5×**、8×→**7.0×**。これは**圧縮で最大batchを拡大した条件**であり、固定batchの1-request latency改善と同義ではない。batchを増やしすぎるとcompute-bound化しlatencyが悪化する。
3. **GQAとの合成**：Llama 2 70Bの既存GQA 8×にDMC 2×を加え、**MHA基準で合計16×相当**のKV削減。Table 1ではMMLU 68.8（元70B）→68.8（DMC）。
4. **発表版間の注意**：ICML公式PMLR abstractはthroughput **最大約3.7×**、arXiv v2のabstract/Fig. 5は**最大7×**。同一の数字として混同せず、実験条件・版の違いを明記して引用する。

## 主要ablation・分析

- **Training schedule**：圧縮なしから開始して徐々にratioを増やすことが重要。初期にperplexityが急増すると、後でperplexityを回復してもdownstream精度が戻りにくい（§4、Appendix E）。
- **Adaptive vs fixed**：Appendix Fでは入力依存のmerge判断と固定的な圧縮を比較し、learned segmentationの意味を検証。
- **Importance weighting / prior**：Appendixのuniform weight、local prior、hard/softな圧縮判断の比較から、境界判断とmerge重みの双方が効く。
- **Layer/headの違い**：高いlayerのheadほど圧縮しやすい傾向が観測される。均一なcache budgetが最適とは限らない。

## Limitations

- **追加パラメータは不要でも、継続事前学習は高コスト**。training-freeなSnapKV/HeadKV等と直接同条件ではない。
- 元のattentionと同じ出力を保証しない。長距離検索やRAG文書間の相互作用修復を直接目的にしていない。
- Headごとに長さが異なるため、PagedAttention等のserving実装に変更が必要。training中の特殊mask/部分accumulationも実装難度が高い。
- 著者は**scratchからDMCを学習する初期実験ではGQAに対して不利**だったと報告（Appendix H）。「新規学習モデルでも常に有利」とは言えない。
- 最大7×throughputは特定のhardware/batch条件であり、通常の固定batch・短いpromptのend-to-end改善率ではない。

## Taxonomy / 研究上の位置付け

`compress > learned online KV merging > variable-length per-head cache`。KV cacheを**どのtokenで保持するか**だけでなく、**複数tokenを1つのKV表現へどう統合するか**をモデルに学習させる系譜。GQA/CLAのhead/layer方向の構造的共有とは直交するが、重みの追加学習とserving kernel対応が前提になる。CacheBlend/ProphetKVのような**cross-document KV reuse時のselective recomputation**とは問題設定が異なる。
